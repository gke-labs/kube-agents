Chat is the harness's primary interface — for requests from humans and for the unprompted messages the harness raises itself ([Proactive alerts](#proactive-alerts-both-channels)). The channels shipping today are **Google Chat** (the reference channel; enable with the installer's `--enable-google-chat`) and **Slack** (enable it in the installer's chat menu). Both are opt-in and default to disabled.

Both channels terminate at the **Planning Agent** — the `default` Hermes profile in the agent pod, and the only profile that receives chat ingress. It knows which specialists exist because the roster is injected into every turn by the `agent_roster` plugin (its `router` MCP tool `list_agents` re-reads the same list on demand), and files the work as a card on the shared **kanban board** (`kanban_create`), assigned to the specialist that can execute it. Results come back on their own: the gateway posts each completed card's answer into the thread verbatim, and the Planning Agent handles the hand-off and anything that blocks or fails. The [Platform Agent](/kube-agents/concepts/platform-agent/) does the actual infrastructure work as a delegated kanban worker, and per-cluster [Cluster Agents](/kube-agents/concepts/cluster-agents/) handle single-cluster runtime debugging; neither receives chat directly. A user still sees a single conversational agent regardless of channel — the delegation is visible only as progress updates in the thread. The design of record for this coordination model is [`docs/designs/agent-communication.md`](https://github.com/gke-labs/kube-agents/blob/main/docs/designs/agent-communication.md).

Under the unsupported `spec.mode: next` toggle, Google Chat terminates at the A2A gateway instead: the same Chat app, topic and subscription, pulled through the credential broker by the gateway rather than by the Planning Agent, with the same `allowedUsers` list deciding who is answered. The Planning Agent's Google Chat platform is off on such an install, so proactive alerts and scheduled reports reach the [home channel](#home-channel) through the gateway instead, which posts them there as new threads or as replies in those threads; a reply a person types in one of those threads starts a new conversation rather than continuing the investigation that raised the alert. The reports of the cards a triage files reach the alert's thread the same way, and so do the answers of the cards the agent files for a question you asked it in chat: they post in the thread or DM you asked in, whether or not a home channel is configured (a home channel that is set but is not a space name turns this off too). Either way there are two differences from the Planning Agent's own delivery: each progress note posts as a message of its own, because the gateway can post but not edit, and a file the card produced is not attached. The design of record is [`docs/designs/spec-chatops-gateway.md`](https://github.com/gke-labs/kube-agents/blob/main/docs/designs/spec-chatops-gateway.md).

## Google Chat

Google Chat is the reference channel. Setup is automated by the install: the [`chat-pubsub` Terraform module](https://github.com/gke-labs/kube-agents/tree/main/terraform/modules/chat-pubsub) provisions the backend when Google Chat is enabled (the installer's `--enable-google-chat`, or `enable_google_chat = true` in `terraform.tfvars`).

### How it's wired

- A **Pub/Sub topic** and **subscription** are created in the target GCP project.
- Your Google Chat app (configured separately in the [Chat API console](https://console.cloud.google.com/apis/api/chat.googleapis.com)) publishes events to the topic.
  A GCP project holds only one Chat app, so a project already running one cannot also run this — see [Prerequisites](/kube-agents/install/prerequisites/).
- The Planning Agent (the pod's `default` Hermes profile) consumes the subscription through Hermes' bundled Google Chat adapter, configured by the `platforms.google_chat` block of [`agents/chat/config.yaml`](https://github.com/gke-labs/kube-agents/blob/main/agents/chat/config.yaml).
- Environment variables `GOOGLE_CHAT_PROJECT_ID` and `GOOGLE_CHAT_SUBSCRIPTION_NAME` are wired into the pod by the operator.

### Allowed users

Google Chat ingress can be gated by `GOOGLE_CHAT_ALLOWED_USERS` (a comma-separated list of user emails, collected by the installer as `ALLOWED_USERS`). Leaving it empty allows all users — the operator sets `GOOGLE_CHAT_ALLOW_ALL_USERS=true` in that case.

### Home channel

`spec.integration.googleChat.homeChannel` on the PlatformAgent (surfaced to the pod as `GOOGLE_CHAT_HOME_CHANNEL`) is the space a notification lands in when there is no thread to reply into — which is every alert-driven investigation, since nobody started the conversation.

Unlike Slack's, this one is not covered by `/sethome`. That command writes the **Planning Agent** profile, which is enough for the gateway's own delivery, but a specialist runs as a kanban worker against its own profile and reads the value from the pod environment instead. Set `GOOGLE_CHAT_HOME_CHANNEL` in `install.env` (or pass `--google-chat-home-channel`), or configure `spec.integration.googleChat.homeChannel` on the `PlatformAgent` resource, before the first Google Chat message if you want the Planning Agent to use the same space (below). If left unset, alert-driven reports have nowhere to go — the investigation still runs and still opens its remediation PR, so the only visible symptom is silence in chat.

When no home channel is set and the install's first chat message, on either platform, comes from Google Chat, it makes its space the Planning Agent's home channel, the same write `/sethome` makes, so scheduled `deliver: chat` reports reach that space from then on. That is often a one-person DM: send the first message from the space the team watches, or run `/sethome` there later. The specialists above still read only the pod environment. Like `/sethome`, the write also goes to the profile's `.env`, which outranks a `homeChannel` set on the CR afterwards. After the first message, a CR value still reaches the specialists, but the Planning Agent's home channel moves only with `/sethome`.

Under `spec.mode: next` only the resource field counts. The operator hands it to the A2A gateway, which posts the agent's proactive messages to that space and nowhere else, and `/sethome` does not reach it. The field must name a space (`spaces/<id>`); with it unset or malformed the agent posts nothing to Google Chat unprompted.

### What it looks like end to end

1. User DMs the app or @-mentions it in a space.
2. Chat sends the message event to the topic; the Planning Agent consumes it from the subscription.
3. The Planning Agent picks the right specialist from the injected roster and files a kanban card with the full request context (`kanban_create`).
4. The gateway's kanban dispatcher spawns the specialist — for infrastructure work, the Platform Agent (`hermes -p platform`) — which runs the tool loop and completes the card with a one-line `summary` and the full answer in `result`. A card filed from chat goes ahead of background triage, and one worker slot is held for it ([Why dispatch is capped by default](/kube-agents/operator/platformagent-crd/#why-dispatch-is-capped-by-default)). If it has to wait anyway, the thread says `⏳ Queued: the system is busy. Your request will start when a worker frees up.` and the specialist's progress joins that message once it starts.
5. The originating chat session is auto-subscribed to the card, so the thread fills itself: each `kanban_heartbeat(note=…)` milestone adds a `⏳` line to one rolling message that the notifier edits in place while the specialist works — so a card with five milestones notifies the space once, not five times — and the completion posts as a separate `✔ … done` message carrying the `result` verbatim. The rolling message is then marked finished (`✓`, or `⏹` for a card that failed). The notifier delivers all of it directly and the Planning Agent is woken for none of it; it is woken when a card blocks or fails.

A card that also produced a file gets the file's contents pasted into the thread rather than attached: Chat's `media.upload` refuses app authentication, so an install reaching Chat through the credential proxy can never produce a native attachment. Text deliverables under a size ceiling are posted as message text, split across messages where they have to be; anything else — a PDF, an image, an oversize file — gets a notice naming the path the agent wrote it to instead. Which formats and what ceiling are in [`agents/platform/scripts/google_chat_relay_patch.py`](https://github.com/gke-labs/kube-agents/blob/main/agents/platform/scripts/google_chat_relay_patch.py).

The agent has to declare the file for any of that to happen. Its terminal and file tools run in a separate sandbox pod, so a file it writes is on a volume the gateway cannot read; only paths the card names in its `artifacts` list get copied across to the gateway for delivery, and only for as long as the delivery takes. Four ceilings apply to that copy — 8 MiB per file, 16 files per card, 16 MiB across the card, and a two-minute deadline for the lot — and a file that exceeds one is skipped with a warning in the gateway log while the rest of the card still delivers. Paths under the sandbox's credential and system directories are refused outright. [`agents/platform/scripts/sandbox_artifact_patch.py`](https://github.com/gke-labs/kube-agents/blob/main/agents/platform/scripts/sandbox_artifact_patch.py) holds the limits and the denied prefixes.

### Session metadata

Every Chat message carries session context (space, user, thread) that flows through Hermes and out as OpenTelemetry spans. The full trace is documented in [`docs/designs/gchat-session-metadata-data-flow.md`](https://github.com/gke-labs/kube-agents/blob/main/docs/designs/gchat-session-metadata-data-flow.md).

## Slack

Slack is opt-in. Enable it in the installer's chat menu; the installer prompts for the token values below.

### How it's wired

- The installer's Slack interview collects `SLACK_BOT_TOKEN`, `SLACK_APP_TOKEN`, `SLACK_ALLOWED_USERS`, `SLACK_HOME_CHANNEL`, and `SLACK_HOME_CHANNEL_NAME`; the chart stores the tokens in the credentials Secret and wires the CR's `slack` section.
- The Slack listener itself lives inside the Hermes runtime; it uses Socket Mode (no public webhook required) driven by the app token.
- Setup for the Slack app itself (creating the app, generating tokens, installing to workspace) is documented in the Hermes docs: [hermes-agent.nousresearch.com/docs/user-guide/messaging/slack](https://hermes-agent.nousresearch.com/docs/user-guide/messaging/slack).

Under the unsupported `spec.mode: next` toggle, Slack terminates at the A2A gateway instead, on the same app and tokens, unless Google Chat is enabled too (Chat then holds the gateway and Slack stays on Hermes). The Hermes Slack listener and the credential broker's Socket Mode relay are off on such an install, so one app has one Socket Mode consumer, except on version skew (a `spec.mode` the operator does not recognise): the legacy consumer renders again beside the frozen gateway's connection, and each message is answered by whichever consumer receives it, both admitting by the same list (only the gateway refuses another workspace's member) (the `slack` field of [`spec.integration`](/kube-agents/operator/platformagent-crd/#specintegration) has the detail). Who is answered is decided by the same `allowedUsers` list, as on Google Chat: a sender must be on the list (or the list must be empty, which allows all), and one who is not is dropped with a notice. A member of another workspace, posting in a channel shared with yours through Slack Connect, is never answered, whatever the list says. The gateway's `user_id` principal map (the `a2a-slack-principal-map` Secret) is optional: a sender it names is attributed by the identity it maps them to, and any other admitted sender by their Slack member id. The [home channel](#home-channel-1) has no Slack target for proactive alerts under `next`, and the gateway takes a single bot token. The design of record is [`docs/designs/spec-chatops-gateway.md`](https://github.com/gke-labs/kube-agents/blob/main/docs/designs/spec-chatops-gateway.md).

### Allowed users

Slack ingress is gated by `SLACK_ALLOWED_USERS` (a comma-separated list of Slack user IDs). Messages from users not on the list are silently ignored — a per-channel allowlist for the harness. Leaving it empty allows all users (the operator sets `SLACK_ALLOW_ALL_USERS=true` in that case).

### Slash commands

Slack only routes a leading-slash message to the app's slash handler if that slash is **registered on the Slack app**, and the install configures the integration from tokens alone. Registering them is an optional post-install step — see [INSTALL.md](https://github.com/gke-labs/kube-agents/blob/main/INSTALL.md#2-slack-configuration-slack_enabledtrue) for the procedure.

Until you do, a typed `/hermes <subcommand>` arrives as an ordinary channel message rather than a command. The `legacy_slash_commands` plugin on the Planning Agent profile unwraps that form before the gateway resolves it, so `/hermes sethome` behaves as `/sethome` either way — registering the slashes adds Slack's autocomplete, not the behaviour. The plugin's [README](https://github.com/gke-labs/kube-agents/blob/main/agents/chat/defaults/plugins/legacy_slash_commands/README.md) is the design of record.

`/new` (alias `/reset`) starts a fresh session and history, after the gateway asks the user to confirm. Asking the Planning Agent in words to reset the chat gets that command named back: the agent cannot clear a conversation itself and does not claim to. `/undo` is disabled on this profile, because rewinding the chat reverses nothing a specialist has done.

### Agent view

With `KAGE_SLACK_UX` on, the default (see [Reactions](#reactions) for turning it off), the Slack bot offers three suggested prompts (is anything unhealthy in my clusters right now, what's on the board, which clusters are behind their release channel), and tapping one sends it as the user's message. Slack shows them when a user starts a new assistant thread or, on an app using agent view, opens the bot's Messages tab. An assistant thread that already exists, a channel mention, and an app whose manifest carries neither view (one generated with `--no-assistant`, or built by hand without them) do not show them. No `PlatformAgent` field replaces the three.

Slack's agent view, where the bot's DM opens on a Messages tab, needs a new manifest, and **the switch cannot be undone**: once Slack applies a manifest carrying agent view, the app cannot go back to the assistant view it has today. The manifest also replaces the whole app definition, so pass the name, description and long description your app already has; left out, the name and description become Hermes's and the long description is dropped. Drop `--long-description` if your app has none; Hermes refuses one under 175 characters or over 4,000. Run it with the flag on, which is what names the agent view after `--name`; with the flag off it reads "Chat with Hermes in Slack Messages.":

```bash
kubectl exec -n kubeagents-system deploy/platform-agent-gateway -c platform-agent -- \
  hermes slack manifest --agent-view --name "<app name>" --description "<app description>" \
  --long-description "<app long description>"
```

Paste the output into your app's **App Manifest** page in the Slack App Console and reinstall the app when Slack asks. Try agent view on an app nobody else depends on first. The manifest does not subscribe `agent_session_stopped`, so Slack offers no Stop button on a running reply. With the flag off the manifest and the DM are Hermes's own; with it on or off, `hermes slack manifest` without `--agent-view` prints the same manifest and never switches the view.

### Home channel

`SLACK_HOME_CHANNEL` designates the channel an unprompted message lands in when no user thread is involved. Set it to a monitoring/oncall channel your team already watches.

It is optional at install time. Leave the prompt empty and, if the install's first chat message on either platform comes from Slack, it makes its channel or DM the home channel. Otherwise Slack has none until you run `/sethome` (or `/hermes sethome`) in the channel you want, which is also how you move it. That writes the value into the **Planning Agent** profile — the one that owns Slack ingress — which is why the command has to run through the gateway rather than being applied by an agent on its own profile.

A scheduled brief posts flat in that channel, never inside a thread. `/sethome` also records whichever thread it happened to be typed in, and threading every scheduled report under one ageing thread leaves only the first one visible — so cron delivery drops the thread deliberately. A job that wants its output in a thread names an explicit `deliver=` target instead.

### Reactions

The `KAGE_SLACK_UX` flag is on by default. It changes how reactions work, turns on the [buttons](#buttons) below, turns the first inventory report and fleet-audit reports into cards, and changes how the harness's own messages read on Slack (below). With it on, your message gets a reaction for the kind of ask it is as soon as the agent picks it up, chosen from its words: 🔍 something to investigate, 🌐 the whole fleet, ⬆️ an upgrade or version, 💰 cost, 🛡️ security, 🛠️ a change, 📋 the board, 🚨 an incident, and 👀 anything else. That reaction comes off when the answer posts, and work that succeeded is left with no reaction; work that failed is left with ❌. A turn the agent answers itself settles as soon as it ends. For work the agent hands to the board, the reaction stays on past the acknowledgement until every card the turn opened for your message has finished, along with any follow-up cards those cards' workers filed in the thread, and ❌ goes on if any of them gave up or the turn itself failed. While a card the turn opened waits on you, or a follow-up filed by one that has since finished, ⏸️ joins it, and comes off once you answer. A follow-up that had already given up when the card above it completed posts its own failure line in the thread and leaves your message without ❌. A cancelled turn has its reaction taken off. Work still running when the agent restarts, or a card closed by hand rather than finishing, leaves the reaction on; a card archived by hand counts as finished, without ❌. The agent only ever removes its own reactions, and a reaction it cannot remove stays on. To turn the flag off, set `KAGE_SLACK_UX=false` in the `PlatformAgent` CR's `spec.deployment.env` (the chart's `platformAgent.deployment.env`); an install that never set it has it on, and any value other than `1`, `true`, `yes` or `on` turns it off. With it off the agent follows the Hermes Slack adapter, adding 👀 to your message when it starts and ✅ or ❌ when the turn ends, and nothing else on this page that the flag gates changes.

With the flag on, a thread's board work shows as one status message instead of a progress message per card: a plan with a row for each card, showing its latest notes and whether it is running, waiting on you (a question, work handed to you for review or sent back for changes, or a card stopped for blocking over and over), done or failed, edited in place as notes arrive. A card's row appears, running, as soon as the card starts work, before its first note; a card that finishes, fails or stops to wait on you before its row appears gets its row then. A row's title is the card's name until its first note, then the card's latest note while it runs, with a step count once it has more than one, and that note alone if it fails; `waiting on you` while it waits; and the first line of the card's summary once it is done (or of its result, when it gave no summary), or the card's name when it finished without either. In a plan of several cards, each title starts with the card's name. A card you unblock shows as running again, a running or waiting card archived by hand shows as failed with an `Archived` note, and a card the dispatcher retries after a crash or a timeout stays running. The card's report still posts as its own message when it finishes, except for a card beneath one that filed several and is still working in the same thread, such as one per cluster for a fleet question, or the card one of those hands on to the cluster's own agent: its row carries its result, and the filing card's report, which waits for every card it filed, gives the answer. A filed card that fails or asks you something is told as any other card is. The thread shows Slack's Working… status while the agent answers any message, which needs slack-sdk 3.44 or later in the image; once the agent hands your message's work to the board, kube-agents also marks the thread's session as working from the acknowledgement on, between the agent's replies (from when the first card starts instead, for a message the agent puts no reaction on, such as a thread reply without a mention), as paused while the only cards left are waiting on you, and as closed once every card has settled. A plan with no new note or settled card for half an hour is set aside: its cards still update their rows on it, the status clears unless one of them is waiting on you, answering one brings Working… back on that plan, and a card silent that long can leave the thread without Working… while it still runs; its next note starts a new plan and brings Working… back. A set-aside plan with no card waiting on you or failed is dropped four hours after it was set aside, or after a card on it was answered or unblocked (a card settling on it does not extend that); a card on it that settles later still posts its report but no longer updates its row. When the agent restarts, a card's next note, its settling, or the next liveness signal from a card still running starts a new plan; a card that settles there, other than by being archived, closes the thread's session, or pauses it while the card waits on you, so Working… from before the restart does not stay; it can also clear Working… for another card from before the restart that is still running, until that card's next liveness signal or note. Past 20 cards the oldest finished ones leave the plan first. A channel thread is titled after its first ask, as a DM thread already is; a thread a crash-looping workload's alert started is titled for the incident instead, such as `payments-api crashloop in prod-east`. If Slack refuses the plan, the thread falls back to a rolling progress message per card until those cards settle, or for half an hour after the last of them goes quiet; a card settling still updates its row on the plan, and Working… holds while those cards run and pauses while they wait on you.

With the flag on, work handed to the board also reads more quietly in Slack. When a card completes, blocks or fails, its rolling progress message (the plan's fallback) collapses to its last line, and a completed card's message posts the worker's summary and report without the `✔ … done` head line; a card that finished with neither keeps the head line. A card that blocks, crashes, times out or gives up posts no line of its own (except a question, below) once the wake asking the agent that created the card to explain it has been queued (the Planning Agent, for work you asked for), so the failure is told by that agent. If that wake fails, the card's own failure line posts instead, and a wake that then succeeds on a retry tells the failure a second time; a failure line still waiting on its wake when the same card recovers (it completes, hands off for review or is moved to done) is dropped, so it never lands beneath the recovery. The agent's reply to that wake opens with its first sentence in bold, and when it ends on one short yes/no question, such as "Check it there?", a **Try again** button follows it (an open or either/or question stays text): clicking it sends "Try again" as your reply in the thread, and the message is rewritten to name who clicked. The reply posts as written if the agent restarts between the wake and its reply; outside a thread the question stays text. Six gaps remain, each leaving the failure untold, and the last three are logged: a queued wake that is lost to a restart or an interrupt before the Planning Agent answers; a restart between the card failing and the wake being queued; the card's notifications stopping, after repeated failed posts or a sweep of stale subscriptions, before the wake is tried; a failure line whose post keeps failing; a held line dropped because too many cards are holding lines at once; and a held line dropped because the card recovered, when the wake after it never succeeds. The lines a card does post name the agent working it when the card has one, such as `@platform`, without the board name or the card's id. Other platforms are unchanged.

Two moments get a message of their own with the flag on. When a card's progress note or report says it opened a pull request on GitHub, the thread gets that pull request beside a green side bar, with **Open PR** and **Files changed** buttons, once per pull request in each thread, until the agent restarts. When a card blocks because it needs something from you, its question posts in place of the blocked line, beside a yellow side bar, with up to 2,000 characters of its detail and a "waiting on you" line, and the note that wakes the Planning Agent tells it the question is already posted so that it need not ask it again. A question that ends with two to five short options, right after a line ending in a question mark, gets a button for each, unless that line only asks whether to go on ("Shall I proceed?", "Sound good?"), in which case the list is the plan and stays as text; any other question keeps its options as text, as does a question outside a thread, since a click answers in the thread it was clicked in. Clicking one answers as if you had typed it as your reply in the thread, with the card's name added while the agent still holds the question (after a restart the click answers with the label alone): it runs as your message and passes the same user and channel checks a typed reply does, so a user the adapter would not answer changes nothing by clicking. A click never needs an @-mention. A typed reply in the thread needs one only where the Slack adapter is set to require a mention in threads, or, in a channel that requires a mention, to ignore every message without one. Where it is set to ignore a message addressed to someone else, a typed reply that opens by mentioning another person is ignored unless it also mentions the agent. The Planning Agent still takes your answer back to the card; the question's text also names the card, so a typed reply that starts a new conversation with the agent still finds it. Once the card moves on the buttons and the "waiting on you" line come off the question, however you answered; a restart in between leaves them on it. In a thread, the question then shows who answered and what (`✓ <name>: <answer>`, your Slack display name, else your real name or handle, in plain text, never an @-mention): a click leaves that line at once, and a typed reply leaves it with your reply's first words, less any mention of the agent it opens with, once the card resumes; one reply answers one question, so where two cards ask in one thread, the reply goes to the first card to resume. A card archived, finished or given up without resuming loses its buttons without the line. In a thread, the Planning Agent posts nothing after carrying your answer to the card, unless carrying it fails, when it says so.

### Buttons

With `KAGE_SLACK_UX` on, the alert for a crash-looping workload reads as one line on Slack, such as "🚨 **payments-api in prod-east keeps crashing.** Looking now."; alerts for other reasons, and alerts on other platforms, read as before. An incident's triage edits its alert in place instead of replying under it. The alert becomes a one-line headline, a button per proposed option showing its title, with the recommended one highlighted and marked "(recommended)", a button for each console link on the report's 🔗 line, and the report, up to its first horizontal rule, folded underneath. Clicking an option answers as if you had replied in the thread yourself with `apply Option B: <its title>`, or `apply: <its title>` when there is a single fix: the agent replaces the option buttons with a line such as "✓ <your name>: <its title>", your Slack name in plain text (or, if Slack refuses that edit, posts that line in the thread), and your reply passes the same user and channel checks a typed reply does. A click never needs an @-mention. A typed reply in the alert's thread needs one only where the Slack adapter is set to require a mention in threads, or, in a channel that requires a mention, to ignore every message without one. Where it is set to ignore a message addressed to someone else, a typed reply that opens by mentioning another person is ignored unless it also mentions the agent. If someone the agent answers has already replied in the thread since the options appeared with `apply`, `apply B` or `apply Option B` (a letter the alert offers, when its options are lettered), with or without a please or thanks after it, or with `apply Option B: ` and that option's title, whole or clipped as the button shows it, a later click runs nothing, and the option buttons are replaced with a line saying the alert was answered in the thread; link buttons stay. A report that does not parse into options, a second report in the same thread, a report too long to fold, a report with a table above its first horizontal rule, or with a horizontal rule above its headline, options or links, or an edit Slack refuses arrives as a threaded reply as before.

### Harness messages

With `KAGE_SLACK_UX` on, the harness's own messages stay out of the way on Slack. Scheduled reports arrive without the `Cronjob Response` header, job ID and footer. The long-turn heartbeat, if it is enabled for Slack, says the agent is still working without naming the tool running. The agent does not announce that it is back after a restart, post the session-database warnings (the error stays in the log), or append Hermes' tip about its queueing setting. Its replies about restarting, shutting down, stopping, being busy with an earlier message, a command sent while it is working, a `/steer` it could not take, or the model provider failing or turning a request down are written plainly in its own voice, with no console commands or error text. That covers the English replies; an install set to another display language gets Hermes' translation of the restart and stop replies. Other chat platforms are unchanged, and with the flag off nothing changes.

## Sending another message while it works

A message sent while the Planning Agent is still answering an earlier one in the same conversation interrupts that turn, and the agent takes the new message up in its place. This is Hermes' default `interrupt` mode, which kube-agents does not change; Hermes queues the message instead while the turn has subagents running or is compressing its context. The agent acknowledges with a short busy reply, at most once every 30 seconds per conversation. Work already filed on the board keeps running, and its progress and report still post into the thread. Under `spec.mode: next` a follow-up is queued behind the running task instead; see [Follow-ups while a task runs](#follow-ups-while-a-task-runs).

## Conversations under `spec.mode: next`

Under the unsupported `spec.mode: next` toggle, the A2A gateway takes chat in place of the Planning Agent's chat platforms. It holds Google Chat when Google Chat is enabled, and Slack otherwise. With both enabled, Slack stays on the default path described above. On the backend the gateway holds, nothing above about the Planning Agent's Slack or Google Chat platform applies. The gateway holds no model. It decides which messages are turns, keeps one status line per task, and answers a few fixed commands itself. Every other message goes as a task, by default to the `platform` route: the Hermes bridge in the agent's pod runs it as a Planning Agent turn in that conversation's own Hermes session, and the Planning Agent answers it or files board cards as it does on the default path. How the agent then answers the question is in [How a chat question is answered under `next`](#how-a-chat-question-is-answered-under-next); this section covers what you see in the conversation.

### Which messages it answers

On Slack:

- **A direct message.** Every message is a turn, with or without a mention. Each top-level message starts a conversation of its own in the thread under it, and the gateway posts its replies in that thread. A message typed in that thread is the same conversation: a follow-up while its task runs, and a new task with the earlier ones in context after it ends.
- **A channel.** A top-level message is a turn only when it mentions the bot. It starts a conversation in the thread under that message, and every reply to it posts in that thread. A reply in the thread is a turn when it mentions the bot. Without a mention, it is a turn only while the thread's conversation is live: a task the gateway started in the thread is still running, or the thread's last task started or ended in the last 30 minutes (the gateway's `A2A_IDLE_TTL`). After that, mention the bot again. A thread someone else started becomes live the same way, once a mention in it starts a task.
- A message that is only a mention, an edit, another bot's message, or a message from a member of another workspace in a Slack Connect channel is not a turn and gets no reply.

On Google Chat:

- **A direct message.** Every message is a turn. Top-level messages share one conversation, and the gateway answers them top-level. A message typed in a thread is a conversation of its own, answered in that thread; the next message typed there joins it.
- **A space.** Chat sends the app only the messages that mention it. In a space with threads, each thread is its own conversation. In a space without threads, and in a group chat, the whole space is one conversation.

A sender the allowlist does not admit gets one notice, once per sender until the gateway restarts, and nothing else. On Slack it reads `⛔ I can't verify who you are on slack (id U0123ABCD), so I can't take asks from you yet — an admin has to add you to the allowed users list (or correct their principal map entry).` On Google Chat it names `gchat`, the sender's email and `the allowed users list`. The fix is in Troubleshooting, [for Slack](https://github.com/gke-labs/kube-agents/blob/main/INSTALL.md#5-slack-bot-doesnt-answer) and [for Google Chat](https://github.com/gke-labs/kube-agents/blob/main/INSTALL.md#6-tracing-where-a-chat-message-stops).

### What carries over from default mode

| In default mode                                                                                                   | Under `next`, on the backend the gateway holds                                                                                                                                            |
| ----------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Slash commands: `/new`, `/sethome`, `/steer`, `/hermes …`                                                         | None of them. The gateway reads one command, [`/session`](#session).                                                                                                                      |
| Reactions, buttons, cards and the plan status message (`KAGE_SLACK_UX`)                                           | None. Each task gets one status line, edited in place.                                                                                                                                    |
| Slack agent view and suggested prompts                                                                            | None.                                                                                                                                                                                     |
| The home channel ([Google Chat](#home-channel), [Slack](#home-channel-1)): proactive alerts and scheduled reports | Posted by the gateway to the home channel on the `PlatformAgent`: `spec.integration.googleChat.homeChannel` on Google Chat, `spec.integration.slack.homeChannel` (a channel ID) on Slack. |
| A board card's progress and report post into the thread                                                           | A card the agent files while answering posts each progress note as a message of its own, and its report, into the conversation you asked in; a file the card produced is not attached.    |
| A message sent while the agent works interrupts its turn                                                          | It is queued as a follow-up to the running task.                                                                                                                                          |
| An unlisted Slack sender is ignored silently                                                                      | An unlisted sender gets one notice.                                                                                                                                                       |
| Several Slack workspaces from one install                                                                         | One workspace.                                                                                                                                                                            |

### What a task looks like

Each turn that becomes a task posts a status line, `⏳ submitted…`, which the gateway edits as the task moves: `⚙️ **working**`, followed on Slack by the agent's latest progress note (on Google Chat only with `googleChat.mode: debug`). The answer posts as a message of its own, and the status line then reads `✅ **completed**`. A task that fails posts `❌ failed: <reason>`; one that is cancelled posts `🛑 canceled`; one the executor refuses posts `🚫 the executor rejected the task: <reason>`. When the agent needs something from you it posts `❓ <its question>`; your next message in the conversation is the answer.

### Follow-ups while a task runs

A conversation runs one task at a time. A message sent while its task runs, other than the commands below, goes to that task as a follow-up, and the gateway answers `✏️ got it, I'll take that next`. The agent finishes the turn it is on, then takes each follow-up in the order it arrived as a further turn in the same session, so it answers with the earlier turns in context. Each turn's answer posts as soon as the next turn starts, and the last one closes the task. A task takes at most 16 follow-ups. One the agent cannot take is answered `⚠️ not taken: <why>. Send it again after the answer.`, where the reason is that the task has already taken as many follow-ups as it runs, that it was already finishing, that the message had no text, that the task's capability check did not pass, or that the agent's executor cannot continue a session (the bridge's `cli` executor; the default `api` executor can). When the task ends, follow-ups that never ran are counted in `⚠️ N queued follow-up(s) did not run before the task ended; send them again if they still matter`, and follow-ups that arrived as it finished in `⚠️ N follow-up(s) arrived as the task finished and were not taken; send them again`.

If the task has produced nothing yet, a follow-up gets `✏️ steering sent — task <id> has shown nothing on its event stream yet, so no reply is promised: it may still be starting, or nothing may have taken it; if it is still silent 10m0s after it was submitted, your next message here starts a new task` instead. When that time is up and nobody has written since, the gateway posts `⚠️ task <id> has produced nothing on its event stream in 10m0s; unless it starts first, your next message here starts a new task instead of going to it`. The next message then posts `⚠️ task <id> has produced nothing on its event stream in 10m0s, so this conversation is released and this message is handled as a new turn` and starts a new task. The 10 minutes are the gateway's `A2A_FIRST_EVENT_GRACE`.

Besides [`/session`](#session), two kinds of message are commands rather than follow-ups. Each must be the whole message; case and punctuation are ignored, and on Slack a mention of the bot is stripped first, so `@bot stop` counts.

- **`stop`, `cancel` or `abort`.** With a task running, the gateway answers `🛑 cancel sent — the task ends when the executor confirms`, and the status line ends at `🛑 **canceled**` when it does. Your next message starts a new task. A second `stop` before the task ends gets `🛑 cancel already sent — the task ends when the executor confirms`. With nothing running in the conversation, `stop` gets `🤷 nothing is running`. A `stop` acts only on the conversation it is sent in, so on Slack send it in the task's thread: a new top-level message in a channel or a DM is a new conversation. A top-level `stop` in a Slack DM starts nothing and gets `🤷 nothing is running here — each question runs in its own thread, so reply in that question's thread`.
- **A status question**, exactly one of `status`, `progress`, `any progress`, `any update`, `any updates`, `what is it doing`, `what's it doing`, `what are you doing`, `what's happening`, `what is happening`, `what's going on`, `what is going on`, `where are we`, `how's it going` or `how is it going`. With a task running, the gateway answers from the task's event stream without asking the agent: `🔎 task <id> is **working** (2m14s so far)`, the request it is working on, its state history, its latest progress note, and the line `(answered by stream replay — no live connection to the executor)`. A task with no events yet gets `📭 no events on the stream for this task yet`. With nothing running, a status question is an ordinary message and starts a task, except at the top level of a Slack DM, where it gets the same `nothing is running here` reply as `stop`. Any other wording, such as "how is the upgrade doing", is a follow-up, which the agent answers itself.

### When it is busy

The agent answers a fixed number of tasks at once: the Hermes bridge's worker count, 10 unless the operator's `A2A_BRIDGE_CONCURRENCY` sets another. When a new task starts while at least that many tasks from other conversations are outstanding, counting the running ones, its status line reads `⏳ **queued** — 12 requests are ahead of yours; I'll start on it as soon as there's room` in place of `⏳ submitted…`, and changes to `⚙️ **working**` when the task starts. The notice is informational: the task is already submitted. The operator's `A2A_BUSY_NOTICE_AT` moves the threshold. A conversation on the session route below never gets the notice, since each of its tasks runs on a pod of its own.

### `/session`

By default every conversation's tasks go to the `platform` route above. `/session` moves the conversation to the session route, where each new task runs in a session pod of its own, started for it from the `chat` profile. The pod is deleted when the conversation's next task starts, or after 30 minutes without activity. An install runs at most 10 session pods at once (`spec.harness.tuning.maxSessions`), and a task refused at that cap is answered `🚦 not started: 10 session workers are already running (cap 10). …`. A follow-up to a task on the session route gets `✏️ steering sent — the worker picks it up at its next turn boundary if the task is still running`.

On Slack, start the message with the bot's mention, `@bot /session`, because Slack takes a bare leading `/` as one of its own slash commands. In a Google Chat space, mention the app as with any message.

| You send          | The gateway answers                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `/session`        | `🧵 session route on — your next message opens a session pod; /session off returns to platform`. In a Slack channel thread it asks for a mention instead: `🧵 session route on — mention me in your next message to open a session pod (a Slack thread carries unmentioned replies only once a task has started); /session off returns to platform`. In a Slack DM, where `/session` sent top-level opens a thread of its own: `🧵 session route on — reply in this thread to open a session pod; /session off returns to platform`. |
| `/session <text>` | Turns the route on and runs `<text>` as its first task.                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| `/session off`    | `↩️ session route off — back to platform`. With a session task still running: `⚠️ a session task is still running — stop it first, then /session off`. When the route was not on: `ℹ️ not on the session route; nothing to turn off`. Sent top-level in a Slack DM: `ℹ️ /session off acts on the thread it's typed in — reply /session off in that question's thread`.                                                                                                                                                               |
| `/session` again  | `ℹ️ already on the session route`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| `/session stop`   | `ℹ️ to leave the session route say /session off; to stop a running task say stop`. Nothing is stopped.                                                                                                                                                                                                                                                                                                                                                                                                                               |

If a task is already running on the `platform` route when you send `/session`, that task finishes there, and the message after it opens the first session pod; `/session <text>` sent then is not run, and the gateway says so. A message that starts with `delegate`, such as `delegate check the node pools`, sends that one task to a fresh session pod and leaves the conversation on the `platform` route.

## Proactive alerts (both channels)

The harness doesn't only reply to messages. A cluster event posted to the in-pod triage endpoint (`inject_message` in [`agents/platform/scripts/session_kv_server.py`](https://github.com/gke-labs/kube-agents/blob/main/agents/platform/scripts/session_kv_server.py)) opens a thread unprompted: it posts the alert first, then runs the triage turn in the thread that alert created. On Slack with `KAGE_SLACK_UX` on, the triage then [edits the alert itself](#buttons). The first-run inventory report arrives the same way, into the thread `bootstrap_onboarding` bound. On Slack, with `KAGE_SLACK_UX` on, the inventory report is also reshaped on its way, into a card with one number on it: a headline saying what was scanned and how many things it found to look at, a line under it when the report says something could not be scanned, every finding the report lists a row each, led by their severity when the report labels it and with the sentence under each kept, the report's line about critical findings it held back, when it has one, then a button to fix the first one and, when it found more than it shows, one to see them all. Clicking one answers as your turn in the thread; a click from someone the agent does not answer changes nothing. Where Slack refuses the card, or the post fails for any other reason, the report is posted as text with the same headline and findings, and its closing lines, or a line asking to see them all, in place of the buttons. A report that does not parse to that shape is posted as written. Where an unprompted message lands:

- **Google Chat**: to the space that owns the interaction, or the space set via `GOOGLE_CHAT_HOME_CHANNEL`.
- **Slack**: to `SLACK_HOME_CHANNEL`.

An alert goes to **one** of them, not both: it opens a thread that the triage turn then replies into, and a thread belongs to a single platform. With both integrations enabled the alert goes to Google Chat, falling through to Slack if that send is not accepted. A scheduled report has no such constraint and is posted to every enabled platform — [the relay design](https://github.com/gke-labs/kube-agents/blob/main/docs/designs/cron-report-relay.md) is canonical for both rules.

A governance watchdog's findings live on its ledger issue and the remediation pull requests that link back to it. Its scheduled report on this path is usually one line of counts ending with the ledger link, so the report to read is the issue — see [Proactive autonomy](/kube-agents/overview/proactive-autonomy/) and [Autonomous watchdogs](/kube-agents/concepts/autonomous-watchdogs/) for the schedules.

With `KAGE_SLACK_UX` on, Slack gets a card built from the open ledger issue. Its headline carries one number, how many findings of the most severe level the issue lists ("Security & RBAC Posture Audit: 2 critical findings"), and up to ten critical findings are listed under it, each led by its severity and tagged "new" when it was not there on the last run; with none critical listed, the headline counts the most severe level listed and lists the top two. A line under them counts the rest by severity ("5 more (1 major, 4 minor) are in the ledger issue."), and another names any clusters the run could not check, since a silent gap reads as clean. Then come a "Look at the first one" button and a button that opens the issue. Clicking "Look at the first one" starts a turn for you in the card's thread, as if you had typed the button's label; the buttons give way to a line naming who chose, only the first click counts, and a click from someone the agent does not answer changes nothing. A clean run closes its ledger, so its card is one line: "Security & RBAC Posture Audit: clean. Ledger closed." A run with no findings that left the ledger open because it could not check everything is posted as the report's own line in bold with the link, since the issue still shows the last run's counts. Nothing else is posted in the card's thread: the ledger issue holds the rest. The headline is posted as text where Slack refuses the buttons or the message, and also where the report was truncated, too little time is left, or the buttons cannot be posted at all. A reply in the thread is answered with the full report in context either way.

## First-run onboarding

On a fresh install the first chat interaction gets a guided onboarding instead of a cold start. Three `no_agent` cron jobs on the Planning Agent profile (`agents/chat/defaults/cron/jobs.json`) drive it:

- **`bootstrap-inventory-scan`** files a kanban card assigned to the Platform Agent, recording the card's id in `/opt/data/.bootstrap_scan_filed` so it never files a second one. That worker runs the environment-discovery SOP ([`agents/platform/governance/inventory.md`](https://github.com/gke-labs/kube-agents/blob/main/agents/platform/governance/inventory.md)): it lists the fleet, audits any cluster the Cluster Agent roster has no agent for, and completes. The same cron job files one audit card per Cluster Agent on the roster, each pointing that agent at the single-cluster audit SOP ([`agents/platform/governance/cluster_inventory_audit_sop.md`](https://github.com/gke-labs/kube-agents/blob/main/agents/platform/governance/cluster_inventory_audit_sop.md)). Once those cards finish, the same cron job's hand-off script merges their structured results — fleet topology, Workload Identity, workload SRE posture — into the complete findings at `/opt/data/INVENTORY.raw.md`, naming any cluster that did not report as a gap, and files a second card, which runs the prioritization SOP ([`agents/platform/governance/inventory_prioritize_sop.md`](https://github.com/gke-labs/kube-agents/blob/main/agents/platform/governance/inventory_prioritize_sop.md)) against those findings alone, scoring each one against a fixed rubric and registering all of them in the findings queue before writing the ranked report the user is sent to `/opt/data/INVENTORY.md`. The full findings stay on disk. The report names the most urgent critical findings, at most `FINDINGS_FIRST_REPORT_CRITICALS` of them, and nothing less severe; it says how many items are queued behind them and how many of those are critical, and the [findings nudge](/kube-agents/reference/cron-jobs/), whose page also covers that limit, brings those to chat a few a day. A scan with no critical finding gets a report that says so and lists none. If no cluster's audit reached the findings, no second card is filed: the hand-off writes a short report saying no cluster was audited and why, so an empty scan is never presented as a clean environment.
- **`bootstrap-inventory-delivery`** posts that report into the chat, **verbatim** unless `KAGE_SLACK_UX` is on and the chat is Slack (where it is reshaped as described above), once two conditions hold: the ranked report has been written, and a human has connected. It claims the delivery atomically first, so overlapping runs can't post the report twice.
- **`oobe`** runs four of the fleet audits once, one after another (`fleet-wide-cost-analysis`, `compliance-audit`, `obtainability-audit`, `stockout-prevention`), starting as soon as the scan's ranking card has finished and none of the four is already running, or at a fallback of 90 minutes or more after the sweep was filed (longer for a larger fleet) if it never does, so their first ledger issues arrive soon after the scan rather than at the next scheduled run. An audit that already completed a scheduled run since the scan began is not run again. It does not wait for a human, and it starts none of them when no GitHub repository is configured for them to publish to, since every audit needs one. It records what it started in `/opt/data/.oobe_audits_fired` and then removes itself. The design is [`docs/designs/oobe.md`](https://github.com/gke-labs/kube-agents/blob/main/docs/designs/oobe.md).

The `bootstrap_onboarding` plugin (enabled in `agents/chat/config.yaml`) hooks the first human turn: it greets the user, binds the delivery job to that chat thread, makes that chat the platform's home channel if none is set, and marks that a human is present. Once the report is delivered, the flow marks itself complete and the two bootstrap jobs remove themselves; `oobe` removes itself once it has started the audits or skipped them. None of them runs again on that data volume.

All three jobs fire every minute (`* * * * *`, see [Autonomous watchdogs](/kube-agents/concepts/autonomous-watchdogs/#what-fires-the-schedule)) while the work they guard takes minutes, so each stage records its own marker the moment it acts rather than inferring from the report or from completion. `oobe`'s design is [`docs/designs/oobe.md`](https://github.com/gke-labs/kube-agents/blob/main/docs/designs/oobe.md); the bootstrap jobs' design, state markers, and maintenance rules live in the plugin's [README](https://github.com/gke-labs/kube-agents/blob/main/agents/chat/defaults/plugins/bootstrap_onboarding/README.md).

## What's not here

- **No user-facing web UI.** Chat is the primary surface. The one web UI the install can run is the Hermes dashboard, a per-pod debugging view the installer offers as `--enable-hermes-dashboard` (off by default there; the CRD's own default is on) that binds loopback inside the pod, so reaching it means a port-forward or the tunnel script — [PlatformAgent CRD](/kube-agents/operator/platformagent-crd/#specharness) is canonical. A local [admin console](/kube-agents/reference/admin-console/) runs from a repository checkout on your own machine, loopback only; the install does not deploy it.
- **No CLI beyond the Hermes CLI inside the pod.** `kubectl exec` into the agent pod and run the Hermes CLI there — note the pod hosts several profiles, so a bare `hermes` command talks to the locked-down Planning Agent; use `hermes -p platform` to reach the Platform Agent (or `hermes -p <cluster-profile>` for a Cluster Agent). `kubectl port-forward` is not a way in on a GKE Sandbox (gVisor) node pool, which is the install default: the forward is established in the host-side netns and cannot see a listener inside the sandbox — [PlatformAgent CRD](/kube-agents/operator/platformagent-crd/#specharness) is canonical on that. `kubectl exec` has no such problem, because it enters the sandbox.
- **No email, PagerDuty, or generic webhook ingress.** Chat channels only.

## When no chat platform is enabled

Both channels are opt-in and default to disabled, so an install that enabled neither has no chat to talk to. The Hermes CLI above is one way in, and the installer prints these two commands when you choose "None" at its chat prompt and again when it finishes:

```bash
gcloud container clusters get-credentials <cluster> --location <region> --project <project> --dns-endpoint
kubectl exec -it deployment/platform-agent-gateway -n kubeagents-system -c platform-agent -- hermes -p platform
```

Pass `--dns-endpoint` only on a cluster that publishes an externally reachable DNS endpoint; gcloud rejects the flag on one that does not. The installer resolves that per cluster and prints the flag only when it applies ([`scripts/installer/gke_dns_endpoint.sh`](https://github.com/gke-labs/kube-agents/blob/main/scripts/installer/gke_dns_endpoint.sh)). The `-c platform-agent` is the Hermes container; the gateway pod runs three, so omitting it works but makes kubectl warn about which one it picked.

This reaches the Platform Agent directly, bypassing the front door: a request typed here is executed by the profile that receives it rather than being planned and filed as a kanban card. A bare `hermes` reaches the Planning Agent instead, which is where a chat message would have landed and which delegates as described above.

The other way in is the [admin console](/kube-agents/reference/admin-console/), started from a repository checkout on your own machine: its Chat page reaches the Planning Agent through the front door, so a request typed there is planned and delegated the way a chat message would be.

Two things a chat-less install does not exercise. Scheduled reports and alert-driven triage are delivered only to enabled chat platforms — the delivery resolver enumerates Google Chat and Slack and nothing else — so neither arrives anywhere. And `bootstrap-inventory-delivery` waits for a human to connect over chat before it posts the first-run inventory report, so that report stays at `/opt/data/INVENTORY.md` on the shell sandbox pod's volume; read it with `kubectl exec -n kubeagents-system platform-agent-shell-0 -c shell -- cat /opt/data/INVENTORY.md` rather than waiting for it.
