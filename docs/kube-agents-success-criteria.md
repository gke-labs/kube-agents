# kube-agents success criteria

## High level summary

This document lists the success criteria (SC) for kube-agents from the end user's point of view. A success criterion is a result a user can observe and measure. The document also records the gap audit: the measured state of each criterion on one install, the gaps, and the changes that close them. The end-state specification keeps its own acceptance criteria in [`docs/architecture/01-vision-scope.md` §7](architecture/01-vision-scope.md#7-success-criteria-how-well-know-its-working); this list is the user-facing subset that is measured per release.

## Goal

What gets measured gets built. This list is for agents, engineers and other product stakeholders to agree on three questions:

1. If we achieve every SC, will the user think kube-agents is great?
2. Which gaps to the SC exist today?
3. How do we close each gap?

## List of SC

1. Agentic installation and onboarding.
2. New-user-friendly out-of-box experience (OOBE):
   - it does not crash when the install stays within the documented limits;
   - the user gets a report within the first two hours.
3. Responsive to simple questions, under one minute:
   - "what model are you running", "which GCP project have you authenticated with", and the like.
4. Responsive to complex requests:
   - an initial acknowledgement within 10 seconds;
   - "Audit any potential issues for my next GKE version upgrade", "Audit, and discover any zonal skew or anomaly that may cause issues soon", and the like;
   - not more than three times slower than a similar query asked directly to Gemini or Claude;
   - responsive to "try again" after a failure or a timeout.

## Gaps

The audit of 2026-10-29 measured each criterion on one development install: `main` 3e5be2e0e plus #3922 (image `5dcb02145`), `spec.mode` today, Vertex AI `gemini-3.1-pro-preview` as `model-default`, `maxInProgress` 5, 47 clusters in scope (the host, two GPU clusters, four seeded clusters and 40 six-node scale clusters). Questions went through the agent's API door (`POST /v1/responses` through the auth sidecar), which is the chat path minus the chat backend's hop; each delegated card was watched on the kanban store until it was terminal. Every timed run, the baseline runs and the install's record are in the audit's tracking issue, #4354, which also tracks the changes below.

### SC3: simple questions under one minute

What exists: the Planning Agent answers greetings, board reads and the roster's static facts (the host cluster's identity and the projects in scope) in its own turn; everything else becomes a card for the Platform Agent.

Measured (opening turn is the ack or the in-turn answer; card time is from the card's creation to its completion on the board):

## Closing the gaps

One issue per change, in the order the numbers above argue for, tracked from #4354; the table rows link them once they exist.

1. A latency series for chat turns (ack and answer, per backend) exported by the gateway, and a 60 s budget for the simple set above as a nightly case that fails on time, not only on content.
2. The roster answers the fleet facts it already holds in the turn: cluster names, versions, the last sweep's health, the deployed harness version and the model behind `model-default`; with the reconcile's prune making the roster trustworthy, or the answer labelled with the roster's age.
3. The readiness report on request reads clusters in parallel under the proxy's cap, keeps one copy per request, and answers from the daily watch's last report when it is fresh.
4. Zonal skew and anomaly discovery built as designed in `docs/designs/fleet-anomaly-detection-checks.md`, and routed by name.
5. "try again" bound to the last card: resume or re-file once, with the card's own result, never a second interpretation.
6. The agent container's memory request sized from the scale data (the sizing epic, #3753), with a restart alert on by default.
7. Scheduled reports reach the Google Chat channel on a Workload Identity install, and a delivery failure surfaces in chat within the hour, not only in a log.
8. An install self-check at the end of `install.sh`: the agent answers one question before the installer reports success, and the time is recorded.
9. A bare-model baseline run beside the eval judge for the two audits above, so the ratio in the table is tracked per release.

The measurements repeat on the next release with the same questions on the same install, and the numbers replace the ones above.
