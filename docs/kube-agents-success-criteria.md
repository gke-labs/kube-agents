# kube-agents success criteria

## High level summary

This document lists the success criteria (SC) for kube-agents from the end user's point of view. A success criterion is a result a user can observe and measure. The document also records the gap audit: the measured state of each criterion on one install, the gaps, and the changes that close them. The end-state specification keeps its own acceptance criteria in [`docs/architecture/01-vision-scope.md` §7](architecture/01-vision-scope.md#7-success-criteria-how-well-know-its-working); this list is the user-facing subset that is measured per release.

## Goal

What gets measured gets built. This list is for agents, engineers and other product stakeholders to agree on three questions:

1. If we achieve every SC, will the user think kube-agents is great?
2. Which gaps to the SC exist today?
3. How do we close each gap?

## List of SC

1. Agentic installation and onboarding: an agent runs the install; an admin does the console steps the providers require.
2. New-user-friendly out-of-box experience (OOBE):
   - it does not crash when the install stays within the documented limits;
   - the user gets a report within the first two hours.
3. Responsive to simple questions, under one minute:
   - "what model are you running", "which GCP project have you authenticated with", and the like.
4. Responsive to complex requests:
   - an initial acknowledgement within 10 seconds;
   - "Audit any potential issues for my next GKE version upgrade", "Audit, and discover any zonal skew or anomaly that may cause issues soon", and the like;
   - not more than three times slower than a similar query asked directly to Gemini or Claude;
   - responsive to "try again" after a failure or a timeout.

## Gaps

Only what a user meets on the core flow is listed here: install, the first report, questions, audits and retries. A missing test, a missing metric, a step an admin does once, or an installer edge case are not gaps in this document. The audit of 2026-10-29 measured each criterion on one development install: `main` 3e5be2e0e plus #3922 (image `5dcb02145`), `spec.mode` today, Vertex AI `gemini-3.1-pro-preview` as `model-default`, `maxInProgress` 5, 47 clusters in scope (the host, two GPU clusters, four seeded clusters and 40 six-node scale clusters). Questions went through the agent's API door (`POST /v1/responses` through the auth sidecar), which is the chat path minus the chat backend's hop; each delegated card was watched on the kanban store until it was terminal. Every timed run, the baseline runs and the install's record are in the audit's tracking issue, #4354, which also tracks the changes below.

### SC1: agentic installation and onboarding

What exists: `INSTALL.md` is written for an agent, `install.sh` runs non-interactively with a dry run and a JSON report, and the `install-kube-agents` skill drives it from a coding assistant's session in a checkout.

#### Gaps found

Accepted and not tracked: an admin does the console steps the providers require (the Google Chat app, the Slack app, the GitHub App), so full agentic onboarding is not a criterion, and the installer's edge cases (a dry run that cannot plan, a shortfall found mid-apply) are not part of the core flow. The gaps below are what the person running the install sees on the normal path.

| Gap                                                                                                                                                                                                                                                               | Evidence                                                                      | State |
| ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------- | ----- |
| The installer prints "Installation Complete" while a deployment has not reported ready (`SUCCESS_PENDING_ROLLOUT`) and hands the user a watch command instead of waiting or announcing readiness; a first boot can take over fifteen minutes.                     | `install.sh`, `docs/site/src/content/docs/install/quickstart-gke.mdx`         | open  |
| Nothing confirms the assistant answers: the installer verifies that the deployments are up, not that a question gets a reply, so the user's first prompt is the test; on the documented first run its acknowledgement took 21 s and its result a further 6.6 min. | `docs/site/src/content/docs/install/first-prompts.md`, `docs/designs/oobe.md` | open  |

### SC3: simple questions under one minute

What exists: the Planning Agent answers greetings, board reads and the roster's static facts (the host cluster's identity and the projects in scope) in its own turn; everything else becomes a card for the Platform Agent.

#### Measured on 2026-10-29

Measured (opening turn is the ack or the in-turn answer; card time is from the card's creation to its completion on the board):

| Question                                               | Route          | Run 1                  | Run 2                  | Run 3                  | Against 60 s            |
| ------------------------------------------------------ | -------------- | ---------------------- | ---------------------- | ---------------------- | ----------------------- |

| What clusters are you running?                         | card           | ack 19 s, answer 114 s | ack 19 s, answer 87 s  | ack 14 s, answer 100 s | over 60 s (worst 114 s) |

| What clusters are you monitoring                       | card / in turn | 15 s                   | 46 s                   | ack 74 s, answer 204 s | over 60 s (worst 204 s) |

| create a github issue for latency                      | in turn        | —                      | 19 s                   | 16 s                   | under 60 s              |
| Overnight crons                                        | card / in turn | —                      | ack 22 s, answer 91 s  | 9 s                    | over 60 s (worst 91 s)  |

The route is not stable: "What clusters are you monitoring" was answered from the roster twice (15 s, 46 s) and delegated once (ack 74 s, answer 204 s); "Overnight crons" was delegated once (91 s) and answered with a clarifying question once (9 s); "create a github issue for latency" drafted a public issue on the upstream repository once and asked which repository once. The delegated run of the monitoring question found that 32 of the install's cluster exclusions name the wrong location, which is why the scale clusters are in scope at all.

## Closing the gaps

The changes that close them, ordered by what the user gains first, tracked from #4354; the table rows link the issues once they exist.

1. The readiness report on request keeps one copy per request, reads clusters in parallel under the credential proxy's cap, and answers from the daily watch's last report when it is fresh: the upgrade audit answers in minutes, not hours.
2. The agent container's memory request sized from the scale data (the sizing epic, #3753), with a restart alert on by default: the assistant stops disappearing under load.
3. The roster answers the fleet facts it already holds in the turn (cluster names, versions, the last sweep's health, the deployed version, the model behind `model-default`), with the reconcile's prune making the roster trustworthy or the answer labelled with its age: fleet questions in seconds.
4. "try again" bound to the last card: resume or re-file once, with the card's own result, never a second interpretation.
5. Zonal skew and anomaly discovery built as designed in `docs/designs/fleet-anomaly-detection-checks.md`, and routed by name.
6. Scheduled reports reach the Google Chat channel on a Workload Identity install, and a delivery failure surfaces in chat within the hour.
7. The first report posts to the home channel when it is ready, without waiting for the user's first message.
8. An install self-check: the assistant answers one question before the installer reports success, and the installer says when the assistant is ready.
9. A sign of life within 10 s of every request on every backend, before the model turn.
10. A stated, tested size the install supports, from the sizing data.

The measurements behind this document (the timed questions, the bare-model baseline, the install's record) were run by hand with the author's scripts and are recorded on #4354; they repeat on the next release with the same questions on the same install, and the numbers then replace the ones above.
