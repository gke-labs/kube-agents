# Design Proposal: Agent Autonomy & Tool Execution Boundaries

**Task ID:** Buganizer Task 537148480  
**Title:** Agent Autonomy & Tool Execution Boundaries  
**Target Files:** `agents/platform/config.yaml`, `agents/platform/SOUL.md`, `agents/platform/skills/`  
**Status:** Proposed / Draft for Review  
**Findings Included:** SKILL-004, SKILL-003, SKILL-005, SKILL-007  

---

## Executive Summary

The `kube-agents` Platform Agent requires strict operational boundaries to ensure safe execution in production GKE environments. Currently, the agent possesses broad shell access via `hermes-cli`, lacks dynamic verification for loaded skills in `/opt/hermes/skills/`, and operates under autonomy guidelines in `SOUL.md` that permit non-destructive state changes without explicit user confirmation.

This proposal establishes a robust security posture by:
1. **Restricting `hermes-cli` Execution Bounds:** Replacing unconstrained terminal access with scoped toolsets, strict command allowlists, and execution sandboxing in `agents/platform/config.yaml`.
2. **Implementing Skill Provenance & Integrity Verification:** Introducing SHA-256 checksum manifest generation and runtime verification for `/opt/hermes/skills/` to prevent skill tampering or unauthorized dynamic skill injection.
3. **Updating `SOUL.md` Autonomy Rules:** Mandatory human-in-the-loop confirmation for all state-changing operations (e.g. resource mutations, manifest applications, Git pushes, PR creation/merges, policy modifications) while preserving autonomous read-only diagnostic audits.
4. **Tool Execution Gating & Audit:** Enhancing pre-execution auditing to intercept and gate state-changing operations across CLI and MCP interfaces.

---

## 1. Background & Security Findings

Security audits of the `kube-agents` harness identified four key findings regarding agent autonomy and tool execution boundaries:

### Finding Breakdown

* **SKILL-004 (Unrestricted Shell Execution Bounds):** The inclusion of `hermes-cli` in `agents/platform/config.yaml` exposes unconstrained terminal execution capabilities (`bash`/`sh`). Without command allowlisting or path scoping, an agent could execute arbitrary system commands, bypass declarative workflows, or invoke dangerous utilities.
* **SKILL-003 (Skill Provenance & Integrity Gaps):** Skills copied to `/opt/hermes/skills/` during container build are ingested by the agent without cryptographic hash or signature verification. An attacker or malicious workload with filesystem access could tamper with `SKILL.md` or helper scripts to inject malicious prompt instructions or executable payloads.
* **SKILL-005 (Permissive Autonomy Guidelines in SOUL.md):** `SOUL.md` currently instructs the agent to prioritize action over clarification ("if the expected user response... would simply be 'yes', proceed autonomously"). This assumption allows state-changing mutations without explicit human confirmation when users issue open-ended prompts like "fix it for me".
* **SKILL-007 (Missing Tool Execution Audit & Gate Controls):** Tool invocations lack structured pre-execution policy gating, allowing state-mutating actions to run without explicit user authorization or structured audit logging.

---

## 2. Proposed Technical Design

### Component 1: Restricting `hermes-cli` Execution Bounds (`agents/platform/config.yaml`)

To mitigate **SKILL-004**, we restrict shell access by replacing open-ended `hermes-cli` capabilities with scoped, sandboxed command execution and explicit tool execution policies.

#### Key Changes in `agents/platform/config.yaml`:
- **Scoped Toolsets:** Restrict `platform_toolsets.cli` and `api_server` to specific, scoped MCP tools (`mcp-platform_control`, `mcp-gke`, `mcp-developer_knowledge`, `mcp-agent_common`) and explicit, restricted CLI commands.
- **Command Allowlisting & Sandbox Bounds:** Define explicit command allowlists for terminal/shell tools (permitting read-only commands like `kubectl get`, `kubectl describe`, `git status`, `git diff`, `helm status`, while blocking raw mutating commands like `kubectl apply`, `kubectl delete`, `gcloud container clusters delete`).
- **Approval Policy Configuration:** Configure strict `approvals` blocks requiring explicit user approval for any interactive shell invocation that performs state modifications.

```yaml
# Updated agents/platform/config.yaml snippet
platform_toolsets:
  cli:
    - mcp-agent_common
    - mcp-platform_control
    - mcp-developer_knowledge
    - mcp-gke
    - restricted-cli
  api_server:
    - mcp-agent_common
    - mcp-platform_control
    - mcp-developer_knowledge
    - mcp-gke
    - restricted-cli

approvals:
  default_mode: require_confirmation
  cron_mode: audit_only
  allowed_commands:
    - "kubectl get *"
    - "kubectl describe *"
    - "kubectl logs *"
    - "git status"
    - "git diff"
    - "helm list"
    - "helm status *"
  blocked_commands:
    - "kubectl apply *"
    - "kubectl delete *"
    - "kubectl edit *"
    - "gcloud * delete *"
    - "rm -rf *"

execution_bounds:
  read_only_enforced: true
  working_dir_restriction: "/opt/data"
  timeout_seconds: 300
```

### Component 2: Skill Provenance & Integrity Checks (`/opt/hermes/skills/`)

To address **SKILL-003**, we implement a multi-stage skill integrity verification mechanism:

#### 1. Build-Time Manifest Generation
During container image build (`deploy/docker/Dockerfile`), after copying skills to `/opt/hermes/skills/`, a SHA-256 checksum manifest (`checksum.manifest`) is generated for all skill files (`SKILL.md`, scripts, references, assets).

```bash
# Dockerfile snippet during image build
RUN cd /opt/hermes/skills && \
    find . -type f -not -name "checksum.manifest" -exec sha256sum {} + | sort -k2 > /opt/hermes/skills/checksum.manifest && \
    chmod 444 /opt/hermes/skills/checksum.manifest
```

#### 2. Filesystem Permission Hardening
Set immutable filesystem permissions on skill directories in the container image:
- Directories: `chmod 555 /opt/hermes/skills`
- Files: `chmod 444` (read-only for `hermes` user)

#### 3. Runtime Verification Hook / Plugin
Before loading any skill, the agent harness executes a Skill Integrity Verifier plugin (`skill_integrity_verifier`) that:
- Reads `/opt/hermes/skills/checksum.manifest`.
- Computes SHA-256 hashes of all files in `/opt/hermes/skills/`.
- Rejects any modified, added, or unauthorized skill files, emitting a security alert event to Cloud Logging / OTel telemetry.

### Component 3: Updating `SOUL.md` Autonomy Rules (`agents/platform/SOUL.md`)

To address **SKILL-005**, we update Section 1 ("Core Truths") of `agents/platform/SOUL.md` to establish strict boundaries between autonomous read-only operations and gated state-changing operations.

#### Modified Autonomy Guidelines in `SOUL.md`:

```markdown
## 1. Core Truths

- **Automation First (Declarative Workflow):** All GKE infrastructure changes, access boundaries, and agent deployments must be automated via the active declarative workflow. You are strictly forbidden from executing direct, manual cluster mutations or applying YAML manifests directly to the Kubernetes API. Every GKE cluster or operator creation must be proposed declaratively (e.g. submitting a Pull Request via `submit-suggestion`) for human review and approval.

- **Mandatory User Confirmation for State-Changing Operations:** You MUST obtain explicit human confirmation before executing any state-changing operation. State-changing operations include:
  - Modifying GKE cluster configuration or custom resources.
  - Applying or editing Kubernetes manifests.
  - Creating, merging, or pushing Git branches and Pull Requests.
  - Executing mutating CLI/shell actions.
  - Modifying tenant boundaries, RBAC bindings, or NetworkPolicies.

- **Autonomous Read-Only Auditing & Diagnosis:** You are fully autonomous when performing read-only diagnostic audits, querying GKE cluster telemetry, inspecting logs, checking resource specifications, and drafting declarative suggestions (PR proposals). You do NOT need human confirmation to query read-only state or build diagnostic context.

- **User Intent Priority (Clarified):** User requests such as "fix it for me", "do it", or "loop until done" instruct you to analyze issues and draft complete, declarative solutions. However, you MUST present the proposed plan or Pull Request to the user and await explicit confirmation before applying changes or triggering automated rollout pipelines.
```

### Component 4: Tool Execution Audit & Approval Gating (`SKILL-007`)

To address **SKILL-007**, all state-changing tool executions are intercepted by the `tool_call_audit` plugin before execution:
1. **Pre-Execution Check:** Verify if the tool call is state-changing (e.g. `submit-suggestion`, mutating RPCs, non-allowlisted shell commands).
2. **Attribution & Context:** Log `user.id`, `session.id`, `trace_id`, and `tool_name` to structured audit logs.
3. **Approval Gate:** If confirmation has not been recorded for the session/transaction, pause execution and prompt the user for confirmation.

## 3. Code Comment Analysis & Questions Raised

Per project guidelines, we explicitly analyze code comments found in relevant sections of the codebase and highlight potential conflicts or open questions.

### Comment 1: Cron Watchdog Autonomy
* **Location:** `deploy/shared/defaults/config.yaml` (Lines 43-45)
* **Code Comment:**
  ```yaml
  # Approval settings. Allow dangerous commands to execute autonomously in cron watchdogs.
  approvals:
    cron_mode: approve
  ```
* **Conflict / Question Raised:**  
  *Question for Proposal Review:* Setting `approvals.cron_mode: approve` allows background cron watchdogs to execute commands autonomously without user intervention. However, updating `SOUL.md` to require explicit human confirmation for state-changing operations directly conflicts with autonomous background execution by cron watchdogs.  
  *Proposed Resolution:* Cron watchdogs should be restricted strictly to **read-only diagnostic audits** (e.g., drift detection, compliance scanning). If a cron watchdog identifies an anomaly, it must generate a declarative suggestion (PR/Issue) rather than applying mutations directly. Pre-approved non-mutating maintenance tasks (such as `./scripts/github_token_refresh.py`) should be explicitly allowlisted.

### Comment 2: Preserving Upstream Hermes Prefix-Mapping Bypass
* **Location:** `deploy/shared/defaults/config.yaml` (Lines 25-30)
* **Code Comment:**
  ```yaml
  # Explicitly list platform_toolsets to bypass the upstream Hermes CLI/API loader prefix mapping bug.
  # platform_toolsets is a reserved framework key in Hermes...
  # Upstream resolves config-based MCP toolsets with a leading "mcp-" prefix, but filters them out
  # using raw names (e.g., "developer_knowledge"). Pre-declaring "mcp-developer_knowledge" here
  # acts as an explicit passthrough that bypasses the filter and loads the tools natively on boot.
  ```
* **Conflict / Question Raised:**  
  *Question for Proposal Review:* When restricting `hermes-cli` in `agents/platform/config.yaml`, could removing `hermes-cli` or altering `platform_toolsets` trigger the upstream loader prefix-mapping bug and cause MCP toolsets (`mcp-agent_common`, `mcp-platform_control`, `mcp-gke`, `mcp-developer_knowledge`) to be filtered out?  
  *Proposed Resolution:* Any update to `agents/platform/config.yaml` MUST preserve the explicit `mcp-` toolset declarations (`mcp-agent_common`, `mcp-platform_control`, `mcp-developer_knowledge`, `mcp-gke`) under `platform_toolsets.cli` and `platform_toolsets.api_server` to ensure MCP tool passthrough continues working as designed.

### Comment 3: Reconciling Autonomous Recovery with Mandatory Confirmation
* **Location:** `agents/platform/SOUL.md` (Lines 16-17)
* **Code Comment / Rule:**
  ```markdown
  - **Autonomous Recovery & Loop-Until-Done:** When executing a request... continue through blockers until the requested outcome is achieved...
  - **User Intent Priority:** As a general rule: if the expected user response ... would simply be "yes", do not ask the question; proceed autonomously...
  ```
* **Conflict / Question Raised:**  
  *Question for Proposal Review:* `SOUL.md` Line 17 explicitly tells the agent to proceed autonomously without asking when the implied answer is "yes". This conflicts with the Buganizer requirement to require explicit user confirmation for state-changing operations.  
  *Proposed Resolution:* We propose amending Section 1 of `SOUL.md` so that "Autonomous Recovery" is strictly bounded to read-only investigation and self-repair actions that do NOT alter cluster state (e.g., token refreshes, log inspections, re-queries). Any recovery action requiring infrastructure mutation or PR submission must present the plan to the user and receive confirmation before execution.
