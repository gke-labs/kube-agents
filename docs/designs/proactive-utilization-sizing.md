# Proactive Utilization-Driven Sizing and Active-Standby Broker Rollout

> **STATUS — implemented.** Covers Phase B of `sizingProfile: auto`: bi-directional utilization-triggered tier transitions with anti-thrashing hysteresis, surge-aware quota and LimitRange admission checks, and operator-coordinated active-standby handoff for `credential-proxy`.

**Scope:** `k8s-operator` (`api/v1alpha1`, `internal/controller/sizing_profile.go`, `internal/controller/sizing_utilization.go`, `internal/controller/credential_proxy_control.go`, `internal/controller/credential_proxy_manifests.go`, `internal/controller/platformagent_controller.go`), `agents/platform/scripts/credential_proxy.py`, Helm quota preflight / footprint assets, and [`docs/designs/credential-proxy-single-pod.md`](credential-proxy-single-pod.md).

**Baseline telemetry & RBAC:**

- Operator ClusterRole grants `get`/`list`/`watch` on `pods.metrics.k8s.io` and `nodes.metrics.k8s.io` plus cluster-wide `get`/`list`/`watch` on `coordination.k8s.io/leases` and `secrets`; namespaced Roles grant writes on Leases and Secrets in the release and `-profiles` namespaces.
- `sizing_utilization.go` queries `PodMetrics` (`metrics.k8s.io/v1beta1`) and scrapes `credential-proxy` `/metrics` (`8766`) directly inside `PlatformAgentReconciler` on `sizingUtilizationPollInterval` (`100s`).
- `credential_proxy.py` exports `kubeagents_credential_proxy_slots_in_use`, `kubeagents_credential_proxy_slot_cap`, `kubeagents_credential_proxy_child_memory_reserved_bytes`, `kubeagents_credential_proxy_child_memory_budget_bytes`, `kubeagents_credential_proxy_cgroup_memory_bytes`, and `kubeagents_credential_proxy_resource_watermark_ratio`.

## 1. Why Cluster Count Alone Is Not Enough

Under the prior `sizingProfile: auto` implementation, tier resolution was an upward-only latch keyed exclusively on cluster count (`10` for `medium`, `25` for `fleet`):

1. A small-count fleet (say `4` very large clusters with tens of thousands of pods) could saturate `small` (`1Gi` request / `2Gi` limit on `credential-proxy`, `384Mi` / `2Gi` on `agent-api-auth`, `512Mi` / `2Gi` on `shell`) without ever crossing `10` clusters.
2. A bursty workload never released `medium` or `fleet` resources after load subsided, because `resolveSizingTier` never stepped down even when utilization dropped well below the lower tier's capacity.
3. Because `buildCredentialProxyDeploymentForPlugins` previously used `Strategy: Recreate`, every tier change stopped the running broker pod before starting its replacement—and if the new pod failed to schedule on node capacity, service dropped until intervention.

## 2. Utilization Signal Model & Bi-Directional Hysteresis

### 2.1 Metrics Sources

`PlatformAgentReconciler` polls live `PodMetrics` (`metrics.k8s.io/v1beta1`) and scrapes `credential-proxy` `/metrics` every `sizingUtilizationPollInterval` (`100s`), excluding `<agent>-credential-proxy-exec-tier-*` pods from stateful-broker signals:

| Component                  | Utilization Signals                                                                                                                                                                                              | Capacity Denominator at Tier `T`                                                                                                                                                                                                                                                                                                                                                                                                                      |
| -------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `credential-proxy`         | `PodMetrics` CPU & memory working set, `/metrics` `slots_in_use / slot_cap`, `child_memory_reserved_bytes / child_memory_budget_bytes`, `cgroup_memory_bytes / min(cgroup limit, memory cap)`, `watermark_ratio` | CPU: effective request (`500m` / `1` / `4` Standard; `2` / `2` / `4` Autopilot); Memory: `Requests[memory]` when Autopilot limits clamp (`clamped=true`), else `Limits[memory]` (`2Gi` / `4Gi` / `8Gi`); slots (`8` / `12` / `16` under `auto` via `CREDENTIAL_PROXY_MAX_CONCURRENT_COMMANDS`, bounded by `credentialProxyAdmittedRequests` `10` / `22` / `45` at tier `T`; fixed/default profiles and `2Gi` exec-tier pods stay pinned at `8` slots) |
| `agent-api-auth`           | `PodMetrics` memory working set                                                                                                                                                                                  | Effective memory denominator (`2Gi` / `4Gi` / `8Gi`, `Requests` when clamped; absent metrics skipped when `scaleToZero: true`)                                                                                                                                                                                                                                                                                                                        |
| `shell` (`<name>-shell-0`) | `PodMetrics` memory working set                                                                                                                                                                                  | Effective memory denominator (`2Gi` / `2Gi` / `4Gi`, `Requests` when clamped)                                                                                                                                                                                                                                                                                                                                                                         |

A tier step is only proposed along a saturated dimension if the candidate higher tier strictly increases that dimension's capacity (for example, on Autopilot `small -> medium` raises `credential-proxy` memory `2Gi -> 4Gi` and slots `8 -> 12` without changing CPU `2 -> 2`, so CPU saturation alone targets `fleet` `2 -> 4`, whereas memory or slots saturation targets `medium` first; when a user memory override pins `credentialProxyAdmittedRequests` below the tier slot cap, `slots` does not trigger a futile promotion).

### 2.2 Step-Up and Step-Down Thresholds (Anti-Thrashing)

Package-level constants in `sizing_utilization.go` govern bi-directional transitions:

1. Cluster-count floor: `floor = sizingTierForClusterCount(observedClusterCount)` (`small` `< 10`, `medium` `10..24`, `fleet` `>= 25`). When `auto` is active, utilization can promote above `floor` (`T > floor`), and step-down stops at `floor` (`T >= floor`), never stepping below what the registered cluster count earns.
2. Step-up (`T -> T+1` or relieving tier): Triggered when any bottleneck dimension `d` where candidate capacity strictly exceeds `cap(T, d)` holds `usage(d) / cap(T, d) >= 75%` (`sizingStepUpThresholdPct`) continuously for `5m` (`sizingStepUpSoakDuration`, tracked via `status.sizing.scaleUpSustainedSince`). Targets the lowest tier relieving all currently saturated dimensions.
3. Step-down (`T -> T-1`, 1 tier at a time): Requires `T > floor` (respects cluster-count floor and manual explicit tier overrides), at least `30m` elapsed since `status.sizing.lastTransitionTime` (`sizingTransitionCooldown`), and every dimension whose capacity strictly shrinks in `T-1` having an observed reading and holding `usage(d) / cap(T-1, d) <= 55%` (`sizingStepDownThresholdPct`) continuously for `25m` (`sizingStepDownSoakDuration`, tracked via `status.sizing.scaleDownSustainedSince`).
4. Missing-metrics fail-safe: Missing `PodMetrics` or unreachable `/metrics` never triggers step-down (only observed dimensions confirm safe step-down), leaving step-up idle while keeping the cluster-count floor enforced. The `75%` step-up (`5m`) and `55%` step-down-of-`T-1` (`25m` + `30m` cooldown) thresholds leave a deadband across tier sizes (`2Gi -> 4Gi`: step-up at `1.5Gi`, step-down from `medium` at `1.1Gi`).

## 3. Active-Standby Rollout for `credential-proxy`

### 3.1 Why Single Active Pod Remained Invariant

As documented in [`docs/designs/credential-proxy-single-pod.md`](credential-proxy-single-pod.md), multiple **simultaneously active** broker pods break stateful single-pod consumers:

- Google Chat relay holds `receipt -> ack_id` in process memory.
- Slack Socket Mode opens a per-process socket and holds `receipt -> event` in process memory.
- `scope_policy.MemberWindow` records prior probe results in process memory.
- `ProfileTaskWrites` (`credential_proxy.py`) records per-task branch claims and opened proposals in process memory so a profile permit writes only to work its own task created.

Therefore, `credential-proxy` preserves **`Replicas: 1` active** at all times. Default (`""`) and fixed profiles (`small`, `medium`, `fleet`) keep `Strategy: Recreate` without standby. Under `sizingProfile: auto` in-cluster (`OperatorNamespace` set to a valid DNS-1123 label), `Deployment.Spec.Strategy` switches to `RollingUpdate` (`MaxSurge: 1, MaxUnavailable: 0`) under operator-coordinated active-standby cutover (first performing one `Recreate` hop while any pre-handoff pod lacking `CREDENTIAL_PROXY_STANDBY` retires so the old `ReplicaSet` cannot recreate an active old pod; off-cluster `make run` with `POD_NAMESPACE` unset or invalid omits standby env vars, keeps `Recreate` with zero surge headroom, and skips handoff cutovers and `:8766` metrics scrapes).

### 3.2 Control Plane Protocol (Zero Hub API Token on `credential-proxy`)

Because `credential-proxy` sets `AutomountServiceAccountToken: false` and holds zero hub Kubernetes API permissions, the operator acts as the external coordinator:

1. **Deployment strategy & control credential (`auto` only):** `credential-proxy` uses `RollingUpdate` (`MaxSurge: 1, MaxUnavailable: 0`) under `sizingProfile: auto` and mounts a read-only operator-owned Secret `<agent>-credential-proxy-control` (`CREDENTIAL_PROXY_CONTROL_FILE`) with `CREDENTIAL_PROXY_STANDBY=1` and `CREDENTIAL_PROXY_PEER_HEALTH_URL` (all three reserved in CR env merges and stripped from exec-tier pods, alongside secret volume name isolation in `credential-proxy-control`; `buildCredentialProxyNetworkPolicy` also admits sibling broker pods on port `8765` under `auto` for peer health probing).
1. **Standby warm-up & self-recovery (`NewPod`):** When `CREDENTIAL_PROXY_STANDBY=1` and `role == broker` (`credential_proxy.py` / `BrokerLifecycle`), `NewPod` initializes Envoy, `CommandExecutor`, and `Policy` (`warm=true`), keeping Socket Mode intake and background proposal readings sweeps stopped until activated and refusing all non-`STANDBY_DEFERRED_ROUTES` calls (`/v1/*` included) with retryable `503`. `/healthz` returns `503 {"status": "standby"}` so Kubernetes keeps 100% of Service Endpoints traffic on the existing active pod. Exact `/healthz` on `:8765` routes through Envoy's `credential_health` cluster (matching `:8768`) so fleet watch saturation cannot starve peer probes. If an OOM, crash, or operator outage leaves the restarted pod with no active peer (`GET CREDENTIAL_PROXY_PEER_HEALTH_URL` returning clean non-`200` or `ConnectionRefusedError` from a resolved empty Service for `STANDBY_SELF_ACTIVATE_GRACE_SECONDS = 45.0`s across `STANDBY_PEER_PROBE_INTERVAL_SECONDS = 3.0`s polls, while failing closed on DNS/timeout/HTTP errors by returning `None` and resetting the grace timer, and refused during `SIGTERM` shutdown), `NewPod` self-activates safely without overlapping `30s+` predecessor drains or `3x10s` readiness blips; whenever a peer returns `200`, the timer resets so operator cutover owns the handoff.
1. **Failure safety before cutover:** If a surge pod stays `Pending` or fails before passing warm checks (`matchesProxyPodTemplate` matching `kubeagents.x-k8s.io/proxy-template-hash` and `kubectl.kubernetes.io/restartedAt`, immune to Pod-level `LimitRanger`/VPA resource mutations), the existing pod stays `Ready` and active; after `sizingSurgePendingTimeout` (`2m`), the operator rolls back to `activeTier` (`SizingCappedByQuota` / `SurgeUnschedulable`) without dropping the active pod. If a rollback or replacement failure leaves a non-terminating `DRAINED` pod with no runnable target candidate (`p.matches || !hasPendingOrWarming`), `reconcileCredentialProxyHandoff` deletes the drained pod to break the `1/1 Ready` deadlock.
1. **Operator Lease & graceful drain (`OldPod` -> `NewPod`):** Once `NewPod` responds `200 {"warm": true, "state": "standby"}` on `GET :8766/control/status` (using `operatorMetricsIngressRule` on port `8766`), `PlatformAgentReconciler.reconcileCredentialProxyHandoff` (excluding `draining`/`drained` and deleting pods from target candidates):
   - sends `POST :8766/control/drain` to any non-target active pod (`OldPod`), which refuses new exec/pull calls (`503 draining`, `Retry-After` `18`s while draining or `5`s once drained) while keeping `/healthz` returning `200 ok` across both `BROKER_STATE_DRAINING` and `BROKER_STATE_DRAINED` (until `SIGTERM` sets `shutting_down`) so Service Endpoints retain a live endpoint and never drop to zero before `NewPod` passes readiness probes (also keeping `DRAIN_OPEN_ROUTES` / `DRAIN_OPEN_REPLY_ROUTES` reachable), stops Slack Socket Mode intake, waits up to `settle_seconds` (`3s`) for unsettled Chat receipts and in-memory Slack/Teams events plus `HANDOFF_DRAIN_SECONDS` (`30.0s`, matching `SHUTDOWN_DRAIN_SECONDS`) for in-flight requests, and NACKs remaining Chat receipts to Pub/Sub upon reaching `BROKER_STATE_DRAINED`, exporting live confirmed `ProfileTaskWrites` entries (`task_writes`) in the drained snapshot (`/control/drain` and `/control/status`);
   - updates the operator-managed `coordination.k8s.io/v1` `Lease` (`<agent>-credential-proxy`, read/written via `APIReader`) as an observability/audit record naming `HolderIdentity = NewPod.Name` (the broker never reads the Lease);
   - sends `POST :8766/control/activate` (carrying any collected `task_writes` payload) to `NewPod`, which atomically imports live confirmed `ProfileTaskWrites` entries, opens Slack Socket Mode + proposal readings sweep, and flips `/healthz` to `200 {"status": "ok"}`.
1. **Cutover, legacy retirement & termination:** Retaining the `5s/10s/5s/3` readiness probe, kubelet marks `NewPod` `Ready`, `DeploymentController` satisfies `maxUnavailable: 0`, and `SIGTERM` reaches the already-drained `OldPod` (setting `shutting_down` so `/healthz` flips to `503` and releasing any late-pulled Chat receipts before exiting; once an `ACTIVE` replacement is `Ready`, the operator also explicitly deletes any non-terminating `DRAINED` pod to protect fast rollbacks). Because `OldPod` stays `200` on `/healthz` until `SIGTERM` after `NewPod` is `Ready`, Service Endpoints never goes empty; any request hitting `OldPod` during the overlap window receives `503 CREDENTIAL_PROXY_BUSY` (`bound="draining"`, `before_admission=true`), which CLI/VCS callers and `a2a/worker-adapter/mcprelay.go` retry onto `NewPod`. On upgrade from a pre-handoff broker pod lacking `CREDENTIAL_PROXY_STANDBY`, `reconcileCredentialProxy` keeps `Strategy: Recreate` until pre-standby pods exit so the old ReplicaSet scales to `0` instead of recreating a second active pod, then flips cleanly in-place to `RollingUpdate`.

### 3.3 Sibling Workloads (`agent-api-auth` & `shell`)

The `shell` workload (`StatefulSet <name>-shell`) keeps ordered single-pod replacement (`RollingUpdate` `StatefulSet`) with `RWO` PVC retention; only `fleet` transitions raise `shell` memory (`2Gi -> 4Gi`), so `medium` transitions do not restart `shell`. Meanwhile, the `agent-api-auth` sidecar (`2Gi`/`4Gi`/`8Gi` memory limits across `small`/`medium`/`fleet`) runs inside the single-replica `Recreate` `<name>-gateway` Deployment (`replicas: 1`), restarting `<name>-gateway` on every tier transition (clamped or unclamped) unless `agentAPIAuth.resources.limits.memory` is overridden.

## 4. Surge-Aware Quota, LimitRange & Capacity Gates

Before admitting any tier transition (promotion or step-down) `running -> candidate` under `auto`, `sizing_profile.go` checks both `LimitRange` bounds and `ResourceQuota` headroom, accounting for simultaneous `old + new` `credential-proxy` pods during active-standby surge (`maxSurge: 1`):

For `ResourceQuota`, unlike `Recreate` delta checks (`after - before`), `credential-proxy` requires `quotaFree >= after` (full replacement pod requests and limits plus `1` extra pod slot in `pods` and `count/pods`) when in-cluster active-standby surge applies, or container deltas with zero surge pods when the operator runs off-cluster without `POD_NAMESPACE`. Post-preflight `ReplicaFailure` quota refusals naming `pods`/`count/pods` or tier-step dimensions revert to `activeTier` when a running broker pod differs (`tier - 1` otherwise); settled same-tier rollouts where the active broker already matches `tier` omit the broker refusal check so image/resource updates never demote the settled tier, while still checking `<name>-gateway` quota refusals when `!useStatefulSet`. For unschedulable surges, if an in-cluster surge pod remains `Pending` past `sizingSurgePendingTimeout` (`2m`), `sizingSurgeStalled` (skipping same-tier rollouts when a running broker matches `tier`, matching pods via `CREDENTIAL_PROXY_MAX_CONCURRENT_COMMANDS` first and falling back to stripped tier resources with `sizingRunningLimitsClamped` plus post-transition `now.Truncate(time.Second)` creation time so a lingering higher-tier surge pod never triggers a second rollback) reverts to `activeTier` when a running broker pod differs (`tier - 1` otherwise) with `SizingCappedByQuota` (`SurgeUnschedulable`), starts `sizingStepBackHoldInterval` (`10m`), and leaves the active broker pod running. All checks preserve `sizingRunningLimitsClamped` so Autopilot keeps CPU/memory limits equal to requests (`medium` CPU stays `2`, memory moves `2Gi -> 4Gi`), and keep Standard node sizing warnings when `fleet` requests `4 vCPU`.

## 5. CRD Status & Observability Additions
