# Reads with no cluster from profile work

A proposal for decision. It says how profile work makes the reads that one task for each cluster
cannot make: the reads of a project that name no cluster. The security approver answers each row
of [Decisions](#decisions) with yes or no. Rows 1, 4, 6, 7, 8, 9, 17 and 18 each state a
choice, with the proposed one named.

The proposal is one new target shape, a project target, for the reads of one project. It adds
no route and no read to a credential that has no target, it gives no task a read on a folder or
an organization, and it gives no task a read that names no project. #5424 is the open issue that
asks for a project-only target and that waits for a decision on the grant scope; row 1 asks
whose design this is.

Related designs: [`spec-subagent-profiles.md`](spec-subagent-profiles.md) (the broker's
confinement of a profile task), [`spec-profiles-dispatch.md`](spec-profiles-dispatch.md) (the
task credential), [`scheduling-on-profiles.md`](scheduling-on-profiles.md) (the built-in table
and the source of the cluster list), [`multi-project-scope.md`](multi-project-scope.md) (the
declared scope). The broker-surface design for blocker 7 of the inventory owns each route and
verb of the profile role. The write-permit design for blocker 12 owns the write verbs of a
credential with no target; this design adds nothing to that credential. The fan-out of profile
tasks, with the parent's page of clusters, is #6789.

## Problem

A profile task's broker credential names one target (a project, a location and a cluster) or
none. Both verifiers hold that rule (`agents/platform/scripts/task_credential.py`,
`a2a/taskcred/taskcred.go`), and so do the gateway (`resolveProfile` in
`a2a/gateway/profiles.go`) and the dispatcher (`a2a/dispatch/admission.go`).

- With a target, the broker holds each `kubectl` and `gcloud` call of the task to that cluster
  and its project (`agents/platform/scripts/task_confinement.py`). It refuses the surfaces that
  name no project (`GCLOUD_PROJECTLESS_SURFACES`, among them `billing`, `storage`,
  `organizations` and `resource-manager`), `projects list` and `projects search`, the flags
  `--organization`, `--folder` and `--billing-account`, and `gcloud config` and `gcloud auth`.
- With no target, a task gets a broker credential only at the `unattended` tier with a trigger.
  That credential reaches the audit-report routes of `REPORT_CREDENTIAL_ROUTES` in
  `credential_proxy.py` and no other route. Each other task with no cluster gets no broker
  credential and runs local commands only.

The platform's fleet-wide work reads many projects in one run, and part of it reads no cluster
at all. This is blocker 4 of [`platform-as-profile-inventory.md`](platform-as-profile-inventory.md).

Which sweeps need a read of a project with no cluster:

- The GCE compute audit reads no cluster. It runs one time for each project in the scope, and
  such a project can have no cluster.
- The networking fabric audit and the fleet health sweep need no cluster target: each reads
  `container clusters list` and project reads for each project. Two checks of the networking
  audit (subnet usage, the firewall check) join the reads of all projects.
- `sa-role-watch` reads the IAM policy of each project in the scope. It also reads the
  PlatformAgent and one ServiceAccount of the management cluster with `kubectl`.
- The waste audit, the stockout audit, the patch-readiness audit, the upgrade retrospective and
  the upgrade report each make reads one time for each project (orphan disks and addresses,
  quotas, reservations, the release-channel baseline, operations). With one task for each
  cluster, a project with N clusters gets each such read N times, and a read that needs
  `--zone` or `--region` fails when that is not the target's location.
- The compliance, obtainability, AI security and consistency-drift audits need only cluster
  reads and a join of the results, after the cluster list exists.

No fleet sweep needs a read on a folder or an organization inside a task, and no fleet sweep
reads `gcloud storage`. On an install that declares a scope, no collector of a scheduled sweep
needs a read with no project: the two fallbacks run only when no scope is given to it. Only the
`gke-cost-analysis` skill uses the billing budgets read and `bq`.

## What must hold

1. One task has one target. A task reaches one cluster with its project, or one project, and
   nothing more. A parent causes a child to get no more than the parent's own grant holds
   (the attenuation rule of [`03-security-model.md`](../architecture/03-security-model.md)).
2. A credential with no target does not reach `/v1/exec` or the MCP relay. This is the decision
   that the approver recorded for row 9 of the write-permit design: that row was "accepted as
   scoped, meaning enumerated, gated by the permit and the broker table, with no `/v1/exec` or
   MCP". This design adds nothing to that credential.
3. A project task reads its project. It gets no write permit, no `kubectl` and no child. Its
   one write is the audit-report stream of a top task that a built-in schedule started, as for
   a cluster task (row 7).
4. A project is a target only if the install's declared scope admits it. An excluded project is
   never a target; the management project cannot be excluded.
5. An excluded cluster stays out of a profile task's reads, as the exclusion rules hold today
   (`cluster_metadata_scope.py`, `scope_exclude.py`).
6. No task lists the projects of the scope with a live read: `projects list` and
   `projects search` stay refused. The two member lookups of row 6 are the one live read that
   names other projects. The clusters of a member project come from the scope publisher's
   resolved set, as section 8 of `scheduling-on-profiles.md` decides. That section lists the
   management project and each explicit project live; for those, a project task's
   `clusters list` of its own project is the list.
7. Each `gcloud` call runs as the agent's one service account, as today. Terraform binds that
   account's read roles on each project of `spec.scope.projects`, also when an exclude entry
   names it, and on each project below a declared folder or organization; a member of a Shared
   VPC host or a Metrics Scope that an exclude entry names gets no binding. By IAM the account
   can read each bound project and get credentials for each of its clusters. So the hold on one
   project and the refusal of `kubectl` are the broker's check of the arguments alone. That
   check does not parse a project that a `--filter` or `--format` text names in a form other
   than a `projects/<id>` path.

### An excluded cluster in a moved audit or watch

The record for `spec.scope.exclude.clusters` names these reads of sweeps that still cover an
excluded cluster: the upgrade-readiness watch and the weekly review grade its versions, the
networking audit counts its subnet usage, and the GCE audit lists its node VMs. The platform
agent's shell keeps the full cluster list for that reason, and the profile role's list is
filtered. So each of them changes when its sweep moves to a profile task: the watch, the review
and the networking audit do not see the cluster in `clusters list`, and the GCE audit does not
list its VMs when the filter of row 8 covers the instance list. The move of each sweep changes
its line of the record. The record's last item, `list_clusters` of the `gke` MCP server, does
not change: a project task gets no `gke` tool (row 16).
