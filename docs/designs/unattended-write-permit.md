# Unattended write permit

A proposal for decision. It defines how a run that a built-in schedule starts can publish a
GitOps proposal with no person to confirm it, as an opt-in for that schedule. The security
approver answers each row of [Decisions](#decisions) with yes or no, and row 12 with "later" or
"in this design". Rows 4, 8, 16 and 19 each state a choice, with the proposed one named.

The child rule (#6790) does not relax in this design. For a schedule that opts in, only the
parent run gets the permit and publishes; its children stay at the read tier with no trigger
(row 11). A child that writes is an option for later (row 12).

Related designs: [`scheduling-on-profiles.md`](scheduling-on-profiles.md) (the built-in table,
canary rows, the schedule tool), [`spec-profiles-dispatch.md`](spec-profiles-dispatch.md) (the
task credential and the confirmed permit),
[`version-control-support.md`](version-control-support.md) (the broker's ownership bar and
per-task bar). The rows for each broker route and verb belong to the broker-surface design for
blocker 7 of the inventory, and the write rules of the report and findings routes to the
state-homes design for blocker 6.

## Problem

A profile worker reaches the broker's version-control write verbs (`publish`, `proposal-create`,
`proposal-update`) only when its task credential carries the permit `vcs:proposal-create`. The
dispatcher mints that permit when three things hold (`carriesPermit` in
`a2a/dispatch/admission.go`, the mint in `taskCredentials` in `a2a/dispatch/dispatcher.go`):

1. The submission says `changeRequested`. The gateway sets it for a structured confirm; a child
   and a wake copy their parent's value; the eval inject door sets it when it is armed.
2. The task names a cluster target.
3. The task runs on its own one-task Job, not on a pool pod.

A run that a schedule starts never has the first: the trigger ingress passes a fixed `false`
(`a2a/gateway/trigger_ingress.go`). A fleet audit also has no single cluster target. So a
scheduled audit cannot publish a fix proposal. This is the scheduled-audit part of blocker 12 of
[`platform-as-profile-inventory.md`](platform-as-profile-inventory.md).

No built-in schedule row ships today, so no unattended profile run reaches a forge write path
yet. The audits of today run through the agent's own role, which this design does not change.

## What must hold

1. A person's confirmed change keeps today's permit and today's rule.
2. A schedule publishes proposals only after an opt-in for that schedule. The default is off.
3. The permit goes only to a run that a built-in schedule started. The grant binds the schedule's
   trigger, and the capability verifier held the request's trigger equal to it.
4. A permitted write reaches only the write families that the schedule opted in to, and only
   branches of that schedule.
5. A canary row never gets the permit. Its `dry_run` parameter is behaviour. For version-control
   writes the missing permit is the enforcement, and it stays the enforcement; the report routes
   read no permit, and the write rule of the findings routes is a decision of the state-homes
   design.
6. Only a chain that a person started creates or changes a schedule (#5635). The permit gives no
   way to write a schedule or the opt-in.
7. Each mixed pair of versions in an upgrade refuses the write. None admits a write that the
   newer rule refuses.

### The repository in the permit (#4428)

#4428 asks that the confirmed permit names the repository that the person approved. The unattended
permit does not need that shape: its scope is the trigger (rows 2 and 7), and row 16 decides its
repositories. If #4428 changes `permits` to entries, the unattended permit becomes
an entry with a name only, in the same change. This design does not decide #4428.

### The older child issue (#5946)

#5946 describes a refusal of each delegation from an unattended task. On `main` delegation is
admitted, with the rule that row 11 states (#6790). Rows 11 and 12 are the decision that #5946
waits for.

## Version skew

Facts, from the code and the upgrade page:

- The dispatcher mints. Its image follows the operator's image; when the operator's reference
  has a digest and no tag, it falls through to the agent's image.
- The broker verifies with the Python verifier. Its image follows the agent's tag.
- The profile worker's image follows the agent's tag unless a profile pins it. Its client
  decides which requests carry the credential, and it verifies with the Go package for script
  runs only.
- The stated upgrade order is the operator first, then the harness. So the minter moves before
  the broker and the worker, and the time between the two runs has no limit.
- Each verifier refuses a permit that it does not know, and then the whole credential. Parity
  fixtures hold the two verifiers to that.
- The dispatcher and the stateful broker each run one replica with the `Recreate` strategy. The
  exec tier is off by default. With two or more replicas, old and new pods serve `/v1/exec` and
  the cloud relay together during a roll; it serves no version-control route.
- The auth callout verifies the bus credential, which never carries a permit.
- A credential is minted once for a task and lives until the task's deadline plus 30 seconds, at
  most 6 hours by default.

Three steps, in three releases:

1. The agent-tag side, whole. The two verifiers know the name; the broker holds rows 6 to 10,
   13 and 15 and reads the table; the worker's client has the list of row 9. Nothing mints the permit.
   The gate change of row 6 merges last, in the same pull request as, or after, rows 7 to 10,
   the label rule of row 13 and the table reader. Before that pull request the broker's gate does not accept the new permit
   for a write. A conformance row holds that a broker that accepts the permit refuses each
   broker case of the [Proof](#proof) list. A later change of the broker's rule is a new permit
   name or a new table version, not a change of this one.
2. The opt-in and the mint (rows 3 to 5), one release after step 1. The upgrade table gets one
   row: upgrade through the release that has step 1 first. The mint stays off while no schedule
   opts in, so this step changes no credential by itself.
3. The first row with a ceiling (row 18), and the proof.

| Operator and dispatcher | Broker          | Worker          | Result                                                                                                                                                                                      |
| ----------------------- | --------------- | --------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| before step 2           | any             | any             | No permit is minted. A write is refused as today.                                                                                                                                           |
| step 2 or later         | before step 1   | any             | For a schedule that opted in: the broker refuses the whole credential, so the run loses each broker route. No write is admitted.                                                            |
| step 2 or later         | step 1 or later | before step 1   | The worker's client sends no credential with no target on `/v1/vcs/`, so the broker refuses each version-control verb of the run. A script run on that worker refuses the whole credential. |
| step 2 or later         | step 1 or later | step 1 or later | The rule of this document.                                                                                                                                                                  |

Where the dispatcher follows the agent's image, read the first column as the dispatcher's
release; an operator of step 2 with an older dispatcher mints nothing.

The report credential used this order: the broker accepted it before the dispatcher minted it.

Other pairs, each of which refuses the write:

- CRDs older than the operator: the API server drops the `writes` key of the PlatformAgent's
  override, or refuses an entry that has only `writes`, so no schedule opts in.
- A broker of step 1 with a table of a newer version: it admits the credential and refuses the
  write (row 4).
- An operator that is rolled back to before step 2 while the table is still mounted: the older
  dispatcher mints no permit.

Option, if a direct upgrade across step 1 must also keep its runs: the operator renders the table
only while the broker's image is at the operator's own release. With an older broker, the run
gets today's report credential and no permit. Row 17 proposes the three steps without it.

## Proof

A run that the inject door starts cannot show this permit: its requester is not a trigger, so it
holds no trigger claim. The proof is a run that a built-in schedule starts.

- The row. No row ships today. The two rows that the schedule design names (the compliance-audit
  canary, #5620, and the run-now-only onboarding row, #5623) are not write rows, so the proof
  needs a row of its own: row 18.
- The lane. One CI lane sets `A2A_AGENT_SCHEDULES`; no lane sets the switch today. The lane opts
  in through the PlatformAgent override of its own install, with an entry that has only `writes`;
  no environment variable, chart default or build flag sets `writes`. The stack
  `bench/tf/prebuilt/builtin-schedule-run-now` sets the run-now annotation; no bench case uses
  it yet.
- Who can start a run. A principal that can update the AgentSchedule can set its run-now
  annotation. That starts the schedule's own fixed prompt, within the trigger's rate cap (12
  runs an hour by default). Where the chart rendered the built-in admission policy, it cannot
  change the prompt or the opt-in of a built-in (row 4).
- Evidence that the write was the schedule's: the task id in the AgentSchedule's status; the
  gateway's task record with the requester backend `trigger`; the broker's log line of row 15.
- Broker refusals, each as a conformance row with its mutation: a canary row; a schedule that did
  not opt in; a family that the schedule did not opt in to; a branch outside the schedule's
  prefix; the schedule's prefix with a confirmed permit; a credential with no trigger; `/v1/exec`
  with a credential that has no target; a proposal with an approving review or a reserved
  auto-merge label (row 8); the auto-merge label for a schedule's proposal, and a repository on a forge where text can set a label
  (row 13).
- Mint refusals, as Go tests: a pool pod; a child of an opted-in run.

## What stays out

- Event sources (the repository watcher, drift and triage). Their triggers name no schedule and
  no stream, so they get no permit in this design.
- The issue verbs for the audit ledger. They are rows of the broker-surface design; this
  document only reserves the `issue` family.
- User schedules. They do not run today, and the plan gives them no trigger. Row 2 refuses each
  origin but `builtin`.
- The confirmed permit, its Job rule, and #4428.
- Open proposals on the audits' old branch names (`platform-agent/fix-<audit-id>-`). A run with
  the new permit cannot update them; the move of each audit says what happens to them.
- Merge. The install merges nothing. Row 13 keeps the auto-merge label away from a schedule's
  proposal; each other merge rule is the repository's.

## Done when

For the group issue of this design:

1. Each row of [Decisions](#decisions) has the security approver's answer.
2. Step 1 of [Version skew](#version-skew) is released: the verifiers, the broker's whole rule

4. One built-in row has a ceiling, and a run that its schedule starts opens a proposal on a
   nightly lane in 3 consecutive nightly runs.

   in a conformance row or in a Go test.
6. The security page states the permit, the opt-in, the child rule (row 11) and the merge rule
   (row 13), and the upgrade table has the row of step 2.
