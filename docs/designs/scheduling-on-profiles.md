- **Author:** [@bnaylor]
- **Date:** 2026-11-03
- **Status:** decided (#4714); epic tracked in #4685 (part of #1721 background automation and #3654 profiles and dispatch).
- **Companions:** [`spec-profiles-dispatch.md`](spec-profiles-dispatch.md) - profile dispatch, Job mode, and the `Unattended` tier; [`spec-subagent-profiles.md`](spec-subagent-profiles.md) - the `AgentProfile` CRD and operator-rendered identities; [`spec-chatops-gateway.md`](spec-chatops-gateway.md) - gateway doors, capability minting, and `chat.notify`; [`gateway-replicas.md`](gateway-replicas.md) - active-standby gateway Lease election; [`cron-report-relay.md`](cron-report-relay.md) - daily report threads and incident context; [`fleet-audit-report-store.md`](fleet-audit-report-store.md) - structured audit envelopes and run-over-run baselines; [`oobe.md`](oobe.md) - first-boot audit chaining.

## Purpose

This spec moves kube-agents' recurring work out of the Hermes in-pod cron scheduler and onto `AgentProfile` dispatch (#3654). Today every recurring job ticks inside the single Hermes gateway pod (`deploy/docker/Dockerfile` cron patches and `agents/chat/scripts/profile_cron_tick.py`), sharing the gateway pod's ServiceAccount, memory ceiling, and `/opt/data` volume. A gateway rollout kills any in-flight fleet audit after a 30-second drain, and a pod outage silently drops missed runs.

Under this design, a schedule is a Kubernetes resource reconciled by the operator. When a run is due, the scheduler submits it through the A2A gateway. A built-in schedule's run is an `Unattended` task, which the profile dispatcher runs in an isolated Kubernetes `Job` pod with the target profile's `unattended` ServiceAccount and narrowed broker credentials. A user-created schedule's run is a task at its creator's own tier ([§6](#6-user-created-schedules)). Deterministic `no_agent` helper scripts that do not run a model become script-run `Unattended` tasks on one helpers profile (#5622), move to Kubernetes `CronJob`s or controller loops, or retire with kanban and the per-cluster Hermes profiles.

## 1. Where schedules live and who owns their state

### The `AgentSchedule` CRD (new)

Schedules live in a namespaced `AgentSchedule` custom resource (`kubeagents.x-k8s.io/v1alpha1`) in the `PlatformAgent`'s namespace (`kubeagents-system` by default), alongside `AgentProfile`. Keeping schedules in their own resource rather than embedding a list on `AgentProfile` separates schedule cadence and per-schedule run state from the profile definition: ten built-in fleet audits and any number of user-created schedules can target the same `platform` (or `fleet-audit`) profile without `helm upgrade` clobbering user schedules or sixty-second status writes contending on `AgentProfile`.

```yaml
apiVersion: kubeagents.x-k8s.io/v1alpha1
kind: AgentSchedule
metadata:
  name: compliance-audit
  namespace: kubeagents-system
  labels:
    kubeagents.x-k8s.io/agent: platform-agent
    kubeagents.x-k8s.io/origin: builtin # builtin | user
  annotations:
    # Set by the broker on origin: user schedules from the caller's attested AuthorityRequester:
    # kubeagents.x-k8s.io/created-by-principal: "<principal-hash>"
    # kubeagents.x-k8s.io/created-by-subject: "<verified-subject>"
spec:
  schedule: "20 6 * * *" # 5-field UTC cron expression
  suspend: false
  profileRef:
    name: platform
  prompt: |
    Run the daily GKE Fleet Compliance & RBAC Governance audit...
  parameters:
    stream: compliance-audit
  skills:
    - fleet-audit
    - gke-security-posture
  delivery:
    mode: chat # chat | local
    silentWhenClean: true
    jobKey: compliance-audit
  concurrencyPolicy: Forbid # sole supported value in v1alpha1
  startingDeadlineSeconds: 900
  activeDeadlineSeconds: 3600
  maxTurns: 250
status:
  observedGeneration: 1
  lastScheduleTime: "2026-11-03T06:20:00Z"
  nextScheduleTime: "2026-11-04T06:20:00Z"
  pendingSlot: null
  activeTaskID: ""
  activeTaskStartedAt: null
  lastTaskID: "task-01jc..."
  lastCompletionTime: "2026-11-03T06:41:12Z"
  lastOutcome: Succeeded # Succeeded | Failed | Cancelled | Lost | Skipped
  lastReason: "" # the terminal reason token, e.g. deadline-exceeded; empty when none
  lastHandledRunNow: ""
  skipCounts:
    alreadyRunning: 0
    missedWindow: 0
    suspended: 0
    gatewayUnavailable: 0
    rateLimited: 0
    creatorUnauthorized: 0
  conditions:
    - type: Accepted
      status: "True"
      reason: ScheduleValid
```

`concurrencyPolicy: Forbid` is the only concurrency policy in `v1alpha1`, defaulted and enforced by CRD schema validation. Every Hermes cron job today runs under a per-job lock, and keeping `Forbid` as the single policy lets `AgentScheduleStatus` track one in-flight run (`activeTaskID` and `activeTaskStartedAt`) without concurrent runs overwriting each other's status or misleading `oobe`'s completion watch ([§7](#7-run-it-now-for-an-operator-or-the-agent)).

The operator renders the shipped schedules (`origin: builtin`) from the `PlatformAgent` CR. The reconciler treats a schedule as `builtin` only when it carries the `origin: builtin` label and a controller reference to the install's `PlatformAgent`, and its name is one of the built-in schedules that `PlatformAgent` renders. A ValidatingAdmissionPolicy (`config/admission/agentschedule-builtin-policy.yaml`, #6038) refuses anyone but the operator's ServiceAccount who sets, changes or removes either the label or a controller reference, or changes a built-in schedule's spec (except `spec.suspend`). The name check covers a schedule written before the policy existed: nothing on it proves who wrote it, since its managed fields name a manager the client chooses. Such a schedule reads `Accepted=False` (`BuiltinNotFromOperator`). Today `charts/kube-agents/templates/profiles.yaml` renders only the `tse` and `cluster` `AgentProfile` resources (with `allowedTiers: [read]`); Track 2 adds the `platform` (or narrower `fleet-audit`) `AgentProfile` resource with `allowedTiers: [read, unattended]`, and Track 5 adds `unattended` to the `cluster` profile's `allowedTiers` (`[read, unattended]`) for `stall-watch`.

The operator renders the built-ins from one table in code (`builtinSchedules`, `platformagent_builtin_schedules.go`), and the schedule reconciler's built-in name set is that table's names, while `A2A_AGENT_SCHEDULES` is on. A built-in's name is reserved: exact, and the operator's alone. A schedule on a reserved name that the operator didn't render is deleted, with an Event and a `BuiltinSchedules` condition, and created again as the built-in, never adopted with its content kept. A schedule on any other name is never touched. A built-in whose row leaves the table is deleted. A shadow run of a built-in, which runs beside the job it will replace until a comparison shows parity, is its own row named `<name>-canary`: its own report stream, local delivery, and the task parameter `dry_run=true`, which the profile's scripts read to skip every write but that stream. The parameter is behaviour, not enforcement: what stops a shadow run writing is that its unattended grant holds no write permit. Going live removes the canary row and adds the real one, and the canary's report stream stays readable. No row ships yet. Onboarding (#5623) and the compliance-audit canary (#5620) add theirs, and each name is listed here when it does.

Operators pause a built-in schedule through `PlatformAgent.spec.schedules.overrides`, a list of `{name, suspend}` keyed on the rendered name, so a canary and its live row are separate entries. With no override, the schedule follows its row's default, so removing an override resumes it. A `spec.suspend` someone set on the schedule directly stands until an override names it: the operator records the value it last applied (the `kubeagents.x-k8s.io/builtin-applied-suspend` annotation) to tell the two apart. The renderer does nothing while the AgentSchedule CRD is missing or the operator's role can't read schedules, and a write refused with a 403 is reported on the `BuiltinSchedules` condition, naming the verb, without failing the PlatformAgent's reconcile. A run-now-only built-in (onboarding) takes only `suspend: true`, which stops the operator from setting its run-now. `suspend: false` there is refused and reported, since it would put the schedule on its nominal cron. Re-timing a built-in isn't supported. A user schedule is edited directly as an `origin: user` `AgentSchedule`. Because a CEL `ValidatingAdmissionPolicy` cannot dynamically fetch the `AgentProfile` named by `spec.profileRef.name` or run a full cron parser, validation splits across three layers:

1. **CRD / CEL admission:** Enforces structural invariants (5-field whitespace-separated cron token shape, `concurrencyPolicy == "Forbid"`, exactly one of `prompt` and `script` with `script` a DNS-1123 label, and a `script` schedule sets neither `skills` nor `maxTurns`, and the broker ServiceAccount's `origin: user` restriction in [§6](#6-user-created-schedules)).
2. **Reconciler validation (`Accepted` condition):** `AgentScheduleReconciler` parses `spec.schedule` with the Go cron parser on every reconcile. It also holds the schedule's name to a dot-free DNS-1123 label, since a run's trigger is `schedule/<name>` (`InvalidName` otherwise). A schedule naming `spec.script` that isn't built-in reads `InvalidSchedule`: only a built-in schedule's run may execute a helper script (#5622). So does a script schedule that sets `skills` or `maxTurns`, for an object stored without the CEL rule. For a built-in schedule it checks that the referenced `AgentProfile`'s `spec.allowedTiers` lists `unattended`, and that its `spec.scripts` lists the schedule's `script` if it names one (`ProfileScriptUnknown` otherwise; the profile watch re-queues the schedule when the profile changes). For a user schedule it checks that the profile exists, but not its tiers, since the run's tier is its creator's, which only the gateway can resolve, at fire time. A user schedule also reads `Accepted=False` when it has no creator annotations (`NeedsAdoption`), is beyond the install's 32 oldest user schedules, or fires more often than every 5 minutes (§6's limits, for which the reconciler is the backstop). The reasons are `InvalidSchedule`, `ProfileTierDisallowed`, `ProfileScriptUnknown`, `NeedsAdoption` and `UserLimitExceeded`. Until Track 7 (#5624) settles the creator identity, none of that runs: a schedule the PlatformAgent doesn't control reads `Accepted=False` (`UserSchedulesDeferred`) and never fires.
3. **Gateway submission gate (authoritative):** Because an `AgentProfile`'s `spec.allowedTiers` can change after an `AgentSchedule` is created, the gateway re-verifies that the target profile exists and lists the run's tier in `spec.allowedTiers` (`unattended` for a built-in schedule, the creator's tier for a user one; see [§6](#6-user-created-schedules)) whenever it mints a task grant ([§3](#3-how-the-gateway-authenticates-a-scheduler-and-other-triggers)).

### State ownership across ephemeral Job pods

Today `/opt/data` holds four kinds of cron state. Each moves to a home that does not depend on a shared ReadWriteOnce pod volume:

1. **Schedule definitions (`cron/jobs.json`):** Owned by `AgentSchedule` resources in the Kubernetes API.
2. **Run ledger and skip ledger (`cron/executions.db`, `cron_skip_ledger.py`):** Owned by `AgentScheduleStatus` (`lastScheduleTime`, `nextScheduleTime`, `activeTaskID`, `activeTaskStartedAt`, `lastTaskID`, `lastOutcome`, `lastReason`, `skipCounts`, and a bounded 10-entry `recentRuns` ring, each run with its `reason`) plus Prometheus counters (`kubeagents_schedule_runs_total{schedule,outcome}` and `kubeagents_schedule_skips_total{schedule,reason}`). This carries forward `already_running` and `missed_window` from `cron_skip_ledger.py` (while retiring the SQLite/flock-specific codes `already_running_elsewhere`, `interpreter_shutdown`, `dispatch_claim_rejected`, `create_execution_failed`, and `fire_claim_lost`), and adds `suspended`, `gateway_unavailable`, `rate_limited` for the per-trigger cap, and `creator_unauthorized` for a user schedule whose creator no longer has a tier ([§6](#6-user-created-schedules)) in [`spec-profiles-dispatch.md`](spec-profiles-dispatch.md#scale-rules).
3. **Incident context for threaded replies (`incidents` table in Session KV):** Owned by the gateway's durable incident store in JetStream KV (see [§4](#4-where-an-unattended-result-goes)).
4. **Fleet-audit report store (`latest.json` and `runs/<timestamp>.json` in [`fleet-audit-report-store.md`](fleet-audit-report-store.md)):** `TierUnattended` tasks run in ephemeral one-shot `Job` pods ([`spec-profiles-dispatch.md`](spec-profiles-dispatch.md#execution)) that do not mount `/opt/data`. While forge-connected runs can seed a missing store once from the open GitHub ledger issue's `<!-- audit-findings: … -->` block, `no_forge/local` and `STORE_LEDGER` installs have no GitHub issue, and `report_status.py` / `fleet-audit-reports` need the 14-run ring across runs. The credential broker serves seven routes under `/v1/audit-reports` (#5619): `GET /v1/audit-reports` (the streams), and for one stream `/v1/audit-reports/{audit_id}/{key}`, `GET`, `PUT` and `DELETE` on `/latest`, `GET /runs`, and `GET` and `PUT` on `/runs/{ts}`. `{key}` is the file store's repository directory as one URL segment: lower-cased, GitHub's host left off, and the `/` escaped as `%2F` (`acme%2Fgitops`; another forge's `host/a/b` is `host%2Fa%252Fb`). The broker relays each request to the install's durable store, the gateway's data volume, served to the broker alone by `audit_report_store.py` on port 8700 in the gateway pod's `agent-api-auth` container ([`fleet-audit-report-store.md`](fleet-audit-report-store.md#3-where-it-lives) §3), and passes its answer back; a body over 1 MiB is refused, and with no store configured every route answers 503. Because the run-over-run baseline determines which findings count as new, built-in audit stream IDs are reserved for `origin: builtin` schedules, and the broker decides every write (`PUT` a run, `PUT` latest, `DELETE` latest) itself. A profile worker may write only when all of these hold: its task credential's profile is in the reports allowlist (`CREDENTIAL_PROXY_REPORT_PROFILES`, which the operator renders on every install as `fleet-audit,platform`), the credential carries a trigger with `origin: "builtin"` named `schedule/{audit_id}` whose `stream` is `{audit_id}` (the dispatcher copies the trigger into the credential only after `profile.run` has checked it against the task's capability grant, #5642), and `{key}` is the repository `finish` publishes to, read per request from the gitops-state ConfigMap: with several managed repositories, the `gitops_repo` key's repository when it is set and registered; with exactly one, that repository; otherwise `no_forge%2Flocal`, which is writable only then. There is no `--repo` target and no `user/` stream: #5624 leaves user schedules out. A profile worker reads any stream when its credential's profile is in the same allowlist, trigger or not; one with no task credential is refused, read or write. The platform agent's own shell (the broker's `shell` role, the sandbox's audience) reads every stream and writes any audit, to that publish key or to the key of any repository in `managed_repos` as the broker reads it, never as the request names it, and never an unregistered repository's. That is what `finish`, with or without `--repo`, writes to today's file store directly, so it grants nothing new. A key is compared in its canonical spelling alone. The A2A gateway's relay reads finished reports through the broker too (#5618). It holds the `a2a-reports` role, which only its own `kubeagents-credential-proxy-a2a-reports` audience confers, and only to the A2A gateway's ServiceAccount (the operator projects that token into the gateway pod on every install, Google Chat on or off). The role reaches no other broker route, and it may read `GET /v1/audit-reports/{audit_id}/publish/latest` and `GET /v1/audit-reports/{audit_id}/publish/runs/{ts}` of any audit. The gateway can't compute the publish key, so it sends the reserved word `publish` as `{key}`, and the broker relays the request with the publish key above in its place (`no_forge%2Flocal` when that rule yields none), or answers 503 when it can't read the install's repositories. `publish` can't name a real stream, since every store key holds a `%2F`, and the broker resolves it for this role alone: the shell's or a profile worker's `publish` is relayed as sent, where it names no stream. The role never lists the streams, reads `GET /runs`, or sends a `PUT` or `DELETE`; each of those, and any other key, the publish key spelled out included, is a 403 naming its own rule (`report_a2a_reports_read_permitted` in `credential_proxy.py`). The gateway's `a2a-chat` role reaches none of these routes. Every other role is refused, so no user schedule or worker can overwrite a built-in audit's baseline. The broker also records who wrote each run. On a run `PUT` it sets `X-Report-Writer` to `shell` or `builtin-schedule:{audit_id}:{task_id}` from the verified caller and drops any value a caller sent. The listener keeps that beside the envelope and answers it on `GET latest` and `GET /runs/{ts}`, so the A2A gateway's relay can trust a report only when its own task wrote it ([`fleet-audit-report-store.md`](fleet-audit-report-store.md#3-where-it-lives) §3).

## 2. The scheduler component

The scheduler runs as `AgentScheduleReconciler` (new) inside `k8s-operator`, gated by the operator's existing Lease leader election (`main.go`). Running the reconciler inside `k8s-operator` avoids a separate Deployment and pod budget on Autopilot, reuses the operator's controller-runtime informer cache and per-agent TLS NATS connection (`natsCardPublisher` in `k8s-operator/internal/controller/agentprofile_card.go`), and ensures only the elected leader fires schedules. Today the operator's `authcallout` identity (`operator-controller`) is narrowed to publishing agent cards on `a2a.agents.*`; Track 2 extends that grant in `a2a/authcallout` so `operator-controller` may also publish to `a2a.trigger.schedule.submit` (new) and subscribe to its reply namespace `a2a.trigger.reply.schedule.>` (§3).

### Two-phase slot claim and restart safety

For each `AgentSchedule`, `Reconcile` computes `nextScheduleTime` in UTC from `max(status.lastScheduleTime, metadata.creationTimestamp)` and returns `ctrl.Result{RequeueAfter: nextScheduleTime.Sub(now)}`. While `spec.suspend` is `true`, whenever `now >= status.nextScheduleTime` the reconciler increments `status.skipCounts.suspended`, advances `status.nextScheduleTime` to the next cron boundary after `now`, and requeues without submitting a task, so unsuspending a schedule later waits for the next future slot rather than firing a stale one or miscounting the pause as `missedWindow`. When `spec.suspend` is `false` and `now >= status.nextScheduleTime`, the reconciler executes a two-phase hand-off so neither an operator restart nor a gateway failover ([`gateway-replicas.md`](gateway-replicas.md)) can double-fire or silently drop a due run:

1. **Check in-flight run and liveness ceiling (`concurrencyPolicy: Forbid`):** If `status.activeTaskID` is non-empty, the reconciler queries the dispatcher/bus for the task's state. While the task holds a live lease on the dispatcher and `now.Sub(status.activeTaskStartedAt)` is within `spec.activeDeadlineSeconds` (defaulting to the target `AgentProfile.spec.lifecycle.activeDeadlineSeconds`) plus a 5-minute grace buffer, the reconciler increments `status.skipCounts.alreadyRunning`, advances `status.nextScheduleTime` to the next cron boundary after `now`, and requeues. If the task record has disappeared (for example across a gateway restart before Lease HA lands, KV expiry, or a missed terminal event) or `now.Sub(status.activeTaskStartedAt)` exceeds the deadline plus grace buffer, the reconciler records `status.lastOutcome = Lost`, increments `kubeagents_schedule_runs_total{outcome="lost"}`, clears `status.activeTaskID` and `status.activeTaskStartedAt`, and proceeds with the due slot so a vanished task never wedges the schedule in `alreadyRunning`.
2. **Collapse stale windows after an outage:** If `now.Sub(status.nextScheduleTime) > spec.startingDeadlineSeconds` (default 900 seconds), the reconciler increments `status.skipCounts.missedWindow`, advances `status.nextScheduleTime` to the most recent slot within the deadline (or the next future slot if none falls within the deadline), and persists status before proceeding.
3. **Phase 1 — Persist `pendingSlot`:** Before publishing to the gateway, the reconciler writes `status.pendingSlot = &PendingSlot{SlotTime: slot, IdempotencyKey: "schedule/<namespace>/<name>/<slot-unix>"}` to the Kubernetes API.
4. **Phase 2 — Submit over NATS with idempotency key:** The reconciler publishes the unattended submission request on NATS (see [§3](#3-how-the-gateway-authenticates-a-scheduler-and-other-triggers)) carrying `IdempotencyKey`. Publishing over NATS reaches the single gateway pod today and, once active-standby gateway Lease election ([`gateway-replicas.md`](gateway-replicas.md#what-only-the-active-replica-runs), #4206) lands, automatically reaches whichever gateway replica holds the Lease without `kubectl port-forward` or pod IP discovery. The gateway records `IdempotencyKey -> taskID` in JetStream KV (with a 24-hour TTL) when it mints the task's capability grant. If the operator crashes after the gateway mints the task but before the status update in step 5 completes, the new operator leader sees `status.pendingSlot` on startup, re-sends the same `IdempotencyKey`, and receives the existing `taskID` back rather than starting a second run.
5. **Phase 3 — Advance schedule:** On receiving `taskID` from the gateway, the reconciler sets `status.activeTaskID = taskID`, `status.activeTaskStartedAt = now`, `status.lastTaskID = taskID`, `status.lastScheduleTime = slot`, advances `status.nextScheduleTime` to the next slot after `now`, clears `status.pendingSlot`, and requeues. If the gateway is unreachable or in the middle of a rollout or Lease handover, the reconciler leaves `status.pendingSlot` set and retries with backoff until `startingDeadlineSeconds` expires; when `startingDeadlineSeconds` expires, it clears `status.pendingSlot`, increments `status.skipCounts.gatewayUnavailable`, and advances `status.nextScheduleTime` to the next cron boundary after `now` so the lost slot is counted once under `gatewayUnavailable` rather than counted a second time under `missedWindow` on the next reconcile.

When the dispatcher publishes the task's terminal event on `a2a.tasks.<profile>.<task>.events`, `AgentScheduleReconciler` records `status.lastCompletionTime`, sets `status.lastOutcome` and `status.lastReason`, and clears `status.activeTaskID` and `status.activeTaskStartedAt`. The reason is the bare token of the task's terminal reason (`reason: <token>[ - detail]`), for example `deadline-exceeded`, `script-timeout` or `canceled-by-request`; a completed run records none. It reaches the reconciler in the gateway's trigger status reply (`lib.TriggerStatusReply.Reason`) only when it is a token the gateway knows (its reason tables in `a2a/gateway/relay.go`, the one vocabulary), never with its detail, and the reconciler keeps it only when it has the CRD's shape. A Lost run, and a task that gave no known reason, records none. A run's `reason` is also stored on its `recentRuns` entry, and the `Reason` print column shows the last one.

## 3. How the gateway authenticates a scheduler and other triggers

[`spec-chatops-gateway.md`](spec-chatops-gateway.md) §"The A2A door" noted that the verifier's `unattended` class was still to come. Three in-cluster system components submit unattended work with no human in the loop: `AgentScheduleReconciler` in `k8s-operator`, `k8s-event-watcher`, and `drift-detector` (plus the `stall-watch` and `github-repo-watcher` collectors in [`scheduling-on-profiles-inventory.md`](scheduling-on-profiles-inventory.md)). Today `k8s-event-watcher` (`k8s-operator/cmd/k8s-event-watcher/injector.go`) and `drift-detector` (`k8s-operator/cmd/drift-detector/inject.go`) do not call the A2A gateway at all: both `POST` to the Session KV daemon (`session_kv_server.py`, `/sessions` and `/sessions/{id}/inject`) using a shared bearer token (`SESSION_KV_BEARER_TOKEN`), which gives them no per-caller identity and bypasses the gateway's tier and capability-grant model (while the gateway's own `/inject` handler in `a2a/gateway/inject.go` is a bearer-authenticated `DEV AND EVAL ONLY` door rendered only when `A2A_INJECT_BACKEND=true`).

### Attested NATS trigger ingress (`a2a.trigger.<source>.submit`, new)

Every unattended trigger runs in the cluster under an operator-rendered Kubernetes ServiceAccount and connects to NATS through `a2a/authcallout`. We authenticate triggers on the bus using the same KSA `TokenReview` path (`a2a/authcallout/tokenreview.go`) that authenticates profile workers and the dispatcher:

1. **Callout identity and reply namespace:** The operator registers each trigger's ServiceAccount in the `authcallout` identity map (`agentprofile_identities.go`) with a fixed trigger source slug (`schedule` on the operator, later `event-watcher`, `drift-detector`, `stall-watch`, and `repo-watcher`). `a2a/authcallout` narrows each trigger identity to publish only to `a2a.trigger.<source>.submit`, `a2a.trigger.<source>.status` (a status query for its own runs) and `a2a.trigger.<source>.stop` (a stop for one of them) and subscribe only to its own reply namespace `a2a.trigger.reply.<source>.>`. The gateway answers there and nowhere else (`lib.TriggerReplySubject`), never into a caller's `_INBOX`, for the reason the verifier answers on `a2a.cap.reply.>`: a grant to publish into callers' inboxes would reach where they read their JetStream replies. A submission naming any other reply subject is dropped, unanswered, before anything is started. No profile worker, chat bridge, or console client can publish to `a2a.trigger.>`. The operator holds the schedule source's grants only while `A2A_AGENT_SCHEDULES` is on.
2. **Request and reply** (`lib.TriggerSubmit`, `lib.TriggerSubmitReply` in `a2a/lib/trigger_submit.go`):
   ```json
   {
     "trigger": {
       "name": "schedule/compliance-audit",
       "origin": "builtin",
       "stream": "compliance-audit"
     },
     "idempotencyKey": "schedule/kubeagents-system/compliance-audit/1793686800",
     "schedule": {
       "namespace": "kubeagents-system",
       "name": "compliance-audit"
     },
     "profile": "fleet-audit",
     "prompt": "Run the daily GKE Fleet Compliance & RBAC Governance audit...",
     "parameters": { "schedule_mode": "scheduled" },
     "skills": ["fleet-audit", "gke-security-posture"],
     "maxTurns": 250,
     "delivery": {
       "mode": "chat",
       "silentWhenClean": true,
       "jobKey": "compliance-audit"
     }
   }
   ```
   The idempotency key is `schedule/<ns>/<name>/<slot-unix>` or `run-now/<ns>/<name>/<token>`. The reply is `{"taskId": "..."}` or `{"refused": {"reason": "...", "detail": "..."}}`, the reason one of `rate_limited`, `unavailable` (both worth a later slot), `invalid`, `profile_unknown`, `tier_not_allowed`. `delivery.mode` is exactly `chat` or `local`, and `delivery.jobKey` is a DNS-1123 label (`lib.ValidateScheduleDelivery`), since it keys Track 3's stores. `activeDeadlineSeconds` and `maxTurns` are validated but not yet carried to the run, so the profile's lifecycle applies. `trigger.script`, optional, names a profile script a built-in schedule's run executes in place of a model turn (#5622). It is a DNS-1123 label, never a path, and only on a `schedule/<name>` trigger (`lib.ValidateTrigger`). An older gateway's strict decode refuses a submission that carries it `invalid`, so that gateway never runs it as a prompt run. A gateway with the field and no dispatcher allowlist (#5953) or worker script mode (#5954) would admit a scripted task as a prompt task, so the writer, the AgentSchedule's `spec.script`, came after both. The reconciler sets `trigger.script` from a built-in schedule's `spec.script`, with the task text `Scheduled script run: <name> (no model turn).` in `prompt`, which the gateway requires and no model reads. A script run's submission carries no `skills` or `maxTurns`. A run recorded but not yet published is published again with the trigger its grant was minted with (`TriggerRun.Trigger`), so a retry naming another script can't make the authority disagree with the grant.
3. **Gateway verification and grant minting** (`a2a/gateway/trigger_ingress.go`): The elected gateway subscribes to `a2a.trigger.*.submit` for its term. On a submission:
   - It drops one whose reply subject isn't in its source's reply namespace, then decodes strictly (no unknown fields, nothing after the object) and validates: source `schedule`, or an event trigger the install admits (`A2A_TRIGGER_EVENT_KINDS`, `<source>/<kind>` entries, empty by default, #6572); origin is `builtin` (a user's schedule runs at its creator's tier with no trigger, #5635); the trigger name is `schedule/<stream>` with `stream` the schedule's own name, and it names the schedule and the key. An event source's trigger is `<source>/<kind>`, with no schedule, stream or script, and its key is `<source>/<kind>/<token>`, the token one segment the source's own dedupe names the event by.
   - It refuses a schedule outside the install's own namespace (an event source names none): a trigger's identity carries no namespace, and built-in schedules live with the one PlatformAgent.
   - Under the trigger's session lock, a recent run's key is that run: one already published is answered with its task before any directory check, and one recorded but not yet published is published again after the route checks below. Neither mints or spends the rate budget. A key published within the last 24 hours whose run has since left the kept runs is answered from `SessionRecord.TriggerKeys` with its task, so a late repeat never starts a second one.
   - It checks the profile's card lists `unattended`, and takes the route every profile task takes (`profileRouteFor`): the install's namespace scope, or a target the scope file admits; the persona's declared parameters; a pin's tiers. A target that routes the task to another profile is refused.
   - It checks the per-trigger rate cap ([`spec-profiles-dispatch.md`](spec-profiles-dispatch.md#scale-rules)): a token bucket per trigger conversation, 12 an hour by default (#5635, so a schedule every five minutes runs every time; the gateway's `TriggerRatePerHour`), and refuses `rate_limited` past it. The bucket lives in the elected gateway's memory, so a failover refills it; the reconciler's one-run-per-slot rule is the steady bound. Each admitted event kind has its own bucket, `<source>/<kind>`, at 30 an hour by default (`TriggerEventRatePerHour`): above the largest daily alert quota the session store applies to one kind, so a day's alerts in one burst still pass. Only listed kinds are admitted, so a source can't open more buckets than the install names. An event source has no reconciler behind it, so after a failover the refilled bucket is its only bound.
   - It stamps `AuthorityRequester{Principal: ps.Hash("trigger:" + name), Backend: "trigger", Subject: name, VerifiedBy: "unattended-ksa"}`.
   - It mints the root grant at a task ID derived from the idempotency key: `Tier: unattended`, the route's profile and scope, `Delegate: dispatcher`, and `Trigger` (name, origin, stream, and the script when there is one), and writes the same trigger into the envelope's `authority.trigger`, which the dispatcher reads back and the verifier holds equal to the grant's.
   - It records the run on the trigger's own conversation, `trigger:schedule/<ns>/<name>`, or `trigger:<source>/<kind>/<token>` for an event run, one record per run: the task, its delivery (`SessionRecord.Delivery`, for Track 3), and the keys of as many recent runs as the conversation's task history keeps (`triggerRunsKept`, 50). Before each mint it records the attempt in `SessionRecord.TriggerPending`, so a retry after a failed record write, or after a restart, resumes at that attempt instead of deriving task IDs from the first again. An attempt is used up once its grant is minted: a mint that failed, or a record write before it, leaves the attempt to retry, while a grant minted but never recorded as a run moves the next try on to the next attempt. Attempts are capped at 16 (`triggerMintAttempts`), counting every one, and a submission that fails before its run is recorded hands its rate token back (#5923). Pending attempts a reconciler gave up on are dropped after a day. The key record is written with the run, and keeps a day of runs at the trigger's rate cap. It publishes the submission to `a2a.submit.<profile>.unattended.top.<task>` on `PROFILE_SUBMITS`, with an envelope ID derived from the key so a repeated publish is the stream's duplicate. Nothing is posted to chat for that conversation; where the result goes is Track 3's.
   - **Open, deferred to Track 7 (#5624, decided on #5635):** which identity the gateway resolves a user schedule's creator from. The creator annotations ([§6](#6-user-created-schedules)) carry the `AuthorityRequester`'s principal and subject, which `BuildAuthority` (`a2a/gateway/authority.go`) hashes into pseudonyms under the install salt. The membership mapping is keyed on raw IDs and groups, so the gateway can't look up a tier from them, and it must not fall back to a wider one. Until Track 7 settles the identity, the gateway refuses every `origin: user` submission and accepts only `origin: builtin`. The rest of this bullet is the intended behaviour once it does.
   - For an `origin: user` schedule, it never mints `TierUnattended` (decided on #5624). It resolves the creator's tier at that moment by the same membership lookup the gateway runs for that person's interactive turns (the PlatformAgent's mapping, groups included). The default-Read rule applies only while the creator still has an identity the install accepts, an account on a door that is still enabled. It checks that the target profile allows that tier, and mints the root grant at that tier with no trigger. The requester is the creator: `AuthorityRequester{Principal: createdByPrincipal, Backend: "schedule", Subject: triggerName, VerifiedBy: "schedule-creator"}`. The grant's scope is the creator's own, as at an interactive turn, not the install's. Per-person caps and the multi-author minimum key on the creator. So the run carries exactly the authority its creator would have interactively. If no tier resolves (the account is gone, the door is disabled, or the mapping excludes them), it refuses the submission as `creator_unauthorized`. The reconciler counts that in `status.skipCounts.creatorUnauthorized` and does not retry the slot, and nothing falls back to a wider tier. It publishes to `a2a.submit.<profile>.<tier>.top.<task>`.
4. **Migrating `k8s-event-watcher` and `drift-detector` (#6572):** Both run today in the A2A gateway pod's `agent-api-auth` sidecar and post to the Session KV daemon (`POST /sessions` and `/sessions/{id}/inject`, with the shared `SESSION_KV_API_KEY`). The daemon holds the triage gating: severity, the Info gate, the workload fold, the open-fix-PR hold, daily quotas, the ledger the daily recap reads, the alert post, and quiet follow-ups. The move has two phases.
   - **Phase 1:** the daemon keeps every gate, and under the session default route only the triage start changes: a `cluster` profile task submitted on the ingress from one event source replaces the turn that files a card today, and the result goes into the alert's thread. The watchers don't change.
   - **Phase 2:** each watcher runs under its own ServiceAccount and submits on `a2a.trigger.event-watcher.submit` and `a2a.trigger.drift-detector.submit`, and the gating moves with it.

## 4. Where an Unattended result goes

A scheduled top-level task, an `Unattended` built-in run or a user schedule's run at its creator's tier, has no asking chat conversation. When its worker publishes a terminal event on `a2a.tasks.<profile>.<task>.events`, the gateway's relay (`a2a/gateway/relay.go` and `notify.go`) routes the output according to the task's `delivery` spec:

1. **Silent-when-clean suppression:** When `delivery.mode` is `local`, or `delivery.silentWhenClean` is `true` and the terminal report is `[SILENT]` (or the structured `audit_report.py finish` artifact carries `silent: true`), the gateway records the completed run in the scheduled-reports store and posts nothing to chat.
2. **Structured fleet-audit report artifact (`kube-agents.report/v1`, new):** Under Hermes cron, a model finishing an audit turn after running `audit_report.py finish` returned its own conversational wrap-up as the job output unless the prompt repeated `finish`'s line (#3217). On profile workers, `audit_report.py finish` emits a `kube-agents.report/v1` task artifact containing both the `kube-agents.chat/v1` card payload and the plain-text fallback. When a task carries a `kube-agents.report/v1` artifact, the gateway delivers that artifact verbatim to chat rather than the model's trailing assistant message.
3. **One thread per schedule per UTC day and reply linkage (#4059):** For `delivery.mode: chat`, the gateway groups posts by `(delivery.jobKey, UTCDate)` using a JetStream KV bucket (`SCHEDULE_THREADS`, new, 48-hour TTL) so the thread key survives gateway Lease failovers ([`gateway-replicas.md`](gateway-replicas.md)). The first non-silent run of `jobKey` on a UTC day starts a new message in the configured home channel and stores the platform's returned `threadID`; later runs of the same `jobKey` on that UTC day post into `threadID`. On every post, the gateway writes `(platform, chatID, threadID) -> reportText` into the incident store so a user reply in that thread has `<untrusted_report>` prepended by the gateway/bridge (shipped in `a2a/hermes-bridge/incident.go`, #4059).
4. **Installs with no home channel (#4053, #3928):** Today `a2a/gateway/notify.go` rejects a home-channel post with `notifyNoHome` when no chat platform has a home channel configured. Under this design, the gateway writes every non-silent unattended report into the durable `SCHEDULED_REPORTS` (new) JetStream stream/KV store before attempting chat delivery. The web console's `#scheduled` channel (#3928) and the on-demand report retrieval tool read directly from `SCHEDULED_REPORTS`. If no chat home channel is configured, the gateway marks the report `stored_no_home` instead of failing the task, and `oobe` / onboarding can still enumerate unposted reports when a home channel is later set.

## 5. What happens to the `no_agent` scripts

Thirty entries ship across the two Hermes rosters on `main`: five in `agents/chat/defaults/cron/jobs.json` and twenty-five in `agents/platform/cron/jobs.json` (Cluster Agents have no `cron/jobs.json`). Eleven are model runs and nineteen are deterministic `no_agent` scripts.

The deterministic helpers that run `kubectl`, `gcloud` or `leeway` (`stall-watch`, both upgrade-readiness scripts, `sa-role-watch` and `leeway-watch`) become `AgentSchedule`s too, run as script-run `Unattended` tasks in Job mode on one helpers profile (decided 2026-11-11 on #5622). The schedule names a script from the profile's `spec.scripts` allowlist, whose paths lie under `/opt/kube-agents/scripts/` in the worker image, and no model runs. Other deterministic scripts that still have work to do become operator-rendered Kubernetes `CronJob`s (or controller loops) running under a narrow ServiceAccount with a broker token scoped to the single capability they need (`chat.notify`, `forge`, or `fleet-read`) and mounting the `<agent>-resolved-scope` ConfigMap ([§8](#8-cluster-lists)). ## 6. User-created schedules

Today the Platform Agent can call Hermes' built-in `cronjob` tool (`create`, `list`, `resnap`, `remove`, `update`, `run`/`run_now`/`trigger`, `pause`, `resume`) to create schedules in `/opt/data/profiles/platform/cron/jobs.json`, while the Chat Agent denies the tool (`agents/chat/config.yaml`).

A brokered MCP tool named `schedule` (new, with `cronjob` kept as an alias) replaces the Hermes tool:

- **Operations:** `list`, `get`, `create`, `update`, `pause`, `resume`, `delete`, `run`, and `history`.
- **Creator attribution and accountability:** On `create`, and again on every `update` that changes what a run does (`schedule`, `prompt`, `parameters`, `skills`, `profileRef`, `delivery`), the broker stamps `kubeagents.x-k8s.io/created-by-principal` and `kubeagents.x-k8s.io/created-by-subject` on the `AgentSchedule` from the calling task's attested `AuthorityRequester` (never from tool arguments). A schedule therefore always runs at the tier of the last person who defined its content, so nobody can rewrite another person's schedule and have it run at that person's tier. `pause` and `resume` don't re-stamp. Adopting a migrated schedule is an `update`: on a schedule that reads `Accepted=False` (`NeedsAdoption`), `update` re-stamps the caller as creator even when it changes no content, and unsuspends it. When `AgentScheduleReconciler` submits an `origin: user` schedule, it forwards both values in the trigger request, and the gateway makes the creator the run's requester ([§3](#3-how-the-gateway-authenticates-a-scheduler-and-other-triggers)), with the trigger name as its `Subject`. So every run of a user-created schedule is attributable to the person who last defined it, and per-person caps key on them. **Open, deferred to Track 7 (#5635, B):** the stamped values are pseudonyms, which can't be resolved to a tier ([§3](#3-how-the-gateway-authenticates-a-scheduler-and-other-triggers)). Track 7 decides what the broker records so that the gateway can resolve the creator, for example an identity sealed so that only the gateway can read it. Until then no user schedule runs.
- **Tier rules:**
  - Scheduled work may call only `list`, `get`, and `history`: every `TierUnattended` task, every user schedule's run, whatever its tier, and every task below a scheduled run at any depth (a scheduled run's children run at `read`, #6744). For scheduled work the broker's `schedule` tool is default-deny: those three verbs are allowed and every other verb is refused, including one added later. So no scheduled run can create, change or trigger further scheduled work.
  - **How the broker knows a run is scheduled (decided on #5635, A):** a user run is at its creator's tier with no trigger, so its tier says nothing. Its grant carries a verified marker instead, `capability.Entry.ScheduledRun{origin: "user", schedule: "<ns>/<name>"}`, minted by the gateway for every `origin: user` submission it accepts on `a2a.trigger.schedule.submit`. The callout binds that subject to the operator's ServiceAccount, and the gateway fills the marker from that bound submission, never from a task payload or a field a task can set (the rule `Trigger` follows). The dispatcher copies it into the task credential's claims beside `Trigger`, and the verifier requires the claim to equal the grant's (the claim-equality plumbing #5642 built for `Trigger`). The broker refuses the schedule tool's other verbs to any credential carrying the claim, and to any `TierUnattended` credential. A child task of a marked run inherits the marker.
  - **Writes need positive interactive origin (#6790):** the schedule tool's `create`, `update`, `run`, `pause`, `resume`, and `delete` are allowed only to a credential that carries interactive human origin: a human principal at the root of its delegation chain. A credential without it is refused, whatever its tier and whether or not it carries a marker. The gateway's `scheduled` mark on a task below a scheduled run feeds attribution and refusal messages, not this check. The PR that builds the schedule tool ships this rule, with a test that a `read` child of a scheduled run is refused.
  - **Version skew:** the verifier and the broker read credentials strictly and refuse an unknown claim, so a broker older than the marker refuses a marked run's credential outright. That fails closed, and only user runs carry the marker, which don't exist until the user-schedule path (Track 7, #5624) ships after the broker that reads it.
  - Interactive human tasks at `TierRead` (the default human tier in [`spec-profiles-dispatch.md`](spec-profiles-dispatch.md#tiers-and-identity)) may call `list`, `get`, `history`, and `run` on any schedule, and may call `create`, `update`, `pause`, `resume`, and `delete` on `origin: user` schedules. On `origin: builtin` schedules, `TierRead` callers may toggle `pause`/`resume` when `PlatformAgent` policy allows in-chat schedule overrides, while `create`, `update`, and `delete` on `origin: builtin` are always refused.
- **Broker and admission guardrails:**
  - Agent workers never receive Kubernetes RBAC to write `AgentSchedule` resources directly; only `k8s-operator` and the broker ServiceAccount can write them.
  - A Kubernetes `ValidatingAdmissionPolicy` bound to the broker's ServiceAccount requires `object.metadata.labels["kubeagents.x-k8s.io/origin"] == "user"` on `CREATE` and `UPDATE` and `oldObject.metadata.labels["kubeagents.x-k8s.io/origin"] == "user"` on `UPDATE` and `DELETE`, and forbids the broker from modifying `origin: builtin` resources even if the broker process is compromised.
  - User schedules are capped per install (`MAX_USER_SCHEDULES = 32`) and must have a minimum interval of at least 5 minutes. A user run carries no trigger on its grant (its `ScheduledRun` marker is what the broker reads, above), so these limits are enforced before it reaches the dispatcher. The broker refuses a `create` past the cap and a `create` or `update` whose schedule fires more often than every 5 minutes. `AgentScheduleReconciler` is the backstop for anything written around the broker: a user schedule beyond the 32 oldest, or firing more often than every 5 minutes, reads `Accepted=False` and never fires. A `ValidatingAdmissionPolicy` can't count objects or parse cron, so it enforces neither. The gateway's per-trigger rate cap still applies to them at ingress, since they submit on `a2a.trigger.schedule.submit` under their `triggerName`.
  - On `create` and `update`, the `schedule` tool refuses any `parameters.stream` value: user schedules write no report stream, so a user schedule can never claim a built-in audit's ([§1](#1-where-schedules-live-and-who-owns-their-state)).
  - **The tier a user schedule runs at** (decided on #5624): its creator's, resolved at fire time, never `TierUnattended`. No human is ever given the Unattended tier, as [`spec-profiles-dispatch.md`](spec-profiles-dispatch.md#tiers-and-identity) requires. A user run is a task its creator could have started by hand, run on their behalf later: at Read it may propose through GitOps only as that person could. A creator removed from the mapping stops their schedules' runs (`creatorUnauthorized`). In Hermes cron today, `cron_risk_gate.py` stamped user-created jobs `risk: "high"`; that boundary is replaced by the creator's own tier rather than by a special constraint on the grant. User runs use the interactive side of the dispatcher's capacity, on warm workers rather than Job mode, bounded by `MAX_USER_SCHEDULES` and the 5-minute minimum interval.
- **One-time migration from `/opt/data`:** On the upgrade that introduces `AgentSchedule`, a migration job inspects `/opt/data/profiles/*/cron/jobs.json`, skips the built-in job IDs listed in [`scheduling-on-profiles-inventory.md`](scheduling-on-profiles-inventory.md), creates an `origin: user` `AgentSchedule` CR for each remaining entry (mapping `schedule.expr` -> `spec.schedule`, `prompt` -> `spec.prompt`, `skills` -> `spec.skills`, `deliver: "local"` -> `spec.delivery.mode: local`, and `"chat"`, `"all"`, or any platform/channel string -> `spec.delivery.mode: chat`, logging a notice when a specific channel target is normalized to the home channel), and writes `/opt/data/.cron_jobs_migrated_to_crd` so the import runs once. Every migrated CR is created with `spec.suspend: true`, whatever the job's `enabled` was, and with no creator annotations, since the migration job is not a person and no tier can be resolved for it. Each reads `Accepted=False` (`NeedsAdoption`) until someone adopts it with the schedule tool's `update` (above), which stamps them as its creator, even with no content change, and unsuspends it. `resume` alone doesn't adopt it.

## 7. "Run it now" for an operator or the agent

Two different callers ask to run a scheduled job immediately, and they expect different routing (#1876):

1. **Operator, `oobe`, or background trigger (`run-now` annotation):**
   - Setting annotation `kubeagents.x-k8s.io/run-now: "<token>"` on an `AgentSchedule` (via `kubectl annotate agentschedule compliance-audit kubeagents.x-k8s.io/run-now="$(date -u +%s)" --overwrite`, the `schedule(action="run")` MCP tool, or `oobe`) wakes `AgentScheduleReconciler`.
   - When `metadata.annotations["kubeagents.x-k8s.io/run-now"] != status.lastHandledRunNow`, the reconciler checks whether a run is already in flight (`status.activeTaskID != ""`, since `spec.concurrencyPolicy` is always `Forbid` in `v1alpha1`): if a live run is already in flight, it adopts the running `activeTaskID` (matching [`oobe.md`](oobe.md#43-firing)), sets `status.lastHandledRunNow = "<token>"`, and starts no duplicate task. Otherwise it claims `status.pendingSlot` with idempotency key `run-now/<namespace>/<name>/<token>`, submits the schedule's run to the gateway (`TierUnattended` for a built-in schedule, the creator's tier for a user one), records `status.lastHandledRunNow = "<token>"`, `status.activeTaskID = taskID`, and `status.activeTaskStartedAt = now`, and leaves `status.nextScheduleTime` unchanged.
   - `oobe`'s first-run audit chain ([`oobe.md`](oobe.md#43-firing)) uses this path instead of `cron.jobs.trigger_job`: it sets `run-now` on `fleet-wide-cost-analysis`, `compliance-audit`, `obtainability-audit`, `stockout-prevention`, and `upgrade-retrospective` one at a time, watching `status.activeTaskID` and `status.lastCompletionTime` on each `AgentSchedule` before triggering the next.
2. **Interactive user request in chat (#1876):**
   - When a user asks in chat to "run the compliance audit now", queueing a background cron tick and replying "queued, wait for the next tick" leaves the user with no answer in their thread and lets a clean run stay `[SILENT]`.
   - Instead, the chat/platform agent delegates a child task to the target profile at the user's `Read` tier without `--scheduled` (so `silent_ok` is `false` and the full report returns to the asking conversation through the gateway's normal child/top result relay). The scheduled cadence on `AgentSchedule` is untouched.

### Stopping a run (#6052)

An operator ends a schedule's run in flight with the `kubeagents.x-k8s.io/stop: "<token>"` annotation, handled as `run-now` is: a token that differs from `status.lastHandledStop` asks the gateway to stop `status.activeTaskID` on `a2a.trigger.<source>.stop` (`lib.TriggerStop`, the status query's shape), and the token is recorded once the gateway answers. The gateway answers only for a run it recorded on that source's trigger record (`unknown_run` otherwise), so a source stops nothing it didn't start. It writes the task's cancel, under the run's own trigger authority, and its dispatcher stop record, so a run still starting has its Job removed and a running one is canceled. The run's terminal arrives through the status query and is recorded `Cancelled`. With no run in flight the token is recorded at once. A claim still in flight waits: the gateway may already have taken it, so the token is acted on once the claim becomes a run, or dropped. The run being stopped (`status.stoppedTaskID`) is written to status before the stop is sent, and the stop is sent only if the API server kept it, so a CRD without the fields can't turn one token into a stop of every later run. The token itself is recorded only once the gateway answers, so a stop lost to a crash or a failed write is sent again on the next pass. A gateway that doesn't answer leaves the token for the next pass; a stop it refuses for good is handled. A `run-now` set after a stop waits for the stopped run to end (`status.stoppedTaskID`), then starts a new one. The stop's subscription is retried on its own, so a bus that hasn't loaded its grant yet leaves submissions and status queries running.

## 8. Cluster lists

All scheduled collectors and helper scripts that enumerate the managed fleet must read the scope publisher's resolved set (`<agent>-resolved-scope` ConfigMap, key `resolved-scope.json`, written every 15 minutes by `scope_publisher.py` / `platformagent_scope_publisher.go`, #4277 / #4119) paired with the rendered `scope.json` (`KUBEAGENTS_SCOPE_FILE`), rather than scanning `/opt/data/profiles/cluster-*` or `/opt/data/fleet_scope.json`:

- `agents/platform/scripts/fleet_scope_targets.py` becomes the single Python scope reader for helper scripts and the `fleet_scope` MCP tool. Its cluster lists (`list_scope_clusters`, #5621) read the rendered `scope.json` (management project, explicit `projects`, and `exclude.clusters`) together with `resolved-scope.json` (mounted read-only from the `<agent>-resolved-scope` ConfigMap at `/etc/kube-agents-resolved`, named by `KUBEAGENTS_RESOLVED_SCOPE_FILE`) and never read `/opt/data/profiles/cluster-*`. Without a resolved-scope render (`KUBEAGENTS_RESOLVED_SCOPE_FILE` unset) they still come from the profiles' `cluster_identity` blocks, and this module is the only helper-script reader that walks that directory. The project set (`declared_scope_targets`) still reads `/opt/data/fleet_scope.json`.
- `scope_publisher.py` already probes each member project with `rec._list_project` (`gcloud container clusters list`); a companion cluster list in `resolved-scope.json` (the `clusters` map, #5621: member projects, plus the management project and the explicit projects the reconcile keeps, which have no row; dropped first when the document would pass its 900 KiB budget; the helper scripts still list the management and explicit projects live) lets `stall_watch.py`, `upgrade_readiness_watch.py`, and `leeway_watch.py` (`roster_clusters_by_project`) read the resolved `(project, location, cluster)` targets from `fleet_scope_targets.py`; their `/opt/data/profiles/cluster-*` directory walks are gone (`sa_role_watch.py` reads projects only). A member project with no entry in the map is unread, never an empty list. `stall_watch.py` sweeps a cluster that is in the resolved scope and not excluded, whether or not it has a Cluster Agent profile.
- `board_snapshot.py`, the Slack Home tab's clusters, follows (#3658): a member project's clusters come from `list_scope_clusters`, never a profile. The projects the scope lists live (the management and explicit projects) keep their Cluster Agent profiles' clusters until those profiles retire, the profiles walk filtered to those projects; a live project no profile names, and the unread members, are each a row that says so, never a project with no clusters. A running card still filed to a per-cluster profile keeps its cluster through that profile's identity, or for a member project the profile name derived from the listed triple. Without the render it reads the profiles as before.
- The reader exposes a narrow target-lookup interface (`declared_scope_targets()` and `list_scope_clusters()`, new) so a future fleet read cache can replace the ConfigMap file read without changing any audit collector or watch script.

2. **Scheduler, `AgentSchedule` CRD, and unattended trigger ingress (#4685 Track 2):** Add `AgentSchedule` types, `AgentScheduleReconciler` in `k8s-operator`, the `platform` (or `fleet-audit`) `AgentProfile` CR with `allowedTiers: [read, unattended]`, the `a2a.trigger.<source>.submit` and `a2a.trigger.reply.<source>.>` grants in `a2a/authcallout` (with contract tests refusing another source's submit and reply subjects), the gateway trigger subscriber and per-trigger token-bucket rate limiter, `run-now` annotation handling, unit/envtest/conformance tests, and an eval case that runs a no-op `Unattended` schedule end to end in Job mode. 3. **Unattended result delivery (#4685 Track 3):** Gateway terminal-event delivery to `chat.notify`, `SCHEDULE_THREADS` daily thread grouping, incident store write for threaded replies (#4059), `kube-agents.report/v1` artifact extraction for `fleet-audit`, and `SCHEDULED_REPORTS` persistence for no-home-channel installs (#4053, #3928).
4. **Fleet audits migration (#4685 Track 4):** Broker-backed `/v1/audit-reports` store with task-grant write scoping; migrate `compliance-audit` first as a canary and compare against Hermes runs, then migrate the remaining nine fleet audits and `upgrade-readiness-weekly-brief`.
5. **Helper jobs and cluster-list cutover (#4685 Track 5):** Switch `fleet_scope_targets.py`, `stall_watch.py`, `upgrade_readiness_watch.py`, `sa_role_watch.py`, and `leeway_watch.py` to `<agent>-resolved-scope`; add `unattended` to the `cluster` `AgentProfile`'s `allowedTiers` (`[read, unattended]`); run `stall-watch`, `upgrade-readiness-watch`, `upgrade-readiness-weekly-review`, `sa-role-watch` and `leeway-watch` as script-run `Unattended` schedules on a helpers profile (#5622); move `github-repo-watcher` to its own trigger; decide `findings-morning-nudge`, `feedback-prompt` and `eod-event-watcher-daily-report` with the script-run task kind; migrate `k8s-event-watcher` and `drift-detector` from Session KV `/sessions/{id}/inject` to `a2a.trigger.<source>.submit`; replace `chat-delivery-watch` with gateway/scheduler metrics and health conditions.
6. **OOBE migration (#4685 Track 6):** Move `oobe` first-run audit chaining onto `AgentSchedule` `run-now` and `AgentScheduleStatus`.
7. **User schedules (#4685 Track 7):** Add the brokered `schedule` (`cronjob`) MCP tool with creator attribution annotations (re-stamped on content edits), the broker `origin: user` `ValidatingAdmissionPolicy`, the gateway's fire-time creator-tier resolution and minting at the creator's tier, the cap and interval enforcement in the broker and reconciler, and the one-time `/opt/data/profiles/*/cron/jobs.json` migration (suspended, awaiting adoption).
8. **Legacy Hermes cron retirement (#4685 Track 8):** Once no job runs on Hermes cron, delete `agents/chat/defaults/cron/jobs.json`, `agents/platform/cron/jobs.json`, `profile_cron_tick.py`, `/v1/cron-reports`, `kanban-workspace-gc`, `kanban-board-health`, `session-retention`, `cluster-agent-reconcile`, and the Hermes cron patches in `deploy/docker/Dockerfile` and `deploy/docker/patches/*cron*`.
