# Platform Agent as a Profile: Inventory

- **Date:** 2026-11-19
- **Status:** living appendix to epic #6526 (run the platform agent as an AgentProfile); issue #6527.

## Purpose

This lists everything the platform agent does today, built from the code, so that nothing gets dropped when the work moves to profiles. Everything was read from `main` at `11917aedf`; docs were not used as a source. Credentials and identities appear by class and purpose only.

## What a Profile Is Today

An AgentProfile is a stateless, time-boxed worker for bus tasks.

- **Pods.** A warm-pool Deployment per interactive tier, or a Job per task. Each pod has one `worker` container: wa/ driving the Claude Code binary from the Agent SDK. Its config dir and transcript are deleted after each task, and it has emptyDirs only, no PVC. `lifecycle.activeDeadlineSeconds` is required, so it can't run daemons. AP:116-258, `wa/profile.go:237-250`.
- **No pod extras.** No Secrets, sidecars, custom env, initContainers, volumes, Service or ingress. Egress is DNS, NATS, LiteLLM and the broker only.
- **Identity.** One operator-made ServiceAccount per tier, with no RBAC and no Workload Identity annotation; RBAC only by naming an existing ServiceAccount in `spec.identity`. `op/agentprofile_identities.go:121-126`.
- **How work arrives.** Tasks come from the dispatcher, which is on by default (`op/platformagent_a2a_dispatcher.go:108-115`); the comment at `op/agentschedule_controller.go:48-51` saying otherwise is stale. The worker publishes events on its own task, and publishes and subscribes only the topics listed in `spec.bus`, with no wildcards. Writes are limited to `shared.*` and `agent.<self>.*` (`a2a/authcallout/profile_narrowing.go:150`).

What it can do at the broker, with its per-task credential:

- `/v1/exec`, kubectl and gcloud only: read-only, and confined to the one target cluster and project named in the task credential (`cp:2415-2422`, `tc`). `wait` and `rollout status` are refused, and so are watch, follow and timeout flags (`cp:2738-2766`). Server-side dry-run counts as a write (`cpol:148-153`).
- 11 VCS verbs (`cp:2525-2563`). Read: `clone`, `proposal-view/list/commits`, `branch-view`, `identity`, `issue-list/view`. Write: `publish`, `proposal-create`, `proposal-update`, only with a `vcs:proposal-create` permit and only on the install's own branch.
- The MCP relay for `developer_knowledge` search and get only (`mp:159-161`).
- `/v1/audit-reports`: read if allowlisted; write only to its own builtin `schedule/<stream>` (`cp:3325-3395`).

What it can't do:

- **No chat.** No chat route of its own and no `chat.notify`. It reaches chat only through its own task's events, in a conversation the gateway already holds.
- **No schedule.** The AgentSchedule CRD and reconciler exist, but the reconciler is never registered in `k8s-operator/cmd/main.go` (AgentProfile and Tier only), and its gate function `AgentSchedulesEnabled` (`op/agentschedule_controller.go:52-57`) has no caller. No principal is granted `a2a.trigger.*`. Nothing in wa/ executes `spec.scripts`. (Since this snapshot, #6032 registers it in `cmd/main.go` behind the `A2A_AGENT_SCHEDULES` gate.)
- **No harness extras.** No plugins, hooks, memory provider or cross-task session.

What the `platform` addressee runs today is two tiers, not one:

- By default the bridge posts `platform` tasks to the Hermes API under the gateway's own profile, the Chat Agent, which delegates to the platform persona through kanban (`hb/api.go:28-31`).
- The image CMD is a bare `hermes gateway run`. The gateway comes up as the `platform` profile only with `spec.harness.experimental.platformFrontDoor` (PAM:5867-5880).
- `P/config.yaml:408` says "The Platform Agent is no longer the chat ingress".
- So a move has to replace the Chat Agent tier (group l) as well as the platform persona.

## Notes From the Code

- **Where the drift-detector and its neighbours start.** `start_drift_detector()` is at `ss:1138`, exec at `ss:1242`; `start_event_watcher()` is at `ss:903`; `start_audit_report_store()` is at `ss:1284`.
- **Where Session KV starts.** Two starters: the entrypoint, on the bootstrap primary (`de:2285-2293`), and `platform_control`'s startup, as a fallback (`pms:1391`).
- **The bridge and A2A stack are not gated on `mode: next`.** `reconcileA2A` runs on every install (PAC:1484-1486: "Every install renders it"), and `a2aBridgeRendered` is "not declared by the CR" (`op/platformagent_a2a_bridge.go:182-184`).
- **Profile pods don't mount `/etc/gitops/managed_repos`.** AP has no gitops volume, and profiles take no custom volumes.
- **The cluster-work topic.** No `cluster-work` subject or producer exists at this commit. #6524 describes it as being added for #3658 step 4c-2, so it isn't inventoried as a live item.
- **The scheduled report credential.** It is refused on every broker route except the audit-report routes, `/v1/exec` and the relays included (`cp:3119-3138`, `P/scripts/task_credential.py:110-115`, `tc:69-71`).
