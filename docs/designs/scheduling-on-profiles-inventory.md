## Purpose

This is the list of every job on the Hermes cron rosters, what it does today, and where it goes under [`scheduling-on-profiles.md`](scheduling-on-profiles.md). It replaces the inventory table that used to sit in that doc's section 5. Citations are against `main` at `638562521`.

**Keeping it current:** any PR that adds, changes, or removes an entry in `agents/chat/defaults/cron/jobs.json` or `agents/platform/cron/jobs.json` updates that job's row here in the same PR, including where the job will live on the new path (profile, trigger kind, report sink). A job with no answer yet says TBD and links an open question below. (@bnaylor, 2026-11-11.)

There are 30 entries on `main`: 5 on the chat roster and 25 on the platform roster. Eleven are model runs and nineteen are `no_agent` scripts. Two of the chat entries ship disabled.

## How to Read the Table

- **Kind:** `model` is an agent turn. `script` is a `no_agent` subprocess with no model. `script+model` runs a script and puts its output above the prompt.
- **Destination:** `AgentSchedule` (an operator-reconciled schedule that submits an `Unattended` task), `CronJob` (an operator-rendered Kubernetes CronJob with a narrow identity), `controller`, or `retire`.
- **Profile:** the `AgentProfile` an `Unattended` task runs on. For a `CronJob` it's the identity the job runs as, plus the profile it submits to when it wakes a model.
- **Trigger:** the `a2a.trigger.<source>.submit` source that submits the task (section 3 of the design). `-` means the job never submits a task.
- **Report sink:** where the output lands. "Home channel" means `chat.notify` to the home channel, grouped one thread per job per UTC day through `SCHEDULE_THREADS`, with a copy in `SCHEDULED_REPORTS` (section 4 of the design).
- Every `deliver: chat` job today posts through the cron relay (`/v1/cron-reports`, [`cron-report-relay.md`](cron-report-relay.md)). That is the "chat relay" in the Today column.

### Fleet Audits

All ten are model runs with the `fleet-audit` skill, `max_turns: 250`, `deliver: chat` and `risk: low`. Each reads its SOP under `governance/`, files or updates one GitHub ledger issue (and narrow PRs when a fix is a manifest), writes the fleet-audit report store on `/opt/data`, and posts a one-line report. A clean scheduled run stays silent.

Under the design each becomes an `origin: builtin` `AgentSchedule` in Job mode, on a dedicated `fleet-audit` profile (O1). The ledger issue doesn't change. The report store moves behind the broker's `/v1/audit-reports` (Track 4).

## Open Questions

These are the places the design doesn't yet say where a job goes, or says something `main` disagrees with.

**O1. Which profile runs the audits.** The design says `platform` "or a narrower `fleet-audit`" and doesn't pick. Decided 2026-11-11: a dedicated `fleet-audit` profile, narrower than `platform` and scaled on its own. Track 2 renders it.

**O2. State for helper scripts.** Section 1 of the design moves four kinds of state off `/opt/data`. The surviving scripts keep more than that, and a `CronJob` pod has no `/opt/data`:

- `stall_watch.json`, `sa_role_watch.json`, `.findings_nudge_state.json`
- the upgrade-readiness watch ledger and reports, and the weekly review's report that the brief reads
- the `leeway-watch` ledger and reports
- `feedback-prompt`'s two once-only markers
- `github-repo-watcher/unreadable-prs.json`

Each needs a home. Direction (2026-11-11): run-over-run state becomes one small KV record per job in the broker store that [`fleet-audit-report-store.md`](fleet-audit-report-store.md) moves behind `/v1/audit-reports` (Track 4a, #5619). A report one job writes for another goes in the same store. Whether these jobs stay `CronJob`s at all is O7.

**O3. Session KV reads.** `findings-morning-nudge`, `upgrade-readiness-weekly-review` and the weekly brief reach the findings queue on Session KV at `127.0.0.1:8699`, which only works inside the agent pod. `eod-event-watcher-daily-report` opens Session KV's SQLite file directly. A `CronJob` needs a network route to the findings queue and the intercepted-events ledger, or those stores need to move. Direction (2026-11-11): broker verbs front the findings queue and a read-only events-ledger endpoint, scoped by task grant like `/v1/audit-reports`. No job opens `session_kv.db` directly. Detail in Track 4a (#5619). Today mode doesn't change.

**O4. The weekly brief's tool narrowing.** Today the brief's turn has the terminal and no MCP servers (`enabled_toolsets: [terminal, no_mcp]`), so text a tenant can write can't make it register, verify or decide a finding. Running it on `platform` as-is would hand it the platform MCP tools. Decided 2026-11-11: a narrow profile with no platform MCP tools, which keeps today's protection.

**O5. OOBE beyond the audit chain.** Track 6 moves the first-run audit chain onto `run-now`. `oobe` also runs the inventory scan, which files kanban cards for `platform`, and keeps its once-only markers in the Chat Agent's home. `findings-morning-nudge` reads those markers too. With kanban retiring, the scan needs another way to reach `platform`, and the markers need a home.

**O6. Nothing replaces the block re-check.** `kanban-block-recheck` retires with kanban. Transient failures should be covered by dispatcher retry, but a task that failed on a cluster condition ("wait until this deployment is Available") has no re-check under dispatch. Probably fine to drop. Noting it so it's a decision rather than an accident.

**O7. Tools in a CronJob.** `stall-watch`, both upgrade-readiness scripts, `sa-role-watch` and `leeway-watch` run `kubectl`, `gcloud` or `leeway` through `sandbox_exec`. A `CronJob` has no shell sandbox. The design says these call the broker for fleet reads, but broker verbs don't cover `leeway report` or the readiness report's own scripts. The other way is to run these helpers as `Unattended` profile tasks in Job mode, which have the sandbox and the broker and need no new identity. A `CronJob` with cluster credentials is a new identity, so this one is @bnaylor's call. Options go on #5622.

**O8. Kanban writes outside the kanban jobs.** `github-repo-watcher` files kanban cards and `stall-watch` comments on and completes its triage card. The design moves `github-repo-watcher` to a task submission. For `stall-watch` it covers the submission but not the card bookkeeping, which needs to follow the task's own status instead.
