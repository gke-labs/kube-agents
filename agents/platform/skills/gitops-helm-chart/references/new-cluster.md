# A chart for a cluster created in the same pull request

Until the pull request merges, the cluster does not exist, so nothing in the
pull request can carry a value that only exists after creation: the API
endpoint IP, the cluster CA, or the DNS endpoint hostname, which holds a
generated identifier. A form works here only when it names the cluster by
values known up front (project, location, cluster name, fleet membership)
and looks up the rest itself after merge.

Use a row only when the repository already reaches its other clusters that
way. Never introduce a hub, a fleet registration scheme or a new
authentication path in a chart request. When no row matches, stop with the
message in SKILL.md Step 2.

| Form                                                      | Works in the same pull request? | What the pull request adds for the new cluster                                                                                                                                                                                                                                                                                                                                                                                                             |
| --------------------------------------------------------- | ------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Flux 2.7 or later, hub and spoke                          | Yes                             | A `ConfigMap` with `provider: gcp` and `cluster: projects/<project>/locations/<location>/clusters/<cluster>`, and the chart's `HelmRelease` (or the cluster's `Kustomization`) pointing at it with `spec.kubeConfig.configMapRef`. Flux reads the endpoint and CA from the GKE API after merge. Only when the sibling clusters use `configMapRef` the same way, and the new cluster keeps its IP endpoint: Flux uses that address when `address` is unset. |
| Config Sync, clusters enrolled through KCC                | Yes                             | A `GKEHubMembership` referencing the new `ContainerCluster` and a `GKEHubFeatureMembership` whose `configSync` points at the new cluster's directory, both copied from a sibling cluster's, through `gcp-config-connector`. The chart goes in that directory as a Helm `RootSync` (`references/forms.md`). Only when sibling clusters are enrolled the same way.                                                                                           |
| Config Sync, fleet default configuration                  | Yes, for the sync               | Fleet membership for the new cluster (the cluster's Terraform `fleet` block, or the KCC membership above); the fleet default then installs Config Sync. A fleet default cannot use a Helm source, so the chart is still a Helm `RootSync` in the cluster's synced directory.                                                                                                                                                                               |
| Argo CD, clusters reached through Connect Gateway         | Yes                             | Fleet membership for the new cluster, and an Argo CD cluster `Secret` whose `server` is the Connect Gateway URL for that membership with `argocd-k8s-auth gcp` and no `caData`, copied from a sibling cluster's Secret. An `ApplicationSet` cluster generator then picks it up. Only when sibling cluster Secrets already use the gateway URL.                                                                                                             |
| Argo CD, clusters registered by endpoint and CA           | No                              | The Secret needs the endpoint and CA, which exist only after creation. Stop.                                                                                                                                                                                                                                                                                                                                                                               |
| Terraform `helm` provider configured from the new cluster | No                              | A provider configured from a cluster created in the same apply is the documented failure case of the `helm` provider; it needs a second apply. Stop.                                                                                                                                                                                                                                                                                                       |
| A pipeline that runs `kubectl apply`                      | No                              | It renders no chart for any cluster (SKILL.md Step 1). Stop.                                                                                                                                                                                                                                                                                                                                                                                               |

Copy every field from the sibling cluster's objects, changing only the
cluster's own name, location and membership. A field you would have to
invent is a sign the repository does not reach its clusters this way.
