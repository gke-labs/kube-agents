# SOP: Workload Reliability Audit (Daily Governance)

**Purpose:** Sweep every managed GKE cluster for workloads configured in a way that will hurt during a node drain, a control-plane or node-pool upgrade, a scale event, or a traffic spike. The question this audit answers for a platform admin is: _which workloads on my fleet break when I upgrade a node pool, and which ones cannot scale?_ Output is this stream's single GitHub ledger issue, rewritten in place on every run, plus narrow remediation Pull Requests carrying generated manifests for the findings that get promoted.

**Cron:** id `obtainability-audit`, schedule `50 6 * * *` (daily 06:50 UTC). The id is a stable observability identifier and does not change even though the audit is named "Workload Reliability".

**Data sources:** `kubectl` read verbs, `gcloud container ...`, `gcloud projects list` (the collector's fleet enumeration), the `gke` MCP server, and the Config Controller MCP tools (`list_cc_pods`, `get_cc_pod_diagnostics`, `list_cc_healthchecks`, `get_cc_operator_status`). **Nothing else** — no BigQuery, no Prometheus/GMP, no VPA recommendations, no Policy Controller, no external blueprint, no delegation to Cluster Agents via kanban. Every conclusion is derived from live cluster reads you performed in this run. The one thing a repository may decide is whether a posture is a finding: §4a reads the GitOps clone and the registered `context_repos` for a declaration that justifies it, and nothing else about a verdict comes from a repository.

---

## Execution Checklist

### 0. Open the audit run

```bash
./skills/fleet-audit/scripts/audit_report.py start --audit obtainability-audit [--repo "<owner>/<repo>"]
```

If multiple repositories are registered in `$GITOPS_STATE_CONFIGMAP` (`managed_repos`), pass `--repo "<owner>/<repo>"` explicitly:

- **Interactive session:** If no `--repo` was specified, prompt the user to choose which repository to target before proceeding.
- **Scheduled / unattended cron:** Iterate over all repositories in `managed_repos` in sequence, executing the audit and running `audit_report.py start` and `audit_report.py finish` for each repository with `--repo "<owner>/<repo>"`.

Returns `{"issue": <int|null>, "repo":"org/repo", "workspace":"/opt/data/gitops/obtainability-audit/org__repo", "findings_path":"/opt/data/scratch/findings_obtainability-audit.json", "pending_remediation_requests":[…], "context_repos":["org/terraform-live"], "declared_intent_repos":["org/repo","org/terraform-live"], "declared_intent_searched":["org/repo@<sha>","org/terraform-live@<sha>"], "declared_intent_sources":[{"repo":"org/repo","ref":null,"paths":["knowledge"]},…], "declared_intent_unsearched":[{"repo":"org/terraform-live","ref":"release-2026"},…], "declarations_path":"/opt/data/scratch/declarations_obtainability-audit.json"}`. Keep `findings_path`, `workspace`, `context_repos`, `declared_intent_repos`, `declared_intent_searched` and `declared_intent_unsearched` from this call; you write into the first two and read the rest in §4a.

- `workspace` is the GitOps clone `start` made for you. The audit pod does not begin life inside a checkout, so this is the only tree that exists, and every `remediation.path` in Step 4 is resolved against it — a manifest written elsewhere is one the harness cannot find.
- `issue` is this stream's open ledger issue, or `null` when it has none. Either way you never create it — `finish` owns that.
- `pending_remediation_requests` lists finding ids a repo writer asked for with a `/remediate` comment on the ledger. Write a manifest for each one while you inspect (Step 4), or the promotion fails for want of a file. Each comment is answered once and only once — an acknowledgement listing every target and its outcome, or a single refusal with the reason (no write access, an id absent from the current document, a target that is not a `manifest`, or a command not written at the start of its own line and so never parsed as one) — with a hidden marker keeping yesterday's request from being answered again today. A request naming a posture §4a's record withholds (below) is the one exception: it is put on hold with its own marker, not refused, and stands until a run records the search.
- `context_repos` lists the repositories registered under the `context_repos` key of `$GITOPS_STATE_CONFIGMAP`, as `owner/name`. §4a reads them for declared intent and nothing else reads them at all: they are never swept, never audited, never sent a pull request — the key is separate from `managed_repos` and the harness never merges the two. Empty when none is registered or the key could not be read (`start` warns on stderr), in which case §4a searches the GitOps clone alone.
- `declared_intent_repos` is the exact set §4a must search and §5's `declared_intent_searched` must name: the GitOps repository plus every `context_repos` entry, one entry each. `start` also writes it to a run record beside the findings document, and `finish` measures your document against that record — what this run was told — rather than against the ConfigMap as it stands at finish time.
- `declared_intent_searched`, `declared_intent_sources` and `declarations_path` are the harness's own half of §4a, already done. `start` has read every repository in `declared_intent_repos` it could for `declares:` frontmatter, within the paths each repository's `.kube-agents/intent.yaml` names (`declared_intent_sources` lists each as `{repo, ref, paths}`, `paths` empty when the whole tree was read), filed what it found at `declarations_path`, and listed each repository it read completely — every note under the searched paths arrived and was read — as `owner/name@sha`. `finish` unions that list into your document's and moves every finding a filed declaration covers to `declared` itself. A slug in `declared_intent_repos` that is missing from `declared_intent_searched` is one the harness could not read — stderr says why — and is yours to search and record, or its postures are withheld; `declared_intent_unsearched` lists each as `{repo, ref}`, `ref` the branch the entry pins (null when it pins none), so your copy reads the branch the harness was told to read; an entry that also carries `refused_ref` names a pin that is not a git branch name, and that repository you do not copy at all — the harness read neither the pin nor the default branch in its place, and its postures stay withheld until the entry is corrected.
- `start` creates and resets no branch. There is no report branch.

The helper owns every `git`/`gh` operation and renders the ledger issue body and every remediation PR body — **never hand-write an issue or PR body, never run `git commit`, `git push`, `gh issue create`, `gh pr create`, or `gh issue comment` yourself.**

**Never comment on the ledger yourself.** `/remediate` is a human reviewer's instruction to this harness, not a step in the audit: an agent that posts it — including when someone asks for a fix in chat — is authorizing its own pull request. `finish` ignores a `/remediate` from a machine account, so posting one achieves nothing but noise on the issue.

### 1. Enumerate the target fleet

**Run Step 2's collector before doing any of this by hand.** Its manifest enumerates the fleet itself and reports one outcome per cluster; the rules below build `scope.clusters` and `scope.skipped` from that outcome for every stream, whether the collector covered a cluster or not. The commands in this step are the manual path, needed only for a cluster the manifest marks `"unreachable"` or `"gate-failed"`.

```bash
gcloud container clusters list --format=json
```

- Target every cluster whose `status` is `RUNNING` or `RECONCILING`. A reconciling cluster is not one you cannot read: GKE sets that status while work proceeds on an otherwise-operational cluster, and the API server stays up throughout. It is also ordinary — any config change puts a cluster there for minutes — so excluding it drops clusters from the audit at random, with no check evaluated against them. `PROVISIONING` has no API server yet and `STOPPING` is on its way out; both are recorded rather than audited. Record `{name, location, project, checks_run}` into `scope.clusters`. Note each cluster's mode — Step 3 changes behaviour on Autopilot. When Step 2's collector ran, that mode is the `autopilot` boolean on the cluster's own manifest entry; this section's `clusters list` is the fallback for when it did not. Carry that in each affected finding's `impact` (§3.1 and §3.2 are the two it moves), and surface it in `evidence.excerpt` where it changes a verdict. **Not in `limitations`:** every non-empty `limitations` string is read as a coverage gap, and a fleet with one Autopilot cluster would then publish `partial: true` on every run it ever makes, with the ledger permanently unclosable. Autopilot changes how severe a finding is, not how much of the cluster you saw.
- **`checks_run` is mandatory on every cluster,** and each entry is an object, never a bare string:

  ```json
  {
    "check": "no-pdb",
    "command": "kubectl --context prod-usc1 get pdb -A -o custom-columns=NS:.metadata.namespace,NAME:.metadata.name --no-headers"
  }
  ```

  `check` is the backticked slug from the §3 heading that defines it — `no-requests`, `no-pdb`, and so on — never the section number and never prose. (`start` prints the full roster of twenty-three; the SOP still says what each check _is_.) `command` is the literal invocation you issued on that cluster for that check, with its `--context` and the namespace or resource it targeted. It must name one of `kubectl`, `gcloud`, `gsutil`, `bq`, `helm`, or `curl`; `echo`, `cat`, `python3 -c`, and a call back into `audit_report.py` are all rejected, as is anything under eight characters.

  The validator rejects an unknown slug, a duplicate, a missing or unusable command, the field being absent, and an empty list unless that cluster's `limitations` says why nothing ran: a cluster you could read but ran nothing against is not a clean cluster, it is an audit that did not happen. Anything short of the checks that apply to that cluster makes the run **partial** exactly as a `limitations` note does, so the ledger stays open and nothing on that cluster is announced as resolved. Append the entry when its check completes, not when you intend to run it, and paste the command rather than reconstructing it — every one is published verbatim in the ledger under _How this run checked the fleet_.

- **A check the cluster's shape rules out is not a gap — declare it.** Alongside `checks_run`, a cluster may carry `checks_not_applicable` as a list of `{check, reason}`:

  ```json
  {
    "check": "no-hpa",
    "reason": "autoscaling/v2 is not served by this cluster's API server; an HPA cannot exist here."
  }
  ```

  Same slugs as `checks_run`, and the `reason` must say why the check _cannot_ apply here — "N/A" and "not applicable" are rejected; name the property of the cluster that rules it out. Those checks leave the denominator instead of counting as missing, so the cluster reads as complete on the checks that remain rather than forever-incomplete by the ones it could not run, and the ledger can eventually close. **Expect to use this rarely on this audit.** Every §3 check applies wherever workloads run, and Autopilot in particular does **not** make any of them inapplicable — it only downgrades 3.1 and 3.2 by one severity, which belongs in those findings' `impact` and in neither of these two lists. A check you could have run and did not is a `limitations` note and a real gap. The validator rejects a slug in both lists, a duplicate, an unknown slug, and a reason under sixteen characters, but it cannot tell an honest exclusion from a convenient one — that part is on you.

- **One question decides the scope list.** A cluster appears in exactly one scope list. Could you read it? Yes → `scope.clusters`; name any check that could have run there and did not in that cluster's `limitations`, and any check its shape rules out in `checks_not_applicable`. No → `scope.skipped`. Nothing goes in both, and nothing in `scope.skipped` may appear in a finding. The validator enforces both halves: it rejects a document whose two lists overlap, and any finding whose `cluster` names a `scope.skipped` entry.
- A cluster you cannot read goes in `scope.skipped` with a literal reason: `"status=STOPPING"`, `"get-credentials failed: <stderr first line>"`, `"timeout after 30s"`. A skipped cluster is never silently dropped.
- A partial read is **not** a skip. If the dump succeeded but one kind was refused, the cluster stays in `scope.clusters` and the refusal goes in its `limitations`: `"RBAC: cannot list horizontalpodautoscalers; checks 3.5, 3.6 and 3.22 not run."` Skipping it would suppress every finding you did prove there.
- Obtain per-cluster credentials into an isolated kubeconfig so clusters cannot bleed into each other — the naming and the reason it must sit under `$HERMES_HOME` are in `AGENTS.md` ("Cluster Credentials"):
  ```bash
  export KC="${HERMES_HOME:-/opt/data}/.kubeconfigs/kubeconfig_<project>_<cluster>_<location>.yaml"
  KUBECONFIG=$KC gcloud container clusters get-credentials <cluster> --location=<location> --project=<project>
  ```
- **Manual fallback only** — a cluster the collector marks `"unreachable"` or `"gate-failed"` still needs this cluster's workload state dumped once, the same object kinds Step 2's collector reads, so every `$STATE` reference in Step 3 has something to derive from:
  ```bash
  export STATE="/opt/data/scratch/state_<cluster>.json"
  KUBECONFIG=$KC kubectl get deployments,statefulsets,daemonsets,poddisruptionbudgets,horizontalpodautoscalers,services,limitranges,cronjobs,jobs,endpointslices,persistentvolumeclaims -A -o json > "$STATE"
  ```
- If **zero** clusters land in `scope.clusters`, do **not** call `finish` — the helper hard-fails on an empty scope. Report the enumeration failure as your one-line summary and stop.

### 2. Run the collector

```bash
python3 ./skills/fleet-audit/scripts/collect.py obtainability-audit --workspace "<the workspace Step 0 returned>" > /opt/data/scratch/manifest_obtainability-audit.json
```

This is the tested, procedural implementation of every check in Step 3 — see the fleet-audit skill's `collect.py`, whose own module docstring is the design record for what it covers. It enumerates the fleet itself, dumps workload state once per cluster behind a fail-closed gate, and evaluates all twenty-three checks against that one dump. Its last line on stderr counts the candidates per check, and that count is the floor on `findings` — the candidates sit under each cluster's entry in `clusters[].candidates`, below its `commands`, so a read of the file's head shows none of them. Read the manifest before doing anything else:

- Every entry in `manifest.clusters` carries one `outcome`. `"collected"` means every check already ran there — do not re-run any of them by hand, and do not re-dump the cluster. `"unreachable"` or `"gate-failed"` means the collector could not cover this cluster; fall back to Step 1's manual enumeration and dump commands for it alone, then evaluate Step 3's Flag-when/Do-NOT-flag rules yourself against what you read. An `"unreachable"` entry whose `error` says the cluster is neither `RUNNING` nor `RECONCILING` is the one case not worth a manual retry: the state that stopped the collector will stop you too, so put it straight into `scope.skipped` with that reason. Every cluster entry also carries an `autopilot` boolean — the mode, already resolved, and on the error shapes too, because a cluster does not stop being Autopilot when a read of it fails. Take the mode from there for any cluster the manifest lists rather than re-deriving it from `clusters list`, and never transcribe a fleet-wide mode map into a script: that hand-copy goes wrong the moment a cluster is added or converted.
- For a `"collected"` cluster, copy its `commands` list verbatim into that cluster's `checks_run` — each entry already carries `{check, command}` in the exact shape the validator wants; do not retype it.
- A `"collected"` cluster's entry may also carry `checks_not_applicable`, already in the `{check, reason}` shape §1 wants — copy it verbatim into that cluster's `checks_not_applicable`. The collector writes it when nothing on the cluster survived the standard exclusions below: every Deployment, StatefulSet and DaemonSet it dumped is in a system namespace, addon-managed, owned by another object, opted out, or scaled to zero. The fifteen workload-scoped checks then examined an empty set, which has cleared nothing, and so did three of the cluster-scoped ones — 3.4, 3.22 and 3.23 grade a PDB or HPA only against the workload it covers — and by publication time an empty cluster and a clean one are the same absence of candidates — the manifest is the last place the two can still be told apart. The other five cluster-scoped checks — 3.6, 3.12, 3.15, 3.16 and 3.17 — stay in `commands`, because an HPA pointing at a workload that no longer exists, a CronJob that stopped succeeding, and a Service routing to no pod are all still true of a cluster running nothing. The field is absent when anything was in scope, and no slug ever appears in both it and `commands`.
- Every entry in a `"collected"` cluster's `candidates` is a verified finding: `check`, `cluster`, `namespace`, `object`, `severity`, and `excerpt` are already computed, including the Autopilot severity downgrade on 3.1/3.2. What is not computed — and is still yours to write — is the `recommendation` (§5) and, for a `kind: manifest` remediation, the manifest file itself (§4's declaration rule). A candidate may also carry `declaration`, which is where this repository declares the object it names: `declaration.path` is the file, and `declaration.directory` is the directory a new sibling object goes in. It is computed by parsing the clone, keyed on all four of cluster, kind, namespace and name, and it is authoritative — prefer it to any `grep` of your own, which is kind-blind and unanchored and is what this field exists to replace. Its **absence** is not a claim that no declaration exists: it means the object was not found, was declared twice, or the collector ran without `--workspace`. Fall back to the declaration rule's own search then. A candidate whose object no file declares may instead carry `release_declaration`, which is where this repository declares the **chart release** that renders it: `release_declaration.path` is the Argo CD `Application` or Flux `HelmRelease` file, `chart`, `repo` and `version` name the chart itself, and `values_field` is the exact field a values override belongs in. `renderer` says how that field is written: `helm` for a values mapping the chart reads by key, or `kustomize` for a list of patches, where the object comes from an overlay over a base in another repository and `chart` holds the overlay directory rather than a chart name. It appears only when `declaration` does not, because an object with its own manifest is edited there and a values override beside it would be a second expression of the same change. §4's Helm branch says what to do with it. A candidate may also carry `namespace_directory`, which answers the third and different question of where a _new_ object for this cluster and namespace goes — the one a create-an-object fix needs and neither field above can answer, because the object they would look up is the one that is missing. `namespace_directory.path` is the directory and `namespace_directory.source` is `sibling`, `overlay` or `cluster`; §4's create branch says what each obliges you to write. It is attached whatever else resolved, since a workload with its own file still needs somewhere to put a PDB that has none. A candidate may also carry `reconciler`, naming what continuously reasserts the object's spec — a Helm release, an Argo CD Application, an operator. It is read off the object's own markers and is authoritative: never write prose calling such a workload unmanaged or applied out-of-band, and never propose a `kubectl patch` or `kubectl edit` as the fix, because the next sync undoes it. A `manual` remediation on such an object says so in its note, and names where the fix belongs instead: the chart, the Application, or the operator's own configuration.
- Pass `--manifest-file <path>` to `finish` (Step 6) so it cross-checks your `checks_run` against what the collector actually ran — a check you claim ran on a `"collected"` cluster with no matching manifest command is rejected before publication, not after.
- A GKE cluster name is unique only inside one project and location, so the collector sweeps every project it can see — the active one and every project `gcloud projects list` returns — and names every cluster `<project>/<location>/<name>`: in the manifest entry's `name`, in each candidate's `cluster`, and so in `scope.clusters[].name` and every finding's `cluster`. Carry that form verbatim, and use it for a cluster you fall back on by hand too: `finish` matches `scope.clusters[].name` against the manifest, so a name shortened back to the bare one reads as a collected cluster the document omitted. `object` keeps the bare resource name, because `cluster` already carries the qualified one beside it; commands still take the real `--project` and `--context`. A project whose `clusters list` failed contributes one `project/<id>` entry at `"gate-failed"` instead of clusters: put it in `scope.skipped` as `{"cluster": "project/<id>", "reason": <the collector's error>}` rather than leaving it out, which would read as a project holding no clusters. The same entry sits beside that project's collected clusters when some of its zones did not respond, and `project/UNENUMERATED_PROJECTS` appears when `gcloud projects list` failed or returned a filtered list; treat both the same way. A manifest with a top-level `error` read no cluster at all, and the collector exits non-zero for it: do not call `finish`, and report the error as your one-line summary.

**A cluster the collector covered is not a cluster you dump or query again.** The manual dump command in Step 1 and the per-check reads below exist for the `"unreachable"`/`"gate-failed"` fallback — never for confirming a candidate the collector already produced, whose evidence `finish` takes from the collector's manifest, and never for re-deriving a verdict the manifest already gives you.

### 3. Checks

**Standard exclusions — apply to every check below.** Skip an object if any holds:

- **S1 — system namespace:** `kube-system`, `kube-public`, `kube-node-lease`, `gmp-system`, `gmp-public`, `gke-gmp-system`, `cnrm-system`, `configconnector-operator-system`, `krmapihosting-system`, `istio-system`, `asm-system`, `anthos-identity-service`, `gatekeeper-system`, `composer-system`, or any namespace matching `gke-*`, `gke-managed-*`, or `config-management-*`. This is the fleet-wide system-namespace set, spelled the same way in the Security & RBAC Posture Audit (`$SYS`) and the Fleet Waste Audit (`SYSTEM_NS`); `kubeagents-system` is deliberately **not** in it, because the harness audits itself.
- **S2 — GKE-managed object:** carries the label `addonmanager.kubernetes.io/mode` (any value). GKE reverts edits to these; a finding is unactionable.
- **S3 — owned by a controller this audit reaches:** `metadata.ownerReferences` names a `Deployment`, `StatefulSet`, `DaemonSet`, `Job`, or `CronJob` — its replica count, PDB, and probes belong to that controller, and the audit either evaluates the controller itself or (Job/CronJob) drops it under S5. An owner this audit never reads, such as a `PlatformAgent` or a KEDA `ScaledObject`, does **not** suppress the workload: deferring to an object nobody looks at loses the finding rather than moving it, and the workload's own PDB and probe gaps are still its own. HPAs are the one exception, for a reason particular to them — see 3.6.
- **S4 — explicit opt-out:** the workload carries `kubeagents.x-k8s.io/reliability-audit: exempt` as a label or annotation.
- **S5 — not running:** `spec.replicas == 0`, or the workload is a Job/CronJob or is owned by one. **3.12 and 3.15 are the two checks S5 does not bind**, and only for CronJobs. S5 exists because a Job has no replica count, no PDB, and no HPA, so the template-reading checks have nothing to say about one; it was never a judgement that a schedule is beneath this audit's notice. 3.12 and 3.15 ask the reliability questions a CronJob can answer — is it still producing anything, and do its runs pile up — and read `status` and retained Jobs, not a pod template. Of the other four exclusions, S1, S2 and S4 bind it unchanged — a namespace and a label mean the same thing on a CronJob as on a Deployment — and only S3 does not, because it would drop every CronJob in the fleet: a CronJob is owned by nothing.

**Evidence discipline for the manual fallback.** The dump is the _detector_; a live single-object read is the _confirmer_. For a candidate you could not get from the collector, run the object-scoped command below, capture a trimmed excerpt, and store that exact string in `evidence.command`. If the confirm command fails or the condition no longer holds, **drop the finding — do not soften it.** A candidate the collector _did_ produce needs no confirm read: `finish` replaces both evidence fields with the collector's computed pair before publishing, so the object-scoped command you ran is not the one the ledger shows. Fill the two fields from the manifest instead — the candidate's own `excerpt`, and the `commands` entry for that check on that cluster — and the document says what the ledger will.

```bash
KUBECONFIG=$KC kubectl get <kind> -n <ns> <name> -o yaml
```

**Never paste a credential into an excerpt.** A Secret's `data:` block, a token, a kubeconfig, or a private key — including one sitting in a container's `env` — must never reach `evidence.excerpt`. Re-run the confirm read with a field selector or an `-o jsonpath` that omits it (`-o jsonpath='{.spec.template.spec.containers[*].name}'`). The harness redacts high-confidence credential shapes as a backstop, not as the primary control.

If one check yields more than 25 findings in a single cluster, roll the surplus into one namespace-level finding per namespace: same severity, and a namespace-scoped confirm command (`kubectl get <kind> -n <ns> -o yaml`). Give the roll-up the scope it covers as its `object` — `Namespace/<ns>`, nothing more — so its identity is that scope; put the workload count in the `title` and the workload names in `evidence.excerpt`, never in `object`, because the count moves the moment a workload is added and an `object` that moves renames the finding. The individual findings it replaces are not also emitted, so nothing collides. The cap is about reviewer attention, not about a byte limit: the harness caps the rendered issue body at 60,000 characters, trims each excerpt to 40 lines / 2,000 characters and the scope tables to 60 rows, and on a large fleet drops findings from the description least-severe-end first and says in the body that it did — while the title's counts stay the true totals. A fleet that has never set requests still gets counted honestly; it just should not spend the whole body saying so.

**Finding identity.** **Do not write an `id`.** The harness derives it from `check`, `cluster`, `namespace` and `object`, and ignores any `id` in the file. `check` is the backticked slug in the check's heading below; a slug outside this SOP's roster is rejected.

Identity is only as stable as those four fields, so **never** let a timestamp, replica count, image tag, pod name, or resource value into `object` — audit the owning controller, never the pod, whose name carries a random suffix. A finding whose identity moves between runs is announced as fixed and re-announced as new, and the delta the ledger exists to produce becomes noise. Two findings agreeing on all four fields are one finding, and the harness refuses the document rather than collapsing them silently.

#### 3.1 No CPU or memory request (`no-requests`)

**This check owns the _absence_ of a request and nothing else.** The **value** of a request belongs to the Fleet Waste Audit (`fleet-wide-cost-analysis` check 3.1, `overrequest`), which has the usage samples this audit does not collect. Never propose a number here: two audits sizing the same container in opposite directions makes each run flag the state the other just created.

- **Command:** derived from `$STATE`; confirmed with the object-scoped read above.
- **Flag when:** any container in `spec.template.spec.containers[]`, or any native sidecar (`initContainers[]` with `restartPolicy: Always`, which counts toward the pod's effective request), declares **no** `resources.requests.cpu` or **no** `resources.requests.memory`.
- **Do NOT flag:** standard exclusions; plain init containers; any container whose namespace has a `LimitRange` with a matching `spec.limits[].defaultRequest` (the request is injected at admission, so there is nothing to fix); **a request that exists but looks wrong** — too large, too small, or copied from a template. Whether a declared request is the right size is the waste audit's question, not this one.
- **Severity:** `major` (`minor` on Autopilot). The scheduler treats an unrequested container as free, so this corrupts bin-packing for every other workload on the node, not just this one.
- **Impact:** "the first evicted under node pressure" is a claim about QoS class, and the flag-when above is an **or** — so most of what this check catches is not the class that sentence describes. The collector computes the pod's real class and writes the matching Impact itself, so the sentence arrives already matched; state it as given rather than re-deriving it. All three arms below are written on the candidate and marked authoritative, so `finish` restores the collector's sentence over anything a run publishes in its place — rewriting one costs the rewrite, not the finding. What it writes, by class:

  - **BestEffort** — no container declares a cpu or memory quantity above zero. The check's own sentence holds unchanged: "The scheduler and cluster autoscaler size this cluster as if this workload costs nothing; its pods are the first evicted under node pressure and its cost cannot be attributed." An extended resource on its own (`nvidia.com/gpu`, `ephemeral-storage`, `hugepages-*`) does not lift a pod out of this class, and neither does an explicit `0`.
  - **Guaranteed** — every container carries a cpu **and** a memory limit above zero with a request equal to it. A missing request is copied from its own limit, so a container declaring limits alone qualifies: nothing is unreserved and the pod is reserved at its ceiling. Still a finding, because this check wants the request declared rather than inferred from a ceiling, but the cost is held headroom and an unreviewed reservation, not free scheduling.
  - **Burstable** — everything else: a user-namespace workload declaring a cpu request and no memory request, or one whose sibling container carries no ceiling. The ubiquitous examples of the shape, `kube-proxy` and `antrea-controller`, are **not** among them — they are in `kube-system`, which S1 drops before this check runs, so no finding for either can exist.

  The class belongs to the **pod**, not to the container the finding names. A sibling carrying no limits makes a limit-backed container's pod Burstable, and a plain init container's requests count toward the class even though they never count toward the flag-when above — QoS reads `containers[]` plus **all** of `initContainers[]`, where the flag-when reads native sidecars only.

  Two things the Impact deliberately does not say, both because they replace one false eviction claim with another. It never says a Burstable pod is evicted after a BestEffort one: the kubelet does not rank by class, it sorts on whether usage exceeds requests and then on Pod Priority, so a pod with no memory request sits in the same first group as a BestEffort one — and an unreserved **cpu** request does not affect eviction at all. And it never says the _pod_ is sized without a resource when a single container is missing it, because a sibling's limit can supply it; that sentence is scoped to a container.

- **Remediation:** `kind: manual`, always. Action: "Declare an explicit `resources.requests.cpu` and `resources.requests.memory` on this container." Note that the size comes from the Fleet Waste Audit's usage sampling or from the owner's own observation (`kubectl top pod -n <ns>`) over a representative window, and that this audit deliberately proposes no figure. **Never invent a request value, and never derive one from the container's limits** — a limit is a ceiling the owner chose, not a steady-state size.

#### 3.2 No memory limit (`no-memory-limit`)

- **Command:** derived from `$STATE`; confirmed with the object-scoped read.
- **Flag when:** a container has no `resources.limits.memory`.
- **Do NOT flag:** standard exclusions; namespaces whose `LimitRange` sets a `default.memory`; **missing CPU limits, ever.** Omitting a CPU limit is a deliberate and widely recommended choice — it avoids CFS throttling — and flagging it would make this audit noise.
- **Severity:** `major` (`minor` on Autopilot, which sets every container's limits from its requests at admission, so the platform bounds what the manifest leaves open). Nothing bounds the container, so a leak runs until the node is under memory pressure and the kubelet starts terminating pods there — this workload's or a neighbour's, depending on the arm below.
- **Impact:** who the leak lands on depends on whether the same container declares a memory **request**, and the two arms point in opposite directions. The collector reads the request and writes the matching sentence itself, marked authoritative, so it arrives already matched — state it as given rather than re-deriving it. What it writes:

  - **No memory request either** — the leak makes this workload the node's first casualty, not its neighbours'. The kubelet ranks a memory-pressure eviction by whether usage exceeds the memory request, then by Pod Priority, then by how far usage sits above that request; a request of zero is exceeded by the first byte, so the pod is in the first group from the start and at equal priority the leak ranks it ahead of the BestEffort pods beside it. This is the arm nearly every real finding lands on.
  - **A memory request declared** — up to that request the kubelet does evict co-located workloads first, and past it the pod joins the group evicted first, ranked by the overage. The kernel's OOM killer scores a container down in proportion to its memory request, so the larger the request the more of the node a leak can take before the kernel picks it over a neighbour.

  Two things the Impact deliberately does not say. It never ranks eviction by QoS class — the kubelet's sort takes no QoS input, and `pod-qos.md` upstream still says otherwise (kubernetes/kubernetes#129759 has that contradiction open), so both arms name the sort keys rather than asserting an order a reader can find an official page against. And it never describes an OOM kill as an eviction: the kernel kills a **container**, which the `restartPolicy` may restart, where the kubelet evicts a **pod**.

- **Remediation:** if `resources.requests.memory` is set, emit `kind: manifest` (subject to §4's declaration rule) setting `limits.memory` to that same declared request, and state in `note` that this is the conservative reading of the owner's own request — no invented number — and needs owner sign-off. **Do not claim it yields Guaranteed QoS**: that also requires a cpu limit equal to the cpu request on every container in the pod, which these workloads do not have, so the class is unchanged unless the whole pod already qualifies. If no memory request exists either, the finding is already covered by 3.1 — emit `kind: manual` and cross-reference it.

#### 3.3 Multi-replica workload with no PodDisruptionBudget (`no-pdb`)

**This audit owns PodDisruptionBudgets** — both their absence (here) and their shape (3.4). The Fleet Waste Audit (`fleet-wide-cost-analysis` check 3.8) defers to these two and reports only the non-PDB reasons a node cannot be drained, so one PDB never carries two verdicts in two ledgers.

- **Command:** derived from `$STATE`; confirmed with the object-scoped read.
- **Flag when:** a Deployment or StatefulSet has `spec.replicas >= 2` and no PDB in the same namespace whose `spec.selector` matches `spec.template.metadata.labels`. Evaluate the selector properly (`matchLabels` **and** `matchExpressions`); never match on names.
- **Do NOT flag:** standard exclusions; **DaemonSets** (a drain deletes DaemonSet pods rather than rescheduling them — a PDB finding on a DaemonSet is nonsense and would be the fastest way to get this audit switched off); workloads with `spec.replicas <= 1`.
- **Severity:** `major`. The upgrade still completes; the workload is simply taken fully offline while it does.
- **Impact:** "Nothing constrains the eviction API, so a single node drain during an upgrade can terminate every replica at once."
- **Remediation:** `kind: manifest`. Generate a PDB with `maxUnavailable: 1` whose `spec.selector` **reproduces the workload's `spec.selector` exactly — every `matchLabels` entry and every `matchExpressions` term**, copied verbatim from the live object. Always `maxUnavailable`, **never** `minAvailable` — `minAvailable` is the shape that deadlocks drains (see 3.4), and `maxUnavailable: 1` is structurally safe at any replica count ≥ 2.
- **Never emit a PodDisruptionBudget whose `spec.selector` is empty or absent.** In `policy/v1` an empty selector matches **every pod in the namespace**, so the budget you meant for one Deployment governs evictions for all of them and can stall every drain there, node upgrades included. A workload selected purely by `matchExpressions` is the trap: copy only `matchLabels` and you emit `selector: {}`. If you cannot reproduce the workload's selector exactly — a term you cannot read, an operator you cannot represent — the finding degrades to `kind: manual` naming the selector the owner must supply. Guessing is not an option here.

#### 3.4 Drain-blocking PodDisruptionBudget (`blocking-pdb`)

- **Command:** derived from `$STATE`; confirmed with `kubectl get pdb -n <ns> <name> -o yaml`, whose `status` block is the corroborating excerpt.
- **Flag when:** a PDB has `maxUnavailable: 0` or `maxUnavailable: "0%"`; or `minAvailable` as an integer `>=` the matched workload's **floor**; or a percentage `minAvailable` that resolves to the whole floor. Where one PDB selects the pods of more than one workload, the floor is theirs together, since the disruption controller counts every pod the budget selects: two Deployments of two under `minAvailable: 2` leave two evictions. Corroborate with `status.expectedPods > 0 && status.disruptionsAllowed == 0`, but decide on the spec — status alone is transient when a pod is briefly unready.
- **Resolve a percentage `minAvailable`; do not read it as one.** Kubernetes computes `desiredHealthy = ceil(pct / 100 × expectedCount)`, rounding **up**, so `minAvailable: "75%"` over three replicas is a desiredHealthy of 3 and permits zero evictions — the identical hard block that `minAvailable: 3` produces, written in the spelling people reach for precisely because it looks proportional and therefore safe. Two corollaries worth stating because they read as surprising: every non-zero percentage over a floor of 1 blocks, since `ceil` of any fraction of 1 is 1; and `"100%"` is not a special case, just the one where the arithmetic is obvious. Put the arithmetic in the excerpt — `minAvailable 75% of 3 resolves to desiredHealthy 3` — because a reader who has not done the rounding in their head will read the finding as wrong. `maxUnavailable` percentages round up too, which is the safe direction, so only the `"0%"` literal above matters there.
- **The floor is `spec.replicas`, unless a HorizontalPodAutoscaler owns that field — then it is the autoscaler's `minReplicas`, defaulting to 1 when unset.** `spec.replicas` on an HPA-managed workload is a reading of what the autoscaler wanted when the dump was taken, not a number anybody wrote, and comparing against it answers "is a drain blocked at this instant" when the question is "can these two manifests block a drain at all". The audit reads at 06:50 UTC, when a `minAvailable: 3` against five replicas looks safe; the drain that has to succeed is the 03:00 node upgrade, when the autoscaler is at its floor of 2 and the eviction API refuses every pod. 3.22 makes the same correction to 3.11's reading of the same field for the same reason. Read the floor off the HPA's `scaleTargetRef` match — same `apiVersion`, `kind` and `name` — and say so in the excerpt, because a reader looking at a live `replicas: 5` will otherwise think the finding is arithmetic that does not add up.
- **Do NOT flag:** S1 and S2; a PDB whose `minAvailable` is genuinely below the target's floor; a PDB matching a workload scaled to zero (`status.expectedPods == 0` — there is nothing to evict, so no drain is blocked); orphan PDBs matching no workload at all (harmless, and reported at most as a `minor` config-rot finding), which includes a PDB selecting only DaemonSet pods, since a drain skips or deletes those rather than evicting them; and the integer `minAvailable` of a PDB whose selector also reaches a DaemonSet's pods beside a scalable workload, because those pods count toward the floor as slack and their number (one per eligible node) is unread — though `maxUnavailable` and a percentage `minAvailable` there **are** flagged, since the disruption controller needs a scale subresource on every selected pod's controller to count them, a DaemonSet has none, and it then permits no evictions (say so in the excerpt); a PDB with no `selector` at all, which selects no pods under `policy/v1` — only an empty `selector: {}` selects every pod in the namespace — and so neither blocks a drain nor satisfies 3.3 for any workload.
- **Read S1 and S2 off the PDB, not off the workload it selects.** A blocking PDB in `kube-system` or a `gke-managed-*` namespace really does wedge every drain and is still not the operator's to edit, so a `critical` naming it is a finding nobody can close — the reason 3.6 records. S2 is the one that changes an outcome: an addon's PDB can carry `addonmanager.kubernetes.io/mode` while the workload it selects does not, so the marker has to be looked for on the budget itself.
- **Severity:** `critical`. This is the highest-value finding in the audit and the one most often missed. It does not degrade a workload — it stops the cluster's entire lifecycle.
- **Impact:** "Blocks every node drain in this cluster indefinitely: node-pool upgrades, node auto-repair, and autoscaler scale-down all stall until a human deletes or edits this PDB."
- **Remediation:** if the matched workload's floor is 2 or more, emit `kind: manifest` (subject to §4's declaration rule) rewriting the PDB to `maxUnavailable: 1`, its `spec.selector` carried over from the live PDB unchanged — 3.3's empty-selector prohibition applies here too. If the floor is 1 and the budget resolves to a desiredHealthy of 1 — `minAvailable: 1`, or any non-zero percentage, which comes to the same thing — emit `kind: manual`: the PDB is doing exactly what it says, and the real fix (run more than one replica) is the owner's call, not a config change. **Unless an autoscaler put it there:** a floor of 1 under a `maxReplicas` above 1 is 3.22's finding as well, and there the owner has already licensed concurrent copies, so `maxUnavailable: 1` is a manifest fix rather than a request to re-architect. Say in `recommendation.risk` that at the floor it permits the last pod to be evicted, which is the trade — a budget that wedges the cluster protects nothing, and 3.22's own remediation raises the floor that made this a choice.

#### 3.5 Deployment with `replicas >= 3` and no HorizontalPodAutoscaler (`no-hpa`)

- **Command:** derived from `$STATE`; confirmed with the object-scoped read.
- **Flag when:** a Deployment has `spec.replicas >= 3` and no HPA in the namespace whose `spec.scaleTargetRef` resolves to `{apiVersion: apps/v1, kind: Deployment, name: <name>}`.
- **Do NOT flag:** standard exclusions; **StatefulSets** (horizontal autoscaling of stateful members is rarely safe and is an owner decision); DaemonSets; workloads already fronted by a KEDA-generated HPA — KEDA creates a real `HorizontalPodAutoscaler`, so the selector match above already covers them.
- **Severity:** `minor`. A fixed replica count is a capacity decision, not a fault; nothing breaks during an upgrade. Ranking it below 3.3 and 3.4 is the point.
- **Impact:** "Capacity is pinned at a hand-chosen number: the workload cannot absorb a traffic spike and cannot give capacity back when idle."
- **Remediation:** `kind: manual`. `minReplicas` can be taken from the observed count, but `maxReplicas` and the utilisation target cannot be derived from anything this audit can read — emit guidance ("set `minReplicas` to the current <n>; choose `maxReplicas` and the CPU target from the workload's own headroom requirements; a CPU request is a prerequisite for utilisation-based scaling") rather than a manifest full of invented numbers.

#### 3.6 HPA that cannot scale (`hpa-cannot-scale`)

- **Command:** derived from `$STATE`; confirmed with `kubectl get hpa -n <ns> <name> -o yaml`.
- **Flag when:** (a) `spec.minReplicas == spec.maxReplicas`; or (b) `spec.scaleTargetRef` names an `apps/v1` Deployment or StatefulSet absent from the dump, unless `status.conditions[type=AbleToScale].status` is `"True"` — the controller resolved the target, so the gap is the dump's.
- **Do NOT flag:** standard exclusions; any HPA carrying `ownerReferences`, KEDA's `ScaledObject` included — this is a wider exclusion than S3 and applies only here, because the `min`/`max` on such an HPA is a copy its operator writes from a CRD this audit cannot read, so grading it grades a projection rather than the configuration; HPAs whose target exists but is a kind outside the dump — the cluster was readable, so it stays in `scope.clusters`; note the unevaluated targets in that cluster's `limitations`, never as a finding.
- **Severity:** (a) `major` — the workload is pinned _and_ the admin believes it is autoscaled, so the HPA silently overrides the Deployment's own `replicas`. (b) `minor` — dangling config rot; nothing is currently degraded.
- **Impact:** (a) "An HPA is attached but `min == max`, so this workload cannot scale in either direction — the autoscaling is cosmetic." (b) "This HPA targets an object that no longer exists and autoscales nothing."
- **Remediation:** `kind: manual` for both. Widening a range and deleting a stale object are owner decisions, and this repo's manifest path cannot express a deletion.

#### 3.7 Rigid scheduling constraints (`rigid-scheduling`)

- **Command:** derived from `$STATE`; confirmed with the object-scoped read.
- **Flag when:** `spec.template.spec.nodeSelector` contains `kubernetes.io/hostname`; or `nodeSelector` pins `topology.kubernetes.io/zone` to one zone; or a `nodeAffinity.requiredDuringSchedulingIgnoredDuringExecution` term restricts `kubernetes.io/hostname` or `topology.kubernetes.io/zone` to exactly one value with operator `In`. A `NotIn` term excludes a node or zone and pins nothing.
- **Do NOT flag:** standard exclusions; zone terms listing two or more `values` (deliberate and healthy); `preferredDuringScheduling…` (soft, never blocks scheduling); hardware selectors — `cloud.google.com/gke-accelerator`, `cloud.google.com/machine-family`, `cloud.google.com/compute-class`, `cloud.google.com/gke-spot` — which are legitimate requirements, not rigidity; StatefulSets with `spec.volumeClaimTemplates` bound to zonal storage, which are _correctly_ zone-pinned by their disks.
- **Severity:** hostname pin → `critical` (with node auto-upgrade the node is guaranteed to be replaced, so this is a scheduled outage). Single-zone pin → `major`.
- **Impact:** hostname — "This pod cannot be rescheduled; the next node upgrade or repair takes it down and it does not come back." Zone — "Pinned to one zone: a zonal stockout or zonal outage takes this workload down while capacity sits unused in the other two."
- **Remediation:** `kind: manual` for both. A pin usually encodes an assumption (node-local state, a zonal disk, a licence) that this audit cannot see, and blindly stripping a scheduling constraint is how an audit causes an incident. Guidance: replace the pin with a compute class plus topology spread (see the `gke-compute-classes` skill).

#### 3.8 Multi-replica workload with no spreading (`no-spread`)

- **Command:** derived from `$STATE`; confirmed with the object-scoped read.
- **Flag when:** `spec.replicas >= 2` and `spec.template.spec.topologySpreadConstraints` is absent or empty **and** there is no `podAntiAffinity` (required or preferred) keyed on `kubernetes.io/hostname` or `topology.kubernetes.io/zone`.
- **Do NOT flag:** standard exclusions; DaemonSets (one pod per node by construction); workloads that already have either mechanism.
- **Severity:** `minor`. kube-scheduler applies best-effort default spreading, so co-location is possible rather than certain — but the default skew tolerance is wide enough that a small Deployment can still land entirely on one node.
- **Impact:** "Nothing guarantees these replicas are on different nodes; losing one node can take the whole workload out despite the replica count."
- **Remediation:** `kind: manifest` (subject to §4's declaration rule). Add a single `topologySpreadConstraints` entry: `maxSkew: 1`, `topologyKey: kubernetes.io/hostname`, `whenUnsatisfiable: ScheduleAnyway`, `labelSelector` reproducing the workload's own `spec.selector` in full — `matchLabels` and `matchExpressions` both, as in 3.3. `ScheduleAnyway` is mandatory here — `DoNotSchedule` can make a workload unschedulable, which is a worse outcome than the finding.

#### 3.9 Missing readiness probe (`probes-readiness`)

- **Command:** derived from `$STATE`; confirmed with the object-scoped read.
- **Flag when:** the workload's pod labels are selected by a `Service` in the same namespace (a metrics-only one is set aside when a serving Service also selects them) and a container **in that Service's path** has no `readinessProbe` — the container declaring a port the Service targets, reading native sidecars (`initContainers` with `restartPolicy: Always`) alongside `containers` because they serve ports too. Where nothing in the pod declares a matching port there is no routing to infer and every container is in the path.
- **Do NOT flag:** standard exclusions; workloads no Service selects (nothing routes to them); Services of `type: ExternalName` or with no `selector`; injected sidecars that manage their own readiness (`istio-proxy`, `cloud-sql-proxy`, `gke-metadata-server`); **a container the Service does not route to** — a probe-less log shipper counts as ready the moment it starts and cannot hold traffic off a pod either way, so only the container holding the port can be the risk this check names. On the live fleet that is `fluent-bit` beside the gateway's `platform-agent`, whose own probe is the one that gates the Service.
- **Severity:** `major`.
- **Impact:** the trailing scope on the candidate's `selecting services:` line decides the sentence, and **only `(serving traffic)` licenses a claim about user requests:** "Every rollout sends production traffic to pods that are not yet serving, and a broken new version is never detected as broken." Under any other scope that sentence is false and you must not write it — including a scope not named here, which takes the other branch rather than this one. `(metrics scrape only)` means every port every selecting Service exposes is a Prometheus scrape port, so no user request reaches it and Prometheus retries a scrape it missed; `(no ports declared)` means those Services expose no port at all, so nothing routes through their ClusterIPs. For both, say instead: "Rollouts and node drains report success as soon as the container starts, before it can do its job, and a broken new version is never detected as broken." Keep the severity at `major` — the rollout and PDB-availability consequences are the same either way — and title the finding for what the exposure line says it is (`has no readiness probe behind its metrics Service`, `has no readiness probe behind a port-less Service`), not `is Service-backed`.
- **Remediation:** `kind: manual` unless the excerpt carries a `readiness derivable from the liveness probe:` line, in which case `kind: manifest` subject to §4's declaration rule. A probe's path, port, and timings are application knowledge, so **do not generate probe YAML** — except from a liveness probe the container already declares, which is the one handler the kubelet is provably already calling and the application provably already answering. The collector writes that line only when **every** container it named as missing readiness has one, because a patch covering some of them leaves this finding open on the rest. Copy the handler verbatim and take the `initialDelaySeconds`, `periodSeconds` and `failureThreshold` the line gives: they are chosen to fail inside the liveness deadline, so the pod leaves the Service before the kubelet restarts it. Do not round them towards the liveness figures — equal deadlines are §3.18, and closing this finding by opening that one on the same container is not a fix.

#### 3.10 Missing liveness probe (`probes-liveness`)

- **Command:** derived from `$STATE`; confirmed with the object-scoped read.
- **Flag when:** a container has no `livenessProbe`.
- **Do NOT flag:** standard exclusions; injected sidecars that manage their own health (`istio-proxy`, `cloud-sql-proxy`, `gke-metadata-server`).
- **Severity:** `minor`, always. This check and 3.9 are deliberately separate and are **not** equivalent: a missing liveness probe is frequently the _correct_ choice — a badly tuned one causes restart storms — so it is reported as information, not as a defect. A workload missing both probes is one finding here and one under 3.9, never a single merged finding: they carry different severities, different impacts, and the harness derives a finding's identity from its check, so merging them would silently drop one.
- **Impact:** "A wedged process is never restarted automatically; recovery requires a human."
- **Remediation:** `kind: manual`, always. A probe's path, port, and timings are application knowledge; a generated `/healthz` probe would break the workload the moment it was applied. **Do not generate probe YAML.** The mirror of 3.9's exception does not hold here and must not be added: a readiness handler is safe to copy into a liveness probe only if you know the workload cannot fail readiness for a reason a restart makes worse, and the severity above says why it is not worth finding out — the probe this would add is one that is frequently better absent.

#### 3.11 Single-replica Service-backed Deployment (`single-replica`)

- **Command:** derived from `$STATE`; confirmed with the object-scoped read.
- **Flag when:** a Deployment has `spec.replicas == 1` and a `Service` in the namespace selects its pods.
- **Do NOT flag:** standard exclusions; StatefulSets (a single-member StatefulSet is usually intentional and often disk-bound); Deployments with `strategy.type: Recreate`, which explicitly declares that two copies must never run at once; workloads carrying the S4 opt-out label, which is the sanctioned way for an owner to say "this is meant to be one replica"; and **any Deployment a HorizontalPodAutoscaler targets**, where both halves of this finding are wrong — the `1` is a snapshot the autoscaler will overwrite rather than a declaration, and the remediation below answers a question the owner settled when they let a controller add replicas unattended. 3.22 reports those off the floor instead.
- **Severity:** `minor`. This is a known-cost design decision, not a misconfiguration.
- **Impact:** "Zero-downtime is impossible: every rollout, node drain, and node repair is a full outage for this service." — **only when the candidate's `selecting services:` line ends in `(serving traffic)`**, the positive test 3.9 uses and for the same reason: under any other scope there is no user traffic to drop. Under `(metrics scrape only)` say instead: "Every rollout, node drain, and node repair leaves this workload's metrics unscraped until the replacement pod is up, so its own dashboards and alerts go blind across the gap." Under `(no ports declared)` say that the gap is in whatever reaches these pods by DNS, which this audit cannot see. Keep the severity at `minor` and do not title the finding for user-facing downtime.
- **Remediation:** `kind: manual` by default. Going HA touches leader election, session handling, and storage, and none of the three is readable off the object. One exception, and it is narrow: emit `kind: manifest` setting the replica key to `2` and changing nothing else where all three of these hold — the candidate carries a `release_declaration` with `renderer: helm`; `helm show values` (§4) lists a replica key that reaches the object _this_ finding names; and the file at `release_declaration.path` does not already set that key. Where the key is absent, name the key you looked for and stay `manual`.
- **Those three are mechanical preconditions, not evidence that a second copy is safe.** Say so. `helm create` scaffolds `replicaCount: 1` into every chart it generates, so a top-level replica key is frequently a default nobody deleted rather than a decision anybody made, and a remediation that tells the reader the chart author vouched for concurrency turns the one human gate this arm has into a rubber stamp. `recommendation.risk` must name the two failures the audit cannot see: a process holding state in memory, whose second copy answers from a different dataset with no crash and no alert, and a controller with no leader election, whose second copy does every side effect twice. Safety is the requester's judgement, exactly as 3.22 says.
- **The refusal direction is the sound one, and it is worth using.** A multi-component chart that keys some components and withholds the key for others is telling you something: `argo-cd` exposes `controller.replicas`, `server.replicas`, `repoServer.replicas` and `applicationSet.replicas`, and exposes no replicas key at all for `redis`, `dex` or `notifications` — `argocd-redis` runs `--save '' --appendonly no`, an unreplicated in-memory cache that must not simply be scaled. "The chart withheld the key, so stay `manual`" holds. "The chart exposed the key, so go" does not.
- **Three other things are not a licence either, and one of them looks like it.** `podAntiAffinity` and `topologySpreadConstraints` are not: a spread rule is a conditional — _if_ there are two copies, keep them apart — and one pod satisfies it legally and inertly. A **hand-written declaration** carrying `replicas: 1` is not, and it is the case that reads as most editable: somebody typed that number, which is the opposite of a chart default nobody overrode. Nor is a `renderer: kustomize` override, where there is no author who vouched for anything, only a base in another repository.
- **A workload mounting an exclusively-attachable claim is `manual`, whatever the chart exposes.** The collector appends `mounts an exclusively-attachable claim:` to the excerpt when it does. A second replica cannot schedule off the first one's node and sits in `ContainerCreating` with a `Multi-Attach error` indefinitely — that is 3.21's finding, whose fix is `Recreate`, on which this check then stops firing at all.
- **Set the chart's PodDisruptionBudget and topology-spread keys in the same override, where the chart has them.** Two replicas with no budget is 3.3, graded `major` — so a `/remediate` somebody asked for here manufactures a finding next run that nobody wanted. Two replicas with no spread rule is 3.8. `podinfo` exposes both `podDisruptionBudget.maxUnavailable` and `topologySpreadConstraints`, and the sibling namespace on this fleet already carries the pair of findings that proves the point. Where the chart exposes no such key, say in `recommendation.risk` which of the two findings is expected on the next run.
- **Severity stays `minor`, and that is load-bearing.** 3.22's reason exactly: the fix bills for a second pod around the clock, so it sits below the auto-promotion floor and waits for `/remediate`, where a repo writer has asked for it by name. Do not count a reviewer as a third gate — merge policy is each operator's choice and not this audit's to assume. Say in `recommendation.risk` what the second replica costs and that nothing else about the release changes.

#### 3.12 CronJob firing without succeeding (`schedule-never-succeeds`)

**One of the two checks here that read `status` rather than a pod template** — 3.15 is the other — and, with 3.15, one of the two S5 does not bind; see S5 for why. Most of §3 asks whether a workload is configured to survive something that has not happened yet. This one asks whether a schedule that is still enabled, still listed, and still firing on time has actually produced anything, which is a question no template answers.

- **Command:** derived from `$STATE`; confirmed with the object-scoped read.
- **Flag when:** a CronJob has `spec.suspend` unset or false, has a `status.lastScheduleTime`, retains at least one _finished_ Job — succeeded or failed, and no longer active; a Job still retrying after a failed pod has not finished — of which none succeeded, and `status.lastScheduleTime` is at least 24 hours later than `status.lastSuccessfulTime` — or, where the CronJob has never succeeded at all, than its own `metadata.creationTimestamp`.
- **The gap is between two recorded times, never against the clock.** Both ends come out of the dump, so the verdict is reproducible from the manifest that produced it; nothing else in this collector reads wall-clock time and this check does not start. A finding that would change depending on when the audit ran is one no reader can check.
- **The 24 hours is flat, and deliberately not scaled to the schedule's period.** The instinct is to give a weekly CronJob a week of grace and an hourly one an hour. That is backwards: the rarer the schedule, the more a single failure costs, because the next attempt is a week away rather than sixty seconds. A flat floor lets an hourly job fail twenty-four times before this says anything and reports a weekly job the day after its one failure, which is the right answer in both directions.
- **Do NOT flag:** standard exclusions S1, S2 and S4 — S4 is the sanctioned way to silence a CronJob whose owner knows it is failing and is not going to act, and it is the only way, since nothing about this finding can be fixed by editing the object's shape; a suspended CronJob, which is not trying; a CronJob with no `lastScheduleTime`, which has either not come due or is not being fired at all — the second is a scheduler fault this check would misattribute to the workload; a CronJob whose retained Jobs are all still active, since none has finished to have failed; **and any CronJob with a succeeded Job in its retained history**, which is what separates "failing" from "failed once". An active Job is counted as neither success nor failure rather than vetoing the check: an hourly schedule almost always has one in flight, and letting it veto would make the check unreachable on the schedules it most needs to cover.
- **The excerpt names the newest failed Job's `Failed` condition reason** where the Job carries one. `BackoffLimitExceeded` means the container exited non-zero and the fix is in the image or its arguments; `DeadlineExceeded` means the Job ran past `activeDeadlineSeconds` and the fix is usually that deadline or the schedule's period. That is the one fact deciding what the owner does next, the Job already records it, and without it the finding says a schedule stopped succeeding and sends the reader to `kubectl describe` for the rest. Only the newest of the retained Jobs: consecutive failures of one schedule almost always share a reason, so listing all three pads the excerpt without adding a fact.
- **Severity:** `major`. Not `critical`: nothing is being served badly and no traffic is being dropped. Not `minor` either — the defining property is that no other signal exists. A Deployment that stops working goes unready and shows up in every dashboard; a CronJob that fails every hour leaves three Error pods and a `lastSuccessfulTime` nobody reads, and the fleet stays green around it.
- **Impact:** "Whatever this schedule exists to do has not been done since its last successful run, and nothing reports that on its own: the CronJob is still listed, still enabled, and still firing on time."
- **Remediation:** `kind: manual`, always. Why a Job fails is in its pod's logs, which this audit does not read — so the fix cannot be derived from anything in the finding, and a manifest guessing at it would be a guess. Name the CronJob, the length of the outage, and the command that shows the reason (`kubectl logs -n <ns> job/<name> --tail=50`), and let the owner read it. **Where `reconciler` names a Helm release or a Config Connector object, say so in `recommendation.action`** — the fix belongs in that chart or manifest, and a pull request against the cluster's GitOps tree would be reverted on the next sync.

#### 3.13 Rollout drops in-flight requests (`rollout-drops-traffic`)

**The failure here happens on every deploy and leaves no trace on the object.** Deleting a pod starts two independent reactions at once: the kubelet begins terminating the container, and the endpoints controller begins propagating the removal out to every node's kube-proxy and to every mesh sidecar and Ingress holding a connection. The container wins that race almost every time, so requests keep arriving at a process that has already been sent `SIGTERM` and are answered with a connection reset. A `preStop` hook is the only thing in the pod lifecycle that delays `SIGTERM`, which is why the fix is a hook that sleeps rather than anything in the application.

- **Command:** derived from `$STATE`; confirmed with the object-scoped read.
- **Flag when:** a workload is selected by at least one Service whose exposure scope is `serving traffic`, and at least one container behind that Service's `targetPort` has no `spec.template.spec.containers[].lifecycle.preStop`. Deployments and StatefulSets additionally need more than one replica; DaemonSets are in scope with no replica test, since one pod per node is not the single-replica case — the other nodes keep serving while one rolls.
- **The narrowing is what makes this a finding rather than a lint rule.** Unnarrowed, the predicate "has no `preStop`" is true of very nearly every workload in any fleet, and a check that fires on everything has told the reader nothing. Three clauses cut it down: the `serving traffic` scope drops the workloads whose only Service is a metrics scrape endpoint, where Prometheus retries and a reset costs a gap in a graph rather than a user's request; the replica test drops the single-replica case, which has a hard outage on every rollout whatever its hooks do and which 3.11 already reports, so adding a hook there delays the outage rather than removing it; and reading only the containers behind the `targetPort` drops the log shippers and sidecars that are not in the request path and cannot reset anything.
- **Do NOT flag:** standard exclusions S1–S5; a workload with no selecting Service, or one whose Services declare no ports or only metrics ports; a single-replica Deployment or StatefulSet; containers in `_SELF_HEALTH_SIDECARS` (`istio-proxy`, `cloud-sql-proxy`, `gke-metadata-server`), which manage their own drain; and any container that already declares a `preStop`, whatever it runs — this check does not grade the hook's contents.
- **Severity:** `major`. Not `critical`: the workload is healthy between rollouts and the loss is bounded by how long a drain takes, so nothing is continuously broken. Not `minor` either — the cost is paid on every deploy, every node drain, every autoscaler scale-down, and every preemption, which on Spot capacity is continuous, and it lands on the client as an error rather than on any dashboard the owner watches.
- **Impact:** "Every rollout, node drain, and preemption resets the connections in flight to the terminating pod: the container is sent SIGTERM while the endpoint removal is still propagating, so requests arrive at a process that has already begun shutting down."
- **Remediation:** `kind: manifest` where the workload is declared, `manual` where it is not. The change is one block on each container named in the excerpt — a `preStop` that waits long enough for endpoint propagation to finish, with `terminationGracePeriodSeconds` raised above that wait if it is not already, since the grace period is the ceiling the hook runs inside and a hook longer than it is cut short. Read the current grace period off the excerpt rather than assuming the default. Do not touch the application's own shutdown handling: the hook exists precisely so that no code change is needed.
- **Write the hook as `lifecycle.preStop.sleep.seconds`, not as an `exec` that runs `sleep`.** The `exec` form is the one every example on the internet uses and it is the wrong default here, because it runs the command _inside the container_ and a distroless or scratch image has no shell and no `sleep` to run. The kubelet does not fail the pod over that — it records a `FailedPreStopHook` event and proceeds straight to `SIGTERM`, so the pull request merges, the behaviour does not change, and the finding goes quiet anyway on the next run because a `preStop` now exists and this check does not grade its contents. That combination is worse than leaving the workload alone: it spends a review, closes the finding, and fixes nothing, with nothing left in the ledger to say so. The native handler runs in the kubelet, needs nothing in the image, and cannot fail this way. It requires Kubernetes 1.30 or newer (1.29 accepts the field and prunes it, which fails silently in exactly the same way) — so where the target cluster is older, and only there, fall back to `exec` **and first confirm the image has a shell**, naming that check in `recommendation.risk`.

#### 3.14 Update strategy takes every replica down (`strategy-causes-downtime`)

**A total outage on every deploy, written into the object and invisible in every other reading of it.** `strategy.type: Recreate` tells the Deployment controller to delete all existing pods and only then create replacements, so a three-replica workload serves nothing from the first deletion until the first new pod passes readiness — an image pull plus a cold start. `RollingUpdate` with `maxUnavailable` at or above the replica count is the same instruction written the long way. Between rollouts the Deployment reports `Available`, the replica count is whatever the author intended, and the probes are correct; the outage lasts only as long as the rollout and leaves nothing behind but errors in a client's log.

- **Command:** derived from `$STATE`; confirmed with the object-scoped read.
- **Flag when:** a Deployment has more than one replica and either `spec.strategy.type: Recreate`, or a `RollingUpdate` whose `spec.strategy.rollingUpdate.maxUnavailable` resolves to at least the replica count. A percentage is resolved against the replica count and rounded **down**, matching Kubernetes' own rounding direction for `maxUnavailable`.
- **Nothing else in this audit reads `spec.strategy`, and 3.11 reads it only to stay quiet.** `single-replica` returns early on `Recreate` — a lone replica has an outage under any strategy, so naming the strategy there would be the wrong finding — and returns early again whenever the replica count is not one. A `Recreate` Deployment with three replicas therefore fell through both arms and was reported by nothing. This check is that gap.
- **Do NOT flag:** standard exclusions S1–S5; StatefulSets and DaemonSets, which have no `Recreate` strategy to set; a single-replica Deployment, for the reason above; and `maxUnavailable` merely being large — `2` of `3` is a deliberate speed-over-capacity choice that still leaves a pod serving. Only reaching the replica count is unambiguous, because at that point the strategy permits zero surviving pods.
- **Severity:** `major` where a Service with a `serving traffic` scope selects the workload, `minor` where none does. A rollout that drops every replica of something taking user requests is an outage; the same strategy on a workload nothing routes to is a latent one, waiting for the first Service to be pointed at it.
- **Impact:** "The update strategy permits every replica to be down at once, so a rollout is a full outage lasting until the first replacement pod passes its readiness probe -- an image pull plus a cold start."
- **Remediation:** `kind: manifest` where the workload is declared, `manual` where it is not. Replace the strategy block with a `RollingUpdate` carrying `maxUnavailable: 0` and `maxSurge: 1`, which are structurally safe at any replica count and need no value invented. **Check first whether `Recreate` was chosen on purpose**: a workload holding a `ReadWriteOnce` volume, or one whose two versions cannot run concurrently against the same schema, needs `Recreate` and needs the outage. Where the excerpt cannot rule that out, say so in `recommendation.risk` and let the owner decide — the read that settles it is whether the pod mounts a `ReadWriteOnce` PVC.

#### 3.15 CronJob runs pile up on each other (`cronjob-runs-overlap`)

**A schedule that takes longer to run than it waits to rerun.** `concurrencyPolicy: Allow` is the default, so it is almost always unstated, and it lets the controller start the next run whether or not the last one finished. That is harmless until a run outlasts its own period, and then every period adds a worker without removing one. The failure does not land on the CronJob: it lands on whatever the job talks to — connection-pool exhaustion on a database, duplicate rows from two copies of one import, a node's memory going to N copies of a batch process — which is why the CronJob looks healthy throughout and every retained Job reports `succeeded`.

- **Command:** derived from `$STATE`; confirmed with the object-scoped read.
- **Flag when:** a CronJob has `spec.suspend` unset or false, has `spec.concurrencyPolicy` either unset or set to `Allow`, retains at least three Jobs from which a period can be observed, and the longest completed run among those Jobs lasts at least as long as that period.
- **Measured from what the cluster recorded, never predicted from the schedule.** The period is the widest gap between consecutive retained Job `creationTimestamp`s, not a parse of `spec.schedule` — this collector has no business learning cron syntax, and a verdict resting on a hand-rolled cron parser fails in whichever direction the parser is wrong. The widest gap rather than the narrowest because retained Jobs are a sample with holes in it, and overestimating the period makes the check quieter rather than louder. A run's length is its own `status.startTime` to `status.completionTime`. So a hit says this schedule **has already overlapped**, not that its policy would allow it to — which is the whole difference between a finding and a lint rule, given that the permissive policy is the default and therefore describes most CronJobs anywhere.
- **Do NOT flag:** standard exclusions S1, S2 and S4, as for 3.12; a suspended CronJob; `concurrencyPolicy: Forbid` or `Replace`, both of which bound the pile-up; a CronJob retaining fewer than three Jobs, since two timestamps make one gap and one gap is a coincidence — a single retry would read as the period; and a Job that started but has not finished, which has no duration to measure and whose long runtime may mean wedged rather than slow.
- **Severity:** `major`. Not `critical`: the job itself is completing, and the damage is to a downstream the audit cannot see. Not `minor` — the overlap compounds with every period rather than staying constant, and the CronJob's own signals all read healthy while it does.
- **Impact:** "Runs of this schedule are piling up on each other: each period starts another copy without the last one having finished, so the load on whatever the job writes to grows until something there gives out."
- **Remediation:** `kind: manifest` where the CronJob is declared, `manual` where it is not. Setting `concurrencyPolicy` is a one-field change, but **which** value is a real decision and the finding must not make it: `Forbid` skips the overlapping run and loses that period's work, `Replace` kills the running one and loses the work in flight. Name both in `recommendation.action` with what each costs, and recommend the third option where the excerpt supports it — lengthening the schedule's period past the observed run time, which loses nothing. Where `reconciler` names a Helm release or a Config Connector object, say so, as 3.12 requires.

#### 3.16 A Service resolves to no pod (`service-selects-nothing`)

**A label query nothing validates, matching nothing.** A Service selects pods by label, and Kubernetes never checks that the selection is non-empty: the object admits, gets a ClusterIP, resolves in DNS, and answers every connection with a refusal that names the Service rather than the workload no longer behind it. Rename a Deployment's pod labels, move a workload to another namespace, mistype a value in a values file, delete the workload and leave the Service — all four produce an object indistinguishable from a healthy one. There is no event, no condition, and no status field that says so.

- **Command:** derived from `$STATE`; confirmed with the object-scoped read.
- **Flag when:** a Service has a non-empty `spec.selector`, is not `type: ExternalName`, and its EndpointSlices list no non-terminating address, ready or not.
- **Read from EndpointSlices, which is the cluster's own answer.** The alternative — re-implementing the selector match against the workload set — gets a different answer than the cluster does whenever a bare Pod is behind the Service, and gets the wrong answer on any workload the standard exclusions dropped. EndpointSlice rather than the v1 `Endpoints` API because that API is deprecated from Kubernetes 1.33, and a check written against a deprecated kind ships with an expiry date on it. Endpoints marked `conditions.terminating` do not count: a pod being drained during a rollout is still listed, and counting it would let a Service that genuinely resolves to nothing read healthy for as long as the last old pod takes to disappear. An address failing its readiness probe **does** count: the selector matched a pod, so this Service does not select nothing, and the only fix this check proposes — a corrected selector or a deleted Service — would be wrong for it.
- **Do NOT flag:** standard exclusions S1, S2 and S4, as for 3.12 — S3 deliberately not, because an operator-owned Service black-holes traffic exactly like a hand-written one and `reconciler` is what tells the reader the fix belongs in the operator's chart; a Service with no selector at all, which is the sanctioned way to point at hand-managed endpoints outside the cluster and has no query to be wrong; `type: ExternalName`, a DNS alias with no endpoints by construction; and a Service whose selector matches a workload deliberately at `spec.replicas: 0`, which is parked rather than broken. Headless Services are **not** excluded: `clusterIP: None` still selects pods and still resolves to their addresses, so one selecting nothing breaks its clients the same way.
- **Severity:** `critical` for `LoadBalancer` and `NodePort`, `major` for everything else. An externally published address with no backends is a black hole something outside the cluster is already pointed at — DNS, a CDN origin, a partner's allowlist — and is already failing for someone who cannot see the cluster. A ClusterIP with no backends breaks its in-cluster callers, which is bad but bounded by who knows the name.
- **Impact:** "This Service resolves to no pod, so every caller that reaches it -- by DNS name, by cluster IP, or through whatever is pointed at its external address -- has its connection refused. The Service object itself stays healthy, which is why nothing has reported this."
- **Remediation:** `kind: manifest` where the Service is declared, `manual` where it is not. **The fix is a judgement, not a template, and the finding must not pretend otherwise.** There are three shapes and the excerpt alone does not distinguish them: the selector is wrong and should match a workload that is running; the workload is gone and the Service should go with it; or the workload was never deployed to this cluster and the Service arrived ahead of it. Read the namespace's workloads and their pod labels before writing anything — where exactly one workload's labels are a near-miss for the selector, correct the selector to match it and say in `recommendation.risk` which workload you matched and on which label; where the namespace holds no candidate at all, propose deleting the Service and say plainly that you could not find a backend, because a deletion the reviewer has to judge is more honest than a selector you guessed. **Never invent a selector value that matches nothing you have read.** That edit merges, silences this check permanently — a Service pointing at a second wrong label still has no endpoints, but so does one nobody has looked at since — and leaves the outage exactly where it was.
- **Where the Service is the one this check found and a workload nearby is the one 3.13 or 3.14 found, they are the same incident and separate findings.** Do not fold them: the Service edit and the workload edit go to different objects, and a reader who sees only one of them still needs the other.

#### 3.17 A Service asks for a port name no container declares (`service-port-unresolved`)

**3.16's near miss, and the one that survives review.** A `targetPort` written as a name is resolved against the pod's `containerPort` names. Where no container declares that name, the endpoint-slice controller drops the port from the slice rather than guessing, kube-proxy programs nothing for it, and the Service refuses on that port. Everything a reader would check says healthy: the selector matches, the pods are Running, the EndpointSlices list their addresses, and `kubectl get endpoints` prints them. A rename does it — a container port renamed `web` to `http`, a chart whose Service and Deployment templates read the name from two different values, a port declaration deleted as tidying — and the file that changed is almost never the Service.

- **Command:** derived from `$STATE`; confirmed with the object-scoped read.
- **Flag when:** a Service port's `targetPort` is a **string**, the Service has at least one non-terminating endpoint, and no EndpointSlice for it carries a port entry under that service port's name.
- **The absent port entry is the controller's own verdict, not an inference.** `getEndpointPorts` skips a service port whose name it cannot find on the pod; it never writes the entry with a null number. So a service-port name missing from the slices is the controller saying it could not resolve it, on the same evidence kube-proxy programmed from.
- **Do NOT flag:** everything 3.16 excludes, on the same grounds; a numeric `targetPort`, which cannot fail this way at all — `containerPort` is informational and traffic goes to the number whether or not any container declares it, so flagging a number would report every Service that omits a redundant declaration; and a Service with no non-terminating endpoints, which is 3.16's finding and not this one.
- **It under-reports a partial failure on purpose.** The controller groups pods by the ports they resolve, so a Deployment mid-rename with old and new pods both up produces two slices, one carrying the port and one not. The union reads as resolved and this check stays quiet, even though half the callers are failing. A check that fired during every rolling update of every renamed port would be switched off within a week, and a check nobody trusts reports nothing at all.
- **Severity:** `critical` for `LoadBalancer` and `NodePort`, `major` for everything else, for 3.16's reasons exactly.
- **Impact:** "This Service asks for a port by a name none of its pods declare, so the endpoint controller left that port out and kube-proxy programmed nothing for it. The pods are up and the Service lists their addresses, so every check anyone would run says it is healthy while the port refuses."
- **Remediation:** `kind: manifest` where the Service is declared, `manual` where it is not, and **the excerpt already carries the answer** — it names the port the Service asked for and every port the workload behind it declares. Two edits close it and they are not interchangeable. Where the workload declares a port that is plainly the same one under another name, correct the Service's `targetPort` to it and say in `recommendation.risk` which name you matched and on which workload. Where the workload declares no ports at all, the Service is not the file to change: adding the `name`/`containerPort` pair to the workload is the fix, and the finding should target that manifest instead. **Do not "fix" this by replacing the name with a number you read off the container.** It works, and it deletes the indirection the name existed for, so the next rename breaks the Service silently again with nothing left to catch it.

#### 3.18 A liveness probe that fires before its readiness twin (`liveness-preempts-readiness`)

**Two responses to one signal, and the destructive one wins.** Where a container's liveness and readiness probes carry the **same handler**, they test the same thing and can only ever fail together. Kubernetes runs them independently, so which response happens — stop routing, or restart — is decided by whichever deadline arrives first. When liveness's is the shorter or equal one, the readiness probe is decoration: it cannot take the pod out of the Service before the container is killed out from under it. A slow dependency then restarts every replica at once, and the restarts keep the dependency from recovering. The two probes usually arrive this way honestly, one `/healthz` copied into both blocks with the timings left at their defaults.

- **Command:** derived from `$STATE`; confirmed with the object-scoped read.
- **Flag when:** a container declares both probes, `_probe_handler` reads the same `(kind, body)` from each, and liveness's `initialDelaySeconds + failureThreshold x periodSeconds` is **less than or equal to** readiness's.
- **Do NOT flag:** standard exclusions S1–S5; the self-health sidecars §3.9 and §3.10 already skip; a shared handler where liveness has real headroom, which is the _documented_ way to serve both probes from one endpoint and is the majority of matching pairs — on the fleet this check was written against, the deadline comparison cut nine matching pairs to four; and a liveness probe stricter than readiness on a **different** handler, which fails the same way but may be the correct shape (a local liveness endpoint beside a dependency-aware readiness one), and the collector cannot tell that apart from a mistake.
- **The deadline arithmetic is approximate, and only ever used as a comparison.** The kubelet's first check lands somewhere inside the first period and a timing-out probe costs `timeoutSeconds` on top, so neither number is the wall-clock truth. Both probes are approximated identically, which is all the rule needs. Do not publish either figure as a measurement — the excerpt writes them with `~`.
- **Severity:** `major`. It is a latent failure: nothing is broken until the shared endpoint goes slow, and then everything is.
- **Impact:** "Both probes test the same endpoint, and the one that kills the container gives up first. Whatever the readiness probe was meant to protect against -- a slow dependency, a cold cache, a downstream outage -- restarts every replica at once instead of quietly taking them out of the Service, and the restarts keep the dependency from recovering. The readiness probe cannot fire first, so it never gets to do its job."
- **Remediation:** `kind: manifest` where the workload is declared, `manual` where it is not. Three edits close it and the excerpt does not choose between them, so read the container before you write. **Widening the liveness probe is the default** — raise its `failureThreshold` or `periodSeconds` until its deadline is several times readiness's, which keeps the restart as a last resort and needs to know nothing about the endpoint. **Repointing liveness at a genuinely local endpoint** is better where the workload serves one, and you must have read that it does; name the endpoint in `recommendation.risk`. **Deleting the liveness probe** is right where the process cannot wedge without exiting, and you should say so plainly rather than implying the probe was useless. **Never tighten the readiness probe to create the gap.** It closes the check by making the outage arrive sooner, which is the opposite of the fix, and the next reader has no way to tell it was deliberate.

#### 3.19 Advisory spreading that did not spread (`spread-not-achieved`)

**A replica count the placement does not back.** 3.8 asks whether a workload declares spreading at all and stops there, so a `topologySpreadConstraints` block satisfies it whatever the block says — and `whenUnsatisfiable: ScheduleAnyway` is scored by the scheduler rather than enforced. The obvious check on that hole, "flag every workload whose spreading is advisory", is one this audit must not ship: **3.8's own remediation prescribes `ScheduleAnyway`**, deliberately, because `DoNotSchedule` on `kubernetes.io/hostname` can leave a pod Pending forever. A check written that way re-flags every workload 3.8 has just fixed, which is this audit arguing with itself in someone's ledger. So this one fires on the outcome instead: the spreading is advisory **and** the replicas are in fact all on one node.

- **Command:** derived from `$STATE`; confirmed with the object-scoped read.
- **Flag when:** `spec.replicas >= 2`, every spreading mechanism the workload declares is advisory (`whenUnsatisfiable: ScheduleAnyway` on all `topologySpreadConstraints`, and any `podAntiAffinity` keyed on node or zone is `preferred` rather than `required`), and the EndpointSlices of a Service this workload **alone** backs list two or more ready endpoints, all with the same `nodeName`.
- **Read placement off EndpointSlices, because Pods are not in this audit's dump.** They are the largest kind in any cluster and the dump is written to disk. The slice carries `nodeName` per endpoint, which is the scheduler's own record of where the pod landed. Endpoints marked `terminating`, marked `ready: false`, or carrying no `nodeName` are not counted — the last is skipped rather than treated as an unknown node, which would read as spread.
- **One Service, not the union of several.** A workload behind both a headless and a ClusterIP Service appears in both sets, and adding them reports twice the endpoints it has replicas. The widest single Service's view is used.
- **Do NOT flag:** standard exclusions S1–S5; DaemonSets; a workload declaring **no** spreading at all, which is 3.8's finding and putting both in one ledger would give one object two verdicts; a workload behind a Service that also selects another audited workload, whose slices mix two workloads' pods so co-location would be a claim about the pair; a workload behind no Service at all, which leaves no evidence — say so in `limitations` rather than reporting it clean; and **any cluster whose EndpointSlices never name a second node**, where co-location is forced and the manifest is not the defect.
- **The single-node test is deliberately weak, and the finding must not overstate it.** It establishes that a second node exists, not that this workload could have been placed on it — taints, node selectors, and capacity are all invisible here. So claim only what is visible: the replicas are together and nothing in the manifest asked otherwise. Do not write that the scheduler "could have" spread them.
- **Severity:** `major`, where 3.8's hypothetical is `minor`, because this one has already happened. A three-replica Deployment on one node has the availability of a single pod, and the next drain of that node takes all of it.
- **Impact:** "Every ready replica of this workload is on one node right now, and the manifest contains nothing that would have stopped that: the spreading it declares is a preference the scheduler is free to ignore, and it did. Losing that one node -- a pool upgrade draining it, a preemption, a hardware fault -- takes the whole workload out at once, and the replica count in the manifest reads as though it could not."
- **Remediation:** `kind: manifest` where the workload is declared, `manual` where it is not. Three edits close it and they are not interchangeable, so the excerpt carries the two counts that choose between them — `this cluster's EndpointSlices name N nodes across M zones` — and you read the branch off those rather than deciding by feel. Where the workload is pinned by 3.7's finding on the same object, that pin is the cause and this is a symptom: say so and let 3.7's remediation carry it. **Never close this by lowering the replica count.** It makes the finding go away by making the workload smaller, which is the outage the finding is about.

  - **`N >= replicas`** — spread on `kubernetes.io/hostname` at `whenUnsatisfiable: DoNotSchedule`, `maxSkew: 1`. Raise the workload's existing constraint if it is already keyed on the hostname; otherwise add one and leave the constraint that is there alone, because a `ScheduleAnyway` zone rule is doing no harm. Where the workload already declares `podAntiAffinity`, a `requiredDuringSchedulingIgnoredDuringExecution` term on the same key is the same guarantee in the mechanism that file already uses, and is the better shape there. Say in `recommendation.risk` that the cluster showed N nodes to this workload's replica count, and that a replica goes Pending rather than co-located if the pool later shrinks below it.
  - **`N < replicas` and `M > 1`** — hostname spreading cannot succeed, so spread across `topology.kubernetes.io/zone` at `DoNotSchedule` instead. This is a weaker guarantee and the `risk` must say so: it keeps the workload alive through a zone failure and does nothing about the single node.
  - **`N < replicas` and `M == 1`** — nothing in the manifest can spread these replicas: there are not enough nodes and there is only one zone. `kind: manual`, and `recommendation.action` names the pool that has to grow before any constraint helps. **Do not raise the zone-keyed constraint here.** A `DoNotSchedule` rule on a key every node shares leaves the skew at nought and changes no placement — the pull request merges, the finding survives the next run, and the reviewer paid attention for nothing. This is the one branch that must not produce a manifest, and the one that a model reading only the old three-way choice most often got wrong in the other direction.

#### 3.20 A `preStop` hook the grace period cuts short (`prestop-outlives-grace`)

**3.13's fix, present in the manifest and inert.** 3.13 stops firing the moment a `preStop` exists — its own do-NOT-flag list ends with "any container that already declares a `preStop`, whatever it runs". That is the right scope for 3.13, and it leaves one shape unreported: the hook that is there and does nothing. `terminationGracePeriodSeconds` is the ceiling the whole termination runs inside, hook included, so when the hook's wait reaches that ceiling the kubelet sends `SIGKILL` with the hook still sleeping. The delay never happens, the container never receives the `SIGTERM` the delay was protecting, and the workload sits in exactly the state 3.13 describes while carrying the fix for it — with 3.13 quiet, so the ledger says nothing at all.

- **Command:** derived from `$STATE`; confirmed with the object-scoped read.
- **Flag when:** a container declares a `preStop` hook whose wait is readable in whole seconds, and that wait is greater than or equal to the pod's `terminationGracePeriodSeconds` (Kubernetes' default of 30 where the field is absent).
- **Two spellings of a wait are readable, and only whole seconds.** `lifecycle.preStop.sleep.seconds` is the native handler and its duration is the field. An `exec` is a shell command, so the duration is read out of the text and the largest integer `sleep` in it is taken — a hook that sleeps that long cannot finish in less time whatever else the command does. `sleep 0.5` and `sleep 1m` are both accepted by GNU coreutils and only one of them by busybox, so a duration parsed from either would be a guess about which shell the image ships; neither is read, and neither produces a finding.
- **Reaching the ceiling is the predicate, not approaching it.** At `wait == grace` the hook is provably truncated, which is a fact about the kubelet. "The hook leaves too little room for the application to shut down afterwards" needs a number for how much room an application needs, and this audit does not have one. That boundary is also the only place a native hook can be caught: the apiserver validates `sleep.seconds` against the grace period and refuses anything larger — on GKE 1.35, `seconds: 31` under a 30s ceiling is rejected and `seconds: 30` is accepted — so a predicate written as "greater than" would find no native hook ever. Nothing validates the shell spelling, which is why the waits that run far past the ceiling are all `exec` hooks.
- **Do NOT flag:** standard exclusions S1–S5; a container with no `preStop`, which is 3.13's finding; an `httpGet` or `tcpSocket` handler, whose duration is a property of whatever answers the request and is not in this dump; an `exec` with no integer `sleep` in it; and any wait shorter than the grace period, however little headroom it leaves.
- **Unlike 3.13, no Service and no replica floor.** 3.13 needs both because "has no `preStop`" is true of nearly every workload in a fleet and has to be narrowed to mean something. This predicate is already narrow — someone wrote a hook, and it does not run — and it is worth reporting wherever that is true, including on a workload that drains for some reason other than serving traffic.
- **Severity:** `major`, matching 3.13. The workload is in the state 3.13 describes, so nothing the hook was added to prevent is prevented. Not rated lower for having a fix already in the manifest: a defect with its own remediation applied and inert is harder to find, not less costly.
- **Impact:** "This container declares a preStop hook that cannot finish. The grace period is the ceiling the hook runs inside, and it expires while the hook is still sleeping, so the kubelet sends SIGKILL: the wait never completes and the process is never given the SIGTERM it was supposed to delay. Every rollout, node drain, and preemption therefore resets the connections in flight, which is the failure the hook was added to prevent -- and 3.13 is silent on this workload because a preStop hook does exist."
- **Remediation:** `kind: manifest` where the workload is declared, `manual` where it is not. **Raise `terminationGracePeriodSeconds` above the hook's wait**, leaving room beyond it for the process's own shutdown, and prefer this shape: it is one pod-level field and it keeps the wait the author chose. Shortening the hook instead is the other direction and is right only where the wait was arbitrary — it re-opens the endpoint-propagation race 3.13 named, so say in `recommendation.rationale` why the shorter wait is still long enough. Where the container was injected by a mesh or by the platform rather than written in the manifest under review, the grace period is the only one of the two you can edit; say so. **Never close this by deleting the hook.** That moves the object back to 3.13's finding, which is the same outage under a different id.

#### 3.21 Two pods sent to one volume only one node can hold (`rwo-claim-contended`)

**A Deployment whose ability to take an update is decided by the scheduler rather than by anything in its manifest.** A `ReadWriteOnce` claim attaches to one **node** at a time — not one pod, which is what `ReadWriteOncePod` means and why both modes exist. `RollingUpdate` — the default, and the strategy of a Deployment that never names one — starts the replacement before removing the original, so the two pods overlap by design. Placed beside the original the replacement mounts the volume and the rollout completes; placed anywhere else it sits in `ContainerCreating` with `Multi-Attach error for volume` until the progress deadline expires. Nothing in the manifest chooses between those, and the moments free capacity on that one node disappears are the moments the rollout matters: the node filled up, or it was cordoned for an upgrade. A workload given a volume of its own is usually sized so a second copy does not fit beside it anyway. **When it does deadlock, the failure is silence.** `maxUnavailable` will not let the old pod leave until the new one is ready and the new one never will be: the workload carries on serving the image it was already running, the rollout records `ProgressDeadlineExceeded` in a status nobody reads, and every later change — a security patch included — is accepted by the API server and reaches no container. This is how a workload with a fully reconciled GitOps repository behind it sits on a year-old image.

- **Command:** derived from `$STATE`; confirmed with the object-scoped read.
- **Flag when:** a Deployment mounts a PersistentVolumeClaim whose every access mode is `ReadWriteOnce` or `ReadWriteOncePod`, and two of its pods can hold that claim at once — either because `replicas > 1`, or because `replicas == 1` under a `RollingUpdate` whose `maxSurge` resolves to 1 or more. A percentage resolves against the replica count and rounds **up**, matching Kubernetes' own direction for `maxSurge`, which is why the default `25%` of a single replica is one extra pod rather than none.
- **The rollout arm is the common one and it needs no unusual manifest.** A Deployment, a claim, and the strategy Kubernetes supplies when none is written are the whole recipe — which describes most of the single-instance dashboards, registries, and datastores that get run as Deployments rather than StatefulSets. The replica arm is rarer: above one replica the pods coexist by definition rather than during a rollout, and the scheduler spreads a ReplicaSet's pods across nodes by default, so what does not co-locate stays pending and what does co-locate has given up the redundancy the replica count was asking for.
- **The finding is usually latent, and say so rather than claiming an outage.** Measured on a GKE Autopilot cluster, a single-replica Deployment holding a bound `ReadWriteOnce` claim under the default strategy rolled cleanly twice in a row: both replacements were scheduled onto the node already holding the volume, which was small enough to take a second copy. That is the good case and it is common on small workloads. Write the evidence as what the manifest permits, not as a failure observed — `recommendation.rationale` should say the rollout succeeds while the surge pod fits beside the original and deadlocks the first time it does not. A finding written as "this workload is broken" is wrong on the cluster where it is not, and an owner who checks and finds a healthy rollout stops reading the rest of the report.
- **3.14 names this situation and cannot detect it.** Its remediation says to "check first whether `Recreate` was chosen on purpose", because a workload holding a `ReadWriteOnce` volume needs it; this is the check that knows. The two never fire on one object: 3.14 excludes single-replica Deployments, and this check recommends `Recreate` only there.
- **Do NOT flag:** standard exclusions S1–S5; `strategy.type: Recreate`, which is the fix already applied; StatefulSets, whose `volumeClaimTemplates` give each replica a claim of its own and whose update strategy replaces one member at a time rather than surging; a claim listing `ReadWriteMany` or `ReadOnlyMany` among its modes, which a second node can attach; generic ephemeral volumes, where the controller creates one claim per pod — reading only `volumes[].persistentVolumeClaim.claimName` excludes those for free; a claim the dump does not contain, where guessing `ReadWriteOnce` because it is the common default would send a pull request over a volume that may well be shared; a Deployment scaled to zero; and `replicas == 1` with `maxSurge: 0`, where the old pod is removed before the new one starts and nothing contends.
- **Read `status.accessModes` where it exists and `spec.accessModes` only where it does not.** The spec is what was asked for and the status is what the bound volume actually supports; an unbound claim has no status yet, and there the request is the best evidence available.
- **Severity:** `major` on both arms. Not `critical` — nothing is down; the rollout arm leaves the old pod serving indefinitely and the replica arm leaves whatever co-located serving, so in both the workload answers requests while being unable to change or to grow. Not `minor` either, even though the failure is conditional: the condition is free capacity on one node, which is not a property anyone controls or watches, and when it goes the workload stops accepting patches without saying so.
- **Impact:** the collector writes it per arm and marks it authoritative, because the two arms fail differently and the sentence for one is false of the other. The rollout arm is about updates that land nowhere; the replica arm is about capacity that is not there. Do not merge them.
- **Remediation:** decided by the arm, and only one of the two is a pull request.

  - **`replicas == 1`** — `kind: manifest` where the workload is declared, `manual` where it is not. Set `spec.strategy` to `{type: Recreate}` and change nothing else. This is the whole fix: the old pod is deleted, its volume detaches, and the replacement attaches it on whatever node it lands on. Say in `recommendation.risk` that the rollout becomes a brief outage — which is inherent to one replica on one disk and is the state 3.11 already reports on this workload, not a new cost this change introduces. **Do not close this by adding a node affinity that pins the pod to the volume's node.** It makes the rollout work and makes the workload unschedulable the first time that node is drained.
  - **`replicas > 1`** — `kind: manual`. `Recreate` would work and would immediately reopen the same object under 3.14, which reports exactly that strategy above one replica as a full outage on every deploy; a fix that trades one `major` for another is not one. The two real fixes are architectural and neither is safe to write from here: move the workload to a StatefulSet, whose `volumeClaimTemplates` give each replica its own volume, or move the claim to a `ReadWriteMany` class — on GKE, Filestore. Name both in `recommendation.action`, say which the storage class in the excerpt makes cheaper, and say that the replica count is not the thing to change: lowering it to one makes the finding go away by giving up the redundancy the manifest was asking for.

#### 3.22 An autoscaler allowed to reach one replica (`hpa-floors-at-one`)

**3.11 asks the same question of the wrong field.** It reads `spec.replicas`, which is the right evidence for a workload whose replica count is a written-down number and worthless for one whose replica count a HorizontalPodAutoscaler rewrites all day: what the dump holds is whatever the autoscaler wanted at the instant the audit read it. This audit fires at 06:50 UTC and reads three; the rollout happens at 03:00 and there is one pod, which goes away. The floor is the durable fact, so this check reads `minReplicas` and does not look at `spec.replicas` at all except to print it.

**It is also the case where 3.11's `manual` answer stops being right.** That answer rests on going HA touching leader election, session handling, and storage — true of a workload nobody has run two copies of, and already settled here: an HPA with `maxReplicas` above one is the owner's written statement that a controller may run several copies concurrently with nobody watching. Raising the floor asks strictly less of the workload than the ceiling it already carries. So 3.11 now excludes any Deployment an HPA targets and this check takes them, and the two can never both fire on one workload.

- **Command:** derived from `$STATE`; confirmed with the object-scoped read of the HPA.
- **Flag when:** an HPA's effective `minReplicas` is 1 — declared, or absent and defaulted by the API — its `maxReplicas` is 2 or more, and its `scaleTargetRef` names an `apps/v1` workload in this audit's set that at least one Service selects.
- **Do NOT flag:** S1 and S2, which this check applies itself for the reason 3.6 records — the managed `kube-state-metrics` and `opentelemetry-collector` HPAs in `gke-managed-*` both floor at one, and reporting them is one finding per cluster about an object the operator cannot edit. Also `maxReplicas: 1`, which is 3.6's pinned arm at `major` and where this fix would ask for a floor above the ceiling; a `scaleTargetRef` the audited set does not contain, which is either an S4 exemption, an S5 scale-to-zero, or 3.6's dangling arm; a target no Service selects, for 3.11's reason — nothing routes to it, so nothing is dropped; and `strategy.type: Recreate`, where the manifest already says two copies must never coexist and the HPA above one already contradicts it. That contradiction is a real defect and this is not the check that should raise it: the owner has two opinions to reconcile before a third helps.
- **Severity:** `minor`, matching 3.11 — a floor is a cost decision, and the fix bills for a second pod during the hours the first was enough. Deliberately below the auto-promotion floor: opening a pull request unasked that raises a customer's bill is not a thing this audit should do. It waits for `/remediate`.
- **Impact:** "The autoscaler is allowed to take this Service-backed workload down to one pod, and at that floor every rollout, node drain, and preemption is a full outage — during exactly the quiet hours the floor is reached."
- **Remediation:** `kind: manifest`, subject to §4's declaration rule — set `spec.minReplicas: 2` on the HPA and change nothing else. **The finding names the HPA and the fix edits the HPA**, which is the ordinary case here — 3.4, 3.6 and 3.16 all name an object that is not a workload, and in each of them the fix edits the object named. 3.17 and 3.23 are the two exceptions, and this is not one of them. Do not write the fix against the Deployment: `spec.replicas` is the field the autoscaler owns, so a pull request setting it to 2 merges, reconciles, and is undone at the next sync — what §3's `reconciler` rule says of a GitOps controller is true of an HPA for this one field. Say in `recommendation.risk` that the floor costs a second replica's requests around the clock, and that `maxReplicas` is untouched so the ceiling and the scaling behaviour are unchanged.

#### 3.23 A workload two PodDisruptionBudgets cover (`pdb-overlapping`)

**A second budget over the same pods is not more protection.** It is the reading that keeps these in place — one team's chart ships a PDB, another writes one for the same Deployment, and both look like belt and braces. `Eviction` on a pod matched by two of them returns 500: `This pod has more than one PodDisruptionBudget, which the eviction subresource does not support`. Not "fewer disruptions allowed" — none, ever. `kubectl drain` never completes, and node-pool upgrades, node auto-repair and autoscaler scale-down all stop on that node.

**It hides better than 3.4 does.** The disruption controller picks exactly one of the covering budgets per pod and says so — `Pod … matches multiple PodDisruptionBudgets. Chose "x" arbitrarily.` Pod events wake only that one, so it alone tracks reality, and it reports a healthy `disruptionsAllowed` while every eviction returns 500. The other freezes at whatever it last computed, which can read anything at all: on a two-replica Deployment the chosen budget sat at `SufficientPods` with one disruption allowed while the loser stayed at `currentHealthy: 0`, `InsufficientPods`, a snapshot of the three seconds before the pods went ready. Which of the pair wins is arbitrary and can change between syncs. So no budget's status answers the question in either direction — a healthy one is the one being kept current and an unhealthy one is usually stale, and the arithmetic 3.4 turns on is fine on both. The overlap exists only in the pair, which is why the check has to be anchored on the workload and count the budgets that reach it.

- **Command:** derived from `$STATE`; confirmed with `kubectl get pdb -n <ns> -o yaml`, which shows every budget's selector at once — the object-scoped read on either one alone cannot show the overlap. `kubectl get events -n <ns> --field-selector reason=MultiplePodDisruptionBudgets` corroborates it in the controller's own words, but events age out within the hour, so its silence is not evidence against.
- **Flag when:** two or more PDBs in a namespace select the same workload's pod labels.
- **Do NOT flag:** S1 through S5, inherited because this check walks the audited workload set rather than the budgets — the `gke-managed-*` namespaces where GKE's own budgets overlap each other are already out. A PDB whose `spec.selector` is absent or null, which in `policy/v1` selects **no** pods (unlike an empty `selector: {}`, which selects them all and is exactly how one budget silently comes to cover a whole namespace). And the case where **every** covering budget carries the addon marker, which is a drain block nobody can close, the reason 3.6 records.
- **S2 does not remove a budget from the count.** An addon's PDB overlapping a user's is the likeliest way a real fleet gets here, the eviction API does not care who wrote either one, and the fix — narrow the user's budget — is the most clearly correct one in this section. Name the addon-managed budget in the excerpt so the reader knows which half is not theirs.
- **Severity:** `critical`, and for 3.4's reason rather than a workload's: it stops the cluster's lifecycle, not one workload's availability.
- **Impact:** "The eviction API refuses every pod covered by more than one PodDisruptionBudget, so node-pool upgrades, node auto-repair and autoscaler scale-down all stall on this workload until one budget is removed — and the budget the disruption controller is keeping current goes on reporting disruptions allowed while it happens."
- **Remediation:** `kind: manifest`, subject to §4's declaration rule. **The finding names the workload and the fix edits a budget** — the second finding here whose remediation may target a manifest other than the object it names, after 3.17, and for a related reason: which of the two budgets should go is a judgement the collector cannot make. Choose it in this order. A budget that covers **only** the workloads already over-covered is a duplicate, so one of the pair goes: keep the one expressed as `maxUnavailable`, the shape 3.3 and 3.4 both prescribe because it is safe at every replica count, and delete the other. Where both are that shape, keep the one a chart renders and delete the hand-written one, which is the copy somebody added on top. A budget that also covers workloads that are **not** over-covered is not a duplicate and must not be deleted — narrow its `spec.selector` so it stops reaching this workload, and say in `recommendation.risk` which other workloads it still protects. Where one of the pair is addon-managed, the other is the one you edit, whichever shape it has. Where you cannot tell the two apart — same selector, same spec, both hand-written, neither obviously the newer — the finding is `kind: manual` naming both; guessing which one a team meant to keep is not a pull request anybody should have to review. **Never resolve an overlap by widening a budget to swallow the other**, which leaves one budget over more workloads than anybody chose and is how the empty-selector trap in 3.3 starts.

**Dropped deliberately.** Right-sizing from VPA recommendations, "HPA pegged at max", CPU-throttling ratios, and OOMKill history all require Prometheus/GMP, VPA, or an event history this audit is forbidden from or cannot sample reliably at a fixed daily time. Node-pool surge and maintenance-window settings are real reliability risks but belong to the upgrade/security-patch audit, not here.

### 4. Generate remediation artifacts

- **The declaration rule decides where the file goes, and both of its branches discover a directory that is already there.** A remediation that _changes an object that already exists_ — 3.2's and 3.8's workload edits, 3.4's PDB rewrite — must go to that object's **existing declaration in the GitOps repo**: take it from the candidate's `declaration.path` (Step 2) and give that as `remediation.path`, falling back to locating it in the `workspace` clone (`grep -rl "name: <object>" --include='*.yaml' <workspace>`) only where the candidate carries no `declaration`, and rewrite it as the object's complete desired manifest. Never emit a patch fragment. A file carrying `metadata.name` and a partial `spec` is not valid `kubectl apply` input, and a second file claiming an object the repo already declares is a duplicate resource id that both Config Sync and Argo reject.
- **A remediation that _creates_ an object the cluster does not have — a new PDB (3.3), a new HPA — goes beside the declaration of the workload it protects.** That workload is what the new object selects, so it is always the anchor and it always exists: write into the candidate's `declaration.directory` (Step 2), which is that anchor's own directory and already confirmed to be on the target cluster. Where the candidate carries no `declaration` — the ordinary case for a workload someone else's chart installs — it will usually carry `namespace_directory` instead, which is the same question answered for the namespace rather than for the object: `namespace_directory.path` is the directory, and its `source` decides what you write. `sibling` and `cluster` take a plain new file, and under `cluster` you must **set `metadata.namespace` explicitly**, since that directory serves the whole cluster; `overlay` means the path is a Kustomize root, which renders only the files its `resources:` list names — and a remediation carries one file, so it cannot add the new object and the entry that makes it render in the same change. Such a finding is `kind: manual`: put the manifest and the `resources:` line it needs in `recommendation.action`. Do not write over a `namespace_directory` the candidate carries with prose saying no file in the repository declares into that namespace — the question was answered against the clone, and denying it publishes a false claim whichever of you is right. Only where the candidate carries neither field, narrow by namespace first (`grep -rl "namespace: <namespace>" --include='*.yaml' <workspace>`), then **open the hits and confirm one actually declares that workload on the target cluster** before writing beside it, matching the naming style of the files already there. Do not anchor on `grep "name: <workload>"` alone — `grep` is kind-blind and unanchored, so it also matches `app.kubernetes.io/name:` label lines and any object whose name merely starts with the workload's, and it will happily return a file under another cluster's directory. **If the hits land in more than one directory, or none can be tied to the target cluster, the finding is `kind: manual`** — writing a namespaced object into the wrong cluster's applied tree fails that tree's sync, which is worse than writing nothing. **Never create a new top-level directory, and never write to a path whose parent directory does not already exist in the clone.** The repository is reconciled by a tool that applies a fixed set of paths, and it is not this SOP's business to know which — that is why the destination is discovered from the workload rather than named here. A file outside those paths is applied by nothing: it merges clean, closes the finding for one run, and leaves the workload exactly as exposed as it was.
- **Where the object has no declaration but the candidate carries `release_declaration`, the fix is an override on whatever renders it, and the finding is `kind: manifest`.** A rendered workload has no file of its own to rewrite — the repository declares a chart release or a Kustomize overlay, and the object exists only after that is expanded. That is why most findings on a real fleet used to end here as `manual`: Argo CD's own Deployments, cert-manager, and every workload installed from a chart or layered over a base in another repository. The override goes in the file at `release_declaration.path`, in the field `values_field` names, and that file is rewritten complete like any other manifest — never a fragment of one.
- **Where `release_declaration.renderer` is `kustomize`, the override is a patch rather than a values key, and the same `kind: manifest` rule holds.** Append to the list `values_field` names an entry whose `target` matches the object the finding names — `kind`, `name`, and `namespace` all three — and whose `patch` carries only the fields you are changing. There is no chart to interrogate and no key that might not exist: a strategic-merge patch reaches any field the object has, so the two bullets below do not apply. What a patch can still get wrong is its `target`: one given only a `kind` rewrites every object of that kind the overlay renders, which is how a one-workload finding becomes a fleet-wide change nobody asked for. Rewrite the Application file complete, like any other manifest.
- **Where `renderer` is `helm`, confirm the values key exists before you propose it.** Read the chart's own defaults: `helm show values <chart> --repo <repo> --version <version>`, taking all three from `release_declaration` (omit `--version` when it is empty, and say in `note` that the release tracks an unpinned revision). This is a read on the evidence-command allowlist and it is the difference between a values override and a guess. Charts vary: `resources` is nearly universal, `topologySpreadConstraints` and `podDisruptionBudget` are common, `terminationGracePeriodSeconds` and `lifecycle` often have no key at all. **Set only keys that appear in that output.** A key the chart does not read is a file that merges, closes the finding for one run, and changes nothing on the cluster — the same failure the "never write to a path nothing applies" rule guards against, one layer up.
- **Match the key to the object the finding names, not to the chart.** A chart that renders several Deployments keys them apart — `controller.resources` and `webhook.resources`, not one top-level `resources` — so a top-level override either does nothing or changes every component at once. Find the sub-key whose rendered object is the one the finding names; where `helm show values` gives no way to tell, `kind: manual`.
- **If the chart exposes no key that reaches the field, the finding is `kind: manual`** with the change spelled out in `recommendation.action` and the chart named, so the owner knows the fix is a chart change or a `postRenderer` rather than a values edit. Say which key you looked for and did not find.
- **If the workload itself has no declaration in the clone and no `release_declaration`, the finding is `kind: manual`.** There is no sibling to anchor to, and a workload this repository does not declare cannot be given a PDB by a pull request against it. Put the manifest you would have written in `recommendation.action`.
- **If the object already exists and you cannot find its declaration, the finding is `kind: manual`.** Put the intended change in `recommendation.action`, write no file, omit `remediation.path`. Never invent a new path for an object that may already be declared somewhere you did not look.
- Either way the path is POSIX and relative to the `workspace` clone from Step 0: no leading `/` or `:`, no `..`, and no glob metacharacters (`*`, `?`, `[`, `]`). The helper rejects all of those outright. A path with no file behind it is handled more gently but is still your mistake: that finding degrades to `kind: manual`, keeps its evidence and recommendation, and the ledger records that the audit named the fix without writing it. The report publishes; the fix just cannot travel in a PR. Name a new file for the object it creates and the workload it protects (`<workload>-pdb.yaml`), not for the finding id: it lands in a directory of hand-named manifests where a finding id reads as noise, and finding ids are re-derived every run while the file has to stay put across them.
- Write the manifest for every id in `pending_remediation_requests` from Step 0 whose finding still reproduces. A human has already asked for that fix; without the file the promotion fails.
- Head each file with a comment naming the cluster, the check, and the finding id.
- Copy selectors and labels verbatim from the live object. **Never invent a resource quantity, replica count, utilisation target, or probe endpoint** — if the value cannot be read off the object or is not structurally safe (`maxUnavailable: 1`, `maxSkew: 1`), the finding is `kind: manual`. **The replica floors 3.11 and 3.22 prescribe are the exception, and they are structurally safe in the same sense `maxSkew: 1` is:** `2` is the smallest number that makes the workload survive losing one copy, so it is derived from the finding rather than chosen, and neither raises a ceiling. Every other replica count is still invented.
- Writing the file does not open a Pull Request. `finish` opens one automatically only for a `critical` finding whose remediation is a `manifest` and whose branch carries no **live** pull request, at most five per run; the ledger names the ones it withheld. "Live" is the operative word: a PR the harness closed itself as stale is labelled `audit:stale-closed` and the same fix may be promoted again, while a PR a human closed and a PR that merged both stay closed — the harness does not overrule either. Everything else waits for a repo writer to comment `/remediate <finding-id>` or `/remediate all` on the ledger issue. In this audit 3.4's drain-blocking PDB and 3.23's overlapping pair are the `critical` manifests, so they are the fixes that normally arrive ready to merge where the repo already declares the object; one that is not declared anywhere stays `manual`. Every other manifest here waits to be asked for, and several owe the eventual reviewer something the diff will not show. 3.17 is one of the two findings in this audit whose remediation may target a manifest other than the object it names, because the missing port declaration is sometimes the workload's to add — 3.23 is the other, where the finding names the workload and the edit lands on one of the budgets covering it. 3.18's widened liveness probe and 3.19's enforced spreading each have three defensible shapes on the same object rather than one, so which of them you chose belongs in `recommendation.rationale`. So does 3.20's raised grace period: it has two shapes, and the one you did not take — shortening the hook — is the one a reviewer will ask about. 3.21 is a manifest on its single-replica arm alone, where the fix is `strategy: {type: Recreate}` and nothing else; its multi-replica arm is `manual` because the same edit there would reopen the object under 3.14. 3.22's raised autoscaler floor and 3.11's raised replica count are held at `minor` on purpose, because each bills for a second replica and an audit that opens that pull request unasked is spending someone else's money. 3.11 reaches `manifest` on one arm only, where a chart the repository declares exposes a replica key for the object named and the workload mounts no exclusively-attachable claim; every other single-replica finding stays `manual`. A `kind: manual` finding is never promotable — it stays prose in the ledger, and 3.12 always lands there, because the reason a Job fails is in a log this audit does not read and a manifest that guessed at it would be a guess. Findings whose manifest paths intersect share one PR.
- These files are proposals for human review; do not `kubectl apply` anything, ever.

### 4a. Check declared intent before reporting a posture

Four checks judge a **posture** — a shape an owner may have chosen on purpose — rather than a fault: 3.3 `no-pdb`, 3.5 `no-hpa`, 3.6(a) `hpa-cannot-scale` with `min == max`, and 3.11 `single-replica`. Before a candidate from one of those four is written to `findings`, search the GitOps clone's `provisioning/` pins for a declaration that pins the flagged property on that object; the OKF notes are the harness's half (below), and a candidate one of them covers is written to `findings` all the same. Every other check is a fault — a missing request, a drain-blocking budget, a hostname pin, a missing probe, a dangling HPA target — and no declaration excuses one: a repository that declares `maxUnavailable: 0` has declared a bug, and it stays a finding.

- **The harness searches first.** `start` reads every repository in `declared_intent_repos` for declarations: each `context_repos` entry copied with `inspect_repository.py clone --depth 1` (at the entry's `ref` when it has one) into a scratch directory it removes afterwards — in directory mode the copy is a leased checkout on the shared volume, left in place as yours are — and the GitOps repository the same way in content mode or straight from the clone Step 0 reset in directory mode. A private context repository copies in content mode only, where the broker presents the minter's read-only token for it; in directory mode the copy fails as before and the repository stays unsearched. It files what it finds at `declarations_path` and lists each repository it read completely — the clone exited 0, no bound stopped it, every `.md` under the searched paths arrived, and it gave a sha; a file the broker withheld elsewhere in the tree, such as a manifest over its per-file ceiling, costs the search nothing — in `declared_intent_searched`. `finish` then moves every finding a filed declaration covers to `declared` (§5) itself, with the finding's `cluster` and `title` and the note's `repo`, `path` and title as the declaration, before it measures the search record. A note the harness can read needs nothing from you; one it filed is applied whether or not you opened it. A posture such a note covers is still written to `findings`: `finish` is what moves it to Declared intent, so a candidate you leave out because you found the note yourself gives `finish` nothing to move, and the declaration never reaches the ledger.
- **What counts as a declaration.** An OKF note — Markdown whose frontmatter carries the `type` the knowledge contract requires — with a `declares:` list, each item `{check, namespace, object}` and optionally `cluster`: `check` one of the four slugs above, `object` as `Kind/name`, `namespace` the workload's namespace (empty for a cluster-scoped object), `cluster` the cluster name when the declaration is scoped to one cluster and omitted when it is fleet-wide. The match is a lookup on those fields compared case-blind, as the finding id compares them (`deployment/api` joins `Deployment/api`), `(check, cluster, namespace, object)` first and the fleet-wide `(check, namespace, object)` second. For `hpa-cannot-scale` the harness moves only the 3.6(a) shape, read off the severity §3.6 fixes: a `major` finding is the `min == max` posture and moves; a `minor` one is the dangling-target fault and stays a finding, with a stderr line naming the declaration it did not apply. An item with a fault slug, a missing field or an `object` that is not `Kind/name` is skipped with a warning naming the file, and the rest of the note still counts. Body text is never read: a note that names the workload and the slug in prose declares nothing.
- **Where the harness looks.** Each repository's `.kube-agents/intent.yaml`, one key `paths:` listing repo-relative prefixes (a trailing `/` allowed), bounds the search to the `.md` files under them; the reference layout ships `paths: [knowledge/]`. A repository with no such file, or one `start` cannot parse, that names a path outside the repository or one the repository broker refuses (surrounding whitespace, a control character), that names a path with nothing behind it at the commit read (a misspelt directory, or one renamed since), or that is itself a symlink, is searched whole, and `start` says so on stderr. `.git` and symlinks are never followed, the intent file included. In content mode the harness copies `.kube-agents/` first and then only the paths the file names, so the copy's file and byte caps count the notes rather than the manifests around them; a repository with no usable file is copied whole under those caps, and one a cap stops is not searched, so naming paths is what keeps a large repository searchable. A note under the searched paths the harness could not read — withheld by the broker (a link it will not follow is not a note, in either mode), or not UTF-8 — costs the repository its `declared_intent_searched` entry rather than being skipped.
- **What stays with you: the `provisioning/` pins.** A declaration HCL or YAML makes under `clusters/<cluster>/provisioning/` — for `no-hpa`, a fixed `replicas` on that Deployment and no HPA declared for it; for `hpa-cannot-scale`, `min_replicas` and `max_replicas` (or `minReplicas`/`maxReplicas`) set equal; for `single-replica`, `replicas = 1` with the reason — has no machine-readable form yet, so it is still yours to find in the GitOps clone (in content mode with `audit_report.py grep` and `fetch`; the fleet-audit skill's _Reading the repository in content mode_ section is the procedure) and to move to `declared` with `repo`, `path` and the lines that pin the property as `excerpt`. Not a match: a file that merely mentions the workload, a value that differs from what the cluster runs (the repository says `replicas = 3` and the cluster runs 1), or a pin under another cluster's directory. Because `start` records the GitOps repository as searched once it has read the notes, `finish` no longer detects a run that skipped these pins; that is accepted until the pins have a machine-readable form, and a `declares:` note is how an owner makes the choice durable today.
- **Record every repository you searched, and the commit you read it at.** §5's top-level `declared_intent_searched` lists each as `owner/name@sha`, and together with `start`'s list — which `finish` unions into yours — it must cover every slug in `declared_intent_repos`, or `finish` treats the step as not run (below). A repository `start` read completely needs no entry from you. One it could not read — a clone that failed, a copy with `complete: false`, a tree with no sha — is missing from its list with a warning saying why: copy it yourself with `python3 ./skills/inspect-repository/scripts/inspect_repository.py clone --repo <owner>/<name> --depth 1 --into "$(mktemp -d)"` (a fresh, empty directory every run; the default destination refuses a non-empty one and `--force` would keep a note the repository has since deleted; a private context repository copies in content mode only, where the broker presents the minter's read-only token for it — in directory mode the copy fails as before and the repository stays unsearched), adding `--ref <ref>` when its `declared_intent_unsearched` entry carries one — that is the branch the administrator pinned and the one `start` tried, and a clone that fails at it is a repository you did not search, never one to read at HEAD instead; an entry with no `ref` is read at the repository's own default branch, so in directory mode, where a clone with no `--ref` checks out the branch `GITOPS_BASE_BRANCH` or `CREDENTIAL_PROXY_BASE_BRANCH` names when one is set, run the copy with both unset as `start` does; an entry carrying `refused_ref` is one you do not copy at all, because its pin is not a git branch name and the repository stays unsearched, HEAD included, until the entry is corrected — grep the tree its output names (`into` in content mode, `workspace` in directory mode, where the copy is a leased checkout you leave in place), delete the directory when done, and record the sha you never invent: the clone's `sha` in content mode, `git -C <tree> rev-parse HEAD` in directory mode, and for the GitOps repository what `list`, `grep` and `fetch` print or `git -C <workspace> rev-parse HEAD`. Write the entry when that repository's search is done, not before, and give none for a repository whose copy failed or came back `complete: false` — that repository was not searched.
- **What a match does.** The candidate moves from `findings` to `declared` (§5) with the same `check`, `cluster`, `namespace` and `object`, a `title` saying what was declared, and `declaration.repo`, `declaration.path` (repo-relative) and `declaration.excerpt` — the lines that pin the property, a few at most, under the same credential rule as evidence. It gets no severity, no remediation and no id; the ledger renders it under _Declared intent_ with `repo:path`, where a reviewer who disagrees changes the declaration and the posture returns as a finding on the next run. A run with nothing but declarations closes the ledger, and a later run with nothing but declarations opens none: the closing comment is the last ledger record, the declaration in the repository is the durable one, and `finish` reports the count as `declared`. Do not report it as a finding again while the declaration stands.
- **No match, or a search you could not complete** — a context repository that failed to copy, a copy with `complete: false`, a `truncated` grep you did not narrow — leaves the candidate a finding. A declaration you did not find does not exist for this run. Never write a `declared` entry for a declaration you did not read.
- **A step you skipped is visible, not silent.** Whenever any cluster's `checks_run` names one of the four checks, `finish` requires `declared_intent_searched` to cover every slug in `declared_intent_repos`. Anything less — a union of your list and `start`'s that misses a repository, or no run record from `start` — is no search: `finish` withholds every finding of the four checks, including a dangling-target 3.6(b) `hpa-cannot-scale`, which shares the slug and which the harness cannot tell from the `min == max` posture; the faults publish, the ledger names each withheld posture under _Declared intent not searched_ as a coverage gap, and the run is `partial`, so the ledger does not close. The requirement is keyed on the checks that ran, not on the postures you wrote: a candidate you left out of `findings` without a search is the same document as one a declaration covered, and only the record tells them apart. The sha is checked for shape only; the record makes a skipped step visible rather than impossible.

### 5. Emit findings.json

Write the schema exactly as the helper validates it to the `findings_path` returned in Step 0: `audit` set to `obtainability-audit`; `scope.clusters` non-empty, each entry carrying the mandatory `checks_run` list of `{check, command}` objects for the §3 checks that actually ran there and optionally a non-empty `limitations` string; `scope.skipped` complete and disjoint from `scope.clusters`; and, for each finding, `check` (the §3 slug that produced it), `severity`, `title`, `cluster`, `namespace`, `object` (as `Kind/name`), `evidence.command` (the literal confirm command you ran) and `evidence.excerpt` (trimmed to the few lines that prove the finding), `impact`, `recommendation`, and `remediation` — with `remediation.path` present and the file on disk whenever `kind == "manifest"`. No `id`: the harness derives it (§3) from `check`, `cluster`, `namespace` and `object`. Sort findings by severity (`critical`, `major`, `minor`), then cluster, then namespace, so the run-over-run diff stays readable. A schema violation publishes nothing: `finish` exits 2 and the ledger is untouched. Validate your own JSON before calling it.

`declared_intent_searched`: a top-level list of `owner/name@sha` strings, one per repository §4a searched (§4a says where each sha comes from). Required in effect whenever any cluster's `checks_run` names one of the four §4a checks: together with the list `start` printed under the same key, which `finish` unions into yours, it must cover every slug in `declared_intent_repos` from Step 0, and a union that does not — or no run record — withholds the four checks' findings as a coverage gap (§4a). The validator rejects an entry that is not `owner/name@sha` with a sha of 7 to 40 lowercase hex characters (exit 2, nothing published); extra repositories beyond `declared_intent_repos` are allowed. Omit the key only on a run where none of the four checks ran anywhere.

Optionally, `declared`: one entry per posture you moved out of `findings` for a `provisioning/` pin (§4a) — `finish` adds the entries for the notes `start` filed itself, so a posture a `declares:` note covers goes in `findings` like any other and `finish` moves it to Declared intent; leaving it out of the document hides the declaration from the ledger — each carrying `check`, `cluster` (a name in `scope.clusters`), `namespace`, `object` (as `Kind/name`), `title`, and `declaration` with `repo` (`owner/name`), `path` (repo-relative, one literal file, no `..` and no glob) and `excerpt` (non-empty). No `severity`, no `remediation`, no `id`. The validator rejects an entry whose four identity fields match a finding — a posture is declared or reported, never both — one whose cluster this run did not read, and one whose `check` is not among the four §4a names (a declared fault exits 2 and publishes nothing). A document without the key is fine; an absent key and `[]` mean the same thing.

Read your `checks_run` lists once more before you write. Padding one to twenty-three because §3 lists twenty-three checks is the one entry in this document that converts a partial audit back into a false all-clear — the harness cannot see the check you skipped, so it takes the list at its word. The `command` on each entry is what makes that padding falsifiable rather than free: it is published verbatim, so an invented command is a false statement in a public issue. `checks_not_applicable` is the same lie wearing a different field: it removes checks from the denominator, so a slug parked there because you ran out of turns is a coverage gap the ledger will never show. It is published too — every exclusion and its reason render under _Not applicable_, where a reviewer who knows the cluster can call it. An honest twenty-one-of-twenty-three costs you nothing but an open ledger, and an honest twenty-one-of-twenty-one on a cluster where the other two cannot apply closes it.

**`recommendation` is required on every finding.** Three sub-fields, all non-empty strings, no exceptions — a `manual` finding that will never become a PR needs it exactly as much as a promotable one. The reasoning is only cheap while the evidence is still in front of you; deferring it to promotion time means writing it blind.

- `action` — what to do, imperative, one or two sentences.
- `rationale` — why this fix and not the obvious alternative; name the alternative you considered and why you rejected it.
- `risk` — what breaks on apply, and the read-only check to run first.

Worked example, for a 3.3 finding on `payments/api`:

```json
"recommendation": {
  "action": "Add a PodDisruptionBudget with maxUnavailable: 1 for the payments/api Deployment, its spec.selector copied verbatim from the Deployment's own selector.",
  "rationale": "maxUnavailable: 1 is structurally safe at any replica count >= 2. The obvious alternative, minAvailable, is rejected: an integer minAvailable at or above the workload's floor is exactly the drain deadlock check 3.4 reports, and a budget that is safe today becomes one the next time the owner scales down -- or, under an autoscaler, the next time the load falls off.",
  "risk": "Once a PDB exists the eviction API refuses the last permitted replica, so draining an already-degraded workload waits instead of proceeding. Confirm the Deployment is at its full replica count first with kubectl --context prod-us-east get deploy -n payments api -o wide."
}
```

### 6. Close the audit run

```bash
./skills/fleet-audit/scripts/audit_report.py finish --audit obtainability-audit \
  --findings-file /opt/data/scratch/findings_obtainability-audit.json \
  --manifest-file /opt/data/scratch/manifest_obtainability-audit.json \
  [--repo "<owner>/<repo>"]
```

Pass `--manifest-file`: it is what lets `finish` check the document against what the collector actually ran. Given a manifest, `finish` rejects a `checks_run` entry on a `"collected"` cluster that names a check the manifest never ran for it, rejects a `"collected"` cluster the document leaves out of `scope.clusters` altogether, rejects a `"gate-failed"` target the document is silent about, and takes each finding's `evidence` from the matching candidate. On a run where Step 2's collector produced no manifest — every check on every cluster came from the manual fallback — pass `--no-collector-manifest "<why>"` in its place; that publishes, but reports the reason as a coverage gap, so the run is partial.

One JSON line comes back, carrying `status`, `issue_url`, `new`, `resolved`, `prs_opened`, `prs_closed`, `partial`, `coverage_gaps`, `silent_ok`, `declared` (how many postures §4a kept off the ledger; it never decides silence), and `postures_withheld` (the ids of the four checks' findings `finish` held back because the document recorded no complete §4a search; empty on a run that recorded one). Exit 2 means the validator rejected the document and nothing was published — fix the document, do not retry blind. Exit 1 is fatal. Exit 0 means it published.

`partial` is `true` when the run could not read the whole fleet: any cluster in `scope.skipped`, any cluster kept in scope with a `limitations` note, any cluster whose `checks_run` is short of the checks that apply to it, or a §4a search the document does not record in full — `declared_intent_searched` missing a repository from `declared_intent_repos`, or absent, on a run where one of the four checks ran. `coverage_gaps` names each one in a sentence; the last names every withheld posture, the repositories not searched, and that a dangling-target `hpa-cannot-scale` is held back with the postures. The harness then refuses to draw conclusions from silence, because a workload you never queried is not a workload that got its PDB: `resolved` comes back `0` and no resolved-delta is posted, no remediation PR is retired as stale, and the ledger issue stays open even at zero findings — `status` is still `CLEAN`, but the issue survives with a comment naming what went unread. A check declared in `checks_not_applicable` is not a gap and does not raise the flag; it left the denominator. Nothing else raises it — it is `true` if and only if `coverage_gaps` is non-empty. A fleet big enough that the description had to drop findings is not a coverage gap: those workloads were queried, the title counts them, and the body says which ones it left out.

**`silent_ok` decides silence. Do not re-derive it.** `finish` returns `silent_ok: true` only when this run moved nothing an operator needs to hear about: nothing new, nothing resolved, no coverage gap, no remediation PR opened or closed. Read the flag rather than reassembling that from `status`, `new`, `resolved`, and `partial` yourself — that arithmetic is where a run talks itself into silence it has not earned. Two rules, and they are the whole rule:

- On a **scheduled** run, `silent_ok: true` → your entire final response is exactly `[SILENT]`. Otherwise report, and every report carries `issue_url` in full.
- **An on-demand run is never silent.** If a person dispatched this job — from a kanban card or straight from chat — someone is waiting on the answer, and `[SILENT]` throws it away. Report the outcome and the ledger URL whatever `silent_ok` says.

What to report in each case:

- `silent_ok: true` — `[SILENT]` on a scheduled run, nothing else and no preamble. On `CLEAN` the ledger issue closed as completed and every open remediation PR for this stream closed with it; on `UPDATED` the ledger was rewritten but nothing moved. Dispatched on demand, say which in one line and give the issue URL.
- `status: "CLEAN"` with `resolved: > 0` — every reliability gap this ledger tracked has been closed. Report the issue URL and the count. A fleet that just became drain-safe is news, and it is the only good news this audit has.
- `status: "CLEAN"` with `partial: true` — nothing reproduced, but the ledger and its PRs stayed open because the coverage was incomplete. One line, the clean result plus the `coverage_gaps`, then stop.
- `status: "HELD"` — zero findings, but the ledger stayed open because the run did not account for findings it was carrying (`start` listed them under `carried`; `unaccounted` names the ones held): one line reporting the clean result, the held ids and the issue URL, then stop. On the next run, report each one, or list it under `resolved_because` if you re-ran its check and saw it gone.
- Any other outcome — reply with **one line**: counts by severity, new vs. resolved, skipped-cluster count if any, remediation PRs opened or closed, and the `issue_url`. Example: `Workload Reliability Audit: 2 critical, 6 major, 11 minor across 4 clusters (3 new, 1 resolved, 1 skipped, 1 remediation PR opened) — <issue_url>`. A partial audit that reads as a complete one is worse than no audit.

## Red Lines

- **Read-only against every cluster.** No `apply`, `patch`, `edit`, `delete`, `scale`, `drain`, `cordon`, or eviction — including dry-runs that reach the eviction API.
- **No hand-written issue or PR bodies, and no direct git/gh calls.** `audit_report.py` owns the ledger issue, the remediation branches, the commits, and every body it renders. Never open a second ledger issue for this stream, never open a remediation PR for a non-`manifest` finding, and never reopen a merged one.
- **No credentials in evidence.** A Secret's `data:` block, a token, or a private key never enters an excerpt; re-read with a projection that omits it.
- **A finding you cannot reproduce is dropped, not softened.** `evidence.command` is the literal command you executed; if the confirm read fails or the condition has cleared, the finding does not ship.
- **No fabricated numbers.** Resource quantities, replica counts, autoscaling targets, and probe endpoints are either read off the live object or left to a human.
- **No forbidden sources.** BigQuery, Prometheus/GMP, VPA recommendations, Policy Controller, and external blueprints are out of scope; so is delegating any part of this audit to a Cluster Agent.
- **A declaration justifies posture, never a fault.** §4a moves a candidate to `declared` only for 3.3, 3.5, 3.6(a) and 3.11, only when a repository you read names the object and pins the property, and only with `repo:path` and the lines that say so. A drain-blocking budget, a missing request or a hostname pin declared in a repository is a declared bug and stays a finding — the validator rejects any other check under `declared`, so such a document publishes nothing; a declaration you did not read does not exist.
- **Stable ids or the delta lies.** An unstable id — one that varies between runs because the `object` it is derived from moved — turns one persistent problem into an infinite stream of "new" findings.
