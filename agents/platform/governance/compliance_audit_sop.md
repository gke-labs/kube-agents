# SOP: Security & RBAC Posture Audit (Daily Governance)

**Purpose:** A read-only, fleet-wide security sweep of every managed GKE cluster. Detects privilege-escalation surfaces, over-broad RBAC, missing network isolation, and cluster-level identity misconfiguration, then emits reproducible findings into one GitHub issue — the stream's ledger — with narrow remediation Pull Requests hung off it. Cron id `compliance-audit`, schedule `20 6 * * *` (daily 06:20 UTC).

**Data sources:** `kubectl` read verbs, `gcloud container clusters|node-pools list|describe`, `gcloud projects list` (the collector's fleet enumeration), the `gke` MCP server, and the GitOps repository the collector reads with `--workspace` to locate each object's declaration — a clone, or in content mode the YAML it copies out of the broker. Nothing else. There are **no external inputs** — no blueprint, no CMDB, no BigQuery, no Prometheus, no Policy Controller / Gatekeeper, no Security Command Center, no kanban delegation to Cluster Agents. Every finding comes from a command this SOP runs itself, in this run.

---

## Execution Checklist

### 0. Open the audit run

The lifecycle is the `fleet-audit` skill's (`skills/fleet-audit/SKILL.md`, "The two-command lifecycle" and "Step 1 — `start`"): what `start` prints; what `workspace`, `findings_path`, `pending_remediation_requests` and `carried` oblige you to do; that there is no report branch; and that no issue body, PR body, commit or forge call is ever yours to write. This stream's invocation:

```bash
./skills/fleet-audit/scripts/audit_report.py start --audit compliance-audit [--repo "<owner>/<repo>"]
```

What the skill does not say:

- If multiple repositories are registered in `$GITOPS_STATE_CONFIGMAP` (`managed_repos`), pass `--repo "<owner>/<repo>"` explicitly. **Interactive session:** if no `--repo` was specified, prompt the user to choose which repository to target before proceeding. **Scheduled / unattended cron:** iterate over all repositories in `managed_repos` in sequence, running `start`, the audit and `finish` for each repository with `--repo "<owner>/<repo>"`.
- Every id in `pending_remediation_requests` gets a `kind: manifest` file during §2 and §3, whether or not this SOP would have promoted it on its own.

### 1. Enumerate the target fleet

§2's collector enumerates the fleet itself and reports one outcome per cluster; the commands below are for a cluster it reports as `"unreachable"` or `"gate-failed"`. The two scope lists, `checks_run`, `checks_not_applicable`, `limitations` and `scope.skipped` are defined in the skill ("The findings document" and "Scope, skipped, and limitations"); what follows is what this stream adds to them.

```bash
PROJECT=$(gcloud config get-value project)
gcloud container clusters list --project="$PROJECT" \
  --format='json(name,location,status,autopilot.enabled,currentMasterVersion)'
```

For each cluster whose `status` is `RUNNING` or `RECONCILING` — GKE sets the second while work proceeds on an otherwise-operational cluster, and the API server stays up throughout — pin a per-cluster kubeconfig (local-only, mutates nothing) the way `platform_mcp_server.switch_kube_context` does — see `AGENTS.md` ("Cluster Credentials") for why the path must sit under `$HERMES_HOME` — then confirm read access:

```bash
export KUBECONFIG="${HERMES_HOME:-/opt/data}/.kubeconfigs/kubeconfig_${PROJECT}_${C}_${L}.yaml"
gcloud container clusters get-credentials "$C" --location="$L" --project="$PROJECT"
kubectl auth can-i list pods --all-namespaces
```

`scope.skipped` reasons: `status` neither `RUNNING` nor `RECONCILING` → `"cluster status <STATUS>, not queried"`; `get-credentials` / `auth can-i` fails → `"no read access: <trimmed stderr>"`. Never infer a finding from a cluster you could not reach. Partial coverage is never a reason to move a cluster you did read to `scope.skipped`: name the checks that could have run there and did not, by number, in its `limitations`.

**`checks_run` is mandatory on every cluster, and it is the record of what you actually did.** Each entry is an object, never a bare string:

```json
{
  "check": "netpol-missing",
  "command": "kubectl --context prod-us-east get networkpolicy -A -o custom-columns=NS:.metadata.namespace --no-headers"
}
```

`check` is the backticked slug from the §2 heading that defines it — `privileged-container`, `netpol-missing`, and so on — never the section number and never prose. (`start` prints the full roster of sixteen, so you never have to reconstruct it from memory; the SOP still says what each check _is_.) `command` is the literal invocation you issued on that cluster for that check, carrying its `--context`/`--project` and the namespace or resource it targeted; the validator rejects one that names none of `kubectl`, `gcloud`, `gsutil`, `bq`, `helm` or `curl`, and anything under eight characters. Append the entry when the check completes, not when you plan to run it, and paste the command rather than reconstructing it afterwards: every command lands verbatim in the ledger under _How this run checked the fleet_, where a reviewer can re-run it.

**A check the cluster's shape rules out is not a gap — declare it in `checks_not_applicable`,** with a reason that names the property of the cluster ruling it out. On this stream that is one cluster shape:

- **Autopilot** (`autopilot.enabled == true`): checks 2.1–2.3 are rejected by admission for in-scope workloads, so those three are inapplicable. The cluster still belongs in `scope.clusters`, and those three go in its `checks_not_applicable`, one entry each:

  ```json
  [
    {
      "check": "privileged-container",
      "reason": "GKE Autopilot: admission rejects privileged: true and the SYS_ADMIN capability for in-scope workloads, and this cluster carries no WorkloadAllowlist that would exempt one."
    },
    {
      "check": "host-namespace",
      "reason": "GKE Autopilot: admission rejects hostPID/hostIPC/hostNetwork for in-scope workloads, and this cluster carries no WorkloadAllowlist that would exempt one."
    },
    {
      "check": "hostpath-mount",
      "reason": "GKE Autopilot: admission rejects write-mode hostPath for in-scope workloads and allows read access under /var/log alone, and this cluster carries no WorkloadAllowlist that would exempt one."
    }
  ]
  ```

  Each reason is scoped twice, and both halves are load-bearing. **In-scope workloads**, because privileged containers, host namespaces and hostPath mounts are all running on Autopilot clusters right now — they are Google's own system add-ons in `kube-system`, which the universal suppressions below remove from every check, so a reason that said the object "cannot exist here" was telling an operator something the cluster contradicts. **No WorkloadAllowlist**, because Autopilot's admission rule is a policy a customer-authored `WorkloadAllowlist` can lift (`autogke-disallow-privilege`, `autogke-no-write-mode-hostpath`, from GKE 1.32.0-gke.1000000) and a partner allowlist can lift too. The collector reads for those objects and withholds all three declarations when any exists, so the clause is verified rather than assumed — if you are writing this by hand on a `gate-failed` cluster, run the read yourself before copying the reason:

  ```bash
  for kind in workloadallowlists.auto.gke.io allowlistsynchronizers.auto.gke.io allowlistedworkloads.auto.gke.io allowlistedv2workloads.auto.gke.io; do
    kubectl --context <ctx> get "$kind" -o name
  done
  ```

  **2.9 is not in this list.** Autopilot node pools exist and carry the setting — five per cluster, each with `config.workloadMetadataConfig` — and every one of them reports the compliant `GKE_METADATA`. What Autopilot refuses is one API surface: `gcloud container node-pools list` answers HTTP 400. `clusters describe` returns the same fields, so 2.9 **runs and passes** there, and declaring it inapplicable published an enforced control as unverified.

  **Do not also name those three in `limitations`.** That field is the coverage flag: any non-empty string in it makes the run `partial`, and a fact about the cluster's shape does not stop being true next week, so the daily security stream would be pinned at `partial: true` forever — no finding on any of those clusters ever announced as resolved, no stale remediation PR of theirs ever closed, the ledger never able to retire. `checks_not_applicable` says the same thing without that cost, because it takes the three out of the denominator instead of adding them to the gaps. Checks 2.4–2.16 run there exactly as on a Standard cluster and **their findings are real** — an Autopilot cluster is audited, not skipped. A privileged-container candidate on Autopilot means admission is not holding there, and §2 reports all three node-facing checks as run for that reason.

- Any other gap on a reachable cluster — a check whose command errored, an API group that is absent — is the other case, and that one _is_ a `limitations` note: name the check and the reason there. The test is whether re-running the audit could close it. A command that errored could succeed tomorrow, so it is a gap; Autopilot's admission policy could not, so it is not. Installing a `WorkloadAllowlist` _could_ change tomorrow, which is why the three reasons name it and the collector re-reads it every run rather than treating the exclusion as permanent.

### 2. Checks

**Run the collector before evaluating any check below by hand.**

```bash
python3 ./skills/fleet-audit/scripts/collect.py compliance-audit --workspace "<the workspace Step 0 returned>" > /opt/data/scratch/manifest_compliance-audit.json
```

This is the tested, procedural implementation of every check below — see the fleet-audit skill's `collect.py`, whose own module docstring is the design record for what it covers. Unlike a single-dump stream, compliance-audit's collector issues nine distinct reads per cluster on a Standard cluster and twelve on an Autopilot one — five `kubectl` dumps (workloads; RBAC; NetworkPolicy plus Namespace; every ServiceAccount, for §2.7 and §2.14; Services, for §2.15), a best-effort `kubectl get ccnp` for §2.6's Dataplane V2 case, a best-effort `kubectl get gcp -A` for §2.12, `gcloud container clusters describe`, and then either `gcloud container node-pools list` on a Standard cluster or a best-effort `kubectl get` of each of the four allowlist types on an Autopilot one — and fails the whole cluster closed if any one of them cannot be gated. Three reads are the exception, all best-effort because their CRDs are not installed everywhere: `ccnp`, where a type the server does not serve reads as zero cluster-wide policies; the allowlist reads, one per type, where a type the server does not serve reads as no exemptions of that type; and `gcp`, whose absence means no Config Connector here and declares §2.12 inapplicable rather than clearing it. Absence is only the API server's own answer that it does not serve the type (`doesn't have a resource type`). Any other failure — forbidden, a timeout, a 5xx — is a read that did not happen: an unread allowlist type withholds all three Autopilot declarations, since the reads cannot vouch for their no-WorkloadAllowlist clause, and a failed `gcp` or `ccnp` read leaves §2.12 or §2.6 unevaluated rather than inapplicable. Its last line on stderr counts the candidates per check, and that count is the floor on `findings` — the candidates sit under each cluster's entry in `clusters[].candidates`, below its `commands`, so a read of the file's head shows none of them. Read the manifest before doing anything else:

- Every entry in `manifest.clusters` carries one `outcome`. `"collected"` means every check already ran there — do not re-run any of them by hand, and do not re-query any of those sources. `"unreachable"` or `"gate-failed"` means the collector could not cover this cluster; fall back to §1's manual enumeration for it alone, then evaluate the Flag-when/Do-NOT-flag rules below yourself against commands you issue directly. An `"unreachable"` entry whose `error` says the cluster is neither `RUNNING` nor `RECONCILING` is the one case not worth a manual retry: the state that stopped the collector will stop you too, so put it straight into `scope.skipped` with that reason. Every cluster entry also carries an `autopilot` boolean — the mode, already resolved, and on the error shapes too, because a cluster does not stop being Autopilot when a read of it fails. Take the mode from there for any cluster the manifest lists rather than re-deriving it from `clusters list`, and never transcribe a fleet-wide mode map into a script: that hand-copy goes wrong the moment a cluster is added or converted.
- For a `"collected"` cluster, copy its `commands` list verbatim into that cluster's `checks_run` — each entry already carries `{check, command}` in the exact shape the validator wants; do not retype it.
- The manifest entry may also carry `checks_not_applicable`, already filled in as `{check, reason}` — copy it verbatim into that cluster's `checks_not_applicable`. The collector writes it from three independent causes, and a cluster can hit more than one. On an **Autopilot** cluster it holds §1's three node-facing slugs and their canonical reasons; that half is **absent** when the collector found a `WorkloadAllowlist`, could not read one of the allowlist types, or when any one of the three produced a candidate — all three reasons rest on the same admission rule, so one candidate falsifies every one of them. On a cluster where **nothing survived the standard exclusions** — every Deployment, StatefulSet, DaemonSet, CronJob and unowned Pod the dump returned is in a system namespace, addon-managed, or a GKE component — it holds the workload-scoped checks 2.1–2.3, 2.11 and 2.13, and 2.7 and 2.14, which walk the workload set — all seven examined an empty set and so cleared nothing; by publication time an empty cluster and a clean one are the same absence of candidates, and the manifest is the last place the two can still be told apart. Third, on a cluster **not running Config Connector** — every cluster but the ones hosting it — it holds §2.12, whose read the API server does not serve there. The other cluster-scoped checks — nine, or eight where §2.12 is declared — stay in `commands` either way: a `cluster-admin` binding and a public control plane are still true of a cluster running nothing, and 2.6's missing NetworkPolicy reads every namespace holding a live Pod rather than the workload set. The collector excludes every declared slug from `commands`, so nothing in `checks_run` can collide with them.
- The manifest entry may also carry `checks_unevaluated`, a list of `{check, reason}` for a check whose own read failed — the `gcp` read for §2.12, or the `ccnp` read for §2.6, answering anything other than "not served". Such a check did not run, and it is not inapplicable either: leave it out of both `checks_run` and `checks_not_applicable`, and name it by number, with the reason, in that cluster's `limitations`. The collector already dropped it from `commands` and its candidates, so the cluster reads as partial and no finding the check filed there is resolved by this run.
- Every entry in a `"collected"` cluster's `candidates` is a verified finding: `check`, `cluster`, `namespace`, `object`, `severity`, and `excerpt` are already computed. What is not computed — and is still yours to write — is the `recommendation` (§4) and, for a `kind: manifest` remediation, the manifest file itself (§3's declaration rule). A candidate may also carry `declaration`, which is where this repository declares the object it names: `declaration.path` is the file, and `declaration.directory` is the directory a new sibling object goes in. It is computed by parsing the repository (a clone, or in content mode the collector's copy of its YAML), keyed on all four of cluster, kind, namespace and name, and it is authoritative — prefer it to any `grep` of your own, which is kind-blind and unanchored and is what this field exists to replace. Its **absence** is not a claim that no declaration exists: it means the object was not found, was declared twice, the collector ran without `--workspace`, or, in content mode, it could not copy all of the repository's YAML out of the broker (it logs a `WARNING` saying why). Fall back to the declaration rule's own search then. A candidate whose object no file declares may instead carry `release_declaration`, which is where this repository declares the **chart release** that renders it: `release_declaration.path` is the Argo CD `Application` or Flux `HelmRelease` file, `chart`, `repo` and `version` name the chart itself, and `values_field` is the exact field a values override belongs in. `renderer` says how that field is written: `helm` for a values mapping the chart reads by key, or `kustomize` for a list of patches, where the object comes from an overlay over a base in another repository and `chart` holds the overlay directory rather than a chart name. It appears only when `declaration` does not, because an object with its own manifest is edited there and a values override beside it would be a second expression of the same change. §3's Helm branch says what to do with it. A candidate may also carry `namespace_directory`, which answers the third and different question of where a _new_ object for this cluster and namespace goes — the one a create-an-object fix needs and neither field above can answer, because the object they would look up is the one that is missing. `namespace_directory.path` is the directory and `namespace_directory.source` is `sibling`, `overlay` or `cluster`; §3's create branch says what each obliges you to write. It is attached whatever else resolved, since an object with its own file still needs somewhere to put a NetworkPolicy that has none. A candidate may also carry `reconciler`, naming what continuously reasserts the object's spec — a Helm release, an Argo CD Application, an operator. It is read off the object's own markers and is authoritative: never write prose calling such a workload unmanaged or applied out-of-band, and never propose a `kubectl patch` or `kubectl edit` as the fix, because the next sync undoes it. A `manual` remediation on such an object says so in its note, and names where the fix belongs instead: the chart, the Application, or the operator's own configuration.
- Pass `--manifest-file <path>` to `finish` (§5) so it cross-checks your `checks_run` against what the collector actually ran — a check you claim ran on a `"collected"` cluster with no matching manifest command is rejected before publication, not after.
- A GKE cluster name is unique only inside one project and location, so the collector sweeps every project it can see — the active one and every project `gcloud projects list` returns — and names every cluster `<project>/<location>/<name>`: in the manifest entry's `name`, in each candidate's `cluster`, and so in `scope.clusters[].name` and every finding's `cluster`. Carry that form verbatim, and use it for a cluster you fall back on by hand too: `finish` matches `scope.clusters[].name` against the manifest, so a name shortened back to the bare one reads as a collected cluster the document omitted. `object` keeps the bare resource name, because `cluster` already carries the qualified one beside it; commands still take the real `--project` and `--context`. A project whose `clusters list` failed contributes one `project/<id>` entry at `"gate-failed"` instead of clusters: put it in `scope.skipped` as `{"cluster": "project/<id>", "reason": <the collector's error>}` rather than leaving it out, which would read as a project holding no clusters. The same entry sits beside that project's collected clusters when some of its zones did not respond, and `project/UNENUMERATED_PROJECTS` appears when `gcloud projects list` failed or returned a filtered list; treat both the same way. A manifest with a top-level `error` read no cluster at all, and the collector exits non-zero for it: do not call `finish`, and report the error as your one-line summary.

**A cluster the collector covered is not a cluster you query again.** The commands you issue directly exist for the `"unreachable"`/`"gate-failed"` fallback — never for confirming a candidate the collector already produced, whose evidence `finish` takes from the collector's manifest, and never for re-deriving a verdict the manifest already gives you.

This is the fleet-wide system-namespace set, and it is canonical — the cost and reliability SOPs' own namespace exclusions are derived from this pattern, so a namespace added here has to be added there too:

```bash
SYS='^(kube-system|kube-public|kube-node-lease|gke-.*|gmp-system|gmp-public|gke-gmp-system|gke-managed-.*|cnrm-system|configconnector-operator-system|krmapihosting-system|istio-system|asm-system|anthos-identity-service|config-management-.*|gatekeeper-system|composer-system)$'
```

**Universal suppressions — every check in this section:** namespaces matching `$SYS` above; objects carrying `addonmanager.kubernetes.io/mode` or `components.gke.io/component-name` (the GKE-managed add-ons — `fluentbit-gke`, `gke-metrics-agent`, `pdcsi-node`, `netd`, `anetd`, `ip-masq-agent`, `konnectivity-agent`, `gke-metadata-server`, `nvidia-gpu-device-plugin`; flagging these is the fastest way to get this audit switched off); pods with a non-empty `ownerReferences` — audit the **owning controller**, never the pod, because pod name suffixes are random. `kubeagents-system` is deliberately **not** suppressed: the harness audits itself.

**Finding identity.** **Do not write an `id`.** The harness derives it from `check`, `cluster`, `namespace` and `object`, and ignores any `id` in the file. Set those four correctly and identity takes care of itself; get one of them wrong and you have renamed the finding, which the ledger reads as the old one being fixed.

`check` is the backticked token in the `####` heading of the check that produced the finding — the slug, not a section number or a description. A slug outside this SOP's roster is rejected.

One finding per (check, object): three privileged containers in one Deployment are **one** finding listing all three in `evidence.excerpt`. Two findings that agree on all four identity fields are the same finding, and the harness refuses the document rather than silently collapsing them.

`object` is therefore load-bearing, and it must name the thing the check actually judged. 2.5 judges the **Role or ClusterRole** that carries the wildcard, so `object` is that role — not the binding that grants it, which merely proves the role is live. Naming the binding one run and the role the next is the same problem wearing two names, and the ledger reports the switch as a fix.

**Evidence.** `evidence.command` is mandatory and must be the literal command run — the manifest's `commands` entry for that check on that cluster for a `"collected"` finding, or the command you issued yourself for the manual fallback, expanded so a human can paste it unchanged. **A finding you cannot reproduce is dropped, not softened** — there is no "possible" severity.

**Credential hygiene.** Never paste a Secret's `data:` block, a ServiceAccount token, a kubeconfig, or a private key into `evidence.excerpt`. Re-run the command with a field selector or an `-o jsonpath` that omits the value and quote that output instead — the object reference proves the finding, the credential never does. The harness redacts high-confidence credential shapes as a backstop, not as the primary control.

#### 2.1 Privileged containers (`privileged-container`)

- **Flag when:** a container or initContainer sets `securityContext.privileged: true`, or adds capability `SYS_ADMIN`.
- **Do NOT flag:** universal suppressions; CSI node drivers and CNI agents shipped as GKE add-ons; Autopilot clusters — the check runs there but §1 declares it inapplicable, in the cluster's `checks_not_applicable` and not its `limitations`, unless the cluster carries a `WorkloadAllowlist`; `allowPrivilegeEscalation: true` on its own — that is the Kubernetes default and would fire on nearly every workload.
- **Severity:** `critical` — a privileged container is one escape away from owning the node and every workload on it.
- **Impact:** "Container has full host device and kernel access; compromising this workload compromises the node."
- **Remediation:** `kind: manual`. Dropping privilege can break a workload that needs one specific capability, so the owner confirms. Note the minimal replacement: remove `privileged`, add only the required `capabilities.add` entries.

#### 2.2 Host namespace sharing (`host-namespace`)

- **Flag when:** the pod spec sets `hostNetwork`, `hostPID`, or `hostIPC` to `true`.
- **Do NOT flag:** universal suppressions; Autopilot clusters, which §1 declares inapplicable unless one carries a `WorkloadAllowlist`; ingress/gateway data-plane DaemonSets that legitimately bind host ports — verify `hostNetwork` is the only flag set **and** a `hostPort` is declared, then record `minor` rather than suppressing silently.
- **Severity:** `critical` when `hostPID` or `hostIPC` is set (direct visibility into other tenants' processes and memory); `major` when only `hostNetwork` is set — it bypasses NetworkPolicy enforcement and exposes node loopback, but does not cross the process boundary.
- **Impact:** the flag-when is an **or** over three independent namespaces, so a sentence covering all three is false on most of what the check catches — a `hostNetwork`-only pod crosses no process boundary, and a `hostPID`/`hostIPC`-only pod is still fully inside NetworkPolicy. The collector composes the Impact from the flags actually set and marks it authoritative, so state it as given. What each flag contributes:

  - **`hostPID`** — every other pod's process table appears in this workload's `/proc`, so the command lines and argv-borne configuration of every tenant on the node are readable from here; where the container runs as root, which is the default, `/proc/<pid>/root` also reaches into those containers' filesystems.
  - **`hostIPC`** — the node's System V IPC and POSIX shared-memory segments are shared, so this workload can read and write memory other tenants' processes expect to be private to their own pod.
  - **`hostNetwork`** — the pod is **out of** NetworkPolicy, not merely loosely covered by it. Neither GKE Dataplane V2 nor Calico enforces policy on a host-networked pod (upstream leaves the behaviour undefined; Calico's `IsValidCalicoWorkloadEndpoint` rejects such pods outright, which is why they disappear as rule **peers** as well as targets — projectcalico#1987, closed `not_planned`). From another node the traffic arrives as the node IP, describable only by an `ipBlock` over the node CIDR; from the same node it is allowed unconditionally, with no `ipBlock` recourse. It also reaches every node-local listener bound to `127.0.0.1`.

  Never write "bypasses NetworkPolicy enforcement" for this: it reads as a policy that still applies and is merely weaker, and it sends a reader looking for a policy fix that does not exist.

- **Remediation:** `kind: manual`. Name the field to remove; for `hostNetwork`, note that a `NodePort` Service or a Gateway listener is the supported replacement for `hostPort`. Do not propose a NetworkPolicy as a mitigation while `hostNetwork` is set — it will not apply.

#### 2.3 hostPath volume mounts (`hostpath-mount`)

- **Flag when:** the pod spec declares a `hostPath` volume that a container actually mounts.
- **Do NOT flag:** universal suppressions; Autopilot clusters, which §1 declares inapplicable unless one carries a `WorkloadAllowlist`; a declared-but-unmounted `hostPath`; the log-shipper pattern (`/var/log`, `/var/lib/docker/containers`) when **every** mount of it is `readOnly: true` — record those `minor`.
- **Severity:** `critical` when the path is `/`, `/etc`, `/proc`, `/var/run/docker.sock`, `/run/containerd/containerd.sock`, or under `/var/lib/kubelet`, **or** when any mount of it is writable — those are node takeover or credential theft. `major` otherwise: still a persistence and cross-tenant leak path.
- **Impact:** "Workload mounts a node filesystem path, giving it access to state belonging to the node and to other tenants' pods."
- **Remediation:** `kind: manual`. Name the replacement — a PersistentVolumeClaim, a ConfigMap/Secret projection, or the CSI driver appropriate to the data.

#### 2.4 `cluster-admin` bound to non-system subjects (`cluster-admin-binding`)

- **Flag when:** a ClusterRoleBinding to `cluster-admin` names a ServiceAccount outside the system namespaces (`kube-system`, every `gke-*` namespace, `gmp-system`, `cnrm-system`, `configconnector-operator-system`, `krmapihosting-system`, every `config-management-*` namespace), or a `User`/`Group` that is neither a `system:` principal nor a Google-managed service identity (`gke-*`, `service-<number>@…`, or any principal ending `.gserviceaccount.com`).
- **Do NOT flag:** `Group/system:masters` (the GKE bootstrap binding); GKE-installed `gce:*` / `system:*` bindings; `cnrm-system/cnrm-controller-manager`, which requires it by design. A `Group` that is an organisation email domain is an intentional human-admin grant — downgrade to `minor` and name the group rather than suppressing it.
- **Severity:** `critical` — a `cluster-admin` ServiceAccount turns any pod compromise in its namespace into full cluster compromise. A binding naming several flagged subjects is one finding naming them all, `minor` only when every one is an organisation group.
- **Impact:** "Subject holds unrestricted read/write on every resource in the cluster, including Secrets in every namespace."
- **Remediation:** `kind: manual`. Give the binding name, its subjects, and the verification step a human runs first: `kubectl auth can-i --list --as=system:serviceaccount:<ns>:<sa>`, then delete the binding and substitute a scoped Role.

#### 2.5 Wildcard verbs/resources in bound Roles and ClusterRoles (`wildcard-rbac`)

Intersect wildcard-carrying Roles/ClusterRoles against ClusterRoleBindings/RoleBindings and report only ones bound to a non-system subject (same subject test as 2.4). An unbound over-broad role grants nothing.

- **Flag when:** a binding grants the role to a non-system subject and it holds a rule that is either **(a)** `verbs: ["*"]` together with `resources: ["*"]`, `apiGroups: ["*"]`, or the core group (`apiGroups: [""]`); or **(b)** `apiGroups: ["*"]` and `resources: ["*"]` with the verbs written out, at least one of which writes (`create`, `update`, `patch`, `delete`, `deletecollection`, `impersonate`, `escalate`, `bind`). Enumerating verbs rather than typing `*` is a spelling, not a boundary: `ClusterRole/argocd-server` carries `verbs: ["delete","get","patch"]` over every resource in every group.
- **Do NOT flag:** roles labelled `kubernetes.io/bootstrapping=rbac-defaults` or named `system:*`; **unbound** roles; a wildcard confined to one vendor apiGroup (`apiGroups: ["kubeagents.io"], resources: ["*"]`) — that is the operator-owns-its-own-CRDs pattern, not an escalation. A wildcard over the core group (`apiGroups: [""]`) or any other Kubernetes group — a dotless one like `apps`, or one under `k8s.io` like `rbac.authorization.k8s.io`, where `*` lets a subject grant itself cluster-admin — is never suppressed; `x-k8s.io` groups are SIG-project CRDs and count as vendor groups. Under (b), a rule whose verbs are only `get`/`list`/`watch` is the ordinary cluster-monitoring shape — Prometheus, a backup agent — and reporting it is the false-positive flood §1 exists to avoid.
- **Severity:** `critical` in a ClusterRole (fleet-wide blast radius); `major` in a namespaced Role, where damage is bounded to one tenant.
- **Impact:** the excerpt is the matched rules verbatim followed by `; bound to <principals>`, so **read the verbs and claim only what they grant.** Naming a power the rule does not confer sends an owner to defend against the wrong thing, and the verb list disproving you is printed directly above the sentence.

  - `verbs: ["*"]` — "Subject can perform any verb on any resource in this scope, including reading Secrets and creating privileged pods — an unbounded escalation path."
  - Verbs written out, and one of them is `bind`, `escalate`, or `impersonate` — the ceiling is the same, so the sentence above still holds; say which verb reaches it, because that one verb is the whole finding and an owner trimming the list needs to know it cannot stay.
  - Verbs written out and none of those three — "any verb" is **false** and you must not write it. RBAC escalation prevention refuses a subject without `bind`/`escalate` a binding granting more than it already has, so the path is real but indirect, and describing it as direct invites a reviewer who knows that to discount the finding. Build the sentence from the verbs that are present, and no others: `get` or `list` reads every Secret in every namespace; `create` makes privileged pods directly, while `patch` or `update` gets there the long way, by rewriting an existing `kube-system` workload into one and taking the node; `delete` or `deletecollection` alone destroys any object in the cluster, which is data loss and denial of service rather than credential theft. Close on the route rather than the label: "…so the subject reaches cluster-admin by rewriting a privileged workload, not by granting itself the role."

  A verb list matching none of these shapes takes the last branch. Understating an escalation costs a reader one follow-up; overstating one costs the audit its credibility. The collector builds this sentence from the parsed verbs and marks it authoritative, so `finish` restores it over anything published in its place — the branch above is what the collector does, not a reading task handed to you.

- **Remediation:** `kind: manual`. The excerpt ends `; bound to <principals>` — those are the subjects to enumerate, and they are the only ones. Name `kubectl auth can-i --list --as=<principal>` as the verification step a human runs first, and say that its output is what the enumerated replacement rule set is built from. Do not run it and do not quote output from it: `--as` is in the command policy's impersonation set, so every invocation is refused with `identity.caller-supplied-impersonation`, and an excerpt that appears to hold its output can only be invented. Naming a different subject is worse than naming none: `ClusterRole/argocd-server` was once sent to diff against `argocd-application-controller`, which holds `verbs: ["*"]` on `["*"]`, so any proposed replacement passed.

#### 2.6 Namespaces with no enforcing NetworkPolicy (`netpol-missing`)

- **Flag when:** a non-system namespace is in a default-allow posture, which it reaches three ways: it has **zero** NetworkPolicies; any policy in it is an allow-all (`podSelector: {}` with an empty ingress rule), which opens every pod whatever narrower policies sit beside it, because policies are additive; or it holds real policies but **some live pod is selected by none of them**. The third is not a weaker version of the first. NetworkPolicy is additive and pod-scoped, so a pod no policy selects has no policy applied and is reachable from anywhere, exactly as if the namespace had none — and a namespace whose policies name four workloads by label is fully policed for those four and unpoliced for anything else running beside them.
- **Do NOT flag:** universal suppressions; namespaces with zero workloads (no live pod: `kubectl get pods -n <ns> --no-headers --field-selector=status.phase!=Succeeded,status.phase!=Failed | wc -l` is `0`) — no exposure, pure churn; namespaces already covered by a cluster-wide policy under Dataplane V2 (`kubectl get ccnp -o name`).
- **Severity:** `major` for zero policies and for partial coverage alike — in both, some pod accepts traffic from anywhere and the namespace boundary and RBAC are all that hold. `minor` for an allow-all: the team engaged with NetworkPolicy and the fix is a one-line edit.
- **Impact:** the excerpt names which of the three you are looking at, and **only the first two license a sentence about every pod in the namespace:**

  - `no NetworkPolicy in this namespace`, or `allow-all (…)` — "Every pod in this namespace accepts traffic from every pod in the cluster; a compromise anywhere reaches these workloads unimpeded."
  - `<n> of <m> pods here are selected by no NetworkPolicy that enforces Ingress: <names>` — that sentence is **false** here and you must not write it: the other `<m> − <n>` pods are policed, and saying otherwise tells an operator their working policies do nothing. Say instead: "The named workloads accept traffic from every pod in the cluster, while the rest of the namespace is policed — so the gap is invisible in a policy review that only asks whether this namespace has NetworkPolicies." Title the finding for the gap (`kubeagents-system has pods no NetworkPolicy selects`), not for an absence that is not there (`kubeagents-system has no NetworkPolicy`).

  An excerpt matching none of the three shapes takes the second branch, not the first: understating an exposure costs a reader one follow-up, and overstating one costs the audit its credibility. The third arm's sentence is written by the collector and marked authoritative — `finish` restores it over anything published in its place, because a run has already published the first arm's sentence over a partial-coverage finding whose own title took the correct branch. The first two arms are yours to write.

- **Remediation:** the three flag conditions are not three different problems — the first and third take the same fix, and the second is fixed by adding no file at all.

  - **Zero policies, and partial coverage** — the policy that would close the gap does not exist, so §3's create rule applies: `kind: manifest`, with §3 deciding the path by finding where this namespace is already declared. Generate **exactly one** `NetworkPolicy`, `default-deny-ingress` (`podSelector: {}`, `policyTypes: [Ingress]`, no `ingress` rules), and nothing else. The empty `podSelector` is right for the partial case too, and does not disturb the pods already covered: additivity cuts both ways, so a pod selected by both this policy and an existing allow rule keeps everything that rule permits. What changes is only that a pod nobody wrote a rule for is no longer reachable by default.
  - **Allow-all only** — the offending policy _is_ the finding, and adding a second file does not fix it. NetworkPolicy is additive: a pod is reachable if **any** policy selecting it permits the traffic, so a deny-everything policy sitting alongside an allow-all one changes nothing. Emitting it produces a pull request that merges cleanly, closes the finding for exactly one run, and leaves the namespace as open as it was — worse than no fix, because it also spends the reviewer's trust. Name the allow-all policy in `object` as `NetworkPolicy/<name>` and fix _that_ object, under §3's change-an-existing-object rule: `kind: manifest` **only** when the GitOps repo already declares it — `remediation.path` is that existing file, rewritten as the policy's complete desired manifest with the empty `ingress` rule removed (`podSelector: {}`, `policyTypes: [Ingress]`, no `ingress`) and its name unchanged — and `kind: manual` otherwise, because the harness will not edit or delete a live object it cannot find declared. Never write a second file for this branch.

  In every branch `remediation.note` says the policy is ingress-only and that the team adds per-service allow rules before merge. **Never add a second policy that lists `Egress` in `policyTypes`** — including an "allow DNS" companion. Any policy naming `Egress` makes every pod it selects egress-isolated, so pairing one with the default-deny does not soften it: it default-denies all outbound traffic for those pods and permits only what that policy allows. Egress isolation is a separate, deliberate, breaking change, and this audit does not make it.

#### 2.7 Default ServiceAccount token automounting (`default-sa-automount`)

- **Flag when:** a workload resolves to the `default` ServiceAccount **and** neither the pod spec nor the `default` SA object sets `automountServiceAccountToken: false`. Both must agree — the SA-level setting suppresses the pod-level default.
- **Do NOT flag:** universal suppressions; workloads using a dedicated named ServiceAccount — a mounted token there is intentional, and whether its RBAC is right is 2.4/2.5's job; namespaces whose `default` SA already sets `automountServiceAccountToken: false`.
- **Severity:** `major` — the mounted token is a live API credential handed to a workload that by definition did not ask for one, and it is the standard first move after a container compromise.
- **Impact:** "Workload mounts an API-server credential by default rather than by request, handing an attacker who lands in the container an authenticated foothold for free." Not "a credential it does not use" — the check reads the ServiceAccount reference and the automount flag, and neither says whether the workload calls the API server. Asserting an unobservable is what lets an owner refute a true finding on a false clause.
- **Remediation:** the namespace's `default` ServiceAccount with `automountServiceAccountToken: false`. That ServiceAccount already exists in the cluster, so §3's rule applies: `kind: manifest` only when the repo already declares it — rewrite that declaration complete — and `kind: manual` otherwise. One file fixes every workload in that namespace, so emit it once per namespace and point all of that namespace's findings at the same path. Where §3a lists one of that namespace's workloads under `declared`, the shared file would take that workload's token too, so `finish` turns the namespace's remaining 2.7 findings to `kind: manual` with a note naming the declared workload; the fix is then per pod spec, or on the account once the declared workload sets `automountServiceAccountToken: true` on its own.

#### 2.8 Workload Identity not enabled on the cluster (`workload-identity-off`)

```bash
gcloud container clusters describe "$C" --location="$L" --project="$PROJECT" \
  --format='json(workloadIdentityConfig.workloadPool,nodeConfig.serviceAccount)'
```

- **Flag when:** `workloadIdentityConfig.workloadPool` is absent or empty.
- **Do NOT flag:** Autopilot clusters — the check runs there, but Workload Identity is always on and the field always populated, so it simply never fires; clusters in `scope.skipped`, which you could not read and about which you therefore have no evidence either way. A `limitations` note is **not** a suppression: on a cluster in `scope.clusters`, run every check its `limitations` string does not name.
- **Severity:** `critical` — without it every pod authenticates to Google Cloud as the node service account, so all workloads on a node share one identity and pod-level IAM is impossible.
- **Impact:** "All pods on this cluster share the node service account's Google Cloud permissions; there is no per-workload IAM boundary."
- **Remediation:** `kind: gcloud` — `gcloud container clusters update <C> --location=<L> --project=<PROJECT> --workload-pool=<PROJECT>.svc.id.goog`. Note that node pools must then move to `GKE_METADATA` (2.9) and that this recreates nodes.
- **Ownership.** This check owns the Workload Identity verdict for the whole fleet; the Fleet Consistency Drift audit defers its `workload-identity` facet here (its §4.2) rather than reporting the same cluster in a second ledger. An absolute check is strictly stronger than a majority vote — a fleet that has Workload Identity off everywhere produces no drift finding at all, and still every cluster is wrong.

#### 2.9 Node pool exposes the legacy GCE metadata endpoint (`legacy-metadata`)

```bash
gcloud container node-pools list --cluster="$C" --location="$L" --project="$PROJECT" \
  --format='value(name,config.workloadMetadataConfig.mode)'
```

- **Flag when:** a node pool's `config.workloadMetadataConfig.mode` is empty or `GCE_METADATA` — metadata concealment is off and any pod can read `169.254.169.254`.
- **Do NOT flag:** pools already reporting `GKE_METADATA`. This check **runs on Autopilot** and is not in §1's not-applicable list: the pools exist and carry `config.workloadMetadataConfig`, `gcloud container node-pools list` merely refuses to show them (HTTP 400), and the `clusters describe` the collector already issues returns the same field. Every Google-managed pool reports `GKE_METADATA`, so the check simply never fires there — the same shape as 2.8, and honest positive coverage rather than a hole in the denominator. Detection is configuration-only **by design** — probing the endpoint live would need `kubectl run`/`exec`, both write verbs forbidden by the Red Lines, and the node pool mode is authoritative for this control anyway.
- **Severity:** `critical` — one unauthenticated HTTP request from any pod to a node-wide credential.
- **Impact:** "Any pod on this node pool can read the node service account's access token from the legacy metadata endpoint and escalate to that identity's full Google Cloud permissions."
- **Remediation:** `kind: gcloud` — `gcloud container node-pools update <POOL> --cluster=<C> --location=<L> --project=<PROJECT> --workload-metadata=GKE_METADATA`. Note that this drains and recreates the pool's nodes.

#### 2.10 Public control plane with no authorized networks (`public-control-plane`)

```bash
gcloud container clusters describe "$C" --location="$L" --project="$PROJECT" \
  --format='json(privateClusterConfig.enablePrivateEndpoint,masterAuthorizedNetworksConfig,controlPlaneEndpointsConfig.ipEndpointsConfig.enabled,controlPlaneEndpointsConfig.ipEndpointsConfig.enablePublicEndpoint,controlPlaneEndpointsConfig.ipEndpointsConfig.authorizedNetworksConfig,controlPlaneEndpointsConfig.dnsEndpointConfig.allowExternalTraffic)'
```

Both authorized-networks surfaces are selected whole. GKE keeps the config on `masterAuthorizedNetworksConfig` or on `controlPlaneEndpointsConfig.ipEndpointsConfig.authorizedNetworksConfig` and rejects a cluster that sets both, so selecting one calls a cluster restricted through the other wide open — and selecting named leaves under either drops `gcpPublicCidrsAccessEnabled`, which decides the finding.

- **Two endpoints, and authorized networks gates only one.** The IP endpoint is what this check was written for. The DNS endpoint is a separate address (`gke-<hash>.<region>.gke.goog`) that GKE answers on whenever `controlPlaneEndpointsConfig.dnsEndpointConfig.allowExternalTraffic` is `true`, and **no IP allowlist applies to it** — it is gated by IAM alone. So authorized networks suppresses the IP path and nothing else: a cluster whose IP endpoint is allowlisted and whose DNS endpoint takes external traffic is still answering the internet, and reporting it clean is a false negative rather than a pass. Select the field in the describe above or the check cannot see it.
- **An allowlist that leaves `gcpPublicCidrsAccessEnabled` on is not an allowlist.** The flag excepts Google Cloud's external addresses from `cidrBlocks` — those of every Compute Engine VM, Cloud Run service and Cloud Function in every Google Cloud project, not this project's alone — so an attacker starts a VM anywhere on Google Cloud and is inside a list that reads as a single `/32`. **It defaults to on**, and `--enable-master-authorized-networks` does not turn it off: run against a live cluster with no mention of the field, that command returns `enabled: true`, the requested `cidrBlocks`, and `gcpPublicCidrsAccessEnabled: true`. Suppressing on `enabled` alone therefore graded the cluster clean the moment someone acted on this finding, which is the worst place for a false negative to sit.
- **Flag when:** any of these paths is open — (a) `controlPlaneEndpointsConfig.ipEndpointsConfig.enablePublicEndpoint` is `true`, or, only where GKE returns no `ipEndpointsConfig`, the legacy inversion `privateClusterConfig.enablePrivateEndpoint` is not `true`; or (b) `controlPlaneEndpointsConfig.dnsEndpointConfig.allowExternalTraffic` is `true`. Path (a) is suppressed only when an authorized-networks surface has `enabled: true`, `gcpPublicCidrsAccessEnabled: false`, and no default route in its `cidrBlocks`; path (b) is never suppressed by it. `ipEndpointsConfig.enabled: false` means no IP endpoint at all, so `enablePublicEndpoint` beneath it is moot.
- **A default route is any prefix of length zero, not the string `0.0.0.0/0`.** A dual-stack cluster writes `::/0`, and matching the v4 spelling alone reads that as an allowlist and drops the finding on a control plane open to every IPv6 address there is. The same test governs `enabled`: GKE returns a populated `masterAuthorizedNetworksConfig` carrying only `gcpPublicCidrsAccessEnabled` on clusters that never turned the feature on, so a cluster is restricted because `enabled` is `true`, never because the object is non-empty.
- **`gcpPublicCidrsAccessEnabled` absent reads as on**, never as off. The API omits it on a cluster that never set it and defaults it to `true`, so treating absence as `false` calls that cluster narrowed on the strength of a field it does not have.
- **Do NOT flag:** clusters with `enablePrivateEndpoint: true` — there is no public endpoint, so authorized networks are moot; a narrow but unfamiliar CIDR list, where `gcpPublicCidrsAccessEnabled` is `false`. Judging whether a specific CIDR _should_ be allowed needs an external source of truth this audit does not have; only a literally unrestricted list is a finding. Nor `enabled: true` with `gcpPublicCidrsAccessEnabled: false` and no `cidrBlocks` at all: that allowlists nothing and so shuts the endpoint, and reading an empty list as "nothing allowlisted, therefore open" would report the most locked-down clusters in the fleet.
- **Severity:** `critical` — the API server answers the whole internet with only credentials in front of it.
- **Impact:** the paths are not the same exposure, so write the arm the finding is actually on. Naming the IP endpoint's exposure on a cluster whose IP endpoint is allowlisted overstates what is open and sends the reader to a control that is already correct.
  - **The IP endpoint is open** with no allowlist, or with one holding a default route (whether or not the DNS endpoint is too): "The cluster's API server accepts connections from any address on the internet; credential compromise or an API-server CVE is directly exploitable from outside the network."
  - **The IP endpoint carries a real allowlist and `gcpPublicCidrsAccessEnabled` is on:** "Authorized networks is enabled on the cluster's public IP endpoint, but gcpPublicCidrsAccessEnabled excepts Google Cloud's external addresses from the allowlist — those of every Compute Engine VM, Cloud Run service and Cloud Function in every Google Cloud project, not this project's alone. An attacker starts a VM anywhere on Google Cloud and is inside the allowlist, so the allowlist narrows reachability to whoever can create a Google Cloud resource rather than closing it." Do not write the sentence above it on this arm: the operator has already turned authorized networks on, and telling them the endpoint answers every address reads as a check that did not notice.
  - **Only the DNS endpoint is open**, the IP endpoint being absent or allowlisted — open with "The IP endpoint is allowlisted, but the cluster also serves" when an allowlist suppressed it, and "The cluster serves no public IP endpoint, but it does serve" when there is none, then: "a DNS endpoint that resolves and answers from any address on the internet. Authorized networks do not gate it — IAM does, so reaching the API server needs a Google identity holding `container.clusters.connect`, and the exposure is that identity's blast radius rather than an unauthenticated API server. Widening the authorized-network list, or narrowing it, changes nothing about this path."
- **Remediation:** `kind: gcloud`, and which command depends on the same arm — the authorized-network flags do nothing to the DNS endpoint, and `--no-enable-dns-access` does nothing to the IP endpoint.
  - IP endpoint open: `gcloud container clusters update <C> --location=<L> --project=<PROJECT> --enable-master-authorized-networks --master-authorized-networks=<CIDR[,CIDR...]> --no-enable-google-cloud-access`. The CIDR list must come from a human; say so in `remediation.note` and do not invent one. `--no-enable-google-cloud-access` is not optional and is not a no-op on a public cluster — without it the allowlist admits every Google Cloud external address and this check still fires. Where the grant is already off, the flag changes nothing and stays in the command.
  - DNS endpoint open: `gcloud container clusters update <C> --location=<L> --project=<PROJECT> --no-enable-dns-access`. Nothing here needs a human-supplied value, but the flag closes the endpoint for everyone, so `#`-comment above it that anyone reaching the cluster over `gke-<hash>.<region>.gke.goog` today loses access.
  - Both open: both commands, one per line, in that order.
  - The harness appends both of these if you leave them out — `audit_report.repair_public_control_plane_commands`, reading which arm fired off the collector's excerpt rather than off this text. That is a backstop, not a substitute: the 2026-09-06 run published sixteen of these and all sixteen stopped at `--enable-master-authorized-networks`, which is how the backstop came to exist. Write the command in full, and do not delete either half on the grounds that the other covers it.

#### 2.11 Pod Security `restricted` profile gaps (`podsecurity-gaps`)

The collector resolves `runAsNonRoot` per container by walking container-level then pod-level `securityContext`, stopping at the first one that actually **sets** the field — absent and `false` are different states, and only checking whether the resolved value is `true` catches a container that explicitly sets `runAsNonRoot: false` over a compliant pod-level default. A manual fallback read must preserve that distinction: do not fold "unset" and "false" together into one default.

Only three of the five settings inherit that way. `PodSecurityContext` carries `runAsNonRoot`, `runAsUser` and `seccompProfile`; it carries neither `allowPrivilegeEscalation` nor `capabilities`, which exist only on the container. A pod-level value for those two is not a value the kubelet reads, so do not fall back to one — that grades a container clean on a setting nothing applied to it.

- **Flag when:** a container neither inherits nor sets `runAsNonRoot: true` — **including a container that explicitly sets `runAsNonRoot: false` over a compliant pod-level default** — or explicitly sets `runAsUser: 0`, or has no `seccompProfile.type` of `RuntimeDefault`/`Localhost`, or does not set `allowPrivilegeEscalation: false`, or does not carry `ALL` in `capabilities.drop`. These are the five container-level settings the restricted profile requires, and the remediation below already writes all five: detecting three of them reported the litellm deployment as needing a seccomp profile when it also escalates privilege and drops no capabilities.
- **Do NOT flag:** universal suppressions; any workload already reported by 2.1 — the privileged finding subsumes this one, never emit both; namespaces labelled `pod-security.kubernetes.io/enforce=restricted`, where admission already guarantees it.
- **Severity:** `minor` — these are defence-in-depth defaults rather than live escalation paths, and the fix is mechanical. Rating them `major` would drown the critical findings, which is how an audit becomes noise.
- **Impact:** "Containers miss the container-level settings the restricted Pod Security Standard requires: running as root, an unfiltered syscall surface, retained Linux capabilities, or privilege escalation left enabled. A runtime escape starts with capabilities to use rather than having to acquire them."
- **Remediation:** the workload already exists, so §3's rule applies. When the repo declares it, `kind: manifest` at that declaration's own path, rewritten as the workload's **complete** desired manifest with `spec.template.spec.securityContext` set to `{runAsNonRoot: true, runAsUser: 10001, seccompProfile: {type: RuntimeDefault}}` and each container's `securityContext` to `{allowPrivilegeEscalation: false, capabilities: {drop: [ALL]}}`, everything else carried over unchanged. `remediation.note` states the UID is a placeholder the image owner must confirm. When you cannot find a declaration, `kind: manual` with the same change spelled out in `recommendation.action`.

#### 2.12 Config Connector has stopped applying a declaration (`kcc-object-wedged`)

```bash
kubectl --context "$CTX" get gcp -A -o json
```

`gcp` is the category Config Connector registers across every CRD it installs, so that one read returns every object it owns. On a cluster that is not running it the API server does not serve the type at all, the command exits non-zero saying so (`doesn't have a resource type`), and §1 declares this check inapplicable there — which on a fleet with one Config Connector host is every cluster but that one, so a fleet-wide run producing one finding is the expected shape and not a partial sweep.

**A non-zero exit is not always that, and the difference matters most on the cluster this check exists for.** A category read is not one list call: `kubectl` expands `gcp` to every CRD carrying the category — 221 of them on one hub — and lists against each, so the read is slow exactly where Config Connector is installed and near-instant everywhere else. Under the collector's parallel sweep the hub's read overran the timeout on 2026-09-06, the first day this check was live, and the collector reported it as though the API server had refused the type: "Config Connector is not installed on this cluster", about the one cluster running Config Connector. The read now gets its own longer timeout, and a timeout is reported as `Undetermined` rather than as absence — as is any other non-zero exit that does not carry the unserved answer, a forbidden read or a 5xx among them. Treat the two reasons as saying opposite things — absence means there was nothing here to clear, `Undetermined` means the check did not run and this cluster is uncovered.

This is the only check here that audits the mechanism the other fifteen depend on. A wedged controller does not crash, does not log outside the object, and emits no event: it requeues the reconcile every two minutes indefinitely. Everything downstream keeps working and keeps lying — the repository says one thing, GCP holds another, and every pull request merged against that object, **including a remediation this audit itself opened**, changes nothing on the cloud. On 2026-09-06 the merged fix for a `firewall-world-open-ingress` critical sat 403-ing for four hours while tcp:22 and tcp:3389 stayed open to `0.0.0.0/0` in front of fourteen externally-addressed instances; the audit republished the finding each run with no way to say why it would not clear.

- **Flag when:** an object's `Ready` condition has `status: "False"`. Absent conditions are not a finding — that is the normal state in the seconds after an apply, and reading it as one fires on every fresh commit.
- **One hit per cause, not per unready object.** An object whose `Ready` reason is `DependencyNotReady` is correct in itself and waiting on another object. Emitting one finding each would have turned the 2026-09-05 incident — one `PubSubTopic` short of `roles/pubsub.editor`, fifteen `ContainerCluster`s stalled behind it — into sixteen findings with one fix, spending the report's body budget on symptoms. The collector counts them onto each cause's excerpt instead. The exception is a cluster where **every** unready object reports `DependencyNotReady`: the cause is then not a Config Connector object at all, there is nothing else to name, and each is emitted at `minor` with its own impact.
- **`DependencyNotFound` is a cause, not a dependent.** It reads like `DependencyNotReady` and means the opposite: the referent does not exist, so no repair to another object will ever clear it and the object naming the missing reference is the one to act on. A live probe on 2026-09-06 confirmed Config Connector writes the two distinctly — the same `ComputeFirewall` got `DependencyNotFound` pointed at an absent network and `DependencyNotReady` pointed at one that existed and had failed to create. Fold only the second.
- **Do NOT flag:** an object with no `Ready` condition; an object `Ready=True`, whatever its other conditions say. Do not read `status.conditions` as proof a **fix** landed either — that is the inverse error, and `kcc-does-not-revert-spec-absent-fields` is the case where the condition is green and the field was never written.
- **Severity:** `critical`. Not for the stalled object's own blast radius, which varies — a stuck `PubSubTopic` is not a stuck firewall — but because the declared state and the live state have diverged with no bound on how long, and nothing else in the fleet reports it. It is also rare: two objects in two days on a sixteen-cluster fleet, so rating it `critical` floods nothing.
- **Impact:** "Config Connector has stopped applying this declaration. The GCP resource holds whatever state it drifted to, the repository says something else, and every pull request merged against this object — including a remediation this audit proposes — changes nothing on the cloud until the controller is unblocked."
- **Remediation:** never `kind: manifest`. Editing the manifest is exactly the thing that is not being applied, so a pull request against it merges, closes the finding for one run, and changes nothing.
  - **The reason names a denied permission** (`403`, `PERMISSION_DENIED`, `Required "…" permission`) — `kind: gcloud`, granting the role that carries it to the controller's service account: `gcloud projects add-iam-policy-binding <PROJECT> --member=serviceAccount:<the SA named in the message> --role=<ROLE>`. Read the permission out of the message and name the role that actually holds it; do not infer it from the resource type. `compute.firewalls.update` lives in `roles/compute.securityAdmin`, not in `roles/compute.networkAdmin`, which grants only the read — that mistake is what produced the four-hour window above.
  - **Anything else** — a bad reference, a field the API rejected, a resource deleted out from under its dependents — `kind: manual`. Put the object's namespace, kind and name in `recommendation.action` with the reason verbatim and `kubectl -n <ns> describe <kind> <name>` as the first step. Do not guess at the fix from the message alone.
  - Either way, say in the note that the finding stays open until the object reports `Ready=True`, and that the Config Connector controller log (`kubectl -n cnrm-system logs <the controller pod> -c manager`) is where a retry is visible — `underlying resource already up to date` is the line that means it cleared.

#### 2.13 A container image reference that does not name specific bytes (`image-floating-tag`)

Read from the workload dump the collector already takes at the top of §2; no extra command.

`image: app:latest` is not a version, it is a lookup performed again on every pull. Restart a pod, scale up, replace a node, lose a Spot instance, and the kubelet re-resolves the tag against whatever the registry serves at that moment — so the pod that comes back can be running code nobody deployed, with no change to the manifest and nothing in the cluster recording that it happened. The same reference is what a rollback resolves, so rolling back does not go back. Every incident that starts "nothing changed" and ends at a different image digest is this.

- **Flag when:** a container or init container's `image` carries no `@sha256:` digest and either ends in one of `latest`, `main`, `master`, `dev`, `nightly`, `stable`, `edge`, or carries no tag at all (which the runtime resolves to `latest`).
- **Deliberately not a "does this look like a version" heuristic.** `v2`, `stable-3` and `python3.12` are mutable in practice and indistinguishable from a pin by shape, so a heuristic either misses them or flags every tag in the fleet. The list above is the set that can be asserted to move. A semver-looking tag is out of scope here even though it is also unpinned — a check that fires on every container in every cluster is a lint rule, and this audit does not publish those.
- **The excerpt carries the digest the tag currently resolves to,** read from the live pods' `status.containerStatuses[].imageID`. That digest is the whole reason this finding is worth a pull request: pinning to what is already running changes no bytes, so the diff is reviewable in one line and cannot break the workload. Six excerpt shapes, and they are not interchangeable — `-> currently running <digest>` is the pinnable case, `live pods are split across N digests` is proven drift inside one pod-template revision (listing only the split revisions' digests, and saying so when no live pod writes the template's reference), `N pod-template revisions live, all writing this reference, resolved to N digests` is the same drift across revisions (a `rollout restart` or an env-only edit made a new revision without changing the image, and the tag moved between the pulls), `N pod-template revisions live, one digest each` is a rollout still in flight that changed the image (the excerpt does not say which revision is newest, so the reviewer picks the pin once the rollout finishes; remediate it like the split arm at `minor`), `no running pod to read a digest from` means there is nothing to pin to yet, and `no live pod runs this reference yet; they still write <reference>` means the template was changed and its pods not yet replaced (an `OnDelete` update strategy, a paused rollout), so the running digest belongs to the old reference and pinning to it would undo the change (a digest an admission webhook added to the pod's reference, beside the tag or in place of it, does not count as another reference).
- **Do NOT flag:** a reference already carrying `@sha256:`, including `tag@sha256:` which is pinned despite the tag; an `imageID` that is not a registry digest (`docker://`, a bare id — a locally-loaded image, and pinning to one produces a manifest no other node can pull); and the universal suppressions of §1.
- **Severity:** `minor`, except `major` where the live pods of the same container are **already running different digests** under one image reference — inside one pod-template revision, or across revisions whose pods all write the template's reference. Two revisions each on its own digest under different references is a rollout, not drift. An unpinned tag is present in every fleet and grading all of it `major` buries the ledger's real `major` findings under hygiene; pods that have actually diverged are a live incident — which build a request gets depends on which pod it lands on, and nobody chose the bytes either way. That split is what the check grades, not the unpinned reference itself.
- **Impact:** "The manifest does not say which bytes run here, so every restart, rescale, node replacement and preemption re-resolves the tag and can bring back different code with no deploy and no record. A rollback resolves the same reference, so it does not go back." On the split arm: "This workload's live pods are already running different builds of \<containers\> at the same time, because the tag was re-resolved when a pod restarted, rescaled or was replaced. Which version a request gets depends on which pod it lands on, and no deploy was made to cause it." On the across-revisions arm: "This workload's live pods are running different builds of \<containers\> under one image reference: a template change made a new revision without changing the reference, and the tag resolved to different bytes for it. The revision was deployed on purpose; the bytes it brought were not chosen by anyone, and which build a request gets depends on which pod it lands on."
- **Remediation:** `kind: manifest` where the workload is declared, `manual` where it is not.
  - **Where the excerpt gives one digest,** replace the image reference with it verbatim and say in `recommendation.rationale` that this is the digest the cluster is already running, so the change is a no-op at merge. Keep the tag alongside it (`app:1.4.2@sha256:…`) where the original had a meaningful one: the tag is then documentation and the digest is the contract. Do not shorten the digest, and do not write one that is not in the excerpt.
  - **Where the pods are split,** the pin is a decision, not a copy: one of the digests is what the workload is supposed to be running and the audit does not know which. Name every digest in the excerpt in `recommendation.action`, recommend the one the newest pod is running if the excerpt supports it, and say in `recommendation.risk` that pinning to the other rolls half the workload backwards — and where the excerpt says the pods still write another reference, that neither digest is the template's and a pin would revert its change, so `kind: manual`.
  - **Where there is no digest at all,** or the live pods still write another reference, there is nothing to read for this one. `kind: manual`, with the pull the reviewer must run to get one (`docker buildx imagetools inspect <image>` or `gcloud artifacts docker images describe <image>`) in `recommendation.action`. **Never invent a digest.** A wrong one is an `ImagePullBackOff` on merge, which is a worse outcome than the finding.
  - **Where `reconciler` names a Helm release,** the image is set from the chart's values and the manifest in the cluster is generated, so a pull request against the rendered object is reverted at the next sync. Target the values file instead: §3's Helm branch says where, and `image.digest` or `image.tag` is the key to confirm with `helm show values`.

#### 2.14 A token mounted for a ServiceAccount nothing has granted (`unbound-sa-automount`)

Read from the workload and RBAC dumps the collector already takes at the top of §2; no extra command.

2.7 covers the `default` ServiceAccount and stops there, which was the right scope when it was written and is no longer where this shape lives. A chart that follows current practice creates a ServiceAccount of its own, so `serviceAccountName` is set and 2.7 goes quiet — and then most charts bind that ServiceAccount to nothing, because the workload never calls the API server, and leave `automountServiceAccountToken` alone, because it defaults to on. What is left is a live API credential in the container filesystem that exists for no reason, on a workload 2.7 by construction cannot see.

- **Flag when:** a workload resolves to a **named** (non-`default`) ServiceAccount that exists in the cluster, no `RoleBinding` or `ClusterRoleBinding` anywhere names it as a subject, and neither the pod spec nor the ServiceAccount object sets `automountServiceAccountToken: false`.
- **The unbound test is what makes this promotable.** "This workload does not use its token" is not readable from a manifest, which is why 2.7's impact sentence deliberately refuses to claim it. "Nothing has granted this ServiceAccount anything" is a different statement — provable from the RBAC dump, and it means the API server gives the token nothing. It does not prove nothing else reads the token: a verifier outside the cluster that reviews it with its own identity — Vault's `kubernetes` auth method is the common one — needs no binding here. Short of that, the token is unused or the workload is already failing every API call it makes, and turning the mount off makes a second problem visible rather than a worse one.
- **Do NOT flag:** the `default` ServiceAccount, which is 2.7's finding — never emit both on one object; a `serviceAccountName` naming a ServiceAccount that does not exist, because that pod mounts no token and does not start, so there is nothing to turn off; a pod template annotated `vault.hashicorp.com/agent-inject` true, whose injected sidecar logs in to Vault with exactly this token; a ServiceAccount any binding names, however narrow the Role — whether that grant is right is 2.4/2.5's business; and the universal suppressions of §1.
- **A cluster that grants every ServiceAccount something by group suppresses the check entirely.** A binding whose subject is `system:authenticated` or `system:serviceaccounts` grants the whole group without naming a ServiceAccount, so on a cluster carrying one every finding this check could emit would be false. `system:serviceaccounts:<ns>` does the same for one namespace, and suppresses the check for workloads in `<ns>` only. Kubernetes ships four such bindings on every cluster — `system:basic-user`, `system:discovery`, `system:public-info-viewer` and `system:service-account-issuer-discovery` — and those are the baseline every authenticated principal already has, so they do not count. Anything else does, and the check reports nothing on that cluster rather than reporting something untrue.
- **An explicit projected `serviceAccountToken` volume is not an exclusion.** `automountServiceAccountToken` governs only the default `kube-api-access-*` volume; a workload federating to an external audience through its own declared projected volume keeps working across this fix — unlike the Vault Agent sidecar, which reads the default mount. GKE Workload Identity is likewise unaffected — it reaches Google Cloud through the metadata server, not through this token.
- **Severity:** `major` — the same grade as 2.7, for the same reason and with a stronger claim behind it.
- **Impact:** "This workload mounts a live API-server credential into every container, and no RoleBinding or ClusterRoleBinding grants the ServiceAccount it belongs to anything. An attacker reaching the filesystem — through a path-traversal read, an SSRF the container proxies, a leaked log of the token, or code execution — gets an authenticated identity on the API server for free, and authenticated is the boundary most of a cluster's defences are written against. No grant in this cluster stands behind the token, so the workload loses nothing here by turning the mount off."
- **Remediation:** `automountServiceAccountToken: false` on the **pod template**, not on the ServiceAccount object. Both spellings work and they are not equivalent: the ServiceAccount is shared, so setting it there changes every workload using that identity — including one added later by someone who does expect a token — while the pod-template setting is scoped to the workload the finding names. The workload already exists, so §3's change-an-existing-object rule applies: `kind: manifest` only when the repo declares it, rewriting that declaration complete, and `kind: manual` otherwise. Where `reconciler` names a Helm release, target the values file — most charts expose this as `serviceAccount.automountServiceAccountToken` or `automountServiceAccountToken`, and a pull request against the rendered object is reverted at the next sync. Say in `recommendation.risk` that this check cannot see a consumer outside the cluster that reviews the token itself (a secrets manager's Kubernetes login, a token-exchange endpoint), so the reviewer must rule one out, and that the check to run first is `kubectl -n <ns> logs <a pod> | grep -i forbidden` and that a workload which turns out to need the API server shows it as a 401 rather than a 403 after the change.

#### 2.15 A LoadBalancer Service publishing a management port to the internet (`lb-world-open`)

Read from a `kubectl get svc -A -o json` the collector takes for this check alone; no extra command.

`type: LoadBalancer` is an instruction to the cloud provider to put a public address and a forwarding rule in front of some pods, and GKE carries it out without asking what is behind them. Point one at a database and the database is on the internet. Nothing objects: the Service admits, the balancer provisions, `EXTERNAL-IP` fills in, and every check anyone would think to run says the Service is healthy — because it is, and it is doing exactly what the manifest asked. It is one field that does it, and usually a copied one: a Service written `ClusterIP` for local work and promoted to reach it from a laptop, a chart whose `service.type` is set in the values file used for every environment, a datastore moved out of `kube-system` with its Service carried across intact.

- **Flag when:** a Service has `spec.type: LoadBalancer`, publishes a TCP port in the management set below, sets neither `networking.gke.io/load-balancer-type: Internal` nor the legacy `cloud.google.com/load-balancer-type: Internal`, and has no `spec.loadBalancerSourceRanges` that restricts anything.
- **The management set is 22 (SSH), 1433 (MSSQL), 2379 and 2380 (etcd), 3306 (MySQL), 3389 (RDP), 5432 (PostgreSQL), 6379 (Redis), 9200 (Elasticsearch), 10250 (kubelet) and 27017 (MongoDB)**.
- **Do NOT flag the web ports (80, 443, 8080).** A LoadBalancer publishing a web port to the internet is a LoadBalancer doing its job; admitting them reports every one in the fleet, daily.
- **Do NOT flag:** a Service every one of whose assigned `status.loadBalancer.ingress` addresses is RFC 1918 — it is not reachable from the internet whatever the spec says, and calling it exposed is simply wrong; a `loadBalancerSourceRanges` that restricts to real CIDRs, however wide, because GKE programs that into the firewall in front of the forwarding rule and it is enforcement rather than intent (a list holding `0.0.0.0/0`, or one entry that will not parse, restricts nothing and stays a finding); a UDP port that happens to share a number, since none of these are UDP services; `type: NodePort`, which GKE's node firewall does not admit from outside by default; and the universal suppressions of §1.
- **The fix is the Service, not the firewall rule.** GKE's service controller writes the `k8s-fw-<hash>` rule for a Service from the Service's spec and rewrites it back, so narrowing that rule by hand merges, reconciles, and is reverted. The durable fix is the Service's own `loadBalancerSourceRanges` or internal-LB annotation.
- **Nor is it §3.1 of the AI security SOP.** `inference-endpoint-public` flags any world-reachable model endpoint and is always `manual`, because the range of callers a model server is meant to serve is a fact about intended usage no audit can read. Here there is no such range: nothing legitimately reaches a cluster's Redis, etcd or kubelet port across the open internet. That is what makes this one promotable.
- **Severity:** `critical`.
- **Impact:** "This Service holds a public load-balancer address that forwards a management or datastore port straight to its pods, with no source-range allowlist in front of it. Anyone on the internet can open a connection to it, so the only thing standing between the service behind that port and the whole internet is whatever authentication that service does itself — and the ports here belong to software that is routinely deployed with none, on the assumption that the network is the boundary. Public address ranges are scanned continuously, so this is found without being looked for."
- **Never write the address into `evidence.excerpt`, `recommendation` or `remediation`.** These findings are filed as comments on a public GitHub issue, and for this check the whole content of the vulnerability is where to connect. The port names what is exposed and the count of assigned addresses carries the scale; neither hands a reader the target. The same rule §3.1 of the AI SOP states, for the same reason.
- **Remediation:** `kind: manifest` on the Service's own declaration, per §3's change-an-existing-object rule; `kind: manual` where nothing declares it. Take the change in this order and say in `recommendation.rationale` which rung you took and why:
  1. **`type: ClusterIP`,** where nothing outside the cluster needs the port. This is the fix for the promoted-for-debugging case, which is most of them. You cannot read "nothing outside needs it" off the manifest, so propose it only where something in the repository says so — a Service of the same workload already publishing the traffic port, an Ingress or Gateway in front of it, a comment or a values key naming the port as internal. Say in `recommendation.risk` that any caller reaching this address from outside the VPC loses it.
  2. **The internal load balancer,** `networking.gke.io/load-balancer-type: "Internal"` in `metadata.annotations`, where callers outside the cluster but inside the VPC do need it. Use that spelling and not the legacy `cloud.google.com/` one. Say in `recommendation.risk` that the address changes when the balancer is replaced, so anything holding the old one — a connection string, a firewall rule, a DNS record — has to be repointed, and that a caller reaching it over Interconnect or a VPN keeps working while one on the public internet does not.
  3. **`spec.loadBalancerSourceRanges`,** where the port genuinely has external callers. This one the audit cannot complete: the CIDRs are a fact about who those callers are. Propose the field, leave the ranges to the reviewer, and say so — do not invent a range, and never write `0.0.0.0/0` as a placeholder, which merges as the same finding with a field added.
- Where `reconciler` names a Helm release or an Argo CD Application, the rendered Service is reasserted at the next sync and §3's release branch applies: the override goes at `release_declaration.path`. Most charts expose the type as `service.type` and the annotations as `service.annotations`; confirm both against `helm show values` before proposing them, per §3.

#### 2.16 A binding whose subject is everyone rather than someone (`anonymous-rbac-binding`)

Read from the same RBAC dump as 2.4 and 2.5; no extra command.

2.4 and 2.5 run every subject through one test, and that test returns false for any `User` or `Group` whose name begins `system:`. It has to: GKE ships dozens of `system:`-prefixed bootstrap bindings on every cluster, and reporting them is the flood §1 exists to avoid. What it also excludes is the three `system:` subjects that are not a component identity but a wildcard over callers, so the worst binding anyone can write is the one shape those two checks cannot report — a ClusterRoleBinding of `cluster-admin` to `system:anonymous` produces nothing from either. This section is that gap and nothing else.

- **Flag when:** a ClusterRoleBinding or RoleBinding names `User/system:anonymous` or `Group/system:unauthenticated` and its `roleRef` is not the anonymous arm's one baseline role below — **or** it names `Group/system:authenticated`, the role it points at resolves in the same dump, and that role carries at least one of `create`, `update`, `patch`, `delete`, `deletecollection`, `impersonate`, `escalate`, `bind` or `*`.
- **The two arms are graded on different evidence, and that is deliberate.** For an anonymous subject the role does not matter: `view` bound to `system:anonymous` hands every ConfigMap, every pod spec and every Service in the cluster to whoever can reach the endpoint. For `system:authenticated` it decides, because a read-only grant to that group is how a great many organisations make a cluster browsable — 2.14 already treats it as a legitimate posture rather than a defect, and a section calling it critical here would be arguing with that one.
- **Do NOT flag:** on the authenticated arm, `system:basic-user`, `system:discovery`, `system:public-info-viewer` or `system:service-account-issuer-discovery`, and on the anonymous arm `system:public-info-viewer` alone — those are the bindings Kubernetes ships, and not a choice anyone made (`system:basic-user` and `system:discovery` lost their anonymous subject in Kubernetes 1.14 and `system:service-account-issuer-discovery` never had one, so binding any of them to an anonymous subject re-enables anonymous access and is reported); a `system:authenticated` binding whose role is read-only, per the arm above; a `system:authenticated` binding whose `roleRef` names a role absent from the dump, which grants nothing today and has no verb list to build a sentence from; `system:serviceaccounts` and `system:serviceaccounts:<ns>`, which are universal in the same way but name workloads rather than people and belong to 2.14; and the universal suppressions of §1. A namespace suppression does **not** apply here — a binding in `kube-system` granting anonymous access is worse than one anywhere else, not exempt.
- **Severity:** `critical` on both arms. A binding naming several universal subjects is one finding naming them all, with the anonymous impact whenever an anonymous subject is among them.
- **Impact:** two sentences, and the collector picks which. Anonymous: "This binding grants a caller that presented no credential at all. Every other control in the cluster — Workload Identity, ServiceAccount tokens, authorized networks, the whole of RBAC — is written on the assumption that reaching the API server means holding an identity, and this binding removes that assumption for the resources it names. If the control plane has a public endpoint, the caller is the internet." Authenticated: "This binding grants write access to `system:authenticated`, which is not a team — it is every principal the API server accepts a credential from. On GKE that is every Google account holding `container.clusters.get` on the project, so the set of people who can write to this cluster is whatever the project's IAM happens to say today, and it widens every time someone is added to the project for an unrelated reason."
- **Read 2.10 before you write the recommendation.** Whether the control plane has a public endpoint decides how much of the anonymous impact sentence's last clause is true, and it is in the same report — a cluster carrying `public-control-plane` alongside this finding is reachable from the internet by an unauthenticated caller today, and one with a private endpoint and no authorized-network gap is reachable from the VPC. Say which, and do not write "the internet" where the evidence says otherwise.
- **Remediation, anonymous arm:** `kind: manifest` on the binding's own declaration. The fix is to delete the subject, or the whole binding where it has no other subject — nothing legitimate depends on anonymous access, which is what makes this one safe to promote without a human deciding who replaces the grant. Where the object has no declaration in the repo, `kind: manual` with `kubectl delete clusterrolebinding <name>` named as the step.
- **Remediation, authenticated arm:** `kind: manual`, always. Deleting this binding removes every human's access at once and the audit cannot see who was relying on it. Name the binding, the role and the verbs, give `kubectl auth can-i --list --as-group=system:authenticated` as the verification step a human runs first, and propose the replacement as a shape — the same role bound to the named groups that turn out to need it — rather than as a diff. Do not run the command and do not quote output from it, for the reason 2.5 gives.
- Where `reconciler` names a Helm release or an Argo CD Application, §3's release branch applies as everywhere else. A chart that renders a binding to one of these subjects usually does it behind an `rbac.create` or a `rbac.clusterWideAccess` values key; confirm against `helm show values` before proposing one.

### 3. Generate remediation artifacts

How a `manifest` finding becomes a pull request — auto-promotion and its five-per-run cap, `/remediate <finding-id>` and `/remediate all`, the branch keyed on the group's path set, and why a path is discovered and never invented — is the skill's ("Remediation pull requests", and the `path` rule under "The findings document"). Write every `kind: manifest` file into the `workspace` clone §0 named, **before** calling `finish`, including one for every id in `pending_remediation_requests`; a path with no file behind it degrades that finding to `kind: manual`, which converts a fix a reviewer could have merged into one a human writes by hand. What this stream adds is which checks edit an existing object and which create one, and what the collector's `declaration`, `namespace_directory` and `release_declaration` fields (§2) oblige you to write:

- **Changing an object that already exists** — 2.7's `default` ServiceAccount, 2.11's workload, and 2.6's other branch where the namespace already has an allow-all policy — goes to that object's **existing declaration in the GitOps repo**: take it from the candidate's `declaration.path` (§2) and name that file as `remediation.path`, falling back to locating it in the `workspace` (`grep -rl "name: <object>" --include='*.yaml' <workspace>`, or in content mode `audit_report.py grep`) only where the candidate carries no `declaration`, and rewrite it as the object's complete desired manifest — as declared, never as read back from the cluster: a manifest is a proposal, so it carries no live `resourceVersion`, `uid`, `managedFields` or `status`. Never write a patch fragment: a file carrying `metadata.name` and a partial `spec` is not valid `kubectl apply` input, and a second file claiming an object the repo already declares is a duplicate resource id that both Config Sync and Argo reject.
- **Creating an object the cluster does not have** — 2.6's NetworkPolicy on a namespace with **zero** of them — goes in a directory the target already reconciles. **Find that directory, never assume it, and take the collector's answer over your own.** The candidate's `namespace_directory` (§2) is the field for exactly this case, parsed out of the repository rather than grepped, and `namespace_directory.path` is the directory. Its `source` is the only part that changes what you write: `sibling` and `cluster` take a plain new file, and under `cluster` you must **set `metadata.namespace` explicitly**, because that directory serves the whole cluster and nothing else will supply it; `overlay` means the path is a Kustomize root, which renders only the files its `resources:` list names — and a remediation carries one file, so it cannot add the new object and the entry that makes it render in the same change. Such a finding is `kind: manual`: put the manifest and the `resources:` line it needs in `recommendation.action`. Where the object being fixed has its own declaration and the new object belongs beside that specific object rather than anywhere in the namespace, `declaration.directory` (§2) is the better anchor. Only where the candidate carries neither, fall back to the namespace and not to a name: `grep -rl "namespace: <namespace>" --include='*.yaml' <workspace>` (in content mode, `audit_report.py grep`) finds the files declaring objects that live in it, and you must then **open what it returns and confirm it before you trust it** — the file must declare an object you actually observed on the target cluster in that namespace. Write the new file into whichever directory you land on, named for the object it creates, matching the naming style of the files already there.
- **A `namespace_directory` the candidate carries is not something to argue with.** The question has been answered against the repository, so writing "no file in this repository declares an applied object in namespace `<ns>`" over the top of it publishes a denial of a fact the run measured — which is a defect whichever of you is right. On 2026-09-07 three findings wrote exactly that sentence, one of them about `podinfo-kustomize` on `spot-capacity-test`, a namespace the collector had already resolved to a directory in the clone. Its **absence** is no claim either way: the index is empty when the collector ran without `--workspace` or, in content mode, could not copy all of the repository's YAML out of the broker (it logs a `WARNING` saying why), and two candidate directories are refused rather than guessed between.
- **Never anchor with `grep "name: <namespace>"`.** `grep` is kind-blind and unanchored: `name: <ns>` also matches every `app.kubernetes.io/name:` label line and every object whose name merely starts with the namespace's, so it finds files that declare nothing in the namespace at all — including files under another cluster's directory, and control-plane files that no workload reconciler applies. A hit is not a declaration until you have opened it.
- **If the anchors land in more than one directory, or you cannot tie one to the target cluster, the finding is `kind: manual`.** Namespace names repeat across a fleet and `grep` does not know which cluster a directory feeds. Guessing puts a namespaced object into another cluster's applied tree, where the namespace may not exist — that fails the whole tree's sync, so it is worse than writing nothing. So is a namespace nothing in the clone declares, and an object that already exists with no declaration you can find and no `release_declaration`: put the manifest you would have written in `recommendation.action`, write no file, and omit `remediation.path`.
- **An object no file declares because something renders it is fixed with an override on that, and it is `kind: manifest`.** A chart's workloads, and an overlay's over a base in another repository, have no manifest of their own — the object exists only after the chart or the overlay is expanded — so until now every one of them ended here as `manual`. Where the candidate carries `release_declaration` (§2), it does not: the override goes in the file at `release_declaration.path`, in the field `values_field` names, rewritten complete like any other manifest and never as a fragment of one. This is the branch that decides most of 2.11's volume, because a container security context is exactly the kind of field a chart renders and an operator never sees.
- **Where `release_declaration.renderer` is `kustomize`, the override is a patch rather than a values key.** Append to the list `values_field` names an entry whose `target` matches the object the finding names — `kind`, `name`, and `namespace` all three — and whose `patch` carries only the fields you are changing. There is no chart to interrogate and no key that might not exist: a strategic-merge patch reaches any field the object has, so the bullet below does not apply. What a patch can still get wrong is its `target`: one given only a `kind` rewrites every object of that kind the overlay renders, turning a one-workload finding into a fleet-wide change nobody asked for.
- **Where `renderer` is `helm`, confirm the values key exists before you propose it.** Read the chart's own defaults: `helm show values <chart> --repo <repo> --version <version>`, taking all three from `release_declaration` (omit `--version` when it is empty, and say in `note` that the release tracks an unpinned revision). **Set only keys that appear in that output**, and match the key to the object the finding names rather than to the chart top level — a chart rendering a controller and a webhook keys them apart. 2.11 usually reaches `securityContext` or `containerSecurityContext` and 2.14 `serviceAccount.automountServiceAccountToken`, both near-universal; charts that expose neither exist, which is why the read is not a formality. Where no key reaches the field, the finding is `kind: manual` and says which key you looked for and did not find.
- One file per remediation, and 2.7 is the one check here that produces a remediation group: every finding in a namespace points at that namespace's single `default` ServiceAccount declaration, so all of them are one group, on one branch, in one PR. Every other check is one finding, one path, one PR. A namespace with a declared 2.7 workload leaves this group: its findings are manual (2.7).
- For `kind: gcloud` and `kind: manual`, write no file and omit `remediation.path`. Put the full command or ordered human steps in `remediation.note`, with real cluster, location, project, and object names substituted — no angle-bracket placeholders except the human-supplied CIDR in 2.10. A `gcloud` note is rendered inside a bash fence, so it must be shell-pasteable: commands on their own lines, and caveats (2.8 and 2.9 both recreate nodes; 2.10 needs a human-supplied CIDR, and its `--no-enable-google-cloud-access` cuts off callers reaching the control plane from a Google Cloud external address) as `#` comment lines above the command they guard. A `manual` note is rendered as prose and should read as prose.

### 3a. Check declared intent before reporting a posture

Two checks judge a **posture** — a shape an owner may have chosen on purpose — rather than a fault: 2.6 `netpol-missing` in its zero-policy and partial-coverage shapes, which name the namespace (`Namespace/<ns>`), and 2.7 `default-sa-automount`, which names the workload. A namespace that talks to nothing and a workload that needs the token the default ServiceAccount mounts are choices an owner may declare. The allow-all shape of 2.6 names the policy (`NetworkPolicy/<name>`) and is a fault: `finish` refuses to apply a declaration to it and the validator rejects a `declared` entry naming it, so a note that names a policy changes nothing. So is every other check in §2 — a privileged container or a `cluster-admin` binding declared in a repository is a declared bug, and it stays a finding.

The step is the one the obtainability SOP's §4a describes, and the harness does its half the same way here:

- **The harness searches first.** `start` reads every repository in `declared_intent_repos` (the GitOps repository plus each `context_repos` entry) for OKF notes whose frontmatter carries a `declares:` list, files what it finds at `declarations_path`, and lists each repository it read completely under `declared_intent_searched`. `finish` moves every finding a filed declaration covers to `declared` (§4) itself. A candidate a note covers is still written to `findings`: `finish` is what moves it, and a candidate you leave out because you found the note yourself gives `finish` nothing to move.
- **What counts as a declaration.** An item `{check, namespace, object}`, optionally `cluster`, with `check` one of the two slugs above and `object` as `Kind/name`: `Namespace/<ns>` with `namespace: <ns>` for 2.6, the workload's `Kind/name` in its namespace for 2.7. The match is case-blind on those fields, scoped `(check, cluster, namespace, object)` first and fleet-wide second. An item with any other slug, a missing field or an `object` that is not `Kind/name` is skipped with a warning, and the rest of the note still counts. Body text is never read.
- **Where the harness looks**, how it records the commit it read, what you do for a repository it could not read, and what a search you could not complete means are the obtainability SOP's §4a, word for word: a repository `start` read completely needs nothing from you; one it could not read is one you copy, grep and record yourself under `declared_intent_searched` as `owner/name@sha`, or leave as the coverage gap it is. Never write a `declared` entry for a declaration you did not read.
- **A step you skipped is visible, not silent.** Whenever any cluster's `checks_run` names 2.6 or 2.7, `finish` requires `declared_intent_searched` to cover every slug in `declared_intent_repos`. Anything less is no search: `finish` withholds every 2.6 and 2.7 finding, the other checks publish, the ledger names each withheld posture under _Declared intent not searched_, and the run is `partial`.

### 4. Emit findings.json

The document's schema and every rule the validator enforces — `checks_run`, `checks_not_applicable`, the derived id, `evidence`, the three `recommendation` strings, the rendering caps — are the skill's ("The findings document", "Evidence rules", "Size"). Write the whole document to `findings_path` in one shot, with `audit: "compliance-audit"`, `scope.clusters` listing every cluster you queried and `scope.skipped` only the clusters you could not read. What this stream adds:

- Write the checks you ran, never the full sixteen because the SOP lists sixteen. An honest seven-of-sixteen costs you nothing but an open ledger, and an honest twelve-of-twelve on a cluster where the other four cannot apply closes it; a slug parked in `checks_not_applicable` because you ran out of turns is a coverage gap the ledger will never show.
- `namespace` is `""` for cluster-scoped findings (2.4, 2.5, 2.8, 2.9, 2.10); `object` is `<Kind>/<name>` (`Deployment/api`, `ClusterRole/dev-admin`, `NodePool/pool-1`, `Cluster/prod-usc1`) and names the object the check judged — for 2.5 the wildcard-bearing Role or ClusterRole, not its binding.
- `remediation.path` is present iff `kind == "manifest"` and that file exists on disk.
- `declared_intent_searched`: a top-level list of `owner/name@sha` strings, one per repository §3a searched. Required in effect whenever any cluster's `checks_run` names 2.6 or 2.7: together with the list `start` printed under the same key, it must cover every slug `start` printed under `declared_intent_repos`, or `finish` withholds those two checks' findings as a coverage gap (§3a). Omit the key only on a run where neither check ran anywhere.
- `declared`, optionally: one entry per posture you moved out of `findings` yourself — `finish` adds the entries for the notes `start` filed — each carrying `check` (2.6 or 2.7 only), `cluster`, `namespace`, `object`, `title` and `declaration` with `repo`, `path` and `excerpt`. No severity, no remediation, no id; a declared fault exits 2 and publishes nothing.
- A `limitations` note suppresses nothing: findings from the checks that _did_ run on that cluster belong in the file.
- Trim `evidence.excerpt` to the lines that prove the finding rather than pasting a dump, and never drop a real finding to keep the ledger short.
- Three `rationale`/`risk` pairs in this SOP are check-specific and must not be written generically: 2.8 and 2.9 both recreate nodes, so say so in `risk`; 2.10's `risk` follows the arm its remediation is on — an incomplete CIDR list locks every operator out of the API server, which is why the list comes from a human; `--no-enable-google-cloud-access` on the same command cuts off anything reaching the control plane from a Google Cloud external address that the CIDR list does not name, which is where Cloud Build, Cloud Shell and CI runners on Compute Engine reach it from; and `--no-enable-dns-access` cuts off everyone who reaches the cluster over the DNS endpoint today.

### 5. Close the audit run

```bash
./skills/fleet-audit/scripts/audit_report.py finish --audit compliance-audit \
  --findings-file /opt/data/scratch/findings_compliance-audit.json \
  --manifest-file /opt/data/scratch/manifest_compliance-audit.json \
  [--repo "<owner>/<repo>"]
```

What `finish` validates, publishes and prints, its exit codes, partial coverage, the held close and the silence rule are the skill's ("Step 3 — `finish`", "Partial coverage", "The clean run"). Pass `--manifest-file`: it is what lets `finish` check the document against what the collector actually ran. Given a manifest, `finish` rejects a `checks_run` entry on a `"collected"` cluster that names a check the manifest never ran for it, rejects a `"collected"` cluster the document leaves out of `scope.clusters` altogether, rejects a `"gate-failed"` target the document is silent about, and takes each finding's `evidence` from the matching candidate. On a run where §2's collector produced no manifest — every check on every cluster came from the manual fallback — pass `--no-collector-manifest "<why>"` in its place; that publishes, but reports the reason as a coverage gap, so the run is partial.

**Two checks here auto-promote.** 2.15's world-open management port and 2.16's anonymous arm are the `critical` checks whose remediation is a `manifest`, and both are a deletion or a narrowing a reviewer can read in full in one screen. Every other `critical` check is `gcloud` or `manual` — 2.12 never a manifest, because editing the declaration Config Connector has stopped applying changes nothing. The `manifest` checks at `major` or `minor` (2.6, 2.7, 2.11, 2.13, 2.14) stay human-requested: worth offering every morning, not worth a pull request nobody asked for. Never inflate a severity to force a PR open.

**Report.** `silent_ok` decides silence; read the flag rather than re-deriving it from `status`, `new`, `resolved` and `partial`. On a **scheduled** run, `silent_ok: true` → your final response is exactly `[SILENT]`. **An on-demand run is never silent:** if a person dispatched this job — from a kanban card or straight from chat — report the outcome and the ledger URL whatever the flag says. Otherwise one line, then stop:

- `status == "CLEAN"` with `resolved: > 0` → the issue URL and how many findings closed with it. This is the one piece of good news the audit produces.
- `status == "CLEAN"` with `partial: true` → the clean result and `coverage_gaps`.
- `status == "HELD"` → the clean result, the held ids (`unaccounted`) and the issue URL. On the next run, report each one, or list it under `resolved_because` if you re-ran its check and saw it gone.
- `status == "OPENED"`, or `"UPDATED"` with a non-zero `new` or `resolved` → `Security & RBAC posture audit: <new> new, <resolved> resolved across <count(scope.clusters)> clusters — <issue_url>`

## Red Lines

The skill's "Red lines" hold in full — read-only against clusters, no `git add`, no path outside the workspace, no second ledger, no hand-written body, no padded `checks_run`, no restored `findings.json`. This stream adds:

- **Read-only.** No `kubectl apply|patch|create|delete|edit|scale|exec|run|port-forward|cp`, no `gcloud container clusters|node-pools update`, no write of any kind against any cluster. `gcloud container clusters get-credentials` is the sole exception and touches only a local kubeconfig.
- **No forge call (`vcs.py` or otherwise) and no `submit-suggestion` from this SOP.** `audit_report.py` owns the entire git and forge path: one stream has one ledger and `finish` owns it, and every remediation PR is its to open.
- **Never comment on the ledger yourself.** `/remediate` is a human reviewer's instruction to this harness, not a step in the audit: an agent that posts it — including when someone asks for a fix in chat — is authorizing its own pull request. `finish` ignores a `/remediate` from a machine account, so posting one achieves nothing but noise on the issue.
- **No unstable identity.** The id is derived, so the way to destabilise it is to write an unstable `object` — a pod name with its ReplicaSet suffix, a generated resource name, the binding one run and the role the next. Name the durable object the check judged and audit the owning controller, never the pod. A finding whose identity moves is reported as fixed and re-reported as new, on a ledger people trust to tell them what is still broken.
- **No inference from an unaudited cluster.** A cluster you could not read goes in `scope.skipped` and never appears in a finding. A cluster you read where some checks did not run stays in `scope.clusters`, with Autopilot's 2.1–2.3 in `checks_not_applicable` and anything a later run could still clear — a command that errored, an absent API group — in `limitations`. Never demote a partially-checked cluster to `scope.skipped`: that silently discards every real finding from the checks that did run on a cluster you were told to audit.
- **No forbidden sources.** No BigQuery, Prometheus, Policy Controller / Gatekeeper, Security Command Center, external blueprint, or CMDB — and no kanban delegation to Cluster Agents. This audit runs entirely in the Platform Agent.
- **Never print raw credentials.** ServiceAccount tokens, kubeconfig contents, Secret `data:` blocks, and private keys never appear in `evidence.excerpt` — record the object reference, or re-run with a field selector or `-o jsonpath` that omits the value. The harness's redaction is a backstop, not permission.
