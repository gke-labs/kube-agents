# SOP: Upgrade Retrospective (Weekly Governance)

**Cron id:** `upgrade-retrospective` — `0 18 * * 0` (Sundays, 18:00 UTC). The Chat Agent's first-run stage also marks it due once, after the inventory scan settles, with or without a GitHub repository.

**Purpose:** Report what the weekend's GKE upgrades did to the workloads on every managed cluster, so the next cluster does not meet the same failure. The other upgrade streams look ahead; this one looks back. For each cluster that is new to it, or that GKE upgraded since its last run, the collector records four things. (A) Which `UPGRADE_MASTER` and `UPGRADE_NODES` operations ran, from which version to which. (B) What stayed down, stuck or restarting afterwards, and which of the catalogue's twenty entries each symptom matches. (C) How to see the failure coming and how to fix it, written for the cluster's own objects. (D) The mitigation it set up. The collector records a guard in `guards.json`, for the readiness watch to read once its reader ships. Where a repository is linked, this stream's one ledger issue carries the finding. The run is **read-only**. It upgrades, rolls back, cordons, deletes and patches nothing, and it opens no pull request on its own.

**Data sources:** the collector `/opt/data/profiles/platform/skills/fleet-audit/scripts/upgrade_retrospective.py`, which runs `gcloud container clusters list`, `gcloud container operations list`, `gcloud container get-server-config`, `gcloud container clusters get-credentials` and read-only `kubectl get`. Also the platform_control `fleet_scope` tool for the scope (section 1), `gcloud container clusters list` per project for section 0's recovery step, `gcloud container operations list` for section 7's freshness check, the collector's store and manifest on the shell volume, and the GitOps clone `start` hands you. **Nothing else.** No BigQuery, no Prometheus, no Cloud Logging, no external blueprint, no delegation to Cluster Agents via kanban. The collector classifies and grades. You confirm each candidate against its report and copy its grade (section 3), tailor the fix (section 4), file the ledger (section 5) and write the chat lines (section 6).

## Execution Checklist

### 0. Which run this is, the lock, and the audit run

Two routes reach this SOP. The route decides the scope.

- **The scheduled tick and the first-run stage** are a **full run**: the `fleet_scope` call (section 1), the lock probe (below), `start` (with or without a repository, below), the collector with `--full` (section 2), `draft` and `finish` with the manifest (section 5), whose record is what chat receives (section 6).
- **A question someone asked** is the on-demand route. "How did our upgrades go", "did anything break when the clusters were upgraded", "anything to fix before the next one", or a question that names a cluster. Read section 7 first. It decides whether the saved report answers the question or a run is needed. It also decides whether that run is full or scoped. Then apply the sections it names.

**Resolve the scope first, on every route** (section 1). A declared scope with no readable project ends the run before the probe: the tool's `collector_args` carry `--scope-unread` alone, the collector refuses them with the line `the install's declared scope has no project this install could read this run…; nothing was swept and nothing was listed`, and that line is the run's one line in chat.

**Probe the lock before `start`.** The collector holds an exclusive lock on `.lock` under its store for the whole run (section 2). `start` leaves an in-flight note that refuses every run of this stream, a fleet-wide question included, until `finish` releases it or two hours pass. So on a full run probe first, before any note exists:

```bash
python3 /opt/data/profiles/platform/skills/fleet-audit/scripts/upgrade_retrospective.py --probe-lock
```

The probe tries the lock without blocking, holds it for no time and writes nothing. Exit 0 (`… is free; no retrospective run holds it`) means go on. Either line may end with `; a reset is pending (…/reset-pending.json): the next full run is a baseline the SOP files nothing from, run without start`: an operator ran `--reset-ledger` (section 2) and no full run has written the new baseline yet. Once the lock is free, run the baseline as the no-repository route below: the collector alone, with `--full`, the tool's flags and `--manifest-file`, and no `start`, `draft` or `finish`. Its manifest carries `after_reset: true`, which `draft` and `finish` refuse. Section 6 reports its lines; the ledger issue keeps its findings until the following full run reads the fleet again. Exit 1 prints the holder line (`another retrospective run holds … since …; nothing started`): wait fifteen seconds and probe again, for up to two minutes. Still held after that: on the scheduled route, report the holder line as the run's one line and stop, without `start`; on demand, answer from the latest saved report (section 7) and say which run holds the lock and since when. A scoped run (section 7) runs no probe: it calls neither `start` nor `finish`, and the collector itself waits up to two minutes for the lock and then prints the lock-held line (`another retrospective run holds … since …; waited 2 min for it; nothing written`) and exits 0.

**Open the audit run before the collector, where a repository is linked.** `finish` refuses a manifest that finished before the run started (`manifest_predates_run`). So on a full run the order is the probe, then `start`, then the collector, then `finish`. Read the managed repository list the way `SOUL.md` §1 says (the `managed_repos` key of `$GITOPS_STATE_CONFIGMAP`). With no GitHub entry, `start` and `finish` still run, as the streams beside this one run them: `start` prints `"mode": "none"`, `"repo": null`, `"issue": null`, a `no_forge` note and a `workspace` (the fleet-audit skill's `references/finish.md`, "No forge configured"); pass that workspace to the collector as on a linked install, then `draft` and `finish`, which stores the document in the report store, prints `status: "NO_FORGE"` with its `summary`, and writes the record the relay posts (section 6). A run that skipped them left no record, and chat then said the run did not finish. The probe runs either way. A scoped run (section 7) never calls `start` or `finish`.

```bash
/opt/data/profiles/platform/skills/fleet-audit/scripts/audit_report.py start --audit upgrade-retrospective [--repo "<owner>/<repo>"]
```

If `managed_repos` names several repositories, pass `--repo "<owner>/<repo>"` with its first entry, whatever repository a question named, and file the stream's one ledger issue there: a second repository would hold a second issue this stream never rewrites. Do not loop over the repositories with `start` and `finish` for each, as the other streams do: the second `start` scrubs the manifest, and a second collector run finds every cluster unchanged (the first run advanced the ledger) and carries the Errors only as held findings at `minor`, so the second ledger would never hold what the first does. `start` returns `{"issue": <int|null>, "repo": "org/repo", "workspace": "...", "findings_path": "/opt/data/scratch/findings_upgrade-retrospective.json", "carried": [...], "pending_remediation_requests": [...], ...}`. Keep `findings_path` (section 2 drafts the document there), `workspace` (section 4 greps it for a manifest's path) and `carried` (the ids the previous run published). `start` also removes a manifest left at the path section 2 names, so a stale one cannot stand for this run. A `START REFUSED` line means the in-flight note stands: a run of this stream is in flight, a scheduled tick's or another session's, or an earlier run left the note. There is no override. On the scheduled route, report it as the run's one line and stop. On demand, answer from the latest saved report (section 7) and say a run is in flight. A `BROKER UNAVAILABLE` line means the credential proxy did not answer: re-run the same command once it does. `start` creates and resets no branch. The helper owns all git and forge work and renders the ledger body itself. **Never hand-write a ledger body, never run `git commit` or a `vcs.py` verb yourself, and never comment on the ledger.**

**A collector exit without a manifest after `start` releases the note at once.** Three kinds of exit do that. The lock-held line, exit 0: the lock was taken between the probe and the run. A refusal of the store or of a state file, exit 2, one line on stderr: a crash record (`… sits beside no live ledger.json: a crash record, not a re-baseline. Restore it as ledger.json or run --reset-ledger to archive it; until then nothing starts from empty. Nothing written.`, or the same line for `guards.json`), a guards file absent beside a live ledger (`… is absent beside a live …: a crash record, not a re-baseline, since a run that started from no guards would announce every held finding resolved. … Nothing written.`), a state file set aside this run (`…; moved to …. A set-aside ledger or guards file is a crash record, not a re-baseline: restore it or remove it on purpose, then rerun. Nothing written.`), a symbolic link at the lock or at the store (`… is a symbolic link, which … may not be; it was not followed and is left as found. Remove it, then rerun. Nothing written.`), or a store this uid cannot write (`…; the run stops here and nothing more is written`). And a scope the collector refused (section 1), exit 2. The first two kinds end with `; this run's projects: <ids>`, the projects the collector resolved for the route, with the listing's note when it was incomplete; the scope refusal names none, so take the projects from the `fleet_scope` tool. Do not wait for the note's two-hour TTL and do not run `--reset-ledger`. Write a limitations-only findings document at `findings_path` and call `finish` with the waiver:

- `audit` is `"upgrade-retrospective"` and `findings` is `[]`.
- `scope.clusters` holds one row per cluster, each with `name` as `<project>/<location>/<name>`, `project` and `location` beside it, `checks_run: []`, and `limitations` set to the collector's exit line. The clusters are the latest saved report's (`fleet` and `reviews` in its JSON, section 7 step 1) or, when no report exists yet, the ones `gcloud container clusters list --project <p> --format='value(name,location)'` returns for each project the exit line names.
- `scope.skipped` is `[]`.

```bash
/opt/data/profiles/platform/skills/fleet-audit/scripts/audit_report.py finish --audit upgrade-retrospective \
  --findings-file /opt/data/scratch/findings_upgrade-retrospective.json \
  --no-collector-manifest "<the collector's exit line>" [--repo "<owner>/<repo>"]
```

`finish` posts a partial all-clear comment naming the gap (or opens the coverage issue when no ledger issue is open), rewrites no body, announces nothing resolved, closes nothing, returns `partial: true` and removes the note, so the next tick or the next question takes the baseline. The one case this cannot cover is a first run whose exit line names no project, or whose every named project fails to list: the validator refuses an empty `scope.clusters`, so report the exit line and the note stands to its TTL. Either way the collector's line is the run's outcome in chat (section 6).

### 1. The scope

Every route reads the fleet the way every fleet-audit stream reads it. Call the platform_control `fleet_scope` tool first. When it reports `declared: true`, the fleet is its `projects` and nothing else, and its `collector_args` go to the collector verbatim: `--scope-projects` with the resolved project set and, for the declared projects this install could not read, `--scope-unread` with each project and its outcome. When no declared project is readable they carry `--scope-unread` alone; the collector refuses them (section 0). When it reports `declared: false`, pass nothing: the collector reads the active `gcloud` project plus every project `gcloud projects list` returns. An answer that starts with `ERROR:` means the scope is unknown: run nothing and report the error as the run's one line.

Never pass `--project` on a full run: `--full` refuses it, with `--cluster` and `--since`. `--project` is a hand run's override and makes the run scoped (section 7). On an install that declares a scope the collector admits `--project` and `--cluster` only beside the tool's flags and for a project inside the readable scope; on a shell sandbox that declares a scope, a run without the tool's flags is refused and lists nothing.

### 2. Run the collector

```bash
python3 /opt/data/profiles/platform/skills/fleet-audit/scripts/upgrade_retrospective.py --full <collector_args from the fleet_scope tool, verbatim, or nothing on an install that declares no scope> --manifest-file /opt/data/scratch/manifest_upgrade-retrospective.json
```

Run it in the foreground with the terminal tool's `timeout: 600`, the foreground maximum, and never in the background: a background run outlives the turn, so you would have to poll for its end before `finish`, and a wake that starts a second run beside it is two writers past the lock. The run reads every fleet cluster on a quiet week too (pods and nodes, one list each), and re-reads every cluster that holds a guard. A second run started beside the first waits up to two minutes for the lock, then exits 0 on the lock-held line without writing. `--full` makes the run full: the collector records the handed scope as the fleet in its ledger, prunes a cluster or project that left it, adds the clusters of a project that joined, writes `reports/<finish-UTC>.md` and points `upgrade-retro-report.md` at it. A run without `--full` is scoped (section 7), whatever its `--project` set. The collector holds its own deadline under that timeout: 480 seconds (`RUN_DEADLINE_S`) from its start, the lock wait included. A read attempted past it fails with `the read budget (480 s) was spent before this read`, a read running past it is cut with `the read budget (480 s) ended this read after <n> s`, and no further cluster is started. What was read is written as a partial run. Each cluster not reached is `gate-failed` in the manifest with `not read this run: the read budget (480 s) was spent; held, read first next run`, so `draft` lists it under `scope.skipped` and `finish` holds its findings; a re-check not started keeps its guards. Info's `Read budget spent: …` line carries the counts, and the next run reads the held clusters first.

The collector writes two things. **The manifest**, at the path `--manifest-file` names, is the contract with `finish` (the fleet-audit collector-manifest design). The path is the harness's for this stream, `audit_report.manifest_path_for`: `manifest_upgrade-retrospective.json` under the scratch directory, `/opt/data/scratch` by default; `start`'s scrub of a previous run's manifest and `finish`'s `--no-collector-manifest` waiver read that path and no other. **The report**, in its store on the shell volume, is the record a reader reads and the source of every detail section 4 tailors.

**The manifest.** One entry per target under `clusters[]`, named `<project>/<location>/<name>`, each with an `outcome`. A `collected` entry carries `commands[]`: one `{check, command, rc}` per check of section 3 that ran there. It also carries `candidates[]`: one per incident the report lists under Errors or Warnings and one per failure guard the run observed again on an object with no incident (section 3), with `check`, `namespace`, `object`, `severity`, `excerpt`, `command`, `impact` and, for a held finding, `persistence`. An entry the collector could not read (`unreachable`, `gate-failed`) carries its `error` instead. Each entry also carries `facts`: the status and reasons, the versions before and after, the operations, the next upgrade and the guard ids written. A candidate's `impact` is the entry's row from the catalogue table, the generic (C). Four rules `finish` enforces from the manifest, so the document never states them by hand:

- A project the run could not list — a declared project the tool reported under `--scope-unread`, or one whose `clusters list` failed inside the run — does not demote the run. Each of its ledger-known clusters appears as `unreachable` with the listing error, the note is the manifest's `limitations`, and a `gate-failed` `project/UNENUMERATED_PROJECTS` target carries the gap even when the ledger knows no cluster there. `draft` lists them under `scope.skipped`; `finish` holds their carried findings rather than resolving them, and the run is partial. A project whose Kubernetes Engine API is off is an empty project, not a gap.
- A project whose `operations list` failed leaves `upgrade-operation-failed` under `checks_unevaluated` on each of its clusters and out of their `commands`. `draft` writes the `limitations` note, and `finish` requires the check out of `checks_run`. A project whose listing failed and that no cluster entry carries gets its own `gate-failed` `project/<id>` target, so `draft` lists the gap under `scope.skipped` and the run is partial.
- A cluster upgrading now or settling (an operation still `PENDING`, `RUNNING` or `ABORTING`, or one that reached `DONE` less than fifteen minutes before the run), a cluster none of whose reads answered, a cluster whose status rules out reading it (`cluster status <status>: not read; ledger entry and guards kept unchanged`) and a cluster the read budget left unread are `gate-failed` with the operation, the error, the status or the budget as `error`: the run read nothing on them. `draft` lists them in `scope.skipped`, and `finish` holds what the ledger carries for them.
- An unchanged cluster is `collected` with all seven checks backed by the operations listing that found no upgrade, so a Sunday on which every cluster was read and nothing was upgraded is a complete run: a clean document closes the ledger issue and runs silent.

With a repository, build the findings document from the manifest rather than by hand:

```bash
/opt/data/profiles/platform/skills/fleet-audit/scripts/audit_report.py draft --audit upgrade-retrospective --manifest-file /opt/data/scratch/manifest_upgrade-retrospective.json --out /opt/data/scratch/findings_upgrade-retrospective.json
```

`draft` writes every `collected` target to `scope.clusters`, with the commands at `rc == 0` as its `checks_run` and the collector's `limitations` copied. It writes every other enumerated target to `scope.skipped` with its error. It writes one finding per candidate, with its evidence, impact and severity. It leaves `recommendation` empty and `remediation` at `manual` for you. Sections 3 to 5 say what to verify and what to write. Never retype a `checks_run` entry. `finish` cross-checks each one against the manifest and refuses a check the collector did not run there.

**When `draft` leaves `scope.clusters` empty** — every cluster upgrading, settling or unreachable at the tick, as on a one-cluster install whose maintenance window overlaps it — move each `scope.skipped` entry into `scope.clusters` as a row with its `name`, `project` and `location`, `checks_run: []` and the entry's reason as `limitations`, and leave `scope.skipped` empty. The validator admits a row with no checks when its `limitations` says why, `finish` takes the partial clean branch, posts the gap and releases the note. The sibling SOPs' rule for zero clusters, no `finish`, would leave the note standing after `start`.

**The report.** The store is `/opt/data/upgrade-retrospective/` on the shell sandbox's volume, where your terminal runs. Your file tools see the gateway's filesystem and do not reach it, so read it with the terminal. Under the root:

- `ledger.json`: the versions, the operations reviewed and the last symptom set per cluster.
- `guards.json`: one entry per filed failure and per risk shape, kept for the readiness watch to read once its reader ships; nothing scheduled reads it yet, and section 7 reads its `kind: risk` entries for a cluster the latest report lists as unchanged.
- `reports/`: the newest fourteen full and fourteen scoped reports, Markdown and JSON by one stamp (`<YYYYMMDD>T<HHMMSS>Z`, `-scoped` for a scoped run).
- `reports/upgrade-retro-report.md`: a link to the newest full report, inside `reports/` beside the file it names; there is no `.json` link.

The Markdown report is what a reader reads: the on-demand answer (section 7) names its path and quotes its Errors and Warnings entries as the file has them, and the chat report (section 6) names the top findings by cluster and object and sends the reader here for the rest. After a full run, `readlink /opt/data/upgrade-retrospective/reports/upgrade-retro-report.md` prints `<stamp>.md`, the newest full report beside the link, and `reports/<stamp>.json` is the detail. After a scoped run it is the newest `reports/*-scoped.json`. In that JSON:

- `sections.errors[]` and `sections.warnings[]` are the incidents. Each carries `kind` (`symptom`, `operation`, `stale-guard` or `log-volume`), `severity`, `cluster`, `object`, `system`, `entries`, `predates_upgrade`, `what_happened`, `symptoms`, `mitigations` and `guards`; an operation incident carries `operation`; a stale-guard incident carries `partial`, `recheck_errors` and `unread_errors`, which say whether the guard was observed again or could not be; a log-volume incident carries `log_volume`, the container's two weeks in bytes and their ratio.
- `sections.info` holds `clean` (every reviewed cluster's next upgrade, its gate, risks and baseline), `unchanged`, `upgrading` (a row with `settling: true` is a cluster inside the fifteen-minute floor), `failed_reads`, `removed`, `rechecked`, `operation_guards`, `families` (one row per `upgrade-family` label value: its members, the canaries whose gate this run read, the family's verdict `go`, `hold` or `pending`, and the members waiting) and `gates_reread` (the pending gates a full run read again).
- `reviews[].gate` is the cluster's gate, `clear`, `risk` or `pending`, with its `reasons`, the window's anchors (`first_start`, `last_end`, `after_complete_at`) and `log_volume` (the two weeks' totals and the rows per container, `breach` on the ones past both thresholds); null for a cluster with no upgrade operation in the window. `families[]` at the top level is the same list as `sections.info.families`.
- `reviews[]` carries (A) under `what_happened` and (B) under `what_failed[]`.
- `generated_at`, `fleet`, `scoped`, `scope_reason` and `outside_fleet[]` say when the run finished and what it covered.

The collector exits 2 with one line on stderr for a usage error or for a refusal of the store or of a state file (section 0 quotes the lines). A crash record is `ledger.json.unreadable-<stamp>` beside no `ledger.json`, or `guards.json.unreadable-<stamp>` beside no `guards.json`: a previous run's state that could not be read, set aside rather than overwritten. A `guards.json` absent beside a live `ledger.json` is refused the same way: a run from no guards would announce every held finding resolved. On a full run that had called `start`, release the note with section 0's recovery `finish`; then report the line as the run's outcome and stop. A `--dry-run` reads everything without the lock, prints the report and writes nothing; it is never a run of this stream.

Do not run `--reset-ledger` yourself: it is an operator's remedy, the second after a restore of the file. It archives the records and the live `ledger.json` and `guards.json` under `archive/<stamp>/` in the store and writes `reset-pending.json` beside them. Until a full run has written the new baseline, the probe names the pending reset (section 0) and every run's manifest and JSON carry `after_reset: true`. That full run reviews every cluster as new, its Info opens with `Baseline after --reset-ledger: …`, and every guard's first-seen date and review count restart. The SOP calls no `start`, `draft` or `finish` for a run that carries the marker: `draft` and `finish` refuse an `after_reset: true` manifest, and the ledger issue keeps its findings until the following full run files them again or resolves them.

### 3. Checks

**Run the collector (section 2) before grading anything by hand.** Every candidate in the manifest is one finding: one object on one cluster. The collector decided its check by the incident's kind, section and classifications, as the seven headings below say. Your part is to confirm each candidate against the report's incident and copy its grade. A symptom the collector did not list is not an incident, and a shape in a cluster's risks table is never one.

**Finding identity.** **Do not write an `id`.** The harness derives it from `check`, `cluster`, `namespace` and `object`, and ignores any `id` in the file. `draft` fills the four from the candidate: `cluster` is the qualified `<project>/<location>/<name>`, `namespace` the object's namespace (`""` when it has none) and `object` the `Kind/name`. Never put a pod name, a version, a date or a count in `object`. The collector keys a symptom by the pod's owner, so a replaced pod is the same finding.

**Severity is the collector's.** It grades an incident under `sections.errors` as a **`major`** candidate, one under `sections.warnings` as **`minor`**, and a held finding (below) as `minor`. Nothing this stream files is ever `critical`, and none of its check ids is on the fleet-audit skill's `MAJOR_SWEEP_CHECKS`. Together those two facts keep `finish` from opening a remediation pull request on this stream's own judgement. Copy the candidate's grade: never raise it and never lower it. A grade you believe wrong is a defect in the collector's signature table; say so in `impact` and leave the grade.

**A failure from an earlier review that is still present has no check id of its own.** The collector re-emits it under the check its guard records, the one its finding was last filed under, at `minor`, with `persists since <first seen>, <n> review(s)` in the candidate's `persistence` and excerpt; the report lists it as a `kind: stale-guard` incident under Warnings. It is the same finding, held, so `finish` announces nothing resolved for it. Only an incident this run grades anew moves a finding to another check. A guard a failed read could not re-observe emits no candidate: its check is unevaluated, the run partial, and the finding returns with its first-seen date and review count when a run reads the cluster again.

**`checks_run`.** `draft` copies each `collected` target's commands into `checks_run`, each entry an object in the shape the validator wants:

```json
{
  "check": "upgrade-broke-workload",
  "command": "KUBECONFIG=/opt/data/.kubeconfigs/kubeconfig_acme-prod_prod-usc1_us-central1-a.yaml kubectl get pods -A -o json"
}
```

`check` is the backticked slug from the heading below; `command` is the read as it ran. The validator rejects an unknown slug, a duplicate and a command under eight characters. It also rejects a command naming none of `kubectl`, `gcloud`, `gsutil`, `bq`, `helm` or `curl`, and a call back into `audit_report.py`. Leave the list as `draft` wrote it. A check added by hand fails the cross-check, and a check the collector left out did not run there.

#### 3.1 GKE reported an upgrade operation as failed (`upgrade-operation-failed`)

- **The collector emits it when:** an incident under `sections.errors` has `kind: operation`: an `UPGRADE_MASTER` or `UPGRADE_NODES` operation in the window reached `DONE` with an `error` (a failed or cancelled operation finishes as `DONE` with `error` set).
- **Not for:** an operation still `PENDING`, `RUNNING` or `ABORTING`, whose cluster is under `info.upgrading` and is not reviewed.
- **Identity:** `namespace: ""`; `object` is `Operation/<name>`, the operation's own name, so two failed operations on one pool are two findings and a retry is a new one.
- **Severity:** `major`.
- **Impact:** the operation, its type and target, when it ran and GKE's error text, from `operation`.
- **Remediation:** `kind: manual`. GKE's error text names the cause. The catalogue's entry 2 (no spare capacity) and entry 5 (window too short, exclusion mid-roll) are the usual ones. The guard clears when a later operation of the same type on the same target reaches `DONE` without error, when the listing returns the operation without an error, or when the target pool is gone.

#### 3.2 The upgrade broke a workload (`upgrade-broke-workload`)

- **The collector emits it when:** an incident under `sections.errors` has `kind: symptom` and its symptoms are not node conditions: a `high`-confidence catalogue match on an object outside the system namespaces, with onset inside the upgrade window.
- **Not for:** an incident whose `predates_upgrade` is true (it sits under `warnings`); a shape under `info.clean[].shapes`, which is a risk and never an incident.
- **Identity:** the incident's object (a budget is `PodDisruptionBudget/<name>` in its namespace).
- **Severity:** `major`.
- **Impact:** what failed and since when, from each symptom's `reason`, `since` and `evidence` (`n of m pods`, the message excerpt), with the catalogue entry number and title.
- **Remediation:** `kind: manual`; section 4 writes it from the entry's row.

#### 3.3 A node stayed broken after its pool's rebuild (`node-broken-after-upgrade`)

- **The collector emits it when:** an incident under `sections.errors` has a symptom of `category: node`: a node `NotReady` or `NetworkUnavailable` after an `UPGRADE_NODES` on its pool (entry 17, `high`).
- **Not for:** a node condition on a pool no operation in the window touched (the collector grades it `medium`, under `warnings`).
- **Identity:** `namespace: ""`, `object: Node/<name>`.
- **Severity:** `major`.
- **Impact:** the condition, its transition time and the pool's operation.
- **Remediation:** `kind: manual`, from entry 17's row: downgrade the pool while GKE still offers the previous version, and fix what the node agent selected on.

#### 3.4 A tentative match, or a sure one on the cluster's own plumbing (`upgrade-symptom-tentative`)

- **The collector emits it when:** an incident under `sections.warnings` has `kind: symptom`, `predates_upgrade` false, and at least one classification whose `entry` is not null: a `medium`-confidence match (a generic `OOMKilled`, a pull failure with no untouched node to compare, a Pending pod whose pool no operation touched, a first-run match whose only onset is a recreated pod's), or a sure match on an object in a system namespace (`system: true`). A pool two or more minors behind its control plane whose skew has stood seven days or longer since the run that first recorded it (entry 5, `medium`) is one too, on `NodePool/<pool>`, when the cluster has a maintenance policy, no window is open and no exclusion is active. A younger skew, one under an open window or an active exclusion, or one on a cluster with no maintenance policy is a note in the cluster's Info block (`Version skew: …; graded once it has stood 7 d or longer.`, `Version skew held: …`, `Version skew, no maintenance policy: …`), not an incident.
- **Not for:** an incident every one of whose classifications has `entry: null` (3.5).
- **Identity:** the incident's object.
- **Severity:** `minor`.
- **Impact:** the symptom, the entry it may match and why the match is tentative, from `evidence` and `detail`.
- **Remediation:** `kind: manual`; section 4, with the alternative entry named where the collector gives two (an `OOMKilled` single-container pod is "14 or 15" when the cgroup mode is unknown).

#### 3.5 A symptom matching none of the twenty (`upgrade-symptom-unclassified`)

- **The collector emits it when:** an incident under `sections.warnings` has `kind: symptom`, `predates_upgrade` false, and every classification `entry: null`.
- **Not for:** a healthy object. The collector lists only pods not Ready, pods Pending, nodes with a bad condition, and `Warning` events since the window's first operation.
- **Identity:** the incident's object.
- **Severity:** `minor`.
- **Impact:** the symptom as the collector read it, and that no catalogue entry matched. The report is a record of the upgrade, not only of the catalogue's part of it.
- **Remediation:** `kind: manual`. The entries the collector cannot identify from one read (4, 8, 9, 10, 11, 13, 16) are the ones the readiness checks have to catch before the upgrade. Say which, if any, the symptom resembles, and that a reader has to classify it.

#### 3.6 A symptom that predates the upgrade (`symptom-predates-upgrade`)

- **The collector emits it when:** an incident under `sections.warnings` has `predates_upgrade: true`: its onset is before the window's first operation, or the previous full run already recorded it, so the upgrade did not cause it.
- **Not for:** a first-run incident whose onset is inside the window. The first run has no stored set, grades by onset alone, and says so in `baseline`.
- **Identity:** the incident's object.
- **Severity:** `minor`.
- **Impact:** the symptom, its onset, and that it was present before the upgrade. It is reported so the next upgrade is not blamed for it either.
- **Remediation:** `kind: manual`. The entry's row still applies to the object, and the fix is the same, without the upgrade as its cause.

#### 3.7 A container's log volume rose after the upgrade (`upgrade-log-volume-rose`)

- **The collector emits it when:** an incident under `sections.warnings` has `kind: log-volume`: a container whose Cloud Logging ingestion bytes in the seven days after the window's last upgrade operation are at least 2.0 times its bytes in the seven days before the first, and at least 1 GiB (`LOG_VOLUME_RISK_RATIO`, `LOG_VOLUME_RISK_MIN_BYTES`; both must hold). The read is Cloud Monitoring's `logging.googleapis.com/byte_count` on `k8s_container`, summed per namespace and container, through the credential proxy's Monitoring route; a container that logged nothing the week before and more than the floor the week after counts.
- **Not for:** a cluster whose after-week is not complete (the gate is `pending` and the check files nothing until a later run reads the full week); a rise below either threshold (it is in the cluster's `**Log volume by container.**` line under Info, not an incident); a cluster whose Monitoring read failed (the check is under `checks_unevaluated` with the read's error and the read is named in the entry's `limitations`, so the run is partial for that cluster while the cluster still counts as reviewed; the gate is `pending`).
- **Identity:** `namespace` is the container's; `object` is `Container/<container name>`.
- **Severity:** `minor`.
- **Impact:** the two weeks in bytes and the ratio, from `log_volume`, and that the rise follows the upgrade.
- **Remediation:** `kind: manual`: prepare the logging exclusion for the namespace and container, or hold the patch for the family. The rollout orchestration SOP reads this as the family's gate.

**The gate.** Every reviewed cluster with an upgrade operation in the window carries a gate, in its Info block (`**Gate.**`) and in `reviews[].gate`: `risk` when the upgrade brought an Error or a Warning (a symptom group that does not predate it and is not a recreated pod alone, or a failed operation) or a container is past both thresholds above; `pending` while the after-week is not complete, the review was partial or the Monitoring read failed; `clear` otherwise. A `pending` gate is kept in the ledger and read again on the next full run (Info's `Gates re-read:` list). The `Families:` list under Info groups the clusters by their `upgrade-family` label and reads each family from its first-upgraded member's gate: `hold` on `risk`, `pending` on `pending`, `go` once every read gate is `clear`. Copy the gate as the report has it; never compute one from a read of your own.

### 4. Tailor (C) and record (D)

The collector renders (C) from a table of the catalogue's twenty entries, in generic words. Your part is to say it about this object. For every finding `draft` wrote:

- **`title`**: name the entry and the object. `Entry 1 (a PodDisruptionBudget forbids the eviction) on seeded-upgrade/PodDisruptionBudget/pinned-batch-runner`, or `Unclassified: <reason> on <object>`, or `Operation <name> (UPGRADE_NODES on <pool>) ended DONE with an error`. A held finding keeps the entry and the object and adds `persists since <date>, <n> reviews`.
- **`recommendation.action`**: the entry's `mitigate_after` (what repairs the cluster now) and `mitigate_before` (what to change before the next upgrade), rewritten for the object the finding names. Use its namespace and name, the field and value (`maxUnavailable: 0` and the replica count for entry 1, the selector key for entry 12, the image and tag for entries 14 and 20, the pool and its cgroup mode for 14, the driver and CUDA version for 18, the volume and the add-on for 19), taken from the candidate's `impact` and `excerpt`, and from the incident's `evidence`, `detail` and `mitigations` in the report JSON. Imperative, one or two sentences. An incident with no catalogue entry says what a reader should look at.
- **`recommendation.rationale`**: why this fix and not the obvious alternative, naming the alternative you rejected: deleting the budget instead of giving it room, raising the limit instead of moving to a runtime that reads cgroup v2, pinning the pool to cgroup v1 instead of fixing the image.
- **`recommendation.risk`**: what the change affects on apply, and the read-only command that confirms it first.
- **`remediation`**: `kind: manual`, always. The `note` names the object's manifest when the GitOps clone `start` handed you holds it (`grep -rl "name: <name>" --include='*.yaml' <workspace>`, then open each hit and confirm it declares this kind in this namespace before you name it; a hit is not a declaration until you have read it), the field and the value the change would set, and the guard ids the collector wrote for the incident (`facts.guards_written` in the manifest, `guards[].id` in the report), which stay in `guards.json` until a review finds the failure gone. Promise no readiness-report line for them: the readiness watch does not read that file yet. Never `kind: manifest` and never a file written into the workspace. The retrospective records what the upgrade did; the change it recommends is a user's decision, made by replying "apply" in chat, which goes through `submit-suggestion`. A `/remediate` comment naming one of these findings is answered by `finish` with a refusal, which is the intended shape.

(D)'s first half, the guards, the collector already wrote; name them. Its second half is the ledger issue, section 5.

### 5. The ledger issue, or the report alone

Where the install has a GitHub repository in `managed_repos`, this stream keeps what every fleet-audit stream keeps: one open ledger issue. Each run rewrites it in full, each finding is identified by cluster and object, and a run that finds nothing closes it. Where the install has no repository, `start` and `finish` still run (section 0): `finish` stores the document in the report store (`new` and `resolved` against the previous no-forge run), prints `status: "NO_FORGE"`, and there is no ledger issue to rewrite; the report on the volume and that store are the record. `start` and `finish` run **only on a full run**, and not on a baseline after a reset (section 0). A scoped run (section 7) never files, so a question about one clean cluster cannot close the fleet's issue.

`pending_remediation_requests` from `start` lists finding ids someone asked `/remediate` for. Every finding here is `manual`, so `finish` answers each request, and `/remediate all`, with one refusal naming the reason, and you write nothing for them. Every id in `carried` is in the document again when the manifest still carries its candidate. Otherwise list it under `resolved_because`, with the review that no longer shows it. A `carried` finding on a cluster in `scope.skipped` is neither, and `finish` holds it.

Before `finish`, self-check the document `draft` wrote and you completed:

- `audit` is `"upgrade-retrospective"`, and `scope.clusters` and `scope.skipped` are as `draft` built them (or as section 2's empty-`scope.clusters` rule moved them).
- Every finding has its `title`, `impact`, `recommendation` (all three fields non-empty) and `remediation` (`kind: manual`, with a `note`), and its `severity` is the candidate's.
- No two findings share a `(check, cluster, namespace, object)` quadruple, no `object` carries a pod name, version or date, and no finding names a skipped cluster.

A schema violation publishes nothing: `finish` exits 2 and the ledger is untouched. Validate here rather than discover it there.

```bash
/opt/data/profiles/platform/skills/fleet-audit/scripts/audit_report.py finish --audit upgrade-retrospective \
  --findings-file /opt/data/scratch/findings_upgrade-retrospective.json \
  --manifest-file /opt/data/scratch/manifest_upgrade-retrospective.json \
  [--repo "<owner>/<repo>"]
```

Pass `--manifest-file`. It lets `finish` hold the document to what the collector read. A `collected` target left out of `scope.clusters` is refused. A `checks_run` entry the manifest did not record at `rc == 0` is refused. Each finding's evidence is taken from its candidate. A previous finding the manifest still carries a candidate for is held, not announced as resolved. `--no-collector-manifest "<why>"` is section 0's recovery alone, for a run on which the collector wrote no manifest; `finish` refuses the waiver when this run's manifest sits at the path, and the waiver publishes with the reason as a coverage gap, so the run is partial. One JSON line comes back with `status`, `issue_url`, `new`, `resolved`, `prs_opened`, `prs_closed`, `partial`, `coverage_gaps`, `silent_ok` and `unpublished_candidates`. Exit 2 means the validator rejected the document and nothing was published: fix the document and run `finish` again, never `start`. A `BROKER UNAVAILABLE` line means the document was fine and the broker went away, possibly after the ledger was rewritten: re-run `finish` once it answers. Exit 1 is fatal. Exit 0 means it published. `partial` is true when any cluster landed in `scope.skipped` or carries a `limitations` note. Then `resolved` is forced to `0` and no finding is announced as fixed. Even a findings-free run keeps the ledger open, with a comment naming the gaps. That is what an unread project or an upgrade still in flight should do. `prs_opened` is always `0` here, by section 3's severity rule and section 4's `manual`.

### 6. Report in chat

What `deliver: chat` posts for this stream is the record `finish` writes (`chat_report_upgrade-retrospective.json`), not the run's final response: the relay drops a fleet-audit job's final message and posts what `finish` rendered, or the scheduler's notice that the run did not finish ([the relay design](../../../docs/designs/cron-report-relay.md), "A fleet-audit report comes from `finish`, not the final message"). So every full run reaches `finish`, with or without a repository (section 0), and the operator reads `finish`'s rendering: the headline (`Upgrade Retrospective: <n> findings (<c> critical) across <k> cluster(s); <new> new, <resolved> resolved since the last run`), the most severe findings with the cluster and object each names, the ids the collector still flags that the document left out, the ledger issue's URL where one exists, and that no forge is configured where none does. A reviewed cluster's top entry is a finding in the document (section 4), so it is in that list by its object; the counts per cluster, the report's path and its Errors and Warnings entries are the report's (`reports/<stamp>.md`, the file `reports/upgrade-retro-report.md` links to), which the on-demand answer (section 7) quotes.

- **The final response** is the record for the log and the ledger, written as the fleet-audit skill's step 5 says: on `status: "NO_FORGE"` the `summary` verbatim; otherwise the `issue_url` in full and every URL in `prs_opened` and `prs_still_open`; after it, one line naming the report (`/opt/data/upgrade-retrospective/reports/<stamp>.md`, produced at `generated_at`). It is not what chat shows, so nothing in it is written for the operator's eye alone.
- **A scheduled run with nothing reviewed** ends in exactly `[SILENT]`, nothing else and no preamble, when `finish` returned `silent_ok: true`. Nothing reviewed means `reviews` empty, `info.rechecked` cleared and refreshed nothing, and `failed_reads` empty. A run that skipped a cluster, lost a project's listing, spent its read budget before a cluster or cleared a guard is never silent, however clean the rest: `silent_ok` is false for it, and `finish`'s rendering names the gap or the guard that cleared. A run that ended on the collector's exit line (the lock, a refusal of the store or of a state file, a refused scope) never reached `finish`: the relay posts the scheduler's notice that it did not finish, and the collector's line is the run's log.
- **A scheduled run that reviewed a cluster** always reaches `finish` and is reported by it, whatever `silent_ok` says: a reviewed cluster is news even when it is clean, because the record tells the operator the upgrade was looked at.
- **A baseline after `--reset-ledger`** (section 0) runs without `start`, `draft` or `finish` by design, so chat receives the scheduler's notice; the report on the volume is its record, and the ledger issue keeps its findings until the next full run.
- **An on-demand run is never silent.** Someone is waiting on the answer; section 7 says what it carries.

### 7. On demand: the same report, from a question

This stream answers a question about what an upgrade did, or whether upgrades have problems. The question may use any words and name no feature, cluster or version. A question about what the _next_ upgrade would stop on is the `fleet-upgrade-verification` skill's readiness report instead; say so and route there.

1. **The source is the saved report, and nothing else.** Before any file search, list the store in your terminal: `ls -l /opt/data/upgrade-retrospective/reports/`. `upgrade-retro-report.md` there is the latest link; `readlink` on it prints the newest full report's name, `<stamp>.md` beside it, and `<stamp>.json` beside that is the report's JSON twin: `generated_at`, `fleet` and `reviews` to decide freshness by, `sections.info.unchanged` for the clusters the run did not review, and `guards[]` for every failure and risk the store holds, an unchanged cluster's included. There is no `.json` link; resolve the Markdown link first. No link means no full run has completed yet. The answer comes from that report, or after step 4 from the `reports/<stamp>-scoped.md` it wrote, and from nothing under `/opt/data/scratch`. `findings_upgrade-retrospective.json` and `manifest_upgrade-retrospective.json` there are the job's working files for `draft` and `finish`: a candidate per incident and the held failure guards, no per-cluster review, no risk and no `generated_at`, so a count or a line read from them is not the report's; `run_upgrade-retrospective.json` is `start`'s record of the run. `chat_report_upgrade-retrospective.json` is the delivered summary only, the fleet-audit skill's record of the last run's chat lines for the relay, with none of the report's entries to quote. A search for `retrospective` finds those files first, which is why the listing comes first.
2. **Decide freshness against the clusters the question covers.** Resolve the scope (section 1). For each project those clusters are in (the whole scope for a fleet-wide question; the named cluster's project otherwise), read the end time of the last terminal upgrade operation: `gcloud container operations list --project <p> --filter 'operationType:(UPGRADE_MASTER OR UPGRADE_NODES) AND status=DONE' --sort-by '~endTime' --limit 1 --format 'value(endTime,targetLink)'`. The report is fresh when `generated_at` is later than every such end time and every cluster the question covers is in its `reviews`, `unchanged` or `upgrading`.
3. **Fresh: answer from it.** Say when it was produced and name its path. Then, per cluster the question covers: whether the report reviewed it, its counts under Errors and Warnings, its Errors and Warnings entries quoted from the report with the tailored (C) of section 4, and for a clean cluster its Info block (the next upgrade, the gate line with its log-volume line, and the risks present); a question about a family, or about whether the rest may follow a cluster that went first, is answered from the `Families:` list and the first-upgraded member's gate (`clear` lets the rest follow; `risk` and `pending` hold them). A cluster the report lists as unchanged was not reviewed this run and its row carries no risks: its risks are its `kind: risk` entries in the report's JSON `guards[]` (`cluster`, `entry` and `object`), the same set `guards.json` in the store holds (one command lists them: `jq -r '.guards[] | "\(.cluster)/\(.object): entry \(.entry)"' /opt/data/upgrade-retrospective/reports/<stamp>.json`), with their `shapes` detail in the cluster's entry under `info.clean` in the report of the review its row names under `last reviewed`, while that report is in the ring; quote them from there, never from a read of your own. Do not run the collector and do not call `start` or `finish`.
4. **Stale or missing: run first, then answer the same way.** A fleet-wide question is a full run: section 1, section 0's probe and `start` (with or without a repository), then sections 2 and 5 as on the scheduled route, then the answer, so the saved link and the ledger move with it. A question naming one or more clusters is a scoped run: `--cluster <project>/<location>/<name>` for each, beside the tool's `collector_args` from section 1 (the collector refuses a cluster outside the declared scope), **no `--full`**, no `--project` and no `--manifest-file` (`draft` and `finish` refuse a `scoped: true` manifest). It reviews those clusters even when unchanged, writes `reports/<stamp>-scoped.md` beside its JSON, moves no link, prunes nothing and files no ledger. Say in the answer that the fleet report and its issue were not touched. A cluster the last run did not review, named in the question, forces that cluster the same way.
5. **Mid-upgrade, settling and locked.** A cluster under `upgrading` has an operation in flight: say it is upgrading now and is reviewed once the operation ends. A cluster whose row carries `settling: true` had an operation reach `DONE` less than fifteen minutes before the run: say the review runs once its pods have settled, on the next run. The lock held past section 0's probe, or the collector's lock-held line, means a run is in progress: answer from the latest saved report with its age, and name the run that holds the lock and since when.

The answer names the report it came from, with its dated path (`/opt/data/upgrade-retrospective/reports/<stamp>.md`, or `<stamp>-scoped.md` after step 4), never a file under `/opt/data/scratch`, and is never `[SILENT]`. `silent_ok` from a full run's `finish` decides nothing about it, only whether the issue URL line reports a change.

## Red Lines

- **Never mutate.** No `gcloud container clusters upgrade`, `clusters update`, `node-pools update`, `operations cancel`, `kubectl apply/patch/delete/cordon/drain`, no `--reset-ledger`, and no change to a cluster's maintenance policy. Every fix is a recommendation a user turns into a pull request by asking.
- **Never open a pull request from this stream.** Every finding is `kind: manual`, an Error files at `major` and a Warning at `minor`, nothing at `critical`. A manifest written into the workspace or a `critical` severity is how `finish` would open one unasked.
- **Never grade from a read of your own, and never move the collector's grade, the gate included.** The collector's classification, confidence, evidence, severity and gate verdict are the finding's. A symptom the collector did not list is not an incident, and a shape in the risks table is never one.
- **Never write an unstable `object`.** The id is derived from `check`, `cluster`, `namespace` and `object`. A pod name, a version or a date in it reports the same failure as fixed and new again, on a ledger that exists to say what is still broken.
- **Never paste a credential into evidence.** No `masterAuth` block, client key, token, service-account key or kubeconfig contents in an `evidence.excerpt`. The collector's evidence strings are object names, reasons and message excerpts, and that is all an excerpt holds.
- **Never hand-write the ledger issue body, never comment on the ledger, and never touch git or the forge directly.** `audit_report.py` owns that surface; a scoped run touches it not at all, and a run with no repository has no forge to touch (`finish` stores the report instead).
- **Never leave the in-flight note to its TTL.** A collector exit without a manifest after `start` takes section 0's recovery `finish` in the same turn.
- **Never delegate to a Cluster Agent** or open kanban cards from this review; it is a self-contained fleet read.
