# SOP: Fleet Waste Audit (Weekly Governance)

**Purpose:** Weekly sweep of the GKE fleet for resources that cost money and do nothing — orphaned storage, idle network reservations, under-allocated node pools, grossly over-requested or idle workloads, registries that never delete an image, and the scale-down blockers that pin them — plus the sizing risks found on the same usage history: workloads using more memory than they request, and workloads requesting nothing. The output is one ledger issue of reproducible findings, not a dashboard.

**Cron:** id `fleet-wide-cost-analysis`, schedule `50 7 * * 1` (Mondays, 07:50 UTC).

**Data sources:** `kubectl` read verbs, `gcloud compute` / `gcloud container` / `gcloud artifacts` (3.14), the Cloud Monitoring read API (GKE system metrics, for workload CPU and memory history), and the `gke` MCP server. **Nothing else.** This environment has no GCP Billing BigQuery export, no GKE Cost Allocation data, no Recommender API, and no Prometheus — so this audit observes _physical_ waste directly and reports it in **resource units** (GiB, vCPU, disk count, node count, object count). **Never state a dollar amount, a monthly saving, or a percentage saving — you have no pricing data.** Where a price would help the reviewer decide, say so in the remediation note and point at the GCP console; never invent the number. (`list_cc_pods` / `get_cc_pod_diagnostics` are scoped to `krmapihosting-system` on the Config Controller management cluster and are not used by this audit.)

## Execution Checklist

### 0. Open the audit run

Run `python3 ./skills/fleet-audit/scripts/audit_report.py start --audit fleet-wide-cost-analysis [--repo "<owner>/<repo>"]`.

If multiple repositories are registered in `$GITOPS_STATE_CONFIGMAP` (`managed_repos`), pass `--repo "<owner>/<repo>"` explicitly:

- **Interactive session:** If no `--repo` was specified, prompt the user to choose which repository to target before proceeding.
- **Scheduled / unattended cron:** Iterate over all repositories in `managed_repos` in sequence, executing the audit and running `audit_report.py start` and `audit_report.py finish` for each repository with `--repo "<owner>/<repo>"`.

It prints one JSON line:

```json
{
  "issue": 128,
  "repo": "acme/fleet",
  "workspace": "/opt/data/gitops/fleet-wide-cost-analysis/acme__fleet",
  "findings_path": "/opt/data/scratch/findings_fleet-wide-cost-analysis.json",
  "pending_remediation_requests": [
    "overrequest--prod-us-east--deployment-payments-api"
  ]
}
```

Keep the returned `findings_path`; write findings there and nowhere else. Keep `workspace` too: it is the GitOps clone `start` created, because this pod does not begin inside a checkout, and it is the root every `remediation.path` in §4 is resolved against. `issue` is this stream's open ledger issue, or `null` when it has none — either way `finish` opens or rewrites it. `pending_remediation_requests` names findings a repo writer asked for with a `/remediate` comment on the ledger: write the manifest for each of those during inspection, **unless** the finding's remediation is `gcloud` or `manual` — those are not promotable, the helper refuses the request with its own comment, and you never manufacture a manifest (least of all a deletion) to satisfy one. Each `/remediate` receives exactly one answer on the ledger — an acknowledgement listing every target and its outcome, or one refusal naming the reason (no write access, an unknown id, a non-`manifest` target, or a command not written at the start of its own line and so never parsed as one) — recorded behind a hidden marker so the same request is not answered twice.

There is no report branch. Do not create branches, commit, push, or call `gh` yourself, and never hand-write the ledger issue body — the helper renders it. **Never comment on the ledger yourself:** `/remediate` is a human reviewer's instruction to this harness, not a step in the audit, and an agent that posts it — including when someone asks for a fix in chat — is authorizing its own pull request. `finish` ignores a `/remediate` from a machine account, so posting one achieves nothing but noise on the issue.

### 1. Enumerate the target fleet

1. `gcloud config get-value project`, then `gcloud container clusters list --project=<p> --format="json(name,location,status,autopilot.enabled,currentNodeCount,createTime)"` for every project the agent can see.
2. `scope.clusters` = every cluster with `status: RUNNING` or `RECONCILING` that you could read. Record every cluster you could **not** read in `scope.skipped` with its status or the stderr excerpt as the reason (`"cluster STOPPING"`, `"no kubeconfig: <stderr excerpt>"`).

   **The one-question scope rule.** A cluster appears in exactly one scope list. Could you read it? Yes → `scope.clusters`; if some checks did not run there, name them in that cluster's `limitations`. No → `scope.skipped`. Nothing goes in both, and nothing in `scope.skipped` may appear in a finding. The validator enforces all three.

   **Each `scope.clusters` entry is `{name, location, project, checks_run}`, and `checks_run` is mandatory.** Each entry in it is an object, never a bare string:

   ```json
   {
     "check": "orphan-pv",
     "command": "kubectl --context prod-usc1 get pv -o custom-columns=NAME:.metadata.name,PHASE:.status.phase,CLAIM:.spec.claimRef.name --no-headers"
   }
   ```

   `check` is the backticked slug from the §3 heading that defines it — `overrequest`, `orphan-pv`, and so on — never the section number and never prose. (`start` prints the full roster of fourteen; the SOP still says what each check _is_.) `command` is the literal invocation you issued on that cluster for that check, with its `--context`/`--project` and the namespace or resource it targeted. It must name one of `kubectl`, `gcloud`, `gsutil`, `bq`, `helm`, or `curl`; `echo`, `cat`, `python3 -c`, and a call back into `audit_report.py` are all rejected, as is anything under eight characters.

   The validator rejects an unknown slug, a duplicate, a missing or unusable command, the field being absent, and an empty list unless that cluster's `limitations` says why nothing ran: a cluster you could read but ran nothing against is not a clean cluster, it is an audit that did not happen. Anything short of the checks that apply to that cluster makes the run **partial** exactly as a `limitations` note does, so the ledger stays open and nothing on that cluster is announced as resolved. Append the entry when its check completes, not when you intend to run it, and paste the command rather than reconstructing it — every one is published verbatim in the ledger under _How this run checked the fleet_.

   **A check the cluster's shape rules out is not a gap — declare it.** Alongside `checks_run`, a cluster may carry `checks_not_applicable` as a list of `{check, reason}`:

   ```json
   {
     "check": "idle-nodepool",
     "reason": "GKE Autopilot: Google owns the node pools; there is no autoscaler floor to lower."
   }
   ```

   Same slugs as `checks_run`, and the `reason` must say why the check _cannot_ apply here — "N/A" and "not applicable" are rejected; name the property of the cluster that rules it out. Those checks leave the denominator instead of counting as missing, so an Autopilot cluster (where 3.7 has no user-managed pool to act on and 3.8 has no flagged node to examine, see §2) reads as complete at eight of eight rather than forever-incomplete at eight of ten — ten, because the four project-scoped checks (3.4–3.6, 3.14) are owed by the `project/<id>` entry, not the cluster. Without it, every run on an Autopilot fleet is partial forever, `resolved` is pinned at `0`, and the ledger can never close. Use it only for checks the cluster's shape rules out. A check you could have run and did not is a `limitations` note and a real gap, and the validator rejects a slug in both lists, a duplicate, an unknown slug, and a reason under sixteen characters.

3. Get credentials per cluster into an **isolated kubeconfig**, so two clusters cannot bleed into each other through a shared current-context:

   ```bash
   export KC="${HERMES_HOME:-/opt/data}/.kubeconfigs/kubeconfig_<project>_<cluster>_<location>.yaml"
   KUBECONFIG=$KC gcloud container clusters get-credentials <cluster> --location=<location> --project=<project>
   ```

   Every `kubectl` in Step 2 runs with that cluster's `KUBECONFIG=$KC`. On failure, skip that cluster with the stderr excerpt as the reason and continue — one unreachable cluster never aborts the run.

4. **Zero RUNNING clusters is not by itself a reason to stop.** The collector still reads every project in scope for its disks, addresses, forwarding rules and registries, and the `project/<project-id>` entries of projects with Compute Engine or Artifact Registry on keep `scope.clusters` non-empty, so run §2 and call `finish` as usual. Stop without calling `finish` only on §2's rule — a manifest with a top-level `error` — and report that error as your one-line summary: a fleet you could not read is not a clean fleet, so that is **not** a `[SILENT]` run.

### 2. Collect state

**Run the collector before evaluating any check below by hand.**

```bash
python3 ./skills/fleet-audit/scripts/fleet_waste.py --workspace "<the workspace Step 0 returned>" > /opt/data/scratch/manifest_fleet-wide-cost-analysis.json
```

This is the one collector that reads a Google API directly rather than through `gcloud`: 3.1, 3.11, 3.12 and 3.13 take each workload's usage from Cloud Monitoring, and no `gcloud` command reads time series. In the sandbox it goes through the credential broker's read-only relay, which attaches the broker's credential for exactly those reads, so it needs no token and no interpreter of its own. Its `commands` record each of those reads as the `curl` commands that issue the same requests outside the sandbox, one per metric, so they pass `finish`'s command check when copied. A cluster whose `commands` lacks `overrequest` with a `limitations` string naming a refused or failed Monitoring read is that path failing, not the cluster — the metrics degradation below.

It reads the whole fleet and runs for minutes, not seconds: give the terminal call `timeout: 600`, the foreground maximum, because a shorter one kills it partway and leaves no manifest. This is the tested, procedural implementation of the collection this section used to describe — see `fleet_waste.py`'s own module docstring for what it covers, including the fifteen `kubectl` object kinds it dumps (StatefulSets and Deployments beyond what the checks below name — StatefulSets to suppress a scaled-to-zero StatefulSet's own claim in 3.2/3.3, Deployments for 3.13's controller age — HPAs and LimitRanges for 3.1's exclusions, and Ingresses for the global static IPs 3.5 counts as in use) and how it reads each workload's peak CPU and memory from Cloud Monitoring over the trailing week instead of sampling `kubectl top`. Its manifest mixes cluster-named entries with `project/<project-id>` entries for the project-scoped checks (3.4–3.6 and 3.14), per §3's project-scoped rule below. Read the manifest before doing anything else:

- Every entry in `manifest.clusters` carries one `outcome`. `"collected"` means every check that applies to that target already ran — copy its `commands` list verbatim into that target's `checks_run` — with a script that loads the manifest and assigns the list, never by retyping it — leaving out only an `idle-workload-traffic` entry, which is 3.13's evidence rather than a check (§3.13 says why). `"unreachable"` or `"gate-failed"` means the collector could not cover it; fall back to this section's manual reads for it alone, and give that target a `limitations` note saying the collector could not read it: `finish` rejects a `checks_run` on a target the manifest does not mark `"collected"` unless `limitations` says why it is not a full read. An `"unreachable"` entry whose `error` says the cluster is neither `RUNNING` nor `RECONCILING` is the one case not worth a manual retry: the state that stopped the collector will stop you too, so put it straight into `scope.skipped` with that reason. Every cluster entry also carries an `autopilot` boolean — the mode, already resolved, and on the error shapes too, because a cluster does not stop being Autopilot when a read of it fails. Take the mode from there for any cluster the manifest lists rather than re-deriving it from `clusters list`, and never transcribe a fleet-wide mode map into a script: that hand-copy goes wrong the moment a cluster is added or converted.
- A `"collected"` cluster whose `commands` is missing `overrequest` means the Cloud Monitoring usage read came back empty or failed there — the metrics degradation below. `unsized-workload` and `idle-workload` read the same series and drop out with it, and `underrequest` drops out on its own when the mean-memory read fails. The collector writes the `limitations` note naming each; carry it and skip exactly the checks it names. Every other check on that cluster is still fully collected.
- The manifest entry may carry `checks_not_applicable`, already filled in as `{check, reason}` — copy it verbatim into that target's `checks_not_applicable`. On an Autopilot cluster, and on a Standard cluster with a single node pool, it holds `idle-nodepool` and `scaledown-blocked`: 3.8 examines only the nodes 3.7 flags, so wherever 3.7 is not applicable 3.8 is not evaluated either and is recorded not-applicable with it. On a cluster with no nodes it holds the usage checks, because nothing ran to be measured. On a `project/<id>` entry it holds the checks whose API is off in that project — 3.4–3.6 without Compute Engine, 3.14 without Artifact Registry — because nothing they look for can exist there; a project with both off has no entry at all. Declare nothing there yourself. A check whose own read failed is in `checks_unevaluated` instead, as `{check, reason}`: leave it out of both `checks_run` and `checks_not_applicable` and carry the entry's `limitations`, which names it. `finish` rejects a document that claims it either way. A `project/<id>` entry whose `clusters list` completed and came back empty, or was refused because that project's own Kubernetes Engine API is off, also carries `clusters_listed: 0`: copy it verbatim onto that project's `scope.clusters` entry, and never write it yourself. It is how `finish` tells a fleet with no clusters from a run that lost them — a run with no cluster target is partial unless every `project/<id>` target carries it, `finish` rejects the marker unless `--manifest-file` is given, and a marker the manifest entry lacks is rejected. A project whose list failed, was refused by another project's API (such as a quota project's), timed out on a zone, or was never reached has no such marker, so its missing clusters stay a gap.
- Every entry in a `"collected"` target's `candidates` is a verified finding: `check`, `object`, `severity`, and `excerpt` are already computed, including 3.1's Autopilot severity bump and 3.8's PDB-deferral to the Workload Reliability audit. What is still yours to write is the `recommendation` (§5) and, for a `kind: manifest` remediation, the manifest file itself (§4). A cluster-scoped candidate may also carry `declaration`, which is where this repository declares the object it names: `declaration.path` is the file, and `declaration.directory` is its parent. Prefer it to any `grep` of your own — §4 says why, and it is what decides whether a right-size travels as a diff or as prose. A project-scoped candidate never carries one: a disk, a reserved address and a forwarding rule are GCP resources with no cluster tree to key on, and all three are `kind: gcloud` or `manual` anyway. A cluster-scoped candidate whose object no file declares may instead carry `release_declaration`, which is where this repository declares the **chart release** that renders it: `release_declaration.path` is the Argo CD `Application` or Flux `HelmRelease` file, `chart`, `repo` and `version` name the chart itself, and `values_field` is the exact field a values override belongs in. `renderer` says how that field is written: `helm` for a values mapping the chart reads by key, or `kustomize` for a list of patches, where the object comes from an overlay over a base in another repository and `chart` holds the overlay directory rather than a chart name. It appears only when `declaration` does not, because an object with its own manifest is edited there and a values override beside it would be a second expression of the same change. §4's Helm branch says what to do with it. A cluster-scoped candidate may also carry `reconciler`, naming what continuously reasserts the object's spec — a Helm release, an Argo CD Application, an operator. It is read off the object's own markers and is authoritative: never write prose calling such a workload unmanaged or applied out-of-band, and never propose a `kubectl patch` or `kubectl edit` as the fix, because the next sync undoes it. A `manual` remediation on such an object says so in its note, and names where the fix belongs instead.
- These sub-conditions are not in the collector, so its candidates have not passed them; check each by hand for the candidates it applies to, and leave out a candidate that meets one:
  - 3.8's "pods being deliberately pinned by a documented anti-eviction annotation with an owner label" — whether a `safe-to-evict: "false"` pin is documented and owned is a judgement the pod's labels alone do not settle, so the collector reports every such pin.
  - 3.2's "carrying a retention marker" — the collector skips a PV annotated by a backup system (`velero.io/*`, `gke.io/backup-*`) or an addon, not one with any other retention marker. And 3.6's "PSC service attachments" on the producer side: the collector skips a rule that targets a service attachment, but not a rule a service attachment publishes, since it does not read service attachments — run `gcloud compute service-attachments list --project=<p> --format="json(name,targetService)"` and leave out an `orphan-lb` rule an attachment's `targetService` names. And 3.3's "referenced by a `VolumeSnapshot` in progress": the collector does not dump `VolumeSnapshot`, so for each `unconsumed-pvc` candidate run `kubectl get volumesnapshot -n <ns> -o json` and leave the claim out when a snapshot whose `spec.source.persistentVolumeClaimName` names it is not yet `status.readyToUse`. The collector does skip a claim any Job or CronJob template references, suspended or not.
- Pass `--manifest-file <path>` to `finish` (§6) so it cross-checks your `checks_run` against what the collector actually ran.
- A GKE cluster name is unique only inside one project and location, so the collector sweeps the active project plus every listed project, whether or not it holds a cluster, and names every cluster `<project>/<location>/<name>`: in the manifest entry's `name`, and so in `scope.clusters[].name` and every finding's `cluster`. Carry that form verbatim, and use it for a cluster you fall back on by hand too: `finish` matches `scope.clusters[].name` against the manifest, so a name shortened back to the bare one reads as a collected cluster the document omitted. `object` keeps the bare resource name, except that a project-scoped disk, address, forwarding rule, target pool, backend service or repository reads `<Kind>/<location>:<name>`, because its name is unique only per zone, region or location; commands still take the real `--project` and `--context`. A project whose `clusters list` failed contributes a `project/<id>` entry at `"gate-failed"` — a list another project's Kubernetes Engine API refused (such as a quota project's), a list with a zone that did not respond (the clusters that did arrive are still audited), and a collector crash on that project all count — as does one the collector never reached — it stops starting project reads partway through so the call can end inside its timeout, and that entry's `error` begins `not read:` — and `project/UNENUMERATED_PROJECTS` appears when `gcloud projects list` failed, returned a list that omits the active project, or `--project` confined the run to one project, since each way other projects may have gone unlisted: put `project/UNENUMERATED_PROJECTS` in `scope.skipped` with the collector's `error` as the reason, and a `gate-failed` `project/<id>` entry there too unless you read it by hand under the first bullet's `limitations` rule; leaving either out would read as a project holding no clusters. A manifest with a top-level `error` left nothing to put in `scope.clusters` — no project could be listed or reached, or none has Compute Engine or Artifact Registry on and none holds a running cluster — and the collector exits non-zero for it: do not call `finish`, and report the error as your one-line summary.

**A target the collector covered is not a target you query again.** The commands below exist for an `"unreachable"` or `"gate-failed"` target — never for confirming a candidate the collector already produced, whose evidence `finish` takes from the manifest, and never for re-deriving a verdict the manifest already gives you. `fleet_waste.py` dumps `nodes,pods,pvc,pv,svc,jobs,cronjobs,pdb,ns,resourcequota,sts,deploy,hpa,limitrange,ingress` on every `"collected"` cluster, so re-reading any of those kinds — on one cluster or in a loop over `.kubeconfigs/` — asks the API for what `candidates` already holds. Reading a kind the dump does not cover is a different thing and is fine: a `VolumeSnapshot` that may name a candidate claim is evidence for the recommendation, not a re-derivation of the finding.

**Manual reads, for a target the collector did not cover** — collect once into `/opt/data/scratch/` and quote from those dumps as `evidence.excerpt`:

- Per cluster: `KUBECONFIG=$KC kubectl get nodes,pods,pvc,pv,svc,jobs,cronjobs,pdb,ns,resourcequota,sts,deploy,hpa,limitrange,ingress -A -o json`, plus `gcloud container node-pools list --cluster=<c> --location=<l> --format=json` and, for 3.7's pool age, `gcloud container operations list --location=<l> --filter='operationType=CREATE_NODE_POOL AND targetLink~/clusters/<c>/nodePools/' --format=json` (Standard clusters only; skip both where `autopilot.enabled` is true). A pool with no operation there is dated from the cluster's `createTime` in `clusters list`.
- Per project: `gcloud compute disks list`, `addresses list`, `forwarding-rules list`, `target-pools list`, `backend-services list`, and `gcloud artifacts repositories list` (all `--format=json`).
- There is no manual usage read: the Monitoring series the collector reads have no `gcloud` form, and `kubectl top` is a point sample that §3.1's week-long peak exists to replace. On a manually read cluster, 3.1, 3.11, 3.12 and 3.13 fall under the metrics degradation below.

**Metrics degradation:** if the Cloud Monitoring usage read fails or returns no time series for either metric, the cluster still belongs in `scope.clusters` — you read it. The collector sets the `limitations` string itself, naming which of the two it was; carry it onto that cluster's `scope.clusters` entry and skip **only** the checks it names there — 3.1, 3.12 and 3.13 when the peak read failed, 3.11 when the mean read did. An empty answer is never read as zero usage: that would flag every workload on the cluster as pure waste. Every other check reads requests and object state, not usage, and still runs.

**Autopilot:** where `autopilot.enabled` is true, there are no user-managed node pools — skip 3.7 and 3.8, and declare both in that cluster's `checks_not_applicable` (the collector writes the entries; on a manual fallback use a reason naming Autopilot's managed nodes). **Not `limitations`:** a non-empty `limitations` string is what makes a run `partial`, and a cluster does not stop being Autopilot, so parking the mode there would pin the weekly cost stream at `partial: true` for good — `resolved: 0`, ledger never closing. An Autopilot cluster is never a skipped cluster either; you read it fine. 3.8 goes with 3.7 because it examines only the nodes 3.7 flags, and 3.1 matters _more_ (Autopilot bills on requests), so **bump 3.1 severity one level on Autopilot clusters**.

**Shared definitions used by every check below.** `SYSTEM_NS` = `kube-system`, `kube-public`, `kube-node-lease`, `gmp-system`, `gmp-public`, `gke-gmp-system`, `cnrm-system`, `configconnector-operator-system`, `krmapihosting-system`, `istio-system`, `asm-system`, `anthos-identity-service`, `gatekeeper-system`, `composer-system`, plus any namespace matching `gke-*`, `gke-managed-*`, or `config-management-*` — the same fleet-wide set the Security & RBAC Posture Audit calls `$SYS` and the Workload Reliability Audit calls S1. Note it is `anthos-identity-service` and not `anthos-*`: a glob there would silently hide waste in any namespace a team happened to prefix `anthos-`. `kubeagents-system` is deliberately **not** suppressed; the harness audits itself. `AGE(x)` = now minus `creationTimestamp`. "Peak usage" = the highest value Cloud Monitoring recorded for that pod over the trailing 168 hours, summed across its containers. A **controller's** peak is then the highest any one of its pods reached, multiplied by its replica count — the worst replica, not the sum and not the average, because the checks that divide back down to size a manifest are asking what one replica needs. The pods counted are every pod of that controller the read saw, including ones it has since replaced: Monitoring is keyed by pod name and answers for the whole window, so a controller rolled this morning has its earlier pods' series in the same response, and matching only the live names threw them away. Where nothing was replaced, the window is the longest-lived live pod's age; where something was, it is the controller's own age. Either way the excerpt names the window it measured and, when it reached back, how many replaced pods it reached through.

### 3. Checks

**Severity discipline.** Waste is not an incident. Default to `minor`; use `major` only for magnitude (roughly a node's worth of capacity, ≥500 GiB of storage, or a systemic leak). **`critical` is reserved for three conditions only:** (a) a condition that blocks node drain, which blocks both scale-down _and_ security patching; (b) a waste finding whose obvious remediation is deletion of an object holding the only copy of data — verified by `gcloud compute snapshots list --filter="sourceDisk~<disk-name>"` returning nothing. Rule (b) is a **warning to the reviewer**, not an urgency claim; say so in the impact line. (c) 3.11's OOMKill arm: a controller whose mean memory already sits at ≥ 90% of a memory limit every container declares, which is a failure in progress rather than waste. Nothing else reaches `critical` — in particular the one-level Autopilot bump in 3.1 and 3.12 stops at `major`, because those three conditions are the whole of `critical` and a request that is merely mis-sized is none of them.

The bump does not open pull requests. The automatic sweep promotes only `critical` manifest findings, so a bumped 3.1 or 3.12 finding at `major` waits for `/remediate` like any other. Grade on the observed delta as this section says and let the bump fall where it falls; do not grade around the sweep in either direction.

**Finding identity.** **Do not write an `id`.** The harness derives it from `check`, `cluster`, `namespace` and `object`, and ignores any `id` in the file. `check` is the backticked slug in the check's heading below; a slug outside this SOP's roster is rejected.

Identity is only as stable as those four fields, so **never** let a timestamp, a counter, a sample value, an age, or a usage figure into `object` — a waste finding re-measured tomorrow is the same finding, and one whose identity moves is announced as fixed and re-announced as new. Two findings agreeing on all four fields are one finding, and the harness refuses the document rather than collapsing them silently.

**Project-scoped GCP objects.** The harness requires a non-empty `cluster` on every finding. For a disk, address, forwarding rule, or registry repository that belongs to a project rather than to one cluster, set `cluster` to the literal string `project/<project-id>` and leave `namespace` empty. A cluster-scoped finding's `cluster` is the qualified `<project>/<location>/<name>` form (§2). A disk keeps `project/<project-id>` even when its labels prove which cluster owns it: the owner goes in the impact line, so the finding's identity does not change with what attribution could prove on a given run.

#### 3.1 Gross over-request vs. observed usage (`overrequest`)

**This check owns the request _value_.** The Workload Reliability audit (`obtainability-audit` check 3.1, `no-requests`) owns the request's _absence_: it flags a container that declares no request at all and deliberately proposes no number, deferring the sizing to here, where the usage history is. A container with no request is that audit's finding; a container whose declared request dwarfs its usage is this one's. Neither audit ever restates the other's half — two streams sizing one container in opposite directions makes each run flag the state the other just created.

**And it owns only the value being too _large_.** A request smaller than the workload is 3.11 (`underrequest`), in this same audit and sharing this check's pod-eligibility rules, so the two directions of one edit are never proposed by two streams. This check reads the peak; 3.11 reads the mean. **One controller can legitimately appear in both**, and on the fleet measured 2026-09-05 one did: `litellm` peaks at 12% of its CPU request and averages 190% of its memory request, so it is over-requested on CPU and under-requested on memory at once. That is two sizing decisions about two dimensions, not a contradiction, and the remediations do not overlap — this check resizes only the dimensions its excerpt names as idle, and 3.11 touches only memory. What cannot happen is the two disagreeing about the same dimension: a mean can never exceed a peak, so a controller whose memory peak is under 20% of its request cannot also average above it.

- **Command:** the collector's Cloud Monitoring read (`kubernetes.io/container/cpu/core_usage_time` as a rate and `kubernetes.io/container/memory/used_bytes` filtered to `memory_type=non-evictable`, so page cache the kernel can reclaim is not counted, summed to the pod and maxed over the window) joined against `kubectl get pods -A -o json | jq '[.items[]|{ns:.metadata.namespace,pod:.metadata.name,owner:([.metadata.ownerReferences[]?|select(.controller)][0]//.metadata.ownerReferences[0]//{}),start:.status.startTime,req:[.spec.containers[].resources.requests],lim:[.spec.containers[].resources.limits]}]'`, aggregated to the owning controller. The `select(.controller)` matters: a pod may carry more than one `ownerReference` and the API orders them arbitrarily, so `[0]` can aggregate the same workload under a different name next week — and §5 rejects an `object` that moves. The dump answers for _now_ and the metric read answers for the week, so the join also matches Monitoring series whose pod names fit the controller's naming pattern and are owned by nothing live — the pods it has replaced. Without that, a controller rolled this morning is measured over this morning, and the week of history sitting in the same response is discarded unread.
- **Flag when:** for a controller, peak aggregate usage over the window is ≤ 20% of aggregate requests on **either** CPU or memory — judged per dimension, not across both — and that idle dimension's **request** is material: ≥ 0.1 vCPU of CPU, **or** ≥ 0.125 GiB of memory, summed across its pods. _Justification:_ sane practice requests at p50–p95 with 1.3–2× headroom; a 5× gap is not headroom, it is a copy-pasted default. CPU and memory are two separate sizing decisions and get two separate verdicts: the commonest shape in a real fleet is a controller sized for its memory footprint and handed a copy-pasted CPU request, and requiring both dimensions to be idle at once vetoed every one of them — on the sixteen-cluster fleet measured 2026-09-05 that rule hid a gateway using 15% of its CPU request and a proxy using 5% of a 40× one. The floor is a property of the **request**, and it is read on an idle dimension only: a workload consuming all 8 GiB it asked for and none of its 10m of CPU must not clear a materiality test on the strength of the memory it is using. Reading it off the reclaimable delta instead is what this check used to do, and the two quantities coincide only where usage is near zero — so the workloads that rule silenced were exactly the ~100%-idle ones, whose delta is their whole request. On the same sixteen-cluster fleet the delta rule at 0.25 vCPU / 0.5 GiB reported 2 controllers across 388 pods: `github-token-minter`, requesting 200m and peaking at 0.001 vCPU over a full week, was dropped for a 199m delta, and seven other idle controllers went with it. What the floor is for is the 10m/32Mi sidecar whose 8m of headroom is arithmetically a 5× over-request and operationally nothing; 0.1 vCPU / 0.125 GiB still excludes it.
- **And flag only where the remediation below would change a number.** The resize clamps to `50m` / `64Mi` per replica, so a controller already declaring that on every dimension this check calls idle has a recommendation identical to its current request: no manifest edit closes the finding, and the only honest answer is "leave it alone". The collector applies the rule to each idle dimension and drops the dimension where it comes out no smaller than the request — so a controller on the floor for CPU but idle on 8 GiB of memory reports the memory alone, and one on the floor for both is not reported at all. Before this gate existed the 2026-09-05 report carried three findings that were nothing else: a `hello-world` Deployment on three Autopilot clusters, each 50m/64Mi per replica, each graded `major` by the Autopilot bump, and each answered with "already at the sizing floor; no resize is possible". Three rows a week that the audit's own remediation rule proves unactionable teach a reader to scroll past the section they are in. This is not the materiality floor relaxing: that floor asks whether the **request** is large enough to be worth reporting and deliberately ignores the delta, because a 199m delta on a 200m request is worth taking. This asks whether a delta exists at all once the resize floor is applied.
- **Observation honesty — state this in the impact line:** the window is a week of Cloud Monitoring history, so it has already seen the nightly batch peak and the weekday traffic curve that three `kubectl top` samples on one Monday morning could not. It has not seen a monthly close, a quarterly load test, or a seasonal peak, and for a controller _created_ more recently than a week ago it has only that controller's lifetime -- which is why the excerpt states the window it actually measured rather than the 168h ceiling. A controller merely _rolled_ this morning is not in that position: its replaced pods' series are read too, so the window is its own age and the excerpt says how many replaced pods it reached through. A StatefulSet recreated this morning needs no replaced pods for that: it recreates them under the same names, so their series already span the earlier incarnations. That is why the check still takes the peak rather than the mean, carries an absolute floor, and — see remediation — never proposes a request below 2× the observed peak. The impact line must name the window so the reviewer knows the basis.
- **Do NOT flag:** `SYSTEM_NS`; DaemonSets (their requests are per-node overhead, not a sizing choice); pods with `AGE < 1h` (cold caches, JIT warmup); anything owned by a `Job` or `CronJob` (periodic by design, sampled at the wrong moment); workloads with an HPA whose `minReplicas` floor is the real lever; `BestEffort` pods (no requests to shrink); pods in `Pending`/`Terminating`; workloads whose request equals the namespace `LimitRange` default (fix the LimitRange, not the workload — note it once per namespace instead); where only one dimension is the default and the other was written by hand, judge the hand-written dimension alone and never propose resizing the defaulted one. Also skip any controller none of whose pods appear in the Monitoring answer — the same exclusion 3.11 and 3.12 carry, and the direction in which it matters most: absent pods summed as zero usage read as 0% of the request on both dimensions at once, which is the most idle a workload can possibly look, so an unmeasured controller would otherwise be reported as grossly over-requested and have its request cut to the floor. The same holds for a controller whose pods reported one dimension and not the other: the unread dimension is unmeasured, not zero, and the controller is skipped.
- **Severity:** `major` if the reclaimable delta on the idle dimensions is ≥ 8 vCPU or ≥ 32 GiB across the controller (a node's worth); else `minor`. One level higher on Autopilot. Lowering the floor above does not change any base grade: a controller that only now clears it clears it by a margin far under a node's worth, so its base grade is `minor`. On an Autopilot cluster the bump then carries it to `major` — that is the Autopilot rule, which bills on requests, not the floor promoting anything.
- **Impact:** "Deployment `ns/name` requests 12 vCPU / 48 GiB; peak observed over the trailing 168h was 0.9 vCPU / 3 GiB — ~11 vCPU and ~45 GiB reserved and unschedulable by anything else." Where only one dimension is reported, say which and give the excerpt's reason for the other: "Deployment `ns/gateway` requests 1.1 vCPU / 1 GiB; peak observed over the trailing 168h was 0.17 vCPU / 0.86 GiB — ~0.9 vCPU reserved and unschedulable by anything else, while its memory request is sized correctly." Or, for the floor case: "…its memory request is already at the 50m/64Mi floor and cannot be reduced." — or, where the excerpt says the request is under the floor: "…its memory request is already below the 50m/64Mi floor, where a resize would raise it rather than reduce it."
- **Remediation:** `kind: manifest`, subject to §4's declaration rule — the controller's **complete** desired manifest, taken from its declaration in the GitOps repo, with `requests` set to what the excerpt's **"Resize to …"** sentence names and limits untouched. Copy those figures; do not recompute them. They are `ceil(peak × 2)` clamped up to `50m` / `64Mi`, already per replica, and the excerpt is the only place the arithmetic is done against unrounded numbers — its headline peaks are rounded to two decimals of a vCPU and one of a GiB, so a small workload reads as `0.00 vCPU / 0.0 GiB` and any figure derived from that is wrong. A recommendation naming a request below the floor is the specific error this replaced: on 2026-09-06 `github-token-minter` was told to go to "about 10m" on a dimension whose floor is `50m`. **Resize every dimension that sentence names, and only those.** Where it says "Over-requested on **both** dimensions", resizing one of them leaves the other satisfying the check on its own and republishes the finding next week against a repository whose manifest now shows the merged pull request. Where it says "Over-requested on cpu only" or "on memory only", read the clause that follows it — the excerpt gives the reason, and every reason calls for the same edit. "the other is **in use** and must not be resized" means the request is load-bearing and copying the 2×-peak rule onto it would cut what the workload consumes. "the other is **already at the 50m/64Mi sizing floor**" (or **below** it) means it is idle too, and the rule returns what it already declares or more. "the other is **the namespace LimitRange default**" means nobody wrote it, and it is fixed in the LimitRange, not in this manifest. "the other is **not requested**" means there is no line to resize. In every case leave that line of the manifest exactly as the GitOps repo declares it; never write a resize that reproduces the current value. **Skip the manifest and emit `kind: manual` for `Guaranteed`-QoS pods** (requests == limits, which the collector judges per container and marks on the candidate as `needs_triage: guaranteed-qos`) — except the fully idle ones **created more than 14 days ago**, which the collector hands to 3.13 instead, where the fix is a stand-down rather than a resize and no ceiling is set. The age bar is 3.13's and the collector applies it, so a `Guaranteed` controller idle on every dimension but younger than that is emitted here, as an `overrequest` candidate, and stays here: publish it under `overrequest` with the `Guaranteed` note. Do not re-file it under `idle-workload` because the prose there fits it better — a workload a fortnight old has not been observed long enough for "nothing is using this" to mean what 3.13 means by it, and a finding published under a slug whose own gate excluded it has no collector evidence behind it. On 2026-09-07 two such controllers were re-filed that way at 7.6 days, cleared the auto-promotion floor, and merged a scale-to-zero unattended. For the rest, the request _is_ the limit, so applying a rule derived from a week of observed idleness sets a hard ceiling — an OOMKill on the first memory spike the window did not contain, and CFS throttling on the CPU side. The frequently-given reason, that lowering requests changes the QoS class, is not the one: lowering requests **and** limits together keeps the pod `Guaranteed`. It is that on a `Guaranteed` pod a sizing observation and an enforcement boundary become the same number, and 2× a 168-hour peak is not a safe enforcement boundary. **Give the `Guaranteed` finding this note verbatim** — the reason just rejected is the one a reader reaches for unprompted, and a note repeating it tells the operator to lower both numbers together, which is the hard ceiling this case exists to prevent: "requests and limits are equal here, so any resize lowers the enforcement ceiling too. 2× a 168-hour idle peak is a sizing observation, not a safe limit — size the limit from the workload's expected worst case, not from this finding." **On the manifest case** the note is instead: "this rests on a 168-hour peak; confirm against any load cycle longer than a week before merging."

#### 3.2 Orphaned PersistentVolumes (`orphan-pv`)

- **Command:** `kubectl get pv -o json | jq '[.items[]|select(.spec.persistentVolumeReclaimPolicy=="Retain")|{name:.metadata.name,phase:.status.phase,since:.status.lastPhaseTransitionTime,created:.metadata.creationTimestamp,cap:.spec.capacity.storage,sc:.spec.storageClassName,claim:.spec.claimRef,handle:(.spec.csi.volumeHandle//.spec.gcePersistentDisk.pdName)}]'`
- **Flag when:** phase is `Released` or `Failed` and `status.lastPhaseTransitionTime` is ≥ 7 days old; or phase is `Available` with a null `claimRef` and `AGE ≥ 30d` and no `Pending` PVC in its cluster matches its storage class (only that cluster's claims can bind it). If `lastPhaseTransitionTime` is absent (pre-1.31 control plane), fall back to `AGE ≥ 30d` and say so in the evidence excerpt. _Justification:_ 7 days outlives any deploy/rollback cycle and any weekly batch job; a `Retain` PV that has sat unclaimed for a week was abandoned, not paused. 30 days for `Available` because statically provisioned PVs are legitimately pre-staged.
- **Do NOT flag:** `Delete`-policy PVs (the disk is already gone); PVs whose `claimRef` names a PVC that still exists with the same `uid` (or where either side has no `uid` to compare) — a PVC deleted and recreated under the same name leaves the old PV `Released`, and that one is flagged; PVs whose claim name matches `^<vct>-<sts>-[0-9]+$` for a StatefulSet that still exists in that namespace — **a StatefulSet scaled to zero is a deliberate state, not waste**; PVs annotated by a backup system (`velero.io/*`, `gke.io/backup-*`) or carrying a retention marker; PVs provisioned for GKE-managed addons; anything younger than 7 days in the terminal phase (deletion churn).
- **Severity:** `major` if capacity ≥ 100 GiB or the storage class is SSD/extreme; else `minor`. `critical` under severity rule (b).
- **Impact:** "PV `pvc-abc123` (500 GiB, `premium-rwo`) has been `Released` with `Retain` since 2026-06-12 — the backing disk still exists and no claim can bind it."
- **Remediation:** `kind: manual`. Steps, in order: identify the backing disk from `spec.csi.volumeHandle`; `gcloud compute disks describe` it; **snapshot it** (`gcloud compute snapshots create <disk>-preaudit --source-disk=<disk> --source-disk-zone=<z>`); confirm the owning team no longer needs the data; only then delete. **Never emit a manifest that deletes a PV or PVC.**

#### 3.3 Bound PVCs with no consuming pod (`unconsumed-pvc`)

- **Command:** `kubectl get pvc -A -o json` cross-referenced against `kubectl get pods -A -o json | jq -r '.items[]|.metadata.namespace+"/"+(.spec.volumes[]?|.persistentVolumeClaim.claimName//empty)'`.
- **Flag when:** the PVC is `Bound`, no pod in **any** phase in that namespace references it in the object dump, and `AGE ≥ 14d`. _Justification:_ 14 days spans a full deploy/rollback cycle and two runs of this weekly audit, so a flagged PVC has been observed unconsumed at least twice.
- **Do NOT flag:** `SYSTEM_NS`; PVCs whose name matches a live StatefulSet's `volumeClaimTemplate` pattern (scaled-to-zero StatefulSets are deliberate); PVCs referenced by any Job or CronJob pod template, suspended or not (the collector spares every such reference); PVCs referenced by a `VolumeSnapshot` in progress; PVCs with a `WaitForFirstConsumer` storage class that are still `Pending`; PVCs in a namespace under active GitOps sync where the workload is temporarily scaled down (`configsync.gke.io/*` annotations present).
- **Severity:** `major` if ≥ 100 GiB or an SSD class; else `minor`.
- **Impact:** "PVC `ns/data-old` (200 GiB, `standard-rwo`) is Bound with no pod mounting it since at least 2026-07-18 — 200 GiB provisioned and unread."
- **Remediation:** `kind: manual` — confirm with the namespace owner, snapshot the volume, then delete the PVC (which deletes the PV under `Delete`). Never a manifest.

#### 3.4 Unattached Compute Engine persistent disks (`unattached-disk`)

- **Command:** `gcloud compute disks list --project=<p> --filter="-users:*" --format=json`. The full projection, and no age term in the filter: the age is measured off `lastDetachTimestamp`, which a field list has to ask for and a `creationTimestamp` filter would exclude the wrong disks on.
- **Flag when:** the disk has no `users` and has been idle for `≥ 30d`, counted from `lastDetachTimestamp` — or from `creationTimestamp` for a disk with no `lastDetachTimestamp`, which is GCE's way of saying it was never attached. _Justification:_ PD-CSI detaches and reattaches during node upgrades, pod rescheduling, and maintenance windows; 30 days outlives a full monthly GKE maintenance cycle, so this is not churn. That reasoning is about detaches, so creation time cannot stand in for it — a year-old boot disk released this morning is the churn, not the waste.
- **The floor drops to `≥ 7d` when the disk's `goog-k8s-cluster-name` label names a cluster the project no longer runs.** Every clause of the 30-day justification is about something reattaching the disk, and a deleted cluster reattaches nothing — no node pool to upgrade, no scheduler to move a pod, no maintenance window. What is left to outlive is the teardown itself, which is asynchronous, and a same-name recreate in the same sitting; a week covers both. Measured on the reference install: two `platform-agent-host` PDs sat unattached from 2026-08-26 for a cluster deleted the same day, and at 10 days the 30-day floor was still three weeks from reporting them. The comparison is against every cluster `gcloud container clusters list` returns for that project **whatever its status** — a DEGRADED or PROVISIONING cluster still owns its disks — and it is withheld entirely on a project whose enumeration failed, because an unknown fleet must not read as an empty one. The collector applies this; the excerpt says which cluster is gone.
- **Attribution decides what the finding says, not whether it is emitted.** Try the `goog-k8s-cluster-name` / `goog-k8s-cluster-location` labels, then a `gke-<cluster>-` name prefix — the longest one among the project's clusters, and only for a cluster the audit read. PD-CSI's `kubernetes.io/created-for/pv/name` description names a PersistentVolume, not a cluster, and a PV on a read cluster already clears the disk under Do NOT flag, so it attributes nothing. The 7-day floor stays keyed on the label. Either way `cluster` is the literal `project/<project-id>` per §3's project-scoped rule, with `object: Disk/<zone>:<name>`, which is the target the collector files the candidate under. If one of them names a cluster, the impact line names it; if none does, the impact line says ownership could not be determined.
- **Do NOT flag:** disks whose name or handle matches a live PV's `spec.csi.volumeHandle` (claimed, just not currently attached); node boot disks (`goog-gke-node`) of a cluster the project still runs — the pool reclaims them; disks with labels from a managed service (`goog-composer-*`, `goog-dataproc-*`); and, where some of the project's clusters were not read, any disk labelled for one of those clusters and any unlabelled disk a PVC created, since its PV may live on a cluster whose PVs this run does not hold. The collector applies all of these.
- **Severity:** `major` if `sizeGb ≥ 500` or the type contains `ssd`/`extreme`; else `minor`. `critical` under severity rule (b), which reaches only the attributable case — rule (b) is about a deletion recommendation, and an unattributable disk never carries one.
- **Impact:** attributable — "3 unattached `pd-ssd` disks in `us-central1` totalling 1,500 GiB, unattached since 2026-05-30, all labelled for cluster `prod-usc1`." Unattributable — "Unattached 500 GiB `pd-ssd` disk `data-2024` in `us-central1`, unattached since 2026-05-30; no label or name prefix ties it to any cluster this audit read, so its owner is unknown." A disk that was never attached reads "never attached, created 2026-05-30" instead — do not write "unattached since" over a detach that never happened. Where PD-CSI provisioned the disk, the excerpt also names the claim it was cut for: a volume is named for its PV's UID, so `pvc-d45cfdfd-f194-4bda-9d53-f83a67d8ac34` tells a reader nothing about what is on it, and "held the `kubeagents-system/platform-agent-data` PersistentVolumeClaim" is most of the decision the remediation asks them to make.
- **Remediation — attributable disk:** `kind: gcloud`, printed for a human to run, never executed here: `gcloud compute disks describe <n> <scope>` → `gcloud compute snapshots list --filter="sourceDisk~<name>"` → **snapshot if none exists** → `gcloud compute disks delete <n> <scope>`. **`<scope>` is `--zone=<z>` for a zonal disk and `--region=<r>` for a regional one, and it goes on both the describe and the delete** — the candidate carries it, so do not infer it. `<n>` is the part of the `Disk/<zone>:<name>` object after the colon; the whole object is not a disk name, and a delete that fails on it reads as a disk already gone. §3.5 covers why an unscoped command is worse than a failing one. Note verbatim: "Verify before deleting — an unattached disk can be a deliberate cold archive. Snapshot first. Price the disk in the console if you need the figure."
- **Remediation — unattributable disk:** `kind: manual`, and **never a deletion**. This audit knows nothing about who owns the disk, so it does not get to recommend destroying it. `recommendation.action` is to identify the owner — read `gcloud compute disks describe <name> <scope>` (`<name>` the part of `object` after the colon, `<scope>` the `--zone=<z>` or `--region=<r>` the candidate carries) for labels, description, and creation metadata, and check the project's audit log for the principal that created it — and only then decide. Naming a delete command for a disk whose owner you could not determine is the single most dangerous thing this audit can do.

#### 3.5 Reserved static IP addresses not in use (`idle-address`)

- **Command:** `gcloud compute addresses list --project=<p> --filter="status!=IN_USE" --format="json(name,address,addressType,purpose,region,status,creationTimestamp,users,description)"`
- **Flag when:** `addressType == EXTERNAL` **and** `status == RESERVED` **and** `AGE ≥ 14d`. All three, every time. _Justification:_ an IP reserved ahead of a cutover is normal for a sprint; two weeks exceeds a typical cutover window and means this audit has already seen it twice. A reserved-but-unused **external** IP bills continuously — an internal one is free, so it is not waste and flagging it is a false positive whose remediation is an irreversible release. `addressType` is projected by the command above precisely so you can test it; the API returns `EXTERNAL` or `INTERNAL`.
- **Do NOT flag:** addresses whose `purpose` is `GCE_ENDPOINT`, `VPC_PEERING`, `PRIVATE_SERVICE_CONNECT`, `NAT_AUTO`, `SHARED_LOADBALANCER_VIP`, or `IPSEC_INTERCONNECT` (legitimately "reserved" while serving) — `GCE_ENDPOINT` is the purpose GCP assigns a reserved internal ILB VIP and a VM alias-IP range, so leaving it off this list turns every internal load balancer in the fleet into a waste finding; addresses named in any fleet annotation — `kubernetes.io/ingress.global-static-ip-name`, `networking.gke.io/load-balancer-ip`, `cloud.google.com/load-balancer-ip`, `networking.gke.io/addresses` — grep the Step 2 dumps for the address name and value before flagging; addresses whose description mentions DR, failover, or a planned migration.
- **Severity:** `minor` per address. If a single project holds ≥ 10 idle addresses, emit one roll-up finding at `major` instead of ten `minor` ones — that is a leak, not a leftover.
- **Impact:** "4 external addresses in `us-central1` have been `RESERVED` and unattached for 40+ days."
- **Remediation:** `kind: gcloud` — `gcloud compute addresses describe <n> <scope>` to confirm nothing references it, then `gcloud compute addresses delete <n> <scope>`. **`<scope>` is `--global` when the listing gave the address no `region` and `--region=<r>` when it gave one, and it goes on both commands.** `<n>` is the part of the `Address/<region or global>:<name>` object after the colon. The command above projects `region` for exactly this reason. Getting it wrong does not fail loudly: an address command with no scope flag resolves against whatever region gcloud is configured for, so a global address answers `was not found` — which a reader takes as a finding somebody already remediated rather than a command that was written wrong, and the waste stays on the bill. Caution: "Releasing an external IP is irreversible — the address returns to the pool and cannot be reclaimed. Confirm no DNS record points at it."

#### 3.6 Orphaned load-balancer resources (`orphan-lb`)

- **Command:** `gcloud compute forwarding-rules list --project=<p> --format="json(name,IPAddress,region,target,backendService,loadBalancingScheme,pscConnectionId,description,creationTimestamp)"`, plus `target-pools list` and `backend-services list --format="json(name,backends,region,creationTimestamp)"`. Project `region` on both: it is what the remediation below scopes against, and a projection that drops it makes a regional backend service look global.
- **Flag when:** a forwarding rule's description carries a `kubernetes.io/service-name` whose `namespace/name` no longer exists anywhere in the fleet dumps and `AGE ≥ 7d`; or a target pool has zero instances; or a backend service has zero backends. _Justification:_ the GKE service controller tears LB resources down within minutes of Service deletion; a week is three orders of magnitude past normal reconcile latency and past any controller outage.
- **Do NOT flag — this is the highest-risk cross-check in the audit:** **run it only if every cluster in that project was successfully enumerated in Step 1.** If any cluster in the project sits in `scope.skipped`, skip the check for that whole project — the Service may live in the cluster you could not read — and declare the omission on that project's `project/<p>` target: the collector already does, with `orphan-lb` in `checks_unevaluated` and a `limitations` text you carry as §2 says; by hand, write `"limitations": "3.6 not run: cluster <skipped> in project <p> could not be enumerated."` there. Never add a second `scope.skipped` row for a cluster that is already in `scope.skipped`; a duplicate fails validation and publishes nothing. Also exclude: rules with no `kubernetes.io/*` description (Terraform- or human-managed); rules backing a `MultiClusterService`/`MultiClusterIngress` (the Service lives at fleet level); PSC service attachments; internal rules (`loadBalancingScheme` starting `INTERNAL`) whose `backendService` is a live backend service.
- **Severity:** `major` — an orphaned forwarding rule keeps a load balancer and usually an IP alive.
- **Impact:** "Forwarding rule `a1b2c3` still targets deleted Service `staging/checkout-lb`; its backend pool has been empty since 2026-06-20."
- **Remediation:** `kind: gcloud` — `gcloud compute forwarding-rules describe <n> <scope>` to confirm the target, then delete the rule, then its target pool / backend service, then release the address. **Every command in that chain carries its own scope flag and they are not all the same flag:** a forwarding rule or backend service is `--global` or `--region=<r>`, a target pool is always `--region=<r>`, and the address takes whichever §3.5 gives it. The candidate carries the flag for the object it names; read the rest off their own listings rather than assuming the rule's. An unscoped `gcloud compute` verb resolves against whatever region gcloud is configured for and answers `was not found` — §3.5 covers why that reads as already-remediated and leaves the resource billing. Caution: "Confirm no DNS record or external client still resolves to this IP."

#### 3.7 Under-allocated node pools and non-zero autoscaler floors (`idle-nodepool`)

- **Command:** `gcloud container node-pools list --cluster=<c> --location=<l> --format="json(name,initialNodeCount,config.machineType,config.taints,autoscaling,management)"` joined against per-node request sums from `kubectl get pods -A --field-selector=status.phase=Running -o json` versus `.status.allocatable` in `kubectl get nodes -o json`.
- **Flag when:** every node in the pool shows **workload** CPU requests ≤ 15% **and** workload memory requests ≤ 15% of allocatable, and the pool has ≥ 1 node, and either autoscaling is disabled or `autoscaling.minNodeCount ≥ 1`. Workload requests are non-DaemonSet **and** outside `SYSTEM_NS`. _Justification:_ measure **requests**, not usage — requests are what the cluster autoscaler acts on, so they are what determines whether the pool can shrink. The ratio excludes GKE's own add-ons for the same reason it excludes DaemonSets: they reschedule with the node, so they are not a reason to keep the pool, and where they need a home it is the "only node pool" exclusion below that gives it to them. Counting them made the bar unreachable rather than merely strict — this check used to read "15% is below the point where DaemonSet and system overhead (typically 10–25% of a small node) dominates", and on the sixteen-cluster fleet measured 2026-09-05 that overhead was 45–70% of every Standard pool, because the non-DaemonSet add-ons (kube-dns 270m, kube-state-metrics 105m, kube-proxy as a static pod 100m, metrics-server, konnectivity, l7-default-backend and two autoscalers) come to ~0.57 vCPU on every node whatever its size. A fixed numerator against a 15% bar means only nodes above ~3.8 vCPU of allocatable can ever clear it, so the check fired on nothing at all — including a lone untainted `e2-small` `default-pool` carrying zero workload pods beside a pool with 1.5 vCPU spare. A `minNodeCount ≥ 1` floor on such a pool is capacity nobody asked for.
- **Do NOT flag:** Autopilot clusters (this check does not apply there and is declared in their `checks_not_applicable` per Step 2); pools created < 7 days ago, dated by the pool's own `CREATE_NODE_POOL` operation (`gcloud container operations list`), or, for a pool with none (the cluster's first, created inside `CREATE_CLUSTER`, or one older than the operations the API keeps), by the cluster's `createTime`; never by its nodes, which every node upgrade recreates, except when the operations read fails, where the oldest node stands in and the collector names each pool it exempted that way in `limitations`; pools already at `minNodeCount: 0` with zero nodes (nothing to reclaim); pools whose nodes are `SchedulingDisabled` or mid-upgrade; the cluster's only node pool (system pods need somewhere to land); pools where DaemonSets alone account for the allocation _and_ the pool is a deliberate burst pool with `minNodeCount: 0`. GPU/TPU pools are **not** suppressed — an idle accelerator pool with a non-zero floor is the single largest reclaimable item this audit can find.
- **Severity:** `major` if the pool has ≥ 3 nodes, a machine type of ≥ 8 vCPU, or attached accelerators; else `minor`.
- **Impact:** "Node pool `gpu-burst` (2 × `a2-highgpu-1g`, `minNodeCount: 1`) has held ≤ 4% non-DaemonSet CPU allocation — 2 accelerator nodes reserved for nothing."
- **Remediation:** `kind: gcloud` — `gcloud container node-pools update <pool> --cluster=<c> --location=<l> --enable-autoscaling --min-nodes=0`, or delete the pool if it has been empty for consecutive audits. **Read the excerpt's drain-blocker sentence before choosing between the two.** Lowering the floor only asks the autoscaler to drain, and it refuses for as long as the node holds a `kube-system` pod with no PodDisruptionBudget or a pod with a `hostPath` or disk-backed `emptyDir` — two default skip rules GKE does not let you turn off — or a system-namespace pod that is bare or `safe-to-evict: "false"`, PDB or not, unless the pod is annotated `safe-to-evict: "true"` (or, for the second, `safe-to-evict-local-volumes` lists every local volume). Where the collector lists blockers, `--min-nodes=0` reclaims nothing and deleting the pool is the remediation that works; annotating the add-ons is not an option, because addon-manager reverts the edit. Caution: "Setting `min-nodes=0` lets the autoscaler drain these nodes; confirm no workload depends on warm capacity. Deleting a pool evicts everything on it." The excerpt's headroom figure is pool-level, leaves out cordoned nodes and every pool the run finds idle, and models neither taints, node selectors nor zonal spread, so it is a necessary condition for the reschedule, not a sufficient one.

#### 3.8 Scale-down blockers pinning under-allocated nodes (`scaledown-blocked`)

**PodDisruptionBudgets are out of scope here.** The Workload Reliability audit (`obtainability-audit`, checks 3.3 and 3.4) owns whether a PDB exists and whether its shape blocks drains, and it emits the rewrite. It reads every PDB in the fleet daily and knows each one's target replica count; this audit sees only the PDBs sitting on the handful of nodes 3.7 flagged, weekly. Two ledgers proposing two edits to one PDB is how a workload owner gets contradictory pull requests. So: where a flagged node's only blocker is a PDB, emit **no** finding — it is already reported there.

- **Command:** `kubectl get pods -A -o json` filtered to pods on the nodes 3.7 flagged — read for `metadata.ownerReferences`, `status.phase`, the `cluster-autoscaler.kubernetes.io/safe-to-evict` and `safe-to-evict-local-volumes` annotations, and `emptyDir`/`hostPath` entries in `spec.volumes`.
- **Flag when:** an under-allocated node hosts at least one pod the autoscaler cannot evict for a reason that is **not** a PDB — the annotation `cluster-autoscaler.kubernetes.io/safe-to-evict: "false"`; or, unless the pod is annotated `safe-to-evict: "true"`, a bare pod with no `ownerReferences` or a pod with local storage (a `hostPath`, or an `emptyDir` not of `medium: Memory`) that `safe-to-evict-local-volumes` does not list in full. All three annotations are compared exactly, as the autoscaler compares them: `"False"` or `"0"` pins nothing, and the volume list is split on `,` with no trimming, so `"cache, logs"` does not list `logs`. Evaluate only nodes flagged in 3.7 — that keeps the check cheap and keeps it a waste finding rather than a policy opinion.
- **Do NOT flag:** `SYSTEM_NS`; pods that have finished (`Succeeded`/`Failed`), and DaemonSet and mirror pods, which go with the node; any node whose only unevictable pod is held by a PDB (see above); nodes already cordoned or mid-upgrade; pods being deliberately pinned by a documented anti-eviction annotation with an owner label.
- **Severity:** `critical` when nothing will ever reschedule the pod — a bare pod with blocking local storage (disk-backed and not fully listed), or `safe-to-evict: "false"` on a pod with no controller — because that blocks node drain permanently, which blocks autoscaler scale-down _and_ security patching and node upgrades. `major` otherwise.
- **Impact:** "Node `gke-prod-default-a1b2` sits at 8% CPU allocation but cannot be drained: bare pod `ci/debug-shell` has no `ownerReferences` and mounts an `emptyDir`, so the autoscaler will hold this node indefinitely."
- **Remediation:** `kind: manual` — move the workload under a controller so it can be rescheduled, or have its owner clear the `safe-to-evict: "false"` annotation once the local state it protects is understood. Caution: "A pod pinned with local storage may hold state that does not survive rescheduling — confirm with the owner what is in the volume before it moves."

#### 3.9 Terminal pods and TTL-less Jobs (`terminal-pods`)

- **Command:** `kubectl get pods -A --field-selector=status.phase==Succeeded -o json` and `...==Failed -o json`, plus `kubectl get jobs -A -o json | jq '[.items[]|{ns:.metadata.namespace,name:.metadata.name,owner:(.metadata.ownerReferences[0].kind//""),ttl:.spec.ttlSecondsAfterFinished,done:.status.completionTime}]'`.
- **Flag when:** a namespace holds ≥ 50 terminal pods, or any terminal pod is older than 7 days; or a standalone Job (no CronJob owner) has been `Complete`/`Failed` for ≥ 7 days with `ttlSecondsAfterFinished` unset. _Justification:_ 50 is well above the handful a normal rollout leaves behind and well below the point where a single namespace hurts anyone; the 7-day floor keeps a debugging engineer's failed pods intact through a working week.
- **Do NOT flag:** `SYSTEM_NS`; pods younger than 24h (someone may still be reading them); Jobs owned by a CronJob (`successfulJobsHistoryLimit` already bounds them, unless it is set above 10 — then flag the CronJob, not the Jobs); Jobs that already set `ttlSecondsAfterFinished`; resources owned by a controller with its own GC (`workflows.argoproj.io/*`, `tekton.dev/*`, `fluxcd.io/*` labels).
- **Severity:** `minor`. `major` when one namespace exceeds 500 terminal pods or the cluster total exceeds 2,000 — at that point it is etcd object growth and API-server list latency, not just untidiness.
- **Impact:** "Namespace `ci` holds 1,840 `Succeeded` pods, the oldest from 2026-03-11 — 1,840 etcd objects listed on every full API-server sweep."
- **Remediation:** `kind: manifest`, subject to §4's declaration rule — the one safe additive change in this SOP: set `ttlSecondsAfterFinished: 86400` on the Job spec or the CronJob's `jobTemplate.spec` in the object's GitOps declaration, rewriting that file complete. Change the declaration, never a live completed Job, and if the object has no declaration you can find, the finding is `kind: manual`. Note that the existing backlog still needs a one-off `kubectl delete pod --field-selector=status.phase==Succeeded -n <ns>` run by a human.

#### 3.10 Idle namespaces holding billable objects (`idle-namespace`)

- **Command:** `kubectl get ns -o json` cross-referenced against the pod, PVC, and Service dumps from Step 2.
- **Flag when:** a non-`SYSTEM_NS` namespace has zero `Running`/`Pending` pods, `AGE ≥ 30d`, and still holds a billable object: a PVC, or a `type: LoadBalancer` Service. _Justification:_ a namespace with no workload but a bound volume or a live load balancer is paying for nothing; 30 days covers a monthly release cycle and a pre-provisioned environment awaiting its first deploy.
- **A ResourceQuota is not one of them**, and must never be offered as the reason a namespace costs anything. Kubernetes reserves nothing for a quota: it is an admission gate on the sum of the requests of the pods in its own namespace, it holds no capacity, it constrains no other namespace, and on Autopilot there is no pool for it to carve up in the first place. An idle namespace whose only object is a quota bills exactly zero, so it is not a finding here at all.
- **Do NOT flag:** `SYSTEM_NS`; namespaces holding only Secrets, ConfigMaps, RBAC, or CRs (free); namespaces under an active GitOps sync (a `configsync.gke.io/*` or `kustomize.toolkit.fluxcd.io/*` label or annotation; Flux stamps labels) — the controller owns their lifecycle; namespaces that are the target of a suspended or infrequent CronJob (idle by design — the collector skips any namespace holding a CronJob); namespaces carrying an explicit ownership or retention annotation (the collector reads one as an annotation key whose name part holds the word `owner`, `retain` or `retention`); namespaces in `Terminating`.
- **Severity:** `major` if it holds a `LoadBalancer` Service or ≥ 100 GiB of PVCs; else `minor`.
- **Impact:** "Namespace `demo-q1` has no running pods, was created 30+ days ago, and still holds a `LoadBalancer` Service and 250 GiB of PVCs."
- **Remediation:** `kind: manual` — confirm the owner, then remove the LB Service and snapshot-then-delete the PVCs before deleting the namespace. Caution: "Deleting a namespace deletes everything in it, including PVCs whose PVs use `Delete`. Snapshot first."

#### 3.11 Sustained memory use above the request (`underrequest`)

**This is 3.1's other half, and it is numbered after 3.10 only to avoid renumbering the nine sections between them.** Read the two together: 3.1 owns a request larger than the workload, this one a request smaller than it, and both are the same question about the same number. Keeping them in one audit is deliberate — the boundary note in 3.1 explains that two streams sizing one container is how an owner gets contradictory pull requests, and that argument applies with more force to the two directions of the same edit than it does across audits.

It is not a waste finding. A request below actual usage costs nothing and reclaims nothing; it is here because this is the audit holding the usage history, and because a right-sizing stream that only ever sizes downward will eventually propose a cut to a workload that was already too small.

- **Command:** the collector's second Cloud Monitoring read — `kubernetes.io/container/memory/used_bytes`, summed to the pod, collapsed over the window with `ALIGN_MEAN` rather than 3.1's `ALIGN_MAX` — joined against the same pod dump 3.1 uses, widened the same way to the pods the controller has replaced, and aggregated to the owning controller. `ALIGN_MEAN` averages the points that exist, so a pod that lived a tenth of the window carries its mean while it was alive rather than a tenth of it, and a replaced pod is comparable to a live one.
- **Flag when:** for a controller, **mean** aggregate memory usage over the window exceeds aggregate memory requests, and the overage is ≥ 128 MiB summed across its pods. _Justification:_ the mean and not the peak is the whole check. A peak above the request is what Burstable QoS exists for and flagging it would report every workload that ever bursts; a mean above it says the request does not describe the workload at all. The floor sits on the overage because the overage is the quantity doing the harm — it is what the scheduler failed to book on the node, and it is the key kubelet sorts Burstable pods by when it picks one to evict. A ratio test alone would flag a pod a megabyte over. Memory only: CPU is compressible, so a CPU request under actual usage costs throttling under contention, while memory cannot be reclaimed from a running process.
- **Do NOT flag:** 3.1's pod exclusions, applied by the same code — `SYSTEM_NS`, DaemonSets, pods under an hour old, `Job`-owned pods, pods in `Pending`/`Terminating` — but not its HPA and `LimitRange`-default exclusions, which guard a request cut and are 3.1's alone. Also skip any controller with a container declaring no nonzero memory request: a pod with none at all is 3.12's and the Workload Reliability audit's `no-requests`, and a sidecar with none, or with `memory: "0"`, would have its usage set against another container's request. Also skip any controller none of whose pods appear in the Monitoring answer: summing absent pods as zero usage would read it as comfortably under its request.
- **Severity:** `major`. `critical` only where every container declares a memory limit and the mean is also ≥ 90% of the aggregate memory **limit** — a limit on some containers only bounds none of the pod, so the excerpt says so and the grade stays `major`. That is an OOMKill waiting for one more request rather than a scheduling mistake, and it is the one arm of this check describing something already failing. No Autopilot bump: this stream already grades most of what it finds at the ceiling, and a severity every finding shares stops ordering any of them.
- **Impact:** the collector writes it. "Sustained memory use above the request means the scheduler has under-booked every node this controller lands on, and kubelet ranks Burstable pods for eviction by exactly this overage — so it is the first thing evicted when any workload on that node needs memory."
- **Remediation:** `kind: manifest`, subject to §4's declaration rule and 3.1's `Guaranteed`-QoS exception — the controller's complete desired manifest with the **memory request** raised to the figure the excerpt names, and **nothing else touched**. The excerpt ends with "Raise the memory request to `N`Mi", per replica where the controller has more than one — on a multi-container pod "of container `<name>`", with `N` already less the other containers' requests; copy `N` onto that container and do not recompute it. It is `ceil(peak × 1.3)` against the per-replica peak — or against the per-replica mean where the excerpt says "peak not read", since a peak is never below its mean — but the peak the excerpt prints beside it is rounded to two decimals of a GiB, and 1.3× a rounded peak is not the same number: on 2026-09-07 `litellm` printed a 1.62 GiB per-replica peak that recomputes to 2157Mi where the measurement gives 2153Mi. 1.3× and not 3.1's 2×: sizing up is the direction that costs bookable capacity on every node the controller lands on, and the mean already establishes that this is the steady state rather than a spike. Not the CPU request, which this check did not measure. **The memory limit only when the excerpt says so** — where the new request exceeds that container's own declared limit the excerpt adds "raise the limit to `M`Mi in the same edit", and `M` goes into the manifest with `N`. Do not make that comparison yourself: the limit in the excerpt's opening clause is the controller total across every replica, so a prescription that collides with the real limit reads as comfortably under it, which is how a manifest the API server rejects at admission was published on 2026-09-07. No such sentence, no limit change. Note: "raising a request can make the pod unschedulable on a full node; confirm the cluster has headroom, or expect a rollout to sit `Pending`."

#### 3.12 Workloads running with no request at all (`unsized-workload`)

**This is where 3.1's deferral lands.** 3.1 says the Workload Reliability audit owns the request's _absence_ and "deliberately proposes no number, deferring the sizing to here, where the usage history is". Until this check existed nothing here accepted that: both 3.1 and 3.11 skip a container with no request, so the value was never produced and the deferral ended nowhere. On the sixteen-cluster fleet measured 2026-09-05 that was seven of the twenty-one eligible controllers — every Argo CD component on the hub, including an application controller peaking at 0.18 vCPU and 1.6 GiB that the scheduler books as zero. The reliability audit named all seven; neither audit gave a number for any of them.

**So this check reports the number and nothing else.** It never says a request is missing — that finding already exists in the other stream, and 3.1's boundary rule is about the two audits not restating one another's half. Read the pair as one sentence split across two ledgers: that audit says the request is absent, this one says what it should be.

- **Command:** 3.1's Cloud Monitoring peak read, joined against the same pod dump and aggregated to the same owning controller. The two checks partition one population — a controller either declared a request, and is 3.1's and 3.11's, or declared none, and is this one's — so they share a code path and cannot both claim the same object.
- **Flag when:** no container in any of a controller's pods declares a nonzero CPU or memory request (`cpu: "0"`, or only `nvidia.com/gpu` or `ephemeral-storage`, counts as none, though `no-requests` passes a declared zero), and its pods appear in the Monitoring answer on both dimensions. _Justification:_ a `BestEffort` pod is booked as zero by the scheduler, so it lands on nodes that are already full, kubelet evicts it first under memory pressure, and the autoscaler cannot count it when sizing the cluster. None of that is visible as waste, which is why the check that owns the usage history is the one positioned to fix it.
- **Do NOT flag:** 3.1's pod exclusions, applied by the same code — `SYSTEM_NS`, DaemonSets, pods under an hour old, `Job`-owned pods, pods in `Pending`/`Terminating` — but not its HPA and `LimitRange`-default exclusions, which are 3.1's alone. A partially sized controller is 3.1's and 3.11's, not this one's: one container with a request and one without is already in their population. And **skip any controller whose pods are absent from the Monitoring answer, or present on one dimension only** — the whole finding is the measurement, and without one the recommendation would be to request zero, which is the state being complained about.
- **Severity:** `minor`; one level higher on Autopilot, stopping at `major` for 3's reason. The Autopilot bump is not the same argument as 3.1's: there the cluster bills for a request nobody uses, here it bills for a default nobody chose, because Autopilot substitutes its own where a manifest declares none.
- **Impact:** the collector writes it. "With no nonzero CPU or memory request, the scheduler books nothing for this controller: it lands on nodes that are already full, it is BestEffort so kubelet evicts it first under pressure, and the autoscaler cannot count it when sizing the cluster."
- **Remediation:** `kind: manifest`, subject to §4's declaration rule and 3.1's `Guaranteed`-QoS exception (which cannot arise here — a container with no request is never `Guaranteed`) — the controller's complete desired manifest with CPU and memory `requests` added at `peak × 2` per replica, floors `10m` / `32Mi`, and limits untouched. The excerpt spells out the per-replica figure; the headline peak is the worst replica's multiplied by the replica count, and sizing against that multiplies the new request by the replica count again. 2× and not 3.11's 1.3× because this is 3.1's peak-based rule, not a mean. Note: "this workload has been running unbooked, so the cluster's current capacity does not account for it — confirm there is headroom, or expect the rollout to sit `Pending`."

#### 3.13 Declared workloads nothing is using (`idle-workload`)

**This is the population 3.1 deliberately drops.** 3.1's last flag-when clause refuses to report a controller whose resize would change no number — right, because a Deployment already declaring `50m`/`64Mi` has no smaller request to propose, and three such rows a week teach a reader to skip the section. What that rule silenced was the reason they kept appearing. On the fleet measured 2026-09-06 it was four `hello-world`-class Deployments, declared 28 to 35 days earlier, each holding the platform's minimum request and peaking between 0.6% and 15% of it. The audit measured all four correctly and said nothing about any of them, because the only question it knew how to ask was "what should this request be" and the honest answer was "exactly what it already is".

**So this check asks the other question.** Not "could the request be smaller" but "is anything using this at all" — and where the answer is no, the fix is not a resize.

The partition with 3.1 is exact and the collector enforces it, and it turns on whether 3.1 will **propose** a resize rather than on whether one is arithmetically available. Usually those are the same thing: this fires where the resize floor makes 3.1's remediation a no-op on **every** dimension, or where the only dimension it could shrink requests less than 3.1's `100m` / `128Mi` materiality floor, which is precisely where 3.1 does not fire. The one exception is `Guaranteed` QoS, below. Either way no controller produces both findings, so the report never asks a reader to shrink and to stand down the same object.

- **Command:** 3.1's Cloud Monitoring peak read, joined against the same pod dump and aggregated to the same owning controller, plus the controller's own `creationTimestamp` from `kubectl get deploy,sts -A -o json`.
- **Flag when:** peak aggregate usage is ≤ 20% of aggregate requests on **every** dimension the controller declares; the controller itself was created **more than 14 days ago**; and 3.1 will propose no resize for it — because the resize would lower no dimension 3.1 judges (floor-bound: every dimension is at or below the `50m`/`64Mi` sizing floor, or is the namespace `LimitRange` default, which gets no verdict there), because the only dimension it could shrink requests less than 3.1's `100m` / `128Mi` materiality floor, **or because the controller is `Guaranteed` QoS**, where 3.1 declines the resize it could compute. _Justification:_ the threshold is 3.1's, on purpose — what separates the two checks is not how idle a workload is but whether anything can be done about it, and a second stricter number here would be one to defend with nothing deciding on it. Requiring **every** dimension rather than 3.1's **either** is what makes the finding "nobody is using this" instead of "one dimension is oversized"; on the measured fleet that is what excludes `cert-manager` (17% of its CPU request but 95% of its memory), its webhook (7% and 68%), and `kube-agents-controller-manager` (44% and 55%).
- **Why `Guaranteed` lands here.** 3.1 refuses to resize a `Guaranteed` controller because on such a pod the request _is_ the limit, so a number derived from a week of idleness becomes an enforcement ceiling. That refusal is right, and it was leaving the fully idle ones with nowhere to go: 3.1 published prose, and this check stayed silent because its partition asked whether a resize was arithmetically available rather than whether 3.1 would make one. Above the `50m`/`64Mi` floor the arithmetic says yes, so both checks declined. Observed on 2026-09-06: `ai-inference-hardened` and `ai-inference-unsafe` on one cluster, each `Guaranteed` at 0.50 vCPU / 2.0 GiB, each peaking at 0.00 vCPU across the trailing week, both declared in the GitOps repo, both published `kind: manual`. The stand-down carries none of the hazard 3.1 is avoiding — scaling to zero sets no ceiling, because no pod is left for one to bind. It stays the narrow case: idle on **every** dimension and past the 14-day bar. A `Guaranteed` controller idle on one dimension only is still 3.1's, where nothing is unused, one number is wrong, and the `manual` note is the right answer.
- **Age is the controller's, not its pods'.** Where a controller's replaced pods are in the Monitoring answer, every check in this audit already measures over the controller's own age. Where they are not — nothing was replaced inside the window — the measurement window clamps to the oldest live pod, because that is how much history exists. Neither is what this bar asks: it asks how long the workload has _existed_, which on a managed platform is a third number again. GKE recreates a pod on every node upgrade, so the four Deployments this check reports had run untouched for a month behind pods under eight days old. Gating on the pod would have excluded all four and gone on excluding them forever, since nothing on Autopilot keeps a pod for a fortnight.
- **Do NOT flag:** 3.1's exclusions, applied by the same code — `SYSTEM_NS`, DaemonSets, pods under an hour old, `Job`-owned pods, pods in `Pending`/`Terminating`, controllers an HPA targets (the HPA scales a `replicas: 0` straight back to `minReplicas`), and any controller absent from the Monitoring answer or present on one dimension only. That last one matters more here than anywhere else in this audit: an unmeasured controller sums to zero usage, which is the most idle a workload can possibly read, and the finding it would produce recommends standing the workload down. Also skip any controller that is not a `Deployment` or a `StatefulSet` — the age test has nothing to read, and this check does not guess an age from a pod.
- **Severity:** `minor`; `major` where a `LoadBalancer` Service selects the controller's pods, **or where a `Guaranteed` controller's request clears 3.1's materiality floor** (0.1 vCPU or 0.125 GiB). A request pinned at the platform floor is small by construction, so on that arm the reservation alone never justifies more than `minor`. The load balancer does: its forwarding rule (and external IP, unless the Service is internal) is the larger charge — on the measured fleet roughly four times the pods it fronts — and an external one, unlike the pod, is reachable from the internet whether or not anything calls it. The `Guaranteed` arm has no such construction: those requests are whatever the author wrote, and half a vCPU held idle for a fortnight is not `minor` because nothing happens to be in front of it.
- **This check measures CPU and memory. It does not measure traffic, and must not claim to.** A controller can hold a week of flat CPU and still be answering — a cache hit, a health probe, a 304, anything cheap. The audit said otherwise for eleven days: the impact sentence read "a workload nobody is calling", three findings carrying it cleared the promotion floor on 2026-09-07, and the pull requests merged unattended and stood down three Deployments. Two sat behind forwarding rules that had metered 837,460 and 785,748 inbound packets across the very window the finding quoted. The packets were internet background scanning, so the conclusion happened to hold — which is the worst version of this, because nothing in the run could have told the difference. Where the collector supplies a traffic line in the excerpt, publish the number and reason from it in the recommendation; never restate it as a claim about callers, and never let its absence become one either. A rule with no series is unmeasured, not zero.
- **What the traffic line is, and what it is not.** Where the controller is fronted by a `LoadBalancer` Service that has been assigned an external address, the collector joins that address to its forwarding rule and reads three `loadbalancing.googleapis.com/l3/external` counters over the same 168 hours — inbound packets, outbound packets, outbound bytes — and writes what it found into the excerpt. Read the sentence it wrote; do not compute anything from it. It comes in five shapes and they mean different things. Under 10,000 inbound packets across the week is **background**, roughly a packet a minute, which is less than a public address collects from internet scanners with nothing behind it. Above that but under 100 bytes per outbound packet is **busy and serving nothing** — an IP and TCP header alone is 40 bytes, so a week averaging under that answered without ever sending a payload, and that is the shape both rules behind the 2026-09-07 stand-downs had. Above that on both counts, something is being served: say so and say the check measured a forwarding rule rather than a caller. And a rule the Monitoring API holds no series for is reported as **unmeasured**, which is not the same as quiet and must never be published as though it were; so is a rule above the floor whose outbound series is missing, since without it neither busy-and-serving-nothing nor serving can be told apart. None of the five changes the severity or releases the triage gate; all five go in the recommendation so the person deciding has the number. The read is recorded in the manifest under `idle-workload-traffic`. That is a command, not a check — §3 has no check by that name, and putting it in the document's `checks_run` fails the run.
- **Impact:** the collector writes it. "This controller's peak usage stayed at or below 20% of its requests on every dimension it declares over the measured window the excerpt names, and no resize can give any of the reservation back — it, and any load balancer in front of it, bill for a reservation nothing draws on. Whether anything is still calling it is a separate question this check does not settle: the excerpt gives what the forwarding rule metered, and packets are not sessions. The excerpt also says which of the three no-resize reasons applies."
- **Remediation:** `kind: manifest`, subject to §4's declaration rule — the controller's **complete** desired manifest with `spec.replicas: 0` and every other field, including `resources`, exactly as the repository declares it. Do not resize anything, on either arm: the finding is that no resize is available (floor-bound), that none is worth proposing (under 3.1's `100m` / `128Mi` materiality floor), or that none is safe (`Guaranteed`), and a PR that also changed the request would be making the edit this check exists to say is off the table. On the `Guaranteed` arm in particular, lowering `requests` alongside the stand-down would reintroduce the enforcement-ceiling hazard 3.1 declined, in a pull request whose stated purpose is to avoid it.
- **Why scale to zero rather than delete the file.** Deleting the declaration is the action this finding is really arguing for, and it is not what the pull request proposes, for two reasons worth stating in the note. It is not expressible: a `manifest` remediation is staged by reading the file named in `remediation.path`, so a removed file degrades the finding to `manual` at `finish` and the audit publishes prose where it promised a fix. And it is not reversible in review — `spec.replicas: 0` reclaims the whole pod charge, survives a `git revert` of one line, and leaves the object and its history in place for the operator who actually knows whether the workload is finished with.
- **Say what the pull request does not reclaim.** Where the finding is `major` because a `LoadBalancer` Service selects it, the load balancer is the larger charge and scaling the Deployment to zero does not release it: the Service keeps its forwarding rule and external IP with no endpoints behind them. Give the finding this note verbatim, after the sentence above, with "its forwarding rule" in place of "its forwarding rule and external IP" for an internal Service, which has no external IP: "this stops the pod charge only. `<Service>` keeps its forwarding rule and external IP until someone removes the Service or changes it to `ClusterIP`, and that is a decision about whether the workload is finished with, which this audit does not make for you."

#### 3.14 Artifact Registry repositories nothing ever deletes from (`registry-no-cleanup`)

**Every other check in this audit finds a resource somebody provisioned and stopped using. This one finds the absence of a policy.** A registry does not go idle and never gets cheaper on its own: Artifact Registry bills for every byte it holds, deletes nothing without being told to, and CI pushes to it on every merge. So the waste here is not a leftover that a reader can look at and decide about — it is a slope, and the finding is worth reporting precisely because nobody is going to notice it. On the reference install the project's one repository held 91.9 GB after 44 days, from image builds nothing prunes, and no other check in this SOP looks at registries at all.

- **Command:** `gcloud artifacts repositories list --project=<p> --format=json`. The full projection, no field list: `mode`, `sizeBytes`, `createTime`, `cleanupPolicies`, and `cleanupPolicyDryRun` each decide the verdict on their own, and a projection that drops one turns a flag into a pass without failing.
- **This read is gated by itself, not with §3.4–3.6.** Those three share one all-or-nothing compute gate. This one has its own, so a project whose Artifact Registry API is disabled, or whose caller lacks `artifactregistry.repositories.list`, loses this check alone instead of the project's whole compute coverage — and the reverse, a compute read that fails, does not take the registry check with it. A disabled API is declared: the project entry lists `registry-no-cleanup` in `checks_not_applicable` (§2). Any other failed read, a missing permission included, leaves the check in `checks_unevaluated`, and the collector appends the omission to that project's `limitations` naming the command and its exit code, **after** the compute gate has written its own sentence, so neither erases the other.
- **Flag when:** `mode == STANDARD_REPOSITORY` **and** `sizeBytes ≥ 50 GiB` **and** `AGE(createTime) ≥ 30d` **and** the repository declares no `cleanupPolicies` — or declares them with `cleanupPolicyDryRun` true. _Justification:_ 50 GiB is roughly $5/month of registry storage, the same order §3.5 already treats as `minor`, and nothing is lost by setting the floor there rather than lower — a repository with no policy only grows, so a smaller one crosses the floor and reports on a later run. The 30-day age is what gives the growth figure below any meaning: one day of pushes divided by one day of age reads as a runaway on every new repository.
- **A dry-run policy counts as no policy, deliberately.** `cleanupPolicyDryRun` makes Artifact Registry log what it would delete and delete nothing. That is how a policy is supposed to be introduced, and it is also how one is forgotten — it reads as configured in the console and in `gcloud ... list`, so a check that tested only for the presence of `cleanupPolicies` would call the forgotten case clean. Say which it was in the finding: "no cleanup policy" and "2 cleanup policies configured, all in dry-run, so nothing is deleted" send a reader to different places.
- **Do NOT flag:** a `REMOTE_REPOSITORY` — it is a pull-through cache and Google evicts it on its own schedule, so there is no policy to write; a `VIRTUAL_REPOSITORY` — it stores nothing and is a view over other repositories, so its `sizeBytes` double-counts the ones this check already reads; anything under the size floor or the age floor, however policy-less.
- **Severity:** `minor`. `major` where the repository is already ≥ 500 GiB, or where average growth — `sizeBytes` over the repository's age, the only growth figure a single `list` can produce — is ≥ 2 GiB/day, which is 730 GiB a year. The check never reaches `critical`: none of §3's rules (a) to (c) is in play, and the remediation below is not a deletion this audit is recommending.
- **Impact:** the collector writes it. "Artifact Registry bills for every byte it holds and deletes nothing on its own, so a repository with no cleanup policy costs more every time CI pushes and never costs less."
- **Remediation:** `kind: gcloud`, and **never `manifest`, even where the GitOps repository declares the repository as a KCC `ArtifactRegistryRepository`** — that resource does carry `cleanupPolicies` and `cleanupPolicyDryRun`, so the fix is expressible as a manifest, and it still must not be one. A cleanup policy deletes container images. A `keep` rule that misses a tag some cluster still deploys is a merge that breaks the next pod schedule in the fleet, and §4's rule against a manifest that deletes data is exactly this case in a different resource. Which images to keep is a decision about what the fleet runs, and this audit does not know that.
- The note goes in a bash fence, as every `gcloud` note does. `<repo>` is the part of the `ArtifactRegistryRepository/<location>:<repo>` object after the colon. `<location>` comes from the excerpt, which carries it as `--location=` for this reason: an Artifact Registry verb with no `--location` resolves against whatever gcloud is configured for and answers `NOT_FOUND`, which reads as a repository somebody already cleaned up. Write it as:

  ```bash
  # Read what is in the repository before writing a policy that deletes from it.
  gcloud artifacts docker images list <location>-docker.pkg.dev/<project>/<repo> --include-tags --format=json

  # Dry-run FIRST. This logs what the policy would delete and deletes nothing.
  gcloud artifacts repositories set-cleanup-policies <repo> --location=<location> --project=<project> --policy=policy.json --dry-run

  # Read the deletions Artifact Registry logged. Only then remove the dry run.
  gcloud artifacts repositories set-cleanup-policies <repo> --location=<location> --project=<project> --policy=policy.json --no-dry-run
  ```

- **Caution, verbatim in the note:** "Deleting an image a running pod already pulled does not stop that pod — it stops the next one. A node that has to pull the image gets `ImagePullBackOff`, so the breakage arrives at the next node upgrade or scale-up rather than at the delete. Keep every tag any cluster in the fleet currently deploys."

### 4. Generate remediation artifacts

Only three manifest kinds are permitted, none of them destructive: the `ttlSecondsAfterFinished` change (3.9), the request right-size change in any of its three directions (3.1 down, 3.11 up, 3.12 from nothing), and the `spec.replicas: 0` stand-down (3.13). **All target an object that already exists**, so all go to that object's **existing declaration in the GitOps repo**. **Where the candidate carries a `declaration`, that is the answer**: `declaration.path` is the file, relative to the repository root, and it goes straight into `remediation.path`. It is computed by parsing the repository (a clone, or in content mode the collector's copy of its YAML), keyed on all four of cluster, kind, namespace and name, and it is authoritative — prefer it to any `grep` of your own. Its **absence** is not a claim that no declaration exists: it means the object was not found, was declared twice, the collector ran without `--workspace`, or, in content mode, it could not copy all of the repository's YAML out of the broker (it logs a `WARNING` saying why). Only then fall back to locating it in the `workspace` (`grep -rl "name: <object>" --include='*.yaml' <workspace>`, or in content mode `audit_report.py grep`), giving that file's path relative to the repository root as `remediation.path`, and rewriting it as the object's complete desired manifest. **Open the hits before you trust them.** `grep` is kind-blind and unanchored: `name: <object>` also matches every `app.kubernetes.io/name:` label line and every object whose name merely starts with the one you flagged, and it will happily return a file under another cluster's directory. A hit is not a declaration until you have opened it and confirmed it declares the object you observed, on the cluster you observed it on. **If the hits land in more than one directory, or none can be tied to the target cluster, the finding is `kind: manual`.** Never emit a patch fragment — a file carrying `metadata.name` and a partial `spec` is not valid `kubectl apply` input, and a second file claiming an object the repo already declares is a duplicate resource id that both Config Sync and Argo reject. **An object no file declares because something renders it is fixed with an override on that, and it is still `kind: manifest`.** Those workloads are most of a real fleet, and a right-size is the fix an override carries best, because `resources` is the one key nearly every chart publishes and a Kustomize patch reaches it unconditionally. The candidate says so: `release_declaration.path` is the file declaring the release or the overlay — an Argo CD `Application` or a Flux `HelmRelease` — and `release_declaration.values_field` is the field inside it the override belongs in. Put that path in `remediation.path` and rewrite that file complete, with the resize expressed as chart values under `values_field`, never as the workload manifest. A rewritten workload manifest is applied and then reverted at the next sync, because the chart still renders the old numbers. **Where `release_declaration.renderer` is `kustomize`, the same holds with a patch in place of a values key**: the object comes from an overlay over a base in another repository rather than from a chart, and `values_field` names a list of patches. Append one whose `target` matches the object the finding names — `kind`, `name`, and `namespace` all three, because a `target` given only a `kind` resizes every object of that kind the overlay renders — and whose `patch` carries only the `resources` block, or only `spec.replicas` for 3.13. There is no chart to interrogate then, so the next sentence does not apply: a strategic-merge patch reaches `resources` whether or not anything publishes a key for it. **Where `renderer` is `helm`, confirm the values key exists before you propose it.** Run `helm show values <release_declaration.chart> --repo <release_declaration.repo> --version <release_declaration.version>` and read the output: a key the chart does not read merges clean, changes nothing, and republishes the finding next week against a repository that now looks fixed. Set only keys that appear there, and match the key to the object rather than the chart's top level — a chart rendering several Deployments usually nests each one's block (`server.resources`, `controller.resources`), and the one to set is the component whose Deployment the finding names. Everything §3 says about the numbers still binds: 3.1's floors and its `Guaranteed`-QoS refusal, 3.11's rule that the request and any limit change are figures copied from the excerpt rather than computed, 3.12's `10m`/`32Mi`, and 3.13's rule that a stand-down touches `replicas` and nothing else. Where the chart publishes no key for the change — no `resources` block, no `replicaCount` — the finding is `kind: manual`, and the note says which key was looked for and was not there. **When you cannot find a declaration for the object, and it carries no `release_declaration` either, the finding is `kind: manual`**, with the intended change in `recommendation.action` and no file written; do not invent a path for it. This audit has no create case at all, and no delete case either — every permitted kind targets an object that already exists, and none of them removes a file. 3.13 is where the second half of that bites: the action it argues for is deleting a declaration, and it proposes a stand-down instead because a `manifest` remediation is staged by _reading_ the path it names, so a finding that removed the file would degrade to `manual` here rather than opening the pull request it promised. Should one ever be added, **the fleet-audit skill's "A `path` is discovered, never invented" rule (`SKILL.md`, under "The findings document") governs it** and nothing here overrides that: an object the repo does not yet declare is a `manifest` too, written beside a sibling that proves the directory is already reconciled onto that cluster and namespace.

Write every manifest into the `workspace` clone **before** calling `finish` — the helper stages the path and rejects the whole document if it is absolute, contains `..`, carries a glob metacharacter (`* ? [ ]`), or starts with `:`. A path that is merely not on disk is treated differently: it costs you the fix, not the run. That finding degrades to `kind: manual` with its evidence and recommendation intact, the ledger records that the audit named the file and never wrote it, and everything else publishes. A right-size that arrives as prose instead of a diff is a right-size nobody applies, so write the file. Head each file with a comment naming the target object and the apply command. Everything else is `kind: gcloud` (a command printed for a human) or `kind: manual`, and those **must omit `remediation.path` entirely** — the helper rejects a path on a non-manifest remediation. **No manifest may delete a PV, PVC, namespace, disk, snapshot, or address.**

**A manifest is the only kind that can become a pull request.** A manifest finding graded `critical` opens a narrow remediation PR automatically, branched from `main` and linked to the ledger with `Part of #<issue>` — capped at five per run, with the withheld ones named in the ledger as awaiting `/remediate`, and only where the branch carries no **live** pull request (one the harness closed itself is labelled `audit:stale-closed` and may be promoted again; one a human closed and one that merged stay closed). Almost nothing here reaches `critical`, and of what does only 3.11's OOMKill arm is a manifest, so that arm is where this audit meets the sweep. **§3.13's stand-downs used to be where that happened, and no longer are.** An idle-workload finding is `major` on either of 3.13's grounds — a `LoadBalancer` Service selects it, or a `Guaranteed` controller's request clears 3.1's floor — and the first is the one that matters here: a Service selecting it is exactly what makes the stand-down capable of taking a caller down, so the collector marks those `needs_triage: service-fronted` and the sweep passes over them however they are graded. On 2026-09-07 it did not: three of them opened and merged unattended within a minute of the run finishing, standing down three Deployments, two of which sat behind forwarding rules metering hundreds of thousands of packets a week. §3.13 now reads those rules and puts what they carried in the excerpt, and that is why the gate stays shut rather than a reason to open it: a forwarding rule is not a caller, and a week under the noise floor is not evidence nothing needs the workload — it is the exact population that merged those three. The finding still publishes, its remediation is still `kind: manifest`, and `/remediate <id>` still opens the pull request — what changed is that a person decides, now with a traffic figure in front of them. Every other manifest finding waits for a repo writer to comment `/remediate <finding-id>` or `/remediate all` on the ledger. Findings whose `remediation.path` values overlap are promoted together in one PR, so keep one file per finding unless two findings genuinely patch the same object. A comment naming ids arrives as `pending_remediation_requests` on the next run's `start`, so you know which manifests to write while inspecting; `all` does not, because it names no particular file — it is expanded at `finish` against that run's manifest findings. `gcloud` and `manual` findings are never promotable: this audit is mostly `gcloud`, so most of what it produces stays prose in the ledger issue and never becomes a PR. That is correct — releasing an IP or deleting a disk is a command a human runs after checking, not a file to merge.

A `kind: gcloud` `note` is rendered into the ledger issue **inside a bash fence**, so write it as a shell-pasteable block: the ordered commands on their own lines, and every caution — verify-before-deleting, snapshot-first, the irreversibility warnings this SOP requires — as a `#` comment line above the command it guards. Prose in a `gcloud` note renders as broken shell. A `kind: manual` note is rendered as prose and should be written as prose.

### 5. Emit findings.json

Write the file at the `findings_path` returned by `start`, matching the harness schema exactly.

- `evidence.command` is **mandatory and must be the literal command you ran** — the same string, with the real cluster, project, and object names substituted, so a reviewer can paste it and see what you saw. **A finding you cannot reproduce is dropped, not softened.** Never reconstruct a plausible command after the fact.
- `evidence.excerpt` is trimmed real output from the Step 2 dumps — never a paraphrase, never invented JSON. The helper clips at 40 lines / 2,000 chars, so trim to the lines that prove the finding yourself rather than pasting a whole dump and letting it be cut mid-object.
- **Credential hygiene:** never paste a Secret's `data:` block, a token, a kubeconfig, or a private key into `evidence.excerpt`. If the output that proves the finding carries one, re-run the read with a field selector or an `-o jsonpath` that omits it and quote that instead. The harness redacts high-confidence credential shapes as a backstop, not as the primary control — the control is not reading the value in the first place.
- Every dollar figure, savings estimate, and percentage-saved claim is forbidden. Resource units only.
- **Noise control:** if one check produces more than 20 findings of the same kind in one cluster or project, collapse them into a single roll-up finding listing the objects in `evidence.excerpt`, and raise its severity one level. Give the roll-up the scope it covers as its `object` — `Cluster/<name>` for a whole cluster, `Namespace/<name>` for one namespace — so its identity is that scope rather than any one workload in it; the individual findings it replaces are not also emitted, so nothing collides. This bounds the fleet-wide noise and it keeps the ledger readable: the harness caps the rendered issue body at 60,000 characters and says so in the body when it has to drop findings, but the counts in the title stay the true totals either way.
- Re-verify the scope before publishing: `scope.clusters` is non-empty; every entry's `checks_run` names the §3 checks that actually ran there, and nothing more, each with the command that ran it; every cluster you could not read is in `scope.skipped` with a specific reason — "unavailable" is not a reason, the stderr excerpt is; every check that did not run on a cluster you _could_ read is named in that cluster's `limitations`; no cluster appears in both lists; no finding names a cluster from `scope.skipped`. The validator rejects the document on any of those.
- Re-read your `checks_run` lists one last time. Padding one to its full roster — ten checks on a cluster, four on a `project/<id>` entry — because the SOP lists them is the one entry in this document that converts a partial audit back into a false all-clear: the harness has no way to see the check you did not run, so it believes you. The `command` on each entry is what makes that padding falsifiable rather than free — it is published verbatim, so an invented command is a false statement in a public issue. `checks_not_applicable` is the same lie wearing a different field: it removes checks from the denominator, so a slug parked there because you ran out of turns is a coverage gap the ledger will never show. It is published too — every exclusion and its reason render under _Not applicable_, where a reviewer who knows the cluster can call it. An honest eight-of-ten costs you nothing but an open ledger, and an honest eight-of-eight on a cluster where the other two cannot apply closes it.

**Every finding carries a `recommendation`.** Three sub-fields, all required, all non-empty, on **every** finding — not only the five checks that can produce a manifest. Write it while the evidence is in front of you; deferring it until someone asks for the fix means writing it from memory.

- `action` — what to do, imperative, one or two sentences.
- `rationale` — why this fix and not the obvious alternative. Name the alternative you considered and say why you rejected it.
- `risk` — what breaks on apply, and the read-only check to run first. **On this audit the `risk` field is what stops a "waste" finding from becoming an outage.** Every usage claim here rests on a one-week observation window; the risk line is where you say what that window cannot see.

Worked example, for a 3.7 finding on an idle batch pool — a `gcloud` remediation that will never become a pull request, and still carries the full recommendation:

```json
"recommendation": {
  "action": "Scale the batch node pool to zero, or delete it if the batch workload has moved.",
  "rationale": "Scaling to zero is reversible and keeps the pool's config; deleting is cheaper to reason about but discards the taint/label set the batch jobs depend on, which nobody has confirmed is obsolete.",
  "risk": "If a CronJob targets this pool with a nodeSelector it will go Pending on the next fire. Check for selectors referencing the pool before scaling."
}
```

### 6. Close the audit run

Run `python3 ./skills/fleet-audit/scripts/audit_report.py finish --audit fleet-wide-cost-analysis --findings-file <findings_path> --manifest-file /opt/data/scratch/manifest_fleet-wide-cost-analysis.json [--repo "<owner>/<repo>"]`. Always pass `--manifest-file`: nothing else checks the document against what the collector actually ran. On a run where §2's collector never produced one — every check on every target came from the manual fallback — pass `--no-collector-manifest '<why>'` instead; it publishes but reports the reason as a coverage gap, so the run is partial. Given a manifest, `finish` rejects a `checks_run` entry on a `"collected"` target that names a check the manifest never recorded at `rc == 0`, and rejects a `"collected"` target the document leaves out of `scope.clusters` altogether. Exit 0 means published; exit 2 means the validator rejected the document and nothing was published — fix the document and re-run, never delete the finding that tripped it; exit 1 is fatal. The helper prints one JSON line, carrying `status`, `issue_url`, `new`, `resolved`, `prs_opened`, `prs_closed`, `partial`, `coverage_gaps`, and `silent_ok`.

`partial` and `coverage_gaps` describe how much of the fleet the run can actually speak for: `partial` is `true` if any cluster is in `scope.skipped` or any audited cluster carries a `limitations` note, and `coverage_gaps` states each gap in a sentence. This matters most on a cost audit, where the conclusion is usually drawn from an absence — an idle disk that stops appearing has not necessarily been released, it may sit in a project nobody could list this week. So over a partial run the helper reports `resolved: 0` and posts no resolved-delta, retires no remediation PR as stale, and keeps the ledger open even with an empty findings array: `status` is still `CLEAN`, but the issue stays and gains a comment naming the gaps. A check declared in `checks_not_applicable` is not a gap and does not raise the flag; it left the denominator. Coverage is the only thing the flag tracks, so `partial` is `true` if and only if `coverage_gaps` is non-empty: the §5 body budget dropping findings from the description does not set it, because the audit still saw them and says as much in the body. A run that audited no cluster is partial too unless every `project/<id>` target carries `clusters_listed: 0`: a project target without it may hold clusters nobody read.

**`silent_ok` decides silence. Do not re-derive it.** `finish` returns `silent_ok: true` only when this run moved nothing an operator needs to hear about: nothing new, nothing resolved, no coverage gap, no remediation PR opened or closed. Read the flag rather than reassembling that from `status`, `new`, `resolved`, and `partial` yourself — that arithmetic is where a run talks itself into silence it has not earned. Two rules, and they are the whole rule:

- On a **scheduled** run, `silent_ok: true` → the final response is **exactly** `[SILENT]`. Otherwise report, and every report carries `issue_url` in full.
- **An on-demand run is never silent.** If a person dispatched this job — from a kanban card or straight from chat — someone is waiting on the answer, and `[SILENT]` throws it away. Report the outcome and the ledger URL whatever `silent_ok` says.

What to report in each case:

- `silent_ok: true` → `[SILENT]` on a scheduled run, nothing else and no preamble. On `CLEAN` the ledger issue closed as completed and every open remediation PR for this stream closed with it; on `UPDATED` nothing moved since last week. Dispatched on demand, say which in one line and give the issue URL.
- `CLEAN` with `resolved: > 0` → the waste this audit was tracking is gone. Report the issue URL and the count that closed with it. Reclaimed capacity is the whole point of the stream and the one result worth interrupting someone for.
- `CLEAN` with `partial: true` → nothing was found, but nothing was closed either. One line giving the clean result, the `coverage_gaps`, and the issue URL.
- `HELD` → zero findings, but the ledger stayed open because the run did not account for findings it was carrying (`start` listed them under `carried`; `unaccounted` names the ones held): one line reporting the clean result, the held ids and the issue URL, then stop. On the next run, report each one, or list it under `resolved_because` if you re-ran its check and saw it gone.
- `OPENED`, or `UPDATED` with a non-zero `new` or `resolved` → one line: counts of new and resolved findings by severity, the ledger issue URL, and anything in `prs_opened` / `prs_closed`. The helper wrote the issue body; do not restate it, do not edit it.

## Red Lines

- **Read-only, always.** Never delete, cordon, drain, patch, scale, or apply anything. Every command in this SOP is a read verb. This is the most dangerous of the six audits to get wrong: **a false positive here can lead a human to delete a disk holding real data.**
- Never emit a manifest that deletes a PV, PVC, namespace, disk, snapshot, or address. Deletion remediations are `kind: manual` or `kind: gcloud` only, always with an explicit verify-before-deleting caution and a snapshot-first step wherever data is involved. A manifest is now one merge away from `main` — a `critical` one opens its own pull request without a human asking — so this line matters more than it did, not less.
- Never state a dollar amount, a monthly saving, a percentage saving, or a price. You have no pricing data, and a fabricated figure is worse than no figure.
- Never emit a finding without a literal, reproducible `evidence.command`. Drop it instead.
- Never infer "unused" from a single observation. Every usage-based claim rests on the peak across the whole window, never on a spot reading.
- Never flag an object in a cluster recorded in `scope.skipped` — the validator rejects the whole document for it — and never flag an object for a check you declared as not run in that cluster's `limitations`. An incomplete read is not evidence of absence.
- **Never print raw credentials.** A Secret's `data:` block, a ServiceAccount token, a kubeconfig, or a private key never appears in `evidence.excerpt` — record the object reference, or re-run the read with a field selector or an `-o jsonpath` that omits the value. The harness's redaction is a backstop, not permission.
- **Never write an unstable `object`.** The id is derived from `check`, `cluster`, `namespace`, and `object`, so an `object` that moves between runs destabilises it: a pod name carrying its ReplicaSet suffix, a generated resource name, or a roll-up named after one of the workloads it covers rather than the scope it covers (§5). Name the durable object the check judged. A finding whose identity moves is reported as fixed one week and re-reported as new the next, on a ledger people trust to tell them what is still wasted.
- Never query BigQuery, the Billing export, the Recommender API, or Prometheus; never delegate any part of this audit to a Cluster Agent or a kanban card. Collection is done inline, here.
- Never write outside the GitOps declaration of the object a remediation targets and the helper's `findings_path`. Never hand-write or edit the ledger issue body or a remediation PR body, and never call `gh issue create` or `gh pr create` — this stream has exactly one ledger issue and `finish` owns it.
