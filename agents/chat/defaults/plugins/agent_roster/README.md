# Agent Roster Injection (`agent_roster`)

Puts the list of specialist agents the Chat Agent can delegate to into its context at the start of every turn, so choosing an `assignee` costs no tool call.

## Why it exists

The Chat Agent cannot delegate without naming an `assignee`, and the set of specialists is genuinely dynamic — per-cluster agents are scaffolded and torn down as the fleet changes — so the persona told it to call `list_agents` before every routing decision.

The tool is cheap; calling it is not. `list_agents` runs in about 0.1s, but a tool call is an LLM roundtrip: on the live deployment, acknowledging a request took ~17s across three LLM calls, one of which existed solely to fetch the roster. That is roughly 6s per request spent re-reading a directory listing that had not changed.

Injecting the roster removes that call from the common path. `list_agents` stays as the refresh path — for an agent created moments ago, or a name the model has reason to doubt — and, on a large fleet, as the lookup: above a threshold the block counts the cluster agents instead of naming them, and the tool's `filter` returns the one name a routing decision needs.

## How it works

A `pre_llm_call` hook, which Hermes fires once per user turn before the first LLM call. It returns `{"context": ...}`, which is appended to the user message, so the roster is present before the model decides anything.

The roster itself is produced by `agent_roster.py`, which also backs the `list_agents` MCP tool in `router_server.py`. Both read the same module deliberately: **a refresh path that renders the fleet differently from the block it refreshes is worse than no refresh path at all.** Discovery walks `$HERMES_HOME/profiles`, skips `default` (the front door is not a delegation target) and dot-prefixed directories (such as `.deleted`), and describes each profile from its `CAPABILITIES.md`, falling back to the first prose line of its `SOUL.md`.

Agents sharing one description are grouped under it, named one per line. A group larger than `KUBEAGENTS_ROSTER_SUMMARY_THRESHOLD` (default 20; a value that is not a whole number of zero or more means the default) is counted instead: its total, the count per project and per location (the twenty largest named, the rest counted), the shared role, and a sentence pointing at the lookup. Profiles record project and location only, so those are the two axes. The block is then constant in the fleet's size: at 2,500 Cluster Agents it is under 2,000 tokens, where naming each cost tens of thousands. `list_agents(filter=...)` matches a case-insensitive substring against the assignee id, cluster, project and location and renders the matches the way the block renders a named group, never counted, up to 50; with no match it says so and points at `platform`, which owns cluster-agent lifecycle. Without `filter` the tool renders what the block renders. The front door's persona (`agents/chat/SOUL.md` §1 and §3) and this plugin's footer, added only when the block carries the counted form, tell the model to take a named cluster's `assignee` from the lookup; fleet inventory still goes to `platform`. The operator passes the variable through its `spec.deployment.env` allowlist, and the router's `env:` block hands it to the MCP child so the tool counts where the block counts.

After the specialist list, `render()` appends two sections. **Host Cluster Identity** comes from the pod's `GKE_CLUSTER_NAME`, `GKE_PROJECT_ID` and `GKE_LOCATION`; it is left out when the cluster name is unset, and a value still holding a literal `${...}` placeholder counts as unset. Its line names an `assignee` only when a discovered profile's `cluster_identity` matches all three values, or a profile with no stamped `cluster_identity` carries the name the scaffold derives from them; when `GKE_PROJECT_ID` is a project number (`spec.harness.projectId` admits one while the reconcile scaffolds on the project ID), the number is never printed as the project and `fleet_scope.json`'s `management` row supplies the resolved project ID before matching all three values (omitting both `project` and `assignee` until the snapshot records it). **GCP Projects in Scope** comes from `fleet_scope_targets.declared_scope_targets()`, the same reader the platform agent's `fleet_scope` tool uses. Declared projects are tagged `(unresolved)` before discovery resolves them, rows discovery could not read carry their outcome (`team-b (denied)`), lists longer than 20 projects name the first 20 and count the remainder (with omitted non-`ok` outcome counts), and the line maps the reader's partial markers onto plain front-door reasons when discovery has not completed or folders and organisations remain unresolved. The router's `env:` block in `agents/chat/config.yaml` passes `GKE_*`, `GCP_PROJECT_ID` and `KUBEAGENTS_SCOPE_FILE`, so `list_agents` renders the same two sections. The plugin adds the footer's "route this cluster to the host" sentence only when `read_host_identity` reports a host cluster.

That module is a loose script rather than an importable package — the entrypoint copies `/opt/defaults/scripts` into `$HERMES_HOME/scripts`, and the MCP server is launched by absolute path — so the plugin loads it by path, trying `$HERMES_HOME/scripts` first and `/opt/defaults/scripts` second. The module object is cached for the process keyed by `(path, st_mtime_ns)` so an in-place script update reloads automatically. The reload covers `agent_roster.py` only: `fleet_scope_targets` stays in `sys.modules`, and the router MCP child imports the roster once, so after an in-place script update `list_agents` keeps the old code until the router restarts.

**The rendered roster is cached on the tree's mtimes, never on time.** `render()` keeps the last roster per process, keyed on the profiles directory's `st_mtime_ns`, the scope snapshot's (`fleet_scope.json`, rewritten in place by every reconcile run), the scope render's when `KUBEAGENTS_SCOPE_FILE` names one, and the threshold; a hit costs those stats and no reads, which at 2,500 profiles replaces 7,500 file reads a turn. A scaffold, a removal, a rename and an archive to `.deleted` all change the directory's mtime, so a cluster agent created a minute ago still appears on the next message. Two cases are deliberately not cached: a tree changed within the last two seconds, because filesystem timestamps are coarse and a second change in the same tick would be invisible; and a `cluster-` profile with no `cluster_identity` yet, because the scaffold creates the directory first and stamps `config.yaml` in place afterwards, which moves no directory mtime. What the cache cannot see is a hand edit inside a profile that creates or removes nothing; it shows on the next add, remove or restart.

## Guardrails for future changes

- **Fail soft, always.** This hook runs ahead of every user turn on the front door. Every failure path returns `None`, which costs the turn its injected roster and nothing else. A raise here is a Chat Agent that cannot answer at all — strictly worse than one that has to look the roster up. That includes the `is_file()` probe for the module: the scripts directory is on the shared PVC and pathlib swallows only `ENOENT`/`ENOTDIR`/`EBADF`/`ELOOP`, so `EACCES` raises for real.
- **"Unreadable" is not "empty".** `agent_roster.render()` returns `None` when discovery itself failed and the `EMPTY_ROSTER` sentence only when the fleet is genuinely empty. Injecting "no specialist agents are currently available" on an I/O fault would state a fault as a fact and stop the front door delegating at all; injecting nothing leaves it able to reach for `list_agents`, which is where it was before this plugin existed. The tool has to answer with a string, so it renders `UNKNOWN_ROSTER` on that path instead.
- **Cache on the directory mtime, never on time.** A TTL cache would go stale in exactly the window that matters: right after the Platform Agent scaffolds a new cluster agent, which is when the user asks about that cluster. The scaffold changes the profiles directory's mtime, so that is the key; anything the roster reads that can change without moving it (the in-place identity stamp, the scope snapshot) is either keyed on its own mtime or kept out of the cache until it settles.
- **Count, never truncate.** Past the threshold a group is counted by project and location and the names come back through `list_agents(filter=...)`; a block that named the first N and dropped the rest would send a named cluster past N to `platform` with no way to find its agent.
- **Do not let the block and the tool drift.** If you change what the roster says, change it in `agents/chat/scripts/agent_roster.py` and let both consumers pick it up. Formatting duplicated into this plugin is a bug waiting for the fleet to grow.
- **`agents/chat/config.yaml` is the one writer of the deployed list.** The image seeds the `default` profile's `plugins.enabled` from it onto a fresh volume, and the entrypoint's back-fill appends the names it has and a live list lacks on an existing one; a removal there takes effect on a fresh volume only. The operator writes no copy: its overlay adds `AgentPlugin` names (and `frontDoorPlugins` under the front-door flag). Note the roster: `agent_roster` deliberately does **not** go in `DefaultBuiltInPlugins`, because that slice doubles as the roster of names an `AgentPlugin` may not shadow (`IsBuiltInPlugin`), and it names plugins baked into the Hermes image — this one ships in `agents/chat/defaults/plugins` and rides on the `default` profile only.
