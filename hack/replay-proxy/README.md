# Inference replay proxy

The inference replay proxy is an eval fixture. It sits in front of LiteLLM on an eval install and records, for every model request, what an inference replay cache would have keyed on. In its default shadow mode it never serves a saved answer: every request goes to LiteLLM and every response comes back unchanged. Record and replay modes (below) are for the replay lane. It serves stages 1 and 2 of the rollout in [`examples/inference-replay/eval-design.md`](../../examples/inference-replay/eval-design.md), which owns the normalization rules, the cache key and the reasons behind them: the proxy, the fingerprint log, the scrubbed request store and the hit-rate script. The collision report is not built yet. An install never uses it; eval runs deploy it in shadow mode by default, a trusted nightly in record mode and the replay lane in replay mode (see [In CI](#in-ci)).

## What it does

For each `/v1/chat/completions` request, after the response has gone back to the client, a background thread does the following. The handler only queues the request; if the queue is full it drops the analysis and logs an `analysis_dropped` line instead of waiting. In replay mode the handler first normalizes the request and looks it up (Modes, below), and hands that normalization to the background thread.

- `normalizer.py` normalizes the request and computes its fingerprint: the normalized request without `stream`, `user` and `metadata`, a checksum of the LiteLLM config that treats the Gemini Developer API and Vertex AI routes as one (what it keeps and drops: [What goes into the cache key](../../examples/inference-replay/eval-design.md#what-goes-into-the-cache-key)), the LiteLLM image, and `NORMALIZER_VERSION` (a hash of `normalizer.py`).
- `replay_proxy.py` writes one JSON line to stdout (`"event": "replay_shadow_request"`): the fingerprint, per-message hashes and roles, prompt, cached and completion tokens, model latency, a hash of the answer (when the response carried no usage, `prompt_tokens` is estimated from the request size and `tokens_estimated` is true), LiteLLM's `x-litellm-model-group` and `x-litellm-attempted-fallbacks` headers, and why replay would not have saved the answer (`unstorable`: for example an upstream that broke off mid-answer, a response the proxy could not parse, or an answer whose scrubbing would mask a credential; reformatting or masking an email or IP doesn't count). A shadow or record line holds no request or answer text (a replay miss adds the short scrubbed snippets described under Modes), but its hashes are of the normalized request and answer and can be guessed against, so the log goes to the same private bucket as the stored text, never to Prow artifacts.
- `diagnosis.py` adds `diag_message_hashes` and `diag_settings_hash`, used only to find the closest earlier request for a miss: each message is normalized with the time the proxy first saw it, and IPs stay literal only if a CIDR appeared in it or an earlier message, so a later CIDR or a later request time doesn't make an earlier message look different. The settings get their own hash, normalized without any message's context. The proxy keeps one first-seen timestamp per distinct message for this, up to a million, oldest dropped first; replay mode also uses them to check a slot's recorded answers (Modes). `schema.py` names the line's fields for both the proxy and the analysis.
- `request_store.py` scrubs the request with the install's `AuditRedactor` and then the `worker_transcript.py` rules, the order `bench/kube_agents_bench/worker_trajectory.py` uses, and writes it under `REPLAY_STORE_DIR`: each distinct message once under `blobs/<sha256>.json`, and each request as a list of blob hashes under `requests/<request_id>.json`. If either scrubber cannot load or scrubbing a request fails, no text from it is written. If a write fails partway, some of its message blobs may be on disk but no request manifest is. Either way its line is still logged.

`/metrics` is answered by the proxy with its own counters and is never forwarded, because the proxy carries the `app: litellm` label (see "Where the proxy runs" in the design). `/replay/healthz` is its health check. Every other path goes to LiteLLM unchanged. The request body is forwarded byte for byte; the hop-by-hop headers and `Accept-Encoding` are dropped, so the usage block can be read. A request body over 64 MiB gets a 413 and is not forwarded. The proxy stops observing a response, streamed or not, after 8 MiB or at anything it can't parse; the bytes keep flowing to the client unchanged. The line then has `observe_failed: true` and the `unstorable` reason `observe_too_large` or `observe_failed`. When the response was cut short, `upstream_incomplete` or `client_disconnected` is the reason instead.

`analyze_shadow.py` reads the lines from a set of jobs and reports the token-weighted would-hit rate. Low counts nightly sightings. High adds earlier finished builds of the same pull request and, given `--merged` (pull request to merge time), another pull request's last build before it merged. Until run verdicts are joined, high is an upper bound: it counts those builds, and nightly answers once written, whatever their runs' verdicts. The report counts presubmit lines without a pull request number, which shows an unset `REPLAY_JOB_PR`. It also reports the share of hits first seen in another project, the tokens and model time hits would save, and the misses ranked by tokens lost with the closest earlier request by longest matching message prefix. Many requests share a prefix (every worker conversation opens the same way); given `--by-text` (each build's own copied-out `REPLAY_STORE_DIR`; see [In CI](#in-ci)) or `--store` (one store, with `--kind`), the closest is the one whose next message is most alike by the words they share, relative to both messages' length (among the 64 most recent distinct next messages with stored text), and otherwise the earliest. A candidate sharing no word with the miss's next message is no match. With either, each miss says which (`closest_by`, with `closest_score` for a text pick and `unranked_reason` when it fell back) and the report counts the misses ranked by text, so stores missing for some jobs show up as fallbacks rather than as a ranked report; a `--store` without `requests/` and `blobs/` is refused. Its `simulated` row is high plus the requests that match with earlier assistant messages ignored, since replay would have served those; the module docstring says what that assumes. For multi-agent runs every estimate here is a floor: one agent's answers feed another's input and pick its actions, which shadow mode can't hold fixed, so the real hit rate comes from the design's replay lane (Rollout step 2), which runs real replay where it gates nothing.

Check the report's health counts after the first day: lines by job kind; untagged lines (an unset or unknown `REPLAY_JOB_KIND`, dropped from every estimate); kind-mismatch lines (tagged with a kind other than the folder they were filed under, dropped too); off-layout files (log files not at the collector's layout, skipped whole); error lines; lines without a fingerprint; `analysis_dropped`; unstorable lines and their share by reason; presubmit lines without a pull request number; lines without message hashes; the upstream-incomplete, observe-failed and observe-too-large counts; and the share of prompt tokens that are estimated. A high number in any of them means the setup is broken, not that replay would miss.

## Modes

`REPLAY_MODE` picks one of three:

- `shadow` (the default): everything above, nothing saved, nothing served.
- `record`: shadow, plus each storable answer (empty `unstorable`) saved under its fingerprint in `REPLAY_CACHE_DIR` (`replay_cache.py`): the answer with the values its request bound swapped for placeholders (each identifier found by the pattern that bound it, and each timestamp the request holds verbatim), its finish reason and usage, and the request's hashes. The rules for what isn't saved are under "Normalization" in the design; each refusal is named in `unstorable` (`schema.py` lists them). One file per key, written atomically; the first write wins. If writing the cache fails, the line still goes out, with `recorded: false` and `record_error`. In record mode `REPLAY_CACHE_DIR` counts against `REPLAY_DATA_MAX_BYTES` with the store and the segments (the collector empties it as it copies it); once the budget is spent nothing more is saved, the line says `record_error: budget_spent`, `replay_shadow_record_budget_spent_total` counts it, and requests are still forwarded. Replay mode's cache is not counted: it is a seeded copy that must stay whole. Each request message is also saved once, normalized and then scrubbed the way the request store scrubs it (a tool result whose call printed a secret's value is withheld whole), so a later miss can show how it differed; a miss's snippets are scrubbed the same way. Record mode never serves.
- `replay`: on a fingerprint hit in `REPLAY_CACHE_DIR`, the saved answer is restored with the current request's values and served, streamed or not, without calling the model; an answer naming a placeholder the request doesn't bind is a miss. On a fingerprint miss, replay tries a second key, where the model's earlier answers are slots any answer a recording stored for that point can fill (`normalizer.answer_slots`, `normalizer.READ_ONLY_TOOLS`); "Different words for the same answer" in the design says what the key keeps and when it serves. A miss goes to the model live and is not recorded. Replay only reads the cache: every lookup reads it as it is, so answers recorded after the proxy started are served too; only the index the miss report searches is built at start.

Replay mode refuses to start unless `REPLAY_ALLOW_SERVE=yes` is also set. Only the chart sets it, and only with both `litellm.replayShadow.mode: replay` and `allowServe: true`, which `hack/ci-env.sh` passes on the replay lane alone, so a saved answer can't be served by accident. A replay proxy rebuilds the index its miss report searches whenever `.seeded` in `REPLAY_CACHE_DIR` changes, which the lane writes after seeding the cache into a running pod.

Every line carries `mode` and `served`. A served line has `served_from`, the job that recorded the answer, and `served_via`: `exact` or `answer_slots`; its answer is a saved one, so its `unstorable` is empty and its LiteLLM headers are null, and `analyze_shadow.py` skips it (counted as `served`) rather than read it as a model answer. A replay miss has a `miss` block: the closest saved request by longest matching `diag_message_hashes` prefix (under `diag_settings_hash`; when several share that prefix, as every worker conversation's opening does, the one whose next message is most alike by the words they share, relative to both lengths), how many messages matched, the index and role of the first differing message, short normalized and scrubbed snippets of that message on both sides, and a signature (narrower windows around the difference, with digit runs and hex runs of six or more collapsed) for grouping. When the request did match a saved answer on either key but a guard refused to serve it, the block also has `refused`: the key (`via`) and the guard (`answer_not_recorded`, `value_only_in_answers`, `unbound_placeholder` or `unreadable_entry`), so the miss doesn't read as an ordinary fork. `analyze_replay.py` groups replay lines into conversations and reports, per conversation and overall, the requests and prompt tokens served before the first miss and the share served through answer slots, the first-miss causes by role and signature ranked by tokens lost, and, with `--verdicts`, whether each conversation's run verdict matched the recording run's. Replay lines whose analysis was dropped or failed carry `mode` and `served` but no hashes, so they join no conversation; the report counts them, served and not, because a conversation that lost a request not served shows its first miss late.

## Configuration

| Environment variable              | Default                               | Meaning                                                                            |
| --------------------------------- | ------------------------------------- | ---------------------------------------------------------------------------------- |
| `REPLAY_LISTEN_PORT`              | `8080`                                | Port the proxy listens on                                                          |
| `REPLAY_UPSTREAM_HOST`            | `inference-gateway-upstream`          | LiteLLM's host                                                                     |
| `REPLAY_UPSTREAM_PORT`            | `80`                                  | LiteLLM's port                                                                     |
| `REPLAY_UPSTREAM_TIMEOUT_SECONDS` | `1800`                                | Socket timeout for each read from LiteLLM                                          |
| `REPLAY_MODEL_BEHAVIOUR_CHECKSUM` | empty                                 | The chart's checksum of the LiteLLM config, Gemini API and Vertex AI routes as one |
| `REPLAY_LITELLM_IMAGE`            | empty                                 | The LiteLLM container image                                                        |
| `REPLAY_STORE_DIR`                | `/data/shadow`                        | Where scrubbed request text is written                                             |
| `REPLAY_REDACTOR_PATH`            | `/app/scrubbers/redactor.py`          | The install's `AuditRedactor`                                                      |
| `REPLAY_TRANSCRIPT_RULES_PATH`    | `/app/scrubbers/worker_transcript.py` | The shared transcript scrubbing rules                                              |
| `REPLAY_JOB_KIND`                 | empty                                 | The job kind ([In CI](#in-ci)), stamped on every line                              |
| `REPLAY_JOB_PR`                   | empty                                 | The pull request number, stamped on every line                                     |
| `REPLAY_JOB_PROJECT`              | empty                                 | The eval project, stamped on every line                                            |
| `REPLAY_JOB_BUILD`                | empty                                 | The Prow build ID, stamped on every line                                           |
| `REPLAY_LOG_DIR`                  | empty                                 | Also write every line to segment files here                                        |
| `REPLAY_LOG_SEGMENT_SECONDS`      | `60`                                  | Close a segment this long after its first line                                     |
| `REPLAY_DATA_MAX_BYTES`           | `0` (no limit)                        | Stop the store, the segments and record mode's cache at this many bytes            |
| `REPLAY_MODE`                     | `shadow`                              | `shadow`, `record` or `replay`                                                     |
| `REPLAY_CACHE_DIR`                | `/data/replay-cache`                  | Saved answers: written by record, read by replay                                   |
| `REPLAY_ALLOW_SERVE`              | empty                                 | Must be `yes` for replay mode to start                                             |

With `REPLAY_LOG_DIR` set, `spool.py` appends each line to `<pod>-<start ms>-<seq>.jsonl.open` and renames it to `.jsonl` once it is 8 MiB or `REPLAY_LOG_SEGMENT_SECONDS` old, so a closed segment never changes. At start it closes the segments a previous run of the container left open, cut to their last whole line. On TERM or INT the proxy stops serving, spends at most 10 seconds logging what is queued, and closes the open segment before it exits. stdout still gets every line. With `REPLAY_DATA_MAX_BYTES` set, the store and the segments stop writing once the files under `REPLAY_STORE_DIR` and `REPLAY_LOG_DIR` hold that many bytes, and start again when the collector has emptied files; the line still goes to stdout and the store reports `budget_spent`.

The image is built from the repository root (`docker build -f hack/replay-proxy/Dockerfile .`), because it copies the scrubbers from `agents/`.

## In CI

Every Prow presubmit and nightly eval puts the proxy in front of LiteLLM, unless the job sets `EVAL_REPLAY_SHADOW=false`. `hack/ci-deploy.sh` builds the image from this directory's `Dockerfile` (the `replay-shadow-proxy` step of `deploy/docker/cloudbuild-ci.yaml`) and installs it through the chart's `litellm.replayShadow` values: two proxy pods take the `inference-gateway` Service, and LiteLLM moves behind `inference-gateway-upstream`. Both carry `app: litellm`, the label the worker pods' egress policies admit, and differ by `kubeagents.x-k8s.io/inference-role` (`replay-shadow` or `litellm`). The comments on `litellm.replayShadow` in `charts/kube-agents/values.yaml` cover the rest. `hack/ci-eval-pr.sh`, which runs the presubmits and the nightlies, starts `collect_shadow.py` once it knows the host cluster and stops it from its EXIT trap. The collector copies closed segments and stored requests out of the proxy pods every 30 seconds, uploads them, then empties each uploaded file in the pod. At the end it makes one last pass, bounded to 60 seconds, that also takes the open segments. It prints counts and error classes to the `replay-shadow-collector.log` artifact and never fails the eval; the EXIT trap waits at most 75 seconds for its last pass, which runs while the trap's other captures do. The image has no `images.json` entry: each run builds it into its own project's registry and nothing publishes it, so there is nothing for `make mirror-images` to copy; `hack/check-image-inventory.sh` holds its Python base to the inventory.

It uploads to `kube-agents-replay-shadow` (`EVAL_REPLAY_SHADOW_BUCKET` points it elsewhere, no `gs://`); the runners' grants on that bucket are in [`docs/ci-pool-projects.md`](../../docs/ci-pool-projects.md). It needs the `JOB_TYPE`, `BUILD_ID` and, on a presubmit, `PULL_NUMBER` that Prow sets. A presubmit is filed as `presubmit`. A periodic or postsubmit is filed as `nightly` only when gcloud's active account, the one the collector uploads as, is `eval-baseline-recorder@kube-agents-prow.iam.gserviceaccount.com` and no impersonation or token override (`auth/impersonate_service_account`, `auth/access_token_file`, `auth/credential_file_override`) is set. Any other account, an override, or an identity that can't be read files it as `nightly-untrusted`. Every presubmit runs pull-request code as `prowjob-default-sa`, so that account must never write `nightly/`, and a periodic that runs as it (the GitLab next lane) gets a folder of its own. `hack/ci-deploy.sh` decides the kind and stamps it on the proxy; `hack/ci-eval-pr.sh` reads it back from the proxy Deployment, so the collector files under the kind the lines carry. The deploy log says when a night's data is filed as untrusted and why. A run it can't serve goes without it, with a one-line note: a batch run, a release-candidate run (`RC_COMMIT_SHA`, which builds no images), a run outside Prow, or a Prow job missing one of those tags. Setting `EVAL_REPLAY_SHADOW=true` makes each of those an error instead. Outside Prow, set `EVAL_REPLAY_SHADOW_JOB_KIND` to `presubmit`, `nightly` or `nightly-untrusted` (a `nightly` gets the same account check), plus `BUILD_ID` and, for a presubmit, `PULL_NUMBER`.

Each run writes under `gs://<bucket>/replay-shadow/<nightly|nightly-untrusted|presubmit>/<YYYY-MM-DD>/<BUILD_ID>/`, the date being the collector's start in UTC: `logs/*.jsonl` (the lines), `store/requests/*.json` and `store/blobs/*.json` (the scrubbed text), and `job-<ms>.json` (kind, project, build and pull request, written even when the run logged nothing). Every name is written once, so a merged copy of many runs loses nothing:

```bash
kinds="nightly nightly-untrusted presubmit"
days="2026-11-01 2026-11-02 2026-11-03 2026-11-04 2026-11-05 2026-11-06 2026-11-07"
mkdir -p week && : > week/objects.txt
for kind in ${kinds}; do
  for day in ${days}; do
    gcloud storage ls "gs://<bucket>/replay-shadow/${kind}/${day}/**" >> week/objects.txt 2>/dev/null || true
  done
done
if grep -E '^gs://[^/]+/(/|\.\.?(/|$)|.*(//|/\.\.?(/|$)))' week/objects.txt; then
  echo "Refusing to download: the object keys above have an empty, '.' or '..' segment." >&2
else
  for kind in ${kinds}; do
    mkdir -p "week/${kind}"
    for day in ${days}; do
      gcloud storage cp -r "gs://<bucket>/replay-shadow/${kind}/${day}" "week/${kind}" || true
    done
  done
  python3 hack/replay-proxy/analyze_shadow.py week/nightly week/nightly-untrusted week/presubmit --by-text
fi
```

The listing comes first because the folders' trust depends on the downloader: IAM matches a key's prefix as text, so `replay-shadow/presubmit/x/../../nightly/...` is a presubmit's object, and a tool that resolved the `..` would write it into `week/nightly`. gcloud 576 skips such keys, older versions and other tools may not, and `collect_shadow.py` refuses a bucket or build that could produce one.

Keep the bucket's layout: `analyze_shadow.py` takes a line's kind from the top-level `nightly`, `nightly-untrusted`, `presubmit` or `replay-lane` folder its file was copied from, not from the line's own `job.kind` tag, which comes from the proxy and so from the commit under test. IAM decides who may create objects under each `replay-shadow/<kind>/` prefix but not what the uploader names below it, so a log file counts only at `<kind>/<YYYY-MM-DD>/<build>/logs/<segment>.jsonl`, with that `<kind>` the only directory in its path named for a kind; a segment anywhere else under a folder you pass, even a whole folder of them, is skipped and counted as `off_layout_files`, with a note for a folder that holds nothing at the layout. Pass the kind folders, their parent, or segments inside them. A path that doesn't exist, or a named file that isn't a `.jsonl` segment, is always an error; a named segment off the layout, or a run whose segments are all off it, is an error unless `--kind` names the kind of every input, which also skips the layout check. A run that finds no segments at all reports nothing. A line whose tag names another kind than its file is dropped and counted as `kind_mismatch_lines`. `nightly-untrusted` lines are counted and are never a source or a miss's closest request, since pull-request code could have written them; `replay-lane` lines are counted the same way, since a replayed run says nothing about what a presubmit would hit. The lane's `report/` files are not segments, so the analysis never reads them as lines. `--by-text` ranks a miss's closest request by text read from each request's own build, `<kind>/<YYYY-MM-DD>/<build>/store/`, never from a store merged across runs: a presubmit can read the bucket, learn a nightly's request ids and upload text under them in its own prefix. A request's stored text is `store/requests/<request_id>.json` in its build, whose entries name files in that build's `store/blobs/`. `--store DIR` reads one store for every input and so works only with `--kind`, for logs from outside the bucket.

### Record and replay: the replay lane

The replay lane is Rollout step 2 in the [design](../../examples/inference-replay/eval-design.md): nightlies record, and a separate periodic replays their answers, gating nothing, to measure the real hit rate and check verdicts hold. `resolve_replay_shadow` in `hack/ci-env.sh` picks the mode, and the deploy and the eval both read it.

**Record, on a trusted nightly.** A run filed as `nightly` (above: a periodic or postsubmit uploading as the nightly runner), and for a postsubmit only one of `main`, runs the proxy in record mode. `EVAL_REPLAY_RECORD=false` keeps it in shadow; `EVAL_REPLAY_RECORD=true` turns the fallback to shadow into an error. A `nightly-untrusted` run, a postsubmit of another branch and every presubmit stays in shadow mode (a batch gets no proxy at all), and `EVAL_REPLAY_RECORD=true` on any of them is refused. A collector follows a recording proxy only when the run's kind, read back from the Deployment like the mode, is `nightly`. The deploy decides the mode once. The eval reads it back from the `inference-replay-shadow` Deployment and runs the collector in that mode. The chart sets `REPLAY_MODE` only for record and replay, so a Deployment read without it is a shadow install, and the collector never records against one. Only when the Deployment can't be read does the eval fall back to its own check. Record mode logs what shadow mode does, plus each line's answer (`answer_variant`) and the answer the request's last assistant message is (`prior_answer`). Its cache counts against `REPLAY_DATA_MAX_BYTES` with the logs and store: once that is spent the proxy stops saving answers (`record_error: budget_spent`) and keeps forwarding, so a cache nobody empties never fills the volume. The collector copies the saved answers out of the pods into a private directory on the job's machine as it goes and empties them in the pod, and keeps a copy of the lines and stored text. Every five minutes, beside collection, and once in its last pass, `publish_cache.py` uploads to `gs://kube-agents-replay-cache` (`EVAL_REPLAY_CACHE_BUCKET`) the answers whose runs passed, as graded so far (bench-gate's `case-<name>.json`). Each call reads only segments and results that changed since the last. `run_attribution.py` ties each saved answer to its runs. A request's cards are the one its worker was started on (`work kanban task t_...`) and the ones its `kanban_create` calls returned. A run's cards are the `task` its results.json trajectory entries carry. A request with no card of its own (a front door's opening) is published only when a request attributed to a passing run went on from exactly the answer that was saved (its `prior_answer`). Only positive evidence publishes, so a line lost before it reached a segment can only leave an answer unpublished. Anything undecided is not uploaded. Each publish writes `replay-cache/builds/<build>/publish-<ms>.json`: the runs, what was decided, and the objects it confirmed in the bucket, with each one's size and each slot's answer. The layout is in `publish_cache.py`'s docstring. Every object is written once, so the first night to record a key keeps it.

**Replay, on the replay lane.** `EVAL_REPLAY_LANE=true` on a periodic with no pull-request ref set (`PULL_NUMBER`, `PULL_BASE_REF`, `PULL_BASE_SHA`, `PULL_PULL_SHA`, `PULL_REFS`), so the proxy image and every script it runs are built from `main`'s checkout. Outside Prow, set `EVAL_REPLAY_SHADOW_JOB_KIND=replay-lane` too. Every refusal is an error. The deploy installs the proxy in replay mode with both chart switches. Before any case, `prepare_replay_lane_cache` runs `fetch_cache.py`, which takes the records younger than 30 hours and the objects they confirmed at this checkout's normalizer version. It chooses what fits in 512 MiB of disk, costed in 4 KiB blocks plus a block per file, from the records' sizes. It chooses in this order, newest record first: answers, then slots whose answer was chosen, then variants, then messages. It leaves the rest out and counts it. After the download it costs each file again at its real size, and removes a slot whose answer didn't arrive. It refuses the whole download only when a key or name is outside the layout, including one with an empty, `.` or `..` segment. `collect_shadow.py --seed-once` then seeds every proxy pod. When no answer arrives, a key is refused, or a pod didn't take the cache, the lane stops there, red. The collector seeds any pod that replaces one. The lane runs `hack/eval/replay-lane-cases.txt`. It never appends to the evidence store, never publishes the dashboard and arms no roster case. Its lines go to `replay-shadow/replay-lane/<YYYY-MM-DD>/<BUILD_ID>/`, a kind folder of its own: `analyze_shadow.py` counts lines filed there (`replay_lane_requests`) and never takes one as a source or estimates for it, and the recipe above leaves the folder out. The collector's last pass writes `lane_report.py`'s report to `report/` there: `replay.json` (`analyze_replay.py`'s report), `verdicts.json` (each case's lane repetitions beside the recording nightlies' outcomes, and each served conversation's verdict against its recording's) and `summary.txt`. The summary's lines also go to `replay-shadow-collector.log`. The bucket and its grants are in [`docs/ci-pool-projects.md`](../../docs/ci-pool-projects.md); the Prow job lives in `GoogleCloudPlatform/oss-test-infra`.

Limitations of record and replay:

- the verdict a replayed conversation is compared with is a pass by construction, since only answers from passing runs are published; the per-case comparison beside the nightly's own outcomes is what shows a case replay changed;
- a variant (`variants/`) is published from every recorded answer, failing runs' too: it only vouches that a model really wrote an earlier answer in a history, and what is served always comes from a published answer;
- a front door's opening is published only when a passing run's next request is in the logs; an opening whose answer was timestamped differently in that run's history, or whose continuation's line was lost, stays unpublished;
- the bucket's grants say who uploaded, not that nothing touched the night: the Prow runner's `roles/container.admin` in every pool project lets a presubmit leased into the same project exec into or patch the nightly's proxy, or the LiteLLM behind it, while it runs, and the nightly then publishes what they hold ([Who can write to the cache](../../examples/inference-replay/eval-design.md#who-can-write-to-the-cache)). There is no cheap check for it at publish time. An exec into the pod changes neither the Deployment's spec nor its pods' identity, the data volume sits on a node the same role reaches, and an answer from a repointed LiteLLM is recorded the ordinary way. It must be closed before replay gates anything;
- the merge copy job and a pull request's own saved answers (design, "How a pull request run finds an answer") are not built.

Limitations of shadow mode:

- each kind writes under its own top-level prefix, and IAM conditions on the object name confine each runner to its own (create and view, never delete): `prowjob-default-sa` to `presubmit/` and `nightly-untrusted/`, `eval-baseline-recorder` to `nightly/`, `nightly-untrusted/` and `replay-lane/`. Below its prefix an uploader names every path, so within `presubmit/` and `nightly-untrusted/` one run could still write under another's build, and any file off the collector's layout is only skipped and counted;
- `nightly/` guarantees who uploaded, not that the night is free of pull-request influence: no account pull-request code runs as can create objects there, but the Prow runner holds `roles/container.admin` in every pool project ([`docs/ci-pool-projects.md`](../../docs/ci-pool-projects.md)), so a presubmit leased into the same project as a running nightly could exec into or patch that night's `inference-replay-shadow` pods, and the nightly runner's collector would upload what they then hold under `nightly/`. The design names the same gap for the cache's nightly writer ([Who can write to the cache](../../examples/inference-replay/eval-design.md#who-can-write-to-the-cache));
- the image is built from the commit under test, not from `PULL_BASE_SHA` as the design's replay stage requires ("The proxy can't come from the pull request"). Shadow mode changes no verdict, but a pull request can change what its own run records. The replay lane serves answers and so refuses to run with any pull-request ref.

## Tests

The tests are standard-library `unittest` and need no cluster (`test_run_attribution.py`, `test_publish_cache.py`, `test_fetch_cache.py` and `test_lane_report.py` cover the lane's scripts against fake buckets): `make test-python` runs them, or run them from this directory with `python3 -m unittest`. `test_replay_proxy.py` runs the proxy against a fake LiteLLM on localhost; `test_collect_shadow.py` runs the collector against a fake cluster and bucket, and as a process with fake `kubectl` and `gcloud`.
