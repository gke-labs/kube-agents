# Inference replay proxy

The inference replay proxy is an eval fixture. It sits in front of LiteLLM on an eval install and records, for every model request, what an inference replay cache would have keyed on. In its default shadow mode it never serves a saved answer: every request goes to LiteLLM and every response comes back unchanged. Record and replay modes (below) are for the replay lane. It serves stages 1 and 2 of the rollout in [`examples/inference-replay/eval-design.md`](../../examples/inference-replay/eval-design.md), which owns the normalization rules, the cache key and the reasons behind them: the proxy, the fingerprint log, the scrubbed request store and the hit-rate script. The join with run verdicts and the collision report are not built yet. An install never uses it; eval runs deploy it in shadow mode by default (see [In CI](#in-ci)), and nothing deploys record or replay mode yet.

## What it does

For each `/v1/chat/completions` request, after the response has gone back to the client, a background thread does the following. The handler only queues the request; if the queue is full it drops the analysis and logs an `analysis_dropped` line instead of waiting. In replay mode the handler first normalizes the request and looks it up (Modes, below), and hands that normalization to the background thread.

- `normalizer.py` normalizes the request and computes its fingerprint: the normalized request without `stream`, `user` and `metadata`, a checksum of the LiteLLM config that treats the Gemini Developer API and Vertex AI routes as one (what it keeps and drops: [What goes into the cache key](../../examples/inference-replay/eval-design.md#what-goes-into-the-cache-key)), the LiteLLM image, and `NORMALIZER_VERSION` (a hash of `normalizer.py`).
- `replay_proxy.py` writes one JSON line to stdout (`"event": "replay_shadow_request"`): the fingerprint, per-message hashes and roles, prompt, cached and completion tokens, model latency, a hash of the answer (when the response carried no usage, `prompt_tokens` is estimated from the request size and `tokens_estimated` is true), LiteLLM's `x-litellm-model-group` and `x-litellm-attempted-fallbacks` headers, the reasoning and cache-write token counts (`reasoning_tokens` from `completion_tokens_details`, `cache_write_tokens` from `cache_creation_input_tokens`), the model behind the alias (`litellm_model_name`, from `x-litellm-model-name`), LiteLLM's retries inside the request (`litellm_attempted_retries`, from `x-litellm-attempted-retries`, an integer when it parses), LiteLLM's cost in USD (`litellm_cost_usd`: the usage block's `cost`, else `x-litellm-response-cost` on a non-streamed response only, since a stream sends that header as `0.0` before the cost is known; null otherwise, and on a served line, which never reached LiteLLM, as are the reasoning and cache-write counts, model name and retries), and why replay would not have saved the answer (`unstorable`: for example an upstream that broke off mid-answer, a response the proxy could not parse, or an answer whose scrubbing would mask a credential; reformatting or masking an email or IP doesn't count). A shadow or record line holds no request or answer text (a replay miss adds the short scrubbed snippets described under Modes), but its hashes are of the normalized request and answer and can be guessed against, so the log goes to the same private bucket as the stored text, never to Prow artifacts.
- `diagnosis.py` adds `diag_message_hashes` and `diag_settings_hash`, used only to find the closest earlier request for a miss: each message is normalized with the time the proxy first saw it, and IPs stay literal only if a CIDR appeared in it or an earlier message, so a later CIDR or a later request time doesn't make an earlier message look different. The settings get their own hash, normalized without any message's context. The proxy keeps one first-seen timestamp per distinct message for this, up to a million, oldest dropped first; replay mode also uses them to check a slot's recorded answers (Modes). `schema.py` names the line's fields for both the proxy and the analysis.
- `request_store.py` scrubs the request with the install's `AuditRedactor` and then the `worker_transcript.py` rules, the order `bench/kube_agents_bench/worker_trajectory.py` uses, and writes it under `REPLAY_STORE_DIR`: each distinct message once under `blobs/<sha256>.json`, and each request as a list of blob hashes under `requests/<request_id>.json`. If either scrubber cannot load or scrubbing a request fails, no text from it is written. If a write fails partway, some of its message blobs may be on disk but no request manifest is. Either way its line is still logged.

`/metrics` is answered by the proxy with its own counters and is never forwarded, because the proxy carries the `app: litellm` label (see "Where the proxy runs" in the design). `/replay/healthz` is its health check. Every other path goes to LiteLLM unchanged. The request body is forwarded byte for byte; the hop-by-hop headers and `Accept-Encoding` are dropped, so the usage block can be read. A request body over 64 MiB gets a 413 and is not forwarded. The proxy stops observing a response, streamed or not, after 8 MiB or at anything it can't parse; the bytes keep flowing to the client unchanged. The line then has `observe_failed: true` and the `unstorable` reason `observe_too_large` or `observe_failed`. When the response was cut short, `upstream_incomplete` or `client_disconnected` is the reason instead.

`analyze_shadow.py` reads the lines from a set of jobs and reports the token-weighted would-hit rate. Low counts nightly sightings. High adds earlier finished builds of the same pull request and, given `--merged` (pull request to merge time), another pull request's last build before it merged. Until run verdicts are joined, high is an upper bound: it counts those builds, and nightly answers once written, whatever their runs' verdicts. The report counts presubmit lines without a pull request number, which shows an unset `REPLAY_JOB_PR`. It also reports the share of hits first seen in another project, the tokens and model time hits would save, and the misses ranked by tokens lost with the closest earlier request by longest matching message prefix. Many requests share a prefix (every worker conversation opens the same way); given `--by-text` (each build's own copied-out `REPLAY_STORE_DIR`; see [In CI](#in-ci)) or `--store` (one store, with `--kind`), the closest is the one whose next message is most alike by the words they share, relative to both messages' length (among the 64 most recent distinct next messages with stored text), and otherwise the earliest. A candidate sharing no word with the miss's next message is no match. With either, each miss says which (`closest_by`, with `closest_score` for a text pick and `unranked_reason` when it fell back) and the report counts the misses ranked by text, so stores missing for some jobs show up as fallbacks rather than as a ranked report; a `--store` without `requests/` and `blobs/` is refused. Its `replayed_low` and `replayed_high` rows count what replay would hit if it kept each conversation on its recording: a request matches a source low or high allows when the settings, the number of messages, each message's role and every message that is not a generated answer match, since replay would have served the source's own answers (an exact match counts too). A generated answer is an assistant message the logs show the model gave in that conversation: an earlier request of the same build with exactly the messages before it got an answer that reached the client. Messages compare by `diag_message_hashes` when both requests carry them, since `message_hashes` can drift between one conversation's requests (a CIDR first seen later, a timestamp crossing a bucket), and by `message_hashes` otherwise; missing or drifted evidence keeps the message's hash, which can only lower the estimate. Any other assistant message (a few-shot example, a prefill, a resumed transcript) is prompt and must match. For `replayed_high` misses only, the report sums prompt tokens by the role of the first message no allowed high source matches, generated answers' words not compared: `settings`, `system`, `user` or `tool`; `assistant` when no allowed source matches at that assistant position (none has a generated answer there, or the message is prompt and differs); `none` when a longer allowed recording passes through but none stopped there. Both rows are estimates: a different live action gives shadow mode a different tool result where replay would have run the saved action, and a live answer naming a new ID, IP or CIDR shifts the hashes of later messages (placeholder numbers and the IP rule run across the whole request), where the saved answer would not; and each request is judged alone, while a real replay ends at the conversation's first miss. For multi-agent runs every estimate here is a floor: one agent's answers feed another's input and pick its actions, which shadow mode can't hold fixed, so the real hit rate comes from the design's replay lane (Rollout step 2), which runs real replay where it gates nothing.

Check the report's health counts after the first day: lines by job kind; untagged lines (an unset or unknown `REPLAY_JOB_KIND`, dropped from every estimate); kind-mismatch lines (tagged with a kind other than the folder they were filed under, dropped too); off-layout files (log files not at the collector's layout, skipped whole); error lines; lines without a fingerprint; `analysis_dropped`; unstorable lines and their share by reason; presubmit lines without a pull request number; lines without message hashes; the upstream-incomplete, observe-failed and observe-too-large counts; and the share of prompt tokens that are estimated. A high number in any of them means the setup is broken, not that replay would miss.

## Modes

`REPLAY_MODE` picks one of three:

- `shadow` (the default): everything above, nothing saved, nothing served.
- `record`: shadow, plus each storable answer (empty `unstorable`) saved under its fingerprint in `REPLAY_CACHE_DIR` (`replay_cache.py`): the answer with the values its request bound swapped for placeholders (each identifier found by the pattern that bound it, and each timestamp the request holds verbatim), its finish reason and usage, and the request's hashes. The rules for what isn't saved are under "Normalization" in the design; each refusal is named in `unstorable` (`schema.py` lists them). One file per key, written atomically; the first write wins. If writing the cache fails, the line still goes out, with `recorded: false` and `record_error`. In record mode `REPLAY_CACHE_DIR` counts against `REPLAY_DATA_MAX_BYTES` with the store and the segments (the collector empties it as it copies it); once the budget is spent nothing more is saved, the line says `record_error: budget_spent`, `replay_shadow_record_budget_spent_total` counts it, and requests are still forwarded. Replay mode's cache is not counted: it is a seeded copy that must stay whole. Each request message is also saved once, normalized and then scrubbed the way the request store scrubs it (a tool result whose call printed a secret's value is withheld whole), so a later miss can show how it differed; a miss's snippets are scrubbed the same way. Record mode never serves.
- `replay`: on a fingerprint hit in `REPLAY_CACHE_DIR`, the saved answer is restored with the current request's values and served, streamed or not, without calling the model; an answer naming a placeholder the request doesn't bind is a miss. On a fingerprint miss, replay tries a second key, where the model's earlier answers are slots any answer a recording stored for that point can fill (`normalizer.answer_slots`, `normalizer.READ_ONLY_TOOLS`); "Different words for the same answer" in the design says what the key keeps and when it serves. A miss goes to the model live and is not recorded. Replay only reads the cache: every lookup reads it as it is, so answers recorded after the proxy started are served too; only the index the miss report searches is built at start.

Replay mode refuses to start unless `REPLAY_ALLOW_SERVE=yes` is also set, and nothing in the repository sets it, so a saved answer can't be served by accident.

Every line carries `mode` and `served`. A served line has `served_from`, the job that recorded the answer, and `served_via`: `exact` or `answer_slots`; its answer is a saved one, so its `unstorable` is empty and its LiteLLM headers are null, and `analyze_shadow.py` skips it (counted as `served`) rather than read it as a model answer. A replay miss has a `miss` block: the closest saved request by longest matching `diag_message_hashes` prefix (under `diag_settings_hash`; when several share that prefix, as every worker conversation's opening does, the one whose next message is most alike by the words they share, relative to both lengths), how many messages matched, the index and role of the first differing message, short normalized and scrubbed snippets of that message on both sides, and a signature (narrower windows around the difference, with digit runs and hex runs of six or more collapsed) for grouping. When the request did match a saved answer on either key but a guard refused to serve it, the block also has `refused`: the key (`via`) and the guard (`answer_not_recorded`, `value_only_in_answers`, `unbound_placeholder` or `unreadable_entry`), so the miss doesn't read as an ordinary fork. `analyze_replay.py` groups replay lines into conversations and reports, per conversation and overall, the requests and prompt tokens served before the first miss and the share served through answer slots, the first-miss causes by role and signature ranked by tokens lost, and, with `--verdicts`, whether each conversation's run verdict matched the recording run's. Replay lines whose analysis was dropped or failed carry `mode` and `served` but no hashes, so they join no conversation; the report counts them, served and not, because a conversation that lost a request not served shows its first miss late.

## Configuration

| Environment variable              | Default                               | Meaning                                                                            |
| --------------------------------- | ------------------------------------- | ---------------------------------------------------------------------------------- |
| `REPLAY_LISTEN_PORT`              | `8080`                                | Port the proxy listens on                                                          |
| `REPLAY_UPSTREAM_HOST`            | `inference-gateway-upstream`          | LiteLLM's host                                                                     |
| `REPLAY_UPSTREAM_PORT`            | `80`                                  | LiteLLM's port                                                                     |
| `REPLAY_UPSTREAM_TIMEOUT_SECONDS` | `1800`                                | Socket timeout for each read from LiteLLM                                          |
| `REPLAY_MODEL_BEHAVIOUR_CHECKSUM` | empty                                 | The chart's checksum of the LiteLLM config, Gemini API and Vertex AI routes as one |
| `REPLAY_LITELLM_IMAGE`            | empty                                 | The LiteLLM container image                                                        |
| `REPLAY_STORE_DIR`                | `/data/shadow`                        | Where scrubbed request text is written                                             |
| `REPLAY_REDACTOR_PATH`            | `/app/scrubbers/redactor.py`          | The install's `AuditRedactor`                                                      |
| `REPLAY_TRANSCRIPT_RULES_PATH`    | `/app/scrubbers/worker_transcript.py` | The shared transcript scrubbing rules                                              |
| `REPLAY_JOB_KIND`                 | empty                                 | The job kind ([In CI](#in-ci)), stamped on every line                              |
| `REPLAY_JOB_PR`                   | empty                                 | The pull request number, stamped on every line                                     |
| `REPLAY_JOB_PROJECT`              | empty                                 | The eval project, stamped on every line                                            |
| `REPLAY_JOB_BUILD`                | empty                                 | The Prow build ID, stamped on every line                                           |
| `REPLAY_LOG_DIR`                  | empty                                 | Also write every line to segment files here                                        |
| `REPLAY_LOG_SEGMENT_SECONDS`      | `60`                                  | Close a segment this long after its first line                                     |
| `REPLAY_DATA_MAX_BYTES`           | `0` (no limit)                        | Stop the store, the segments and record mode's cache at this many bytes            |
| `REPLAY_MODE`                     | `shadow`                              | `shadow`, `record` or `replay`                                                     |
| `REPLAY_CACHE_DIR`                | `/data/replay-cache`                  | Saved answers: written by record, read by replay                                   |
| `REPLAY_ALLOW_SERVE`              | empty                                 | Must be `yes` for replay mode to start                                             |

With `REPLAY_LOG_DIR` set, `spool.py` appends each line to `<pod>-<start ms>-<seq>.jsonl.open` and renames it to `.jsonl` once it is 8 MiB or `REPLAY_LOG_SEGMENT_SECONDS` old, so a closed segment never changes. At start it closes the segments a previous run of the container left open, cut to their last whole line. On TERM or INT the proxy stops serving, spends at most 10 seconds logging what is queued, and closes the open segment before it exits. stdout still gets every line. With `REPLAY_DATA_MAX_BYTES` set, the store and the segments stop writing once the files under `REPLAY_STORE_DIR` and `REPLAY_LOG_DIR` hold that many bytes, and start again when the collector has emptied files; the line still goes to stdout and the store reports `budget_spent`.

The image is built from the repository root (`docker build -f hack/replay-proxy/Dockerfile .`), because it copies the scrubbers from `agents/`.

## In CI

Every Prow presubmit and nightly eval puts the proxy in front of LiteLLM, unless the job sets `EVAL_REPLAY_SHADOW=false`. `hack/ci-deploy.sh` builds the image from this directory's `Dockerfile` (the `replay-shadow-proxy` step of `deploy/docker/cloudbuild-ci.yaml`) and installs it through the chart's `litellm.replayShadow` values: two proxy pods take the `inference-gateway` Service, and LiteLLM moves behind `inference-gateway-upstream`. Both carry `app: litellm`, the label the worker pods' egress policies admit, and differ by `kubeagents.x-k8s.io/inference-role` (`replay-shadow` or `litellm`). The comments on `litellm.replayShadow` in `charts/kube-agents/values.yaml` cover the rest. `hack/ci-eval-pr.sh`, which runs the presubmits and the nightlies, starts `collect_shadow.py` once it knows the host cluster and stops it from its EXIT trap. The collector copies closed segments and stored requests out of the proxy pods every 30 seconds, uploads them, then empties each uploaded file in the pod. At the end it makes one last pass, bounded to 60 seconds, that also takes the open segments. It prints counts and error classes to the `replay-shadow-collector.log` artifact and never fails the eval; the EXIT trap waits at most 75 seconds for its last pass, which runs while the trap's other captures do. The image has no `images.json` entry: each run builds it into its own project's registry and nothing publishes it, so there is nothing for `make mirror-images` to copy; `hack/check-image-inventory.sh` holds its Python base to the inventory.

It uploads to `kube-agents-replay-shadow` (`EVAL_REPLAY_SHADOW_BUCKET` points it elsewhere, no `gs://`); the runners' grants on that bucket are in [`docs/ci-pool-projects.md`](../../docs/ci-pool-projects.md). It needs the `JOB_TYPE`, `BUILD_ID` and, on a presubmit, `PULL_NUMBER` that Prow sets. A presubmit is filed as `presubmit`. A periodic or postsubmit is filed as `nightly` only when gcloud's active account, the one the collector uploads as, is `eval-baseline-recorder@kube-agents-prow.iam.gserviceaccount.com` and no impersonation or token override (`auth/impersonate_service_account`, `auth/access_token_file`, `auth/credential_file_override`) is set. Any other account, an override, or an identity that can't be read files it as `nightly-untrusted`. Every presubmit runs pull-request code as `prowjob-default-sa`, so that account must never write `nightly/`, and a periodic that runs as it (the GitLab next lane) gets a folder of its own. `hack/ci-deploy.sh` decides the kind and stamps it on the proxy; `hack/ci-eval-pr.sh` reads it back from the proxy Deployment, so the collector files under the kind the lines carry. The deploy log says when a night's data is filed as untrusted and why. A run it can't serve goes without it, with a one-line note: a batch run, a release-candidate run (`RC_COMMIT_SHA`, which builds no images), a run outside Prow, or a Prow job missing one of those tags. Setting `EVAL_REPLAY_SHADOW=true` makes each of those an error instead. Outside Prow, set `EVAL_REPLAY_SHADOW_JOB_KIND` to `presubmit`, `nightly` or `nightly-untrusted` (a `nightly` gets the same account check), plus `BUILD_ID` and, for a presubmit, `PULL_NUMBER`.

Each run writes under `gs://<bucket>/replay-shadow/<nightly|nightly-untrusted|presubmit>/<YYYY-MM-DD>/<BUILD_ID>/`, the date being the collector's start in UTC: `logs/*.jsonl` (the lines), `store/requests/*.json` and `store/blobs/*.json` (the scrubbed text), and `job-<ms>.json` (kind, project, build and pull request, written even when the run logged nothing). Every name is written once, so a merged copy of many runs loses nothing:

```bash
kinds="nightly nightly-untrusted presubmit"
days="2026-11-01 2026-11-02 2026-11-03 2026-11-04 2026-11-05 2026-11-06 2026-11-07"
mkdir -p week && : > week/objects.txt
for kind in ${kinds}; do
  for day in ${days}; do
    gcloud storage ls "gs://<bucket>/replay-shadow/${kind}/${day}/**" >> week/objects.txt 2>/dev/null || true
  done
done
if grep -E '^gs://[^/]+/(/|\.\.?(/|$)|.*(//|/\.\.?(/|$)))' week/objects.txt; then
  echo "Refusing to download: the object keys above have an empty, '.' or '..' segment." >&2
else
  for kind in ${kinds}; do
    mkdir -p "week/${kind}"
    for day in ${days}; do
      gcloud storage cp -r "gs://<bucket>/replay-shadow/${kind}/${day}" "week/${kind}" || true
    done
  done
  python3 hack/replay-proxy/analyze_shadow.py week/nightly week/nightly-untrusted week/presubmit --by-text
fi
```

The listing comes first because the folders' trust depends on the downloader: IAM matches a key's prefix as text, so `replay-shadow/presubmit/x/../../nightly/...` is a presubmit's object, and a tool that resolved the `..` would write it into `week/nightly`. gcloud 576 skips such keys, older versions and other tools may not, and `collect_shadow.py` refuses a bucket or build that could produce one.

Keep the bucket's layout: `analyze_shadow.py` takes a line's kind from the top-level `nightly`, `nightly-untrusted` or `presubmit` folder its file was copied from, not from the line's own `job.kind` tag, which comes from the proxy and so from the commit under test. IAM decides who may create objects under each `replay-shadow/<kind>/` prefix but not what the uploader names below it, so a log file counts only at `<kind>/<YYYY-MM-DD>/<build>/logs/<segment>.jsonl`, with that `<kind>` the only directory in its path named for a kind; a segment anywhere else under a folder you pass, even a whole folder of them, is skipped and counted as `off_layout_files`, with a note for a folder that holds nothing at the layout. Pass the kind folders, their parent, or segments inside them. A path that doesn't exist, or a named file that isn't a `.jsonl` segment, is always an error; a named segment off the layout, or a run whose segments are all off it, is an error unless `--kind` names the kind of every input, which also skips the layout check. A run that finds no segments at all reports nothing. A line whose tag names another kind than its file is dropped and counted as `kind_mismatch_lines`. `nightly-untrusted` lines are counted and are never a source or a miss's closest request, since pull-request code could have written them. `--by-text` ranks a miss's closest request by text read from each request's own build, `<kind>/<YYYY-MM-DD>/<build>/store/`, never from a store merged across runs: a presubmit can read the bucket, learn a nightly's request ids and upload text under them in its own prefix. A request's stored text is `store/requests/<request_id>.json` in its build, whose entries name files in that build's `store/blobs/`. `--store DIR` reads one store for every input and so works only with `--kind`, for logs from outside the bucket.

Limitations:

- each kind writes under its own top-level prefix, and IAM conditions on the object name confine each runner to its own (create and view, never delete): `prowjob-default-sa` to `presubmit/` and `nightly-untrusted/`, `eval-baseline-recorder` to `nightly/` and `nightly-untrusted/`. Below its prefix an uploader names every path, so within `presubmit/` and `nightly-untrusted/` one run could still write under another's build, and any file off the collector's layout is only skipped and counted;
- `nightly/` guarantees who uploaded, not that the night is free of pull-request influence: no account pull-request code runs as can create objects there, but the Prow runner holds `roles/container.admin` in every pool project ([`docs/ci-pool-projects.md`](../../docs/ci-pool-projects.md)), so a presubmit leased into the same project as a running nightly could exec into or patch that night's `inference-replay-shadow` pods, and the nightly runner's collector would upload what they then hold under `nightly/`. The design names the same gap for the cache's nightly writer ([Who can write to the cache](../../examples/inference-replay/eval-design.md#who-can-write-to-the-cache));
- the image is built from the commit under test, not from `PULL_BASE_SHA` as the design's replay stage requires ("The proxy can't come from the pull request"). Shadow mode changes no verdict, but a pull request can change what its own run records.

## Baseline report

`baseline_report.py` reports what eval inference costs today, from the same lines: requests, prompt tokens split cached and uncached, completion tokens, the token-weighted cache hit rate, estimated cost, model time, non-200 statuses (429s above all), LiteLLM fallbacks, and, given the eval dashboard's `data.json`, model time against agent time, pass rates and flaky cases. It reports totals, each job kind, each build and, from the eval data, each case. The baseline is the report over the shadow data from before replay is switched on; every later report comes from the same script, so `--compare` measures the change the same way.

It reads its inputs the way `analyze_shadow.py` does (see [In CI](#in-ci)): each line's kind is the top-level kind folder its file was copied from, at the collector's layout, never its own `job.kind` tag, with the same rules for off-layout files (skipped and counted as `off_layout_files`), missing paths, named files and `--kind`. It also reads the job manifests, `<kind>/<YYYY-MM-DD>/<build>/job-<ms>.json`, by the same layout rule, and a file named outright may be one. A line whose tag names another kind is dropped and counted as `kind_mismatch`, and a manifest likewise under `manifest_kind_mismatches`. `nightly-untrusted`, a scheduled run that did not upload as the baseline recorder, is a scope of its own beside `nightly` and `presubmit`. A build named in a manifest with no lines is listed under data quality. A line replay mode served (`served: true`) is skipped and counted as `served`, as `analyze_shadow.py` skips it: the model was not called, so it is no model usage, cost or time. Tokens and cost count the lines answered with 200, because a refused request bills nothing; model time counts every line with a latency. A line whose analysis failed or was dropped still counts as a request and by status.

`cost_usd` takes LiteLLM's own cost for a line (`litellm_cost_usd`) when it has one, and otherwise an estimate from `model-prices.json`: a dated table of list prices per 1M tokens (input, cached input, output, and a long-context tier above a prompt size). The report gives both totals and how many lines each covered (`litellm_cost_usd`, `table_cost_usd`, `cost_from_table_requests`), and `table_to_litellm_cost_ratio` compares them over the lines that have both, which checks the table. The table is looked up by the deployment's model (`litellm_model_name`, with and then without its provider prefix such as `vertex_ai/`), then by the model group and the request's model; `--price-as <group>=<model>` is only the fallback, for lines written before the model name was logged (the group on an eval install is the `model-default` alias). A line with neither a LiteLLM cost nor a price is reported as unpriced with its count and left out, never counted as zero. A line whose tokens were estimated (the response carried no usage, so `prompt_tokens` is the request's size and there is no completion count) is never priced from the table: it counts only through a LiteLLM cost, and otherwise goes to `estimated_unpriced_requests` and out of `cost_usd`. Such lines are a minority, and a streamed answer that carries its usage carries LiteLLM's cost too, but `--compare` notes them on either side. The report prints the table's `as_of` date, whether its prices were `confirmed` against the provider's price page on that date, its `source` and its hash; the checked-in table is not confirmed. The table does not price cache writes.

The eval join matches a line's `job.build` to a dashboard run's `build_id`. Lines carry no case, so tokens, cost and model time stop at the build; the case table comes from the eval data's repetitions. Model time includes every agent on the install and every request a repetition never waited on, so its ratio to agent time can pass 100%.

The baseline window is two weeks starting on the first full UTC day after the proxy began logging `litellm_cost_usd`, `litellm_model_name`, `litellm_attempted_retries`, `reasoning_tokens` and `cache_write_tokens`, so that every nightly and presubmit line in it carries them. To freeze it, download the window's days with the recipe in [In CI](#in-ci), which lists the keys first and keeps each kind's folder, then keep the report and its inputs together:

```bash
gcloud storage cp gs://kube-agents-dashboards/evals/data.json data.json
python3 hack/replay-proxy/baseline_report.py week/nightly week/nightly-untrusted week/presubmit \
  --eval-data data.json --price-as model-default=<model> \
  --since <first full day after those fields reached main> --until <thirteen days later> --json > baseline.json
```

Each of those fields has a coverage: the share of analysed lines that carry it, printed under the metrics and given per field as `coverage` in `--json`. A field missing from older lines is never counted as zero: a figure built from a field no line carries reads `not logged` (null in `--json`), one built from a field only some lines carry is shown with that share, and `--compare` notes every field whose coverage differs between the two reports, since the change in its figures is then not replay's.

`--since` and `--until` take epoch seconds (a plain run of at least nine digits, up to the end of year 9999), a `YYYY-MM-DD` date (`--until` includes that day) or an ISO time that starts with one, and refuse anything else. They keep whole builds by their first request, and the manifests of the builds they keep; a line without a build id is kept or left out by its own time, and counts in every sum but in no per-build figure. A line's value outside its bound (a time past year 9999, a latency over a day, a count over a trillion, a cost over a million dollars) is a bad field value, not a number. Read the data-quality block before freezing: skipped lines, bad field values, estimated token lines and unpriced requests each mean a number above is short. Later, download the new window the same way, into its own directory with the same `<kind>/` folders, and run the same command over it with `--compare baseline.json` (add `--json` for the deltas as JSON), or compare two saved reports with `--report current.json --compare baseline.json`. The deltas are current minus baseline, absolutely (percentage points for rates) and as a percent of the baseline; a note says when the price tables, `--price-as` or the report schema differ, or when either side's cost is partial. Compare per-build metrics: two windows rarely hold the same number of builds.
