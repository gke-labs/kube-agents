# Each is a copy of the first with the same grants (docs/ci-pool-projects.md
# 5.4: contents, issues and pull_requests write, metadata read; grading
# mints only the four reads), installed on the infrastructure organisation
# with `selected` repositories: its share of the pool's
# kube-agents-evals-*-infra repositories, ten projects per App in number
# order (LEDGER_READER_SHARD_SIZE in hack/ci-eval-pr.sh): row 1 holds
# kube-agents-evals (number 1) through kube-agents-evals-10, row 2 holds
# -11 through -20, and so on, so no table maps projects to Apps:
# hack/ci-eval-pr.sh mints from the shard of the project it leased,
# scripts/verify_ci_pool_project.py checks a project against its shard, and
# scripts/provision_ci_pool_project.sh names the shard a new project's
# repository goes to. Splitting the pool this way gives concurrent runs on
# different projects different hourly budgets (gke-labs/kube-agents#6240).
#

# registered: scripts/test_verify_ci_pool_project.py fails a pull request

# every onboarding check and lease would fail.
