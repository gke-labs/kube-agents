# The GitLab lane's presubmit matrix: what pull-kube-agents-smoke-test-gitlab
# runs (kube-agents#2394). hack/ci-eval-pr.sh reads this file instead of
# presubmit-cases.txt when EVAL_FORGE=gitlab and EVAL_TIER is presubmit. A
# GitLab nightly would run the whole catalogue, as the GitHub nightly does,
# but none exists yet (#2832): today nothing runs the twelve cases
# this file leaves out, or the nightly-only cases, against GitLab.
#
# One `./tasks/<id>/task.yaml` path per line, relative to bench/. `#` starts
# a comment, blank lines are skipped. Every entry must be a registered case,
# a line in presubmit-cases.txt or nightly-cases.txt: the lane picks from the
# catalogue, it does not register. The script refuses to start on an entry
# in neither file and on a file that names nothing.
#
# WHAT BELONGS HERE. Cases that grade the forge: a `pull_request_opened` or
# `pull_request_diff_contains` check (a merge request on GitLab) or a
# `ledger_issue_contains` check (a ledger issue). A chat probe passes the
# same on either forge and proves nothing about GitLab; the GitHub run
# already grades it on every pull request. scripts/test_eval_rosters.py pins
# the set, and that each entry requires a positive forge check (not under a
# `none`, not one alternative under an `any`).
#
# WHAT CAN RED THE LANE. The blocking roster still applies, intersected with
# this list: a roster case here arms rung 4 on the lane; a held-out case here
# runs and reports without arming it, as it does on the GitHub presubmit.
# Rungs 1-3 red the lane like every case. Both seats below are held out, so
# the lane cannot red a pull request on a graded failure today, and the job
# stays optional in Prow until it has a green history (oss-test-infra#2724).
#
# WHO APPROVES. The normal approvers (root OWNERS), as for nightly-cases.txt
# and the inject-lane files: this file changes what one optional lane runs,
# not what can red a pull request. It moves under the eval-crew rule in
# hack/OWNERS the day the lane gates.
#
# BUDGET. Three cases, nine units at EVAL_REPETITIONS of 3, every one in the
# fan-out's second phase (each requests a merge request; unit_phase in the
# script), so they run one at a time: pdb-remediation-pr (hinted 1250s),
# vcs-spent-branch-reuse (1000s) and vcs-review-feedback-read-back (700s)
# are ~150 minutes of units at the hints, plus ~16 minutes of lease, build
# and deploy: inside the job's 360-minute deadline, and longer than the
# GitHub presubmit's ~136-minute median. Dropping pdb-remediation-pr is the
# lighter lane, if the lane ever runs on every pull request.
#
# WHY THESE. The two vcs cases exist to exercise the forge (a branch reused
# after its first proposal closed; a second revision read back before it is
# described) and pass 100 % and 92 % on the GitHub nightly over 30 days, so
# a red here points at GitLab, not at the agent. No ledger case is in the
# lane: none passes three repetitions anywhere today (the compliance canary
# publishes a ledger in about half its runs on either forge, the agent's
# doing), so the ledger path is proven by the harness (the per-repetition
# ledger reset, and a harness-side probe to come), not by a case.

# A second proposal under a branch name whose first proposal was closed:
# branch lookup, delete, push and open on the forge (pull_request_opened).
./tasks/vcs-spent-branch-reuse/task.yaml
# A second revision on an existing merge request, read back from the forge
# before it is described (pull_request_opened).
./tasks/vcs-review-feedback-read-back/task.yaml
# The remediation path: the fix lands as a merge request on the project's
# GitLab repository, never on the cluster (pull_request_opened).
./tasks/pdb-remediation-pr/task.yaml
