# The GitLab lane's matrix: what pull-kube-agents-smoke-test-gitlab runs on
# a pull request and ci-kube-agents-eval-nightly-gitlab runs once a night
# (kube-agents#2394, #2832), and ci-kube-agents-eval-nightly-gitlab-next runs
# once a night under spec.mode next (EVAL_MODE_NEXT=1, through the inject
# door). hack/ci-eval-pr.sh reads this file in place of the catalogue
# whenever EVAL_FORGE is gitlab or gitlab-ce (a self-managed instance,
# kube-agents#3682), on either tier: nothing else grades the forge,
# so the presubmit cases and the other nightly-only cases run on GitHub
# only. Neither nightly appends to the evidence store.
#
# One `./tasks/<id>/task.yaml` path per line, relative to bench/. `#` starts
# a comment, blank lines are skipped. Every entry must be a registered case,
# a line in presubmit-cases.txt or nightly-cases.txt: the lane picks from the
# catalogue, it does not register. The script refuses to start on an entry
# in neither file and on a file that names nothing.
#
# WHAT BELONGS HERE. Cases that grade the forge: a `pull_request_opened` or
# `pull_request_diff_contains` check (a merge request on GitLab) or a
# `ledger_issue_contains` check (a ledger issue). A chat probe passes the
# same on either forge and proves nothing about GitLab; the GitHub run
# already grades it on every pull request. scripts/test_eval_rosters.py pins
# the set, and that each entry requires a positive forge check (not under a
# `none`, not one alternative under an `any`).
#
# WHAT CAN RED THE LANE. The blocking roster still applies, intersected with
# this list: a roster case here arms rung 4 on the lane; a held-out case here
# runs and reports without arming it, as it does on the GitHub presubmit.
# Rungs 1-3 red the lane like every case. pdb-remediation-pr was on the
# roster from 2026-10-14 (#2016) until its demotion to the nightly on
# 2026-10-17 (#3120), and the lane ran with rung 4 disarmed from then until
# vcs-spent-branch-reuse took its roster line on 2026-10-23; pdb-remediation-pr
# took its own back on 2026-10-26: today those two arm rung 4 on the lane,
# and vcs-review-feedback-read-back is held out.
# The job runs on demand (`/test pull-kube-agents-smoke-test-gitlab`) and
# nightly, never as a blocking presubmit: the agent goes through the same
# forge abstraction on both forges, so the GitHub presubmit grades what a
# pull request can break in the agent; what GitLab can break on its own is
# the provider and the forge, and the nightly catches that within a day.
#
# WHO APPROVES. The normal approvers (root OWNERS), as for nightly-cases.txt
# and the inject-lane files: this file changes what one on-demand lane and
# the two nightlies run, not what can red a pull request.
#
# BUDGET. Three cases, nine units at EVAL_REPETITIONS of 3, every one in the
# fan-out's second phase (each requests a merge request; unit_phase in the
# script), so they run one at a time: pdb-remediation-pr (hinted 1250s),
# vcs-spent-branch-reuse (1000s) and vcs-review-feedback-read-back (700s)
# are ~150 minutes of units at the hints, plus ~16 minutes of lease, build
# and deploy: inside the presubmit's 360-minute deadline and the nightlies'
# 480, and longer than the GitHub presubmit's ~136-minute median.
#
# WHY THESE. The two vcs cases exist to exercise the forge (a branch reused
# after its first proposal closed; a second revision read back before it is
# described) and pass 100 % and 92 % on the GitHub nightly over 30 days, so
# a red here points at GitLab, not at the agent. No ledger case is in the
# lane: the compliance canary publishes a ledger in about half its runs on
# either forge, the agent's doing, and consistency-drift-outlier, which
# passes on the GitHub nightlies (a roster seat since 2026-10-26), has no
# GitLab record yet. So the ledger path is proven by the harness, not by a case: the
# lease-time probe, probe_gitlab_ledger_path in the script and
# docs/ci-pool-projects.md 5.6. That says the forge takes a ledger; whether
# the agent publishes one is #2856's question.
