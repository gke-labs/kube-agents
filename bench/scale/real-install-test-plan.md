# Real-install test plan: one install at the L container size

## High level summary

This test checks the sizing answer on a real setup. The sizing answer says that one install at the L container size holds 40 clusters. An install is one kube-agents deployment. The L container size gives the agent 8 CPU and 16 GB, the credential proxy 8 CPU and 8 GB, and the event watcher 2 CPU and 4 GB. The test builds 40 test clusters, makes a new install, and watches its first-run flow. The first-run flow is the onboarding that a new install does by itself. The test then asks typical heavy questions and adds a high rate of Pod churn. Pod churn is the creation and deletion of Pods. Each step records resource use, model traffic, tool calls and response times. The report says whether each step stayed inside the safe limits.

## What "safe" means

A step is safe when all of these hold:

- no container restarts or is killed for memory;
- no brokered command is refused, and no command waits near 60 s;
- no question is refused for lack of run slots;
- no model call fails with a 429 in a way that loses work;
- every step that should finish, finishes.

## Steps

1. **Build the workload fleet.** Create 40 test clusters with about 5 nodes and about 1,200 objects
   each. Add about 3 Pods created per minute and about 5 Pods failing at once. Plant signals for
   the questions: workloads skewed into one zone, one Deployment with heavy traffic, and a few
   clusters on an older GKE version. Print a dry run of the cluster changes first.
2. **Make a new install.** Uninstall the current install. Install the current `main` build with
   the L container size and a GitOps repository. Re-point the IAM guard at the new install's
   bindings.
3. **Watch the first-run flow (2 to 3 hours).** Record each stage and the time its report appears:
   the cluster sync, the scan (one card per cluster), the ranking card, and each first-run audit.
4. **Report whether the first-run flow was safe.** Give each stage's duration, peaks, model traffic
   and tool calls against the safe limits.
5. **Ask heavy questions, at fair use.** One or two people, never more than 3 questions at once:
   - (A) an upgrade readiness report for the fleet;
   - (B) fleet health: the heaviest traffic, zonal skew and anomalies;
   - (A) and (B) together, and 3 questions at once.

   Run each 3 times. Check that each answer finds the planted signals.

6. **Other checks.**
   - Restart the agent with 40 clusters registered, and time how long until all are watched again.
   - A 20-failing-Pod window: does the session storm start?
   - Stall Watch coverage: how often each cluster is read.
   - An overnight soak (12 to 24 hours) that includes the morning's scheduled audits, for model
     tokens per day.
7. **High Pod churn.** Run a churn generator inside a test cluster and raise its rate in steps
   (about 500, 1,000 and 3,000 Pods per minute, or to the cluster's own limit). Watch the event
   watcher, the session count and the agent's memory.
8. **Red test: the same fleet with the S container size.** Set every container to its request,
   which is what GKE Autopilot without bursting gives: the agent 1 CPU and 2 GiB, the credential
   proxy 0.5 CPU and 1 GiB, the event watcher 0.15 CPU and 384 MiB, the sandbox shell 0.2 CPU and
   512 MiB. Reset the install's state and run the first-run flow and one heavy question again.
   The forecast says this size is not enough, so the step passes when it fails in the predicted
   way: an OOMKill, refused or 60-second commands, or a stage that does not finish. Record which
   limit breaks first and when, and compare it with the forecast's first limit. Restore the L
   size after.

## Parameters

This section gives each parameter of the test. A parameter is a number, size, rate, duration,
count, threshold or setting that the test uses. The tables follow the steps, and Steps 3 and 4
share one table. Two more tables apply to every step. "Why this value" gives the measurement,
design decision or default that the value comes from. "How to set it" gives the plan-file key,
`PlatformAgent` field, Helm value, flag or environment variable. When the source holds no value,
the row says that the plan sets it. "Computed" marks a value that the page's model gives for the
Step 1 values with the Phase 1 to 4 data, and that no file holds.

The tables use these terms:

- The runner is `python3 -m kube_agents_bench.scale.runner`. Run it from `bench/`.
- A plan file is the YAML file that the runner reads, for example `bench/scale/phase4.yaml`. Its
  keys are `phase` (required), `base_last`, `target`, `base`, `factors`, `combined`, `settings`
  and `operations`. The environment variable `SCALE_<KEY>` overrides the `target` key of the same
  name.
- An operation is one measured action in a plan file. Its window is the time that the runner
  measures.
- A record is the result of one run in `bench/scale/harness-limits.json`.
- The page is the Harness limits page of the admin console (Setup > Harness limits).
- The CR is the `PlatformAgent` resource `platform-agent` in namespace `kubeagents-system`.
- The gateway Pod holds the agent container and the event watcher container.
- A brokered command is a `kubectl` or `gcloud` command that the credential proxy runs for the
  agent.
- A run slot is one of the turns that the agent runs at the same time.
- GB is 10^9 bytes, and GiB is 2^30 bytes. The Kubernetes quantity `16G` is 16 GB, and `16Gi` is
  larger.
- The label "Phase 4 runner" marks a setting that only the Phase 4 version of the runner has.

To see the page's forecast for this fleet, enter the Step 1 values under "Change the fleet size".
Then select L under "Container size".

## Cost

Cost is part of the scalability answer, so each step also gives what it cost:

- **GKE.** The host cluster's node pools (machine type and count) times the step's duration, plus
  the GKE cluster fee and the data volumes' disks. The report gives the cost per hour of one install
  at the L size, and the cost of the installs a fleet needs (for example 63 to 105 installs for the
  XL fleet). The test clusters' own cost is the fleet's, not the install's, so the report lists it
  apart.
- **Model tokens.** LiteLLM's input, cached and output tokens for the step, times the list price of
  the install's model (`gemini-3.5-flash` on this install) per million tokens of each kind. The
  report gives the cost of the first-run flow, of each heavy question, and of a day of scheduled
  work from the overnight soak.
- **Prices.** GKE prices come from the Cloud Billing Catalog API and the model's from the provider's
  published price list, each recorded with its date and region; no price is copied from memory.
  The report states list prices, before any discount.

## Output

- The records in `bench/scale/harness-limits.json`, beside Phases 1 to 4.
- A report: for each step, safe or not, and why, with the numbers.
- The design doc's answer for the L container size, confirmed or corrected.
- For the red test: whether the S size broke where the forecast said it would.
- The cost of each step, of one install per hour and per day, and of the XL fleet's installs: GKE
  and model tokens apart.
