# Eval fix loop

One root cause per loop. A classified cause with quoted evidence before any code. Never loosen a check to fit a model's wording; a bar above the product's own rule under the standing fixture state is lowered only on a replay that flips addressed fails and zero passes, with the dropped branch pinned by a unit test. Three greens on the final head. Markers flip in the same pull request.

## First-day addendum (2026-11-02)

Only a harness fix with no recorded answer to replay takes the unit test instead, red against `main` and green ten of ten. Three live greens are for an agent or product change only; a live repetition of a recorded red proves nothing the record does not.

## Inputs

- A case id under `bench/tasks/<id>/`, or a root cause with its case ids.
- The run directories that show the failure: a nightly build's `artifacts/` in the local cache, or a local `bench/results/run_*/`.
- A checkout with the case, its fixture (`bench/tf/prebuilt/<stack>/` or the seeded fleet), and the product code behind it: the procedure (`agents/platform/skills/<skill>/` SOP markdown), the collector scripts (`agents/platform/skills/<skill>/scripts/`), the checks (`bench/kube_agents_bench/verifiers.py`).
- The rules: `.agents/rules/eval_driven_development.md` governs red, green and registration; this skill adds the diagnosis and the refusals.

## Step 1: pick and brief

Write a one-screen brief before reading anything else in depth:

- Case id, domain, audit stream, the install model and release of the failing runs.
- For a case that plants a fixture: the fields the lane's host type adds or changes on the planted objects, read with `kubectl -n default create -f - --dry-run=server -o yaml` over the manifest. A safeguard on a field admission writes is wrong, and a condition admission removes cannot be planted there (Autopilot writes `limits.ephemeral-storage` on every container).
- Pass counts per model from the record (`bench/run-store/runs/` if present, else the run directories).
- The failing checks by name, with their `reason` strings quoted verbatim from `results.json` `verification_report[]`.

## Step 2: diagnose from the runs

Read in this order, and quote what you find with its source path:

1. `results.json` → `verification_report[]`: which checks failed, which passed, and the exact reasons.
2. `results.json` → `output`: the agent's final report. Does it name the target resource? Does it name the planted object under a different finding? Does it say anything was "unevaluated", "unjudged", "skipped", a "coverage gap", or "not applicable"?
3. `results.json` → `trajectory[]`: did the required collector or script run (`tool_called`, `terminal` commands)? What did the collector print? Grep for the target resource, the namespace, and words like `unevaluated`, `skipped`, `error`, `429`, `timeout`.
4. The ledger or pull request the check read, when the check names one (`ledger_issue_contains` reasons name the issue): what finding ids does it carry? A ledger is rewritten by every later run, so when the live issue has moved on, recover the body the check graded from the issue's edit history (GraphQL `userContentEdits { editedAt diff }` on the issue) rather than reading the current one.
5. For a fleet-audit case, the collector manifest and the findings document the run wrote in the sandbox, copied out during the run since the next run overwrites them: `kubectl -n kubeagents-system exec platform-agent-shell-0 -c shell -- cat /opt/data/scratch/manifest_<audit>.json` (per cluster, `candidates` and `checks_not_applicable`) and the same for `findings_<audit>.json`.
6. What those two files split, which the ledger alone cannot: the collector never listed the object (collector gap); the collector listed it and the worker dropped it (agent behaviour); the finding is in the document and the ledger body left it out (ledger rendering).
7. The fixture: was the planted state really there (the safeguard's reason tells you; a `resource_property` pass proves the object existed with that value)?
8. The product code the case exercises: the collector predicate or the procedure line that should have produced the finding. Find where the slug the check wants would be emitted. If nowhere, say so.
9. The last green record of the same case on the same lane, when one exists: diff its `trajectory[]` and `output` against the first red's. A part that differs in shape rather than in the agent's choices (a marker count, an entry's tag, an argument written as `<string, N chars>`) names the writer of that part, and `git log <green head>..<red head> -- <its path>` names the change. #5201's cause showed only this way, and #5179 names the writer it suspects.

## Step 3: classify

Pick exactly one class, by the first rule that matches, and write the rule you used:

| Class            | Rule that selects it                                                                                                                                                                                                                                                                                                                                                                                                                                                         | Fix type allowed                                                                                                                                                                                                                                                                                                                                                                                         |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Scenario unheld  | The state the header asserts cannot be produced or held by the stack: a provider rule, a channel's list (#5175, #4222: a REGULAR cluster cannot leave its channel's list)                                                                                                                                                                                                                                                                                                    | Bind the check to the state the fixture holds, or to the run-time state a check reads; pin the other branch in a unit test on recorded inputs; prove by item 5's replay                                                                                                                                                                                                                                  |
| Fixture defect   | The safeguard or the planted object is absent, or the planted state differs from the scenario (wrong namespace, wrong value, pods not in the state the scenario describes)                                                                                                                                                                                                                                                                                                   | Fix the stack; re-run red                                                                                                                                                                                                                                                                                                                                                                                |
| Record defect    | Step 2 item 9 shows that the part of the record which differs from the last green was written by the transport, the harness or a product component off the case's path, while the agent followed the rule and the check read the record as written (a worker's calls on the router trace, #5201, the writer #5179 names; an argument shaped on the inject door, #5077, whose fix set the check aside until #2619, the lever this row refuses; a stale in-flight note, #4268) | Fix the writer, never the check, and prove with a record from the fixed head replayed through the check as it is on `main`: a writer in `bench/kube_agents_bench/` or `hack/ci-eval-pr.sh` by that replay alone, with the one-line exemption under Live validation; a writer in `a2a/` with one live run on the fixed head so replayed; a writer under `agents/` runs the loop (item 5 and Step 6 stand) |
| Check defect     | The report or ledger shows the right outcome, but the check reads it wrong: a phrase list the report does not use, a type compare (string against boolean), a shortened id, a display-line parse                                                                                                                                                                                                                                                                             | Make the check read state or the ledger id, not words; add the missing phrasing only beside a state check; never delete the check                                                                                                                                                                                                                                                                        |
| Collector gap    | The collector ran and logged that it skipped, could not evaluate, or does not know the object or shape (for example a ComputeClass priority of a kind it does not parse)                                                                                                                                                                                                                                                                                                     | A predicate or a parser branch in the collector, with a test                                                                                                                                                                                                                                                                                                                                             |
| Procedure gap    | The collector saw the state, the procedure has no check for the pattern, and no finding was emitted                                                                                                                                                                                                                                                                                                                                                                          | A new check in the procedure with a published source line, and the collector support it needs                                                                                                                                                                                                                                                                                                            |

| Infrastructure   | A 429, a timeout, a lost lease, a missing token, a forge-less install for a ledger check                                                                                                                                                                                                                                                                                                                                                                                     | Not a red; fix the environment and re-run                                                                                                                                                                                                                                                                                                                                                                |

A row's rule names what the reader sees in the record; it may not depend on an earlier row's fix failing. Write the class with three evidence quotes and one sentence on why the next-nearest class does not apply. If two classes apply to different checks of the same case, split: one loop per class.
Then, for any class but Infrastructure, write the Step 3b card; no code and no run beyond the record before it. An Infrastructure red is fixed and re-run first, with no card.

## Step 3b: the decision card

One card per loop, written from the record after Step 3. It goes to the human first; code starts on the human's word. Fixed headings, this order, each within the size its text names.

1. **The case in customer terms.** Two sentences: who asks, and what they should get back.
2. **What the agent does.** One verbatim line per failing shape, its count over the record, and the `file:line` of the code that produced the text.
3. **Root cause.** One paragraph: the Step 3 class, the evidence line that selects it, and why the next-nearest class does not apply.
4. **Behaviour or case.** In two sentences, say whether the case's bar is the product's own stated rule, and quote the rule. If the case is loose or unbound, give the one-line tweak: bind the claim to the planted object, or require the thing the customer must see.
5. **What the customer wants to see.** Before and after, real text, each under 10 lines. The after carries the verdict, the one proving number, and the one thing they did not ask but should know; for a check-only fix the after is the recorded answer and the card says so.
6. **The fix, one lever per cause.** One paragraph per lever. Prose for a prompt contradiction, code for a code behaviour, a fixture change for a fixture gap; never prose to cover code. Give the size in lines, the resource cost in requests and objects, and where it lives; name a Hermes patch as one, with the note that it moves when Hermes goes. When one root cause takes two levers, both halves ship in one pull request.
7. **Do less.** The one-line option, and what it would certify falsely.
8. **Live run needs.** One line each: install, forge, fixture, model, minutes.
9. **Not covered.** At most three bullets.
10. **Rec and principle.** One line each.

The card and the fix it proposes obey these rules:

| Do                                                                           | Do not                                                     |
| ---------------------------------------------------------------------------- | ---------------------------------------------------------- |
| Name the model of each red and green; compare no two models (rule 58).       | Report a green on one model as a green on another.         |
| Bind every check to the planted object.                                      | Grade a sibling finding as the planted one.                |
| Keep to one lever per cause.                                                 | Use prose to cover a code behaviour.                       |
| State a limit as a ceiling ("stays under").                                  | State a limit as a target ("aim for").                     |
| Show the customer the verdict, the proving number and the one unasked thing. | Patch wording round after round when a state check exists. |
| Count server-side, with a field or label selector.                           | List everything and filter locally.                        |
| Put numbers in a table and link every pull request and issue.                | Add a constant or a mechanism for its own sake.            |
| Keep every claim on the record, with its run directory or line.              | Widen the fix mid-loop without a new card.                 |
| Stop after the card and wait for the word.                                   | Take a review clear as push authority.                     |
| Let the review check's green or the third round assign the human reviewer.   | Request a human reviewer by hand.                          |

## Step 4: red

Run the case once, unchanged, on an install the check can be graded on (a ledger check needs a forge; a plain-report check does not). Keep the run directory; the pull request cites it by name and the failing reason stays in it. Use the lease tool. For a Record defect, a Check defect or a Scenario unheld the red is already on the record (the Step 1 brief: build ids, reason, two run directories); a live repetition proves nothing the record does not and spends a lease.

## Step 5: fix

Make the smallest change the class allows, on a branch from fresh `upstream/main`:

- A check gains a state or ledger read; a phrase list grows only beside one; a type compare becomes a typed compare.
- A collector gains the predicate or parser branch, with a unit test on the shape that was skipped.
- A procedure gains the check and its `source:` line.
- A behaviour rule moves into a script, a check, or the persona file, and the prose line that failed is removed or shortened.

Refuse: a fixture name or a test id in product code; a phrase list edited to match one model's report; two root causes in one branch; a product change that makes the eval pass without changing what the product does for a customer.

## Step 6: green

On the final head: run the case three times; run every sibling case of the same root cause once. All three must pass on the deterministic checks. The one exception is a Record defect whose writer is in `bench/kube_agents_bench/` or `hack/ci-eval-pr.sh`: its green is the replay of the fixed head's record through the check on `main`, with the exemption line under Live validation; a writer in `a2a/` adds one live run on the fixed head so replayed. A judged score moving is not a pass.

## Step 7: ship

Before the push, run the whole set the CI shards run, not the touched files: `make test-python` and `make test-bench`; a change to a shared writer (a hand-off's compose, a finding line, a collector's object) reaches every fixture derived from it. Derived fixtures regenerate with their own writer, never by hand: the planted raw reports under `bench/tf/prebuilt/bootstrap-ranking/` by writing `bootstrap_handoff.compose(state, timed_out=False, now=PLANTED_AT)` over their `*.cards.json` to the `.txt` (`bench/tests/test_bootstrap_ranking.py` pins the equality), the shared chat cases with `agents/chat/scripts/test_inventory_card.py --write-cases` then prettier. Open the pull request from the template: the red (install, commit, failing check by name, the run's build id or directory), the three greens (run build ids or directories), the class and where its evidence is (run directory, `file:line`), the markers flipped (`expected_fail: true` removed for the cases the fix proves), the registration line, and the self-review from `/pr-preflight`. A declared-gap case names its gap issue and never `Closes` it; a reviewer is not named by hand before the review check's green assigns one, and `/request-review` is for a disputed finding or a missing review only.

## Step 8: record

Append the runs to the run store and move the case's row in the suite status file from red to fixing, with the pull request number.

## A new certification case

A new case is not a repair: it has no class and no fix. Its evidence follows `.agents/rules/eval_driven_development.md` in two shapes. A baseline (the product check exists and names the planted object) has no red; the record is three passes on the install's release build, run directories in the body. A declared gap (no check reads the planted signal, a procedure or collector gap you will not fix) lands with one red for the declared reason, `expected_fail: true`, and the gap issue named in its header and in the `#` reason lines above its roster line ("When the fix is not yours"); no green exists until the gap's check lands, and the pull request that adds the check flips the marker and closes the issue. A certification case carries `suite: certification` in its `task.yaml`, and its roster line with those reason lines goes in the certification roster (`hack/eval/certification-cases.txt` while that file exists; `scripts/validate_bench_cases.py` refuses the suite key without it), never the nightly file, so the rule's step 4 file does not apply. The card replaces Step 3b's headings and Step 7's evidence list (trap 7 is that list) with: the product check or the gap issue; the fixture (objects, labels, destroy); the objective under `scope: finding`; the safeguards, each read whole; the risk to the host cluster; the size in lines; the evidence shape. Before the card: verify every slug the sketch names against the collector (`git grep` the slug constant), and grep `bench/tf/fleet/fixtures.json` and the fleet README for the condition, since a plant that exists is read, not built. A new case skips addendum items 2, 4 and 5 (store rows and replay), and its card adds what it plants against the customer failure, the do-less line and the skill shortcomings. The fixture rules live in `bench/README.md` ("Certification suite", rules 1 to 7); the traps below point at them and add what the loop itself met on a certification case:

1. **Fixture readability.** Rule 4 of the README: the plant is something the agent's role can read, never a Secret; a webhook configuration's `caBundle` stood in for a TLS Secret (`security-expiring-node-bootstrap-and-webhook-certs`, #4960).
2. **Host mode and admission.** Rule 5 of the README: the lane's hosts are Autopilot, and the Step 1 dry-run says what admission writes; the ComputeClass case was parked under it (#4943, planting issue #5143). When no lease is open at card time, the dry run moves to the red step under the lease, the card marks its safeguard values pending the dry-run output, and a sibling case's recorded dry run on the same host type is the placeholder.
3. **The plant shell.** Rule 6 of the README: the shared module for a namespace-scoped plant, its guards copied for a cluster-scoped one (#4939, #4979).
4. **Objectives.** For a ledger case, one `ledger_issue_contains` with `scope: finding`, `finding_check` the accepted slugs and the planted object as the phrase (both objects of a pair under `any_of_phrases`). A body phrase for the object beside a slug among the ids is unpaired: a run can file them on different findings and pass (#4978; `bench/tests/test_webhook_ca_bundle_case_binding.py` pins one case against it). A chat case has no ledger: its objective is a `report_contains` on the gate-rendered line. The gap issue names the slugs and says a fixing pull request that picks another edits `finding_check` in the same diff. When the fixture rules keep part of the customer defect off the planted object (a check that reads a namespace list the fixture cannot use, such as a GKE-managed namespace; a fail-closed webhook whose selector must exclude what the customer's webhook fails to exclude, rule 1 of the README), the case header and the gap issue state both flip conditions: the shape of check that flips the case, and the shape that reads only the kept-off part and does not (`security-webhook-blocks-config-management-system`, #5338, #5335: backend reachability flips it, the selector exemption alone does not).
5. **Safeguards.** Rule 7 of the README: one per tempted property, read whole, values from the dry run; never a replica count on an autoscaled Deployment (#4949).
6. **The run.** One run on a forge install: a ledger check cannot fail for the gap's reason without a forge. Pre-open the agent API on a port of your own with the `kubectl exec` relay `bench/README.md` names under Sandboxed installs (`scripts/hermes-dashboard-tunnel.py --container agent-api-auth --remote-port 8643 --local-port <port>`; a plain `kubectl port-forward` binds but cannot reach a sandboxed pod, and every request dies with `RemoteDisconnected`) and set `AGENT_LOCAL_PORT` to it (another session's relay on the harness's default port sends the run to another install and it reads 401; a non-default port with nothing behind it is forwarded by the harness to the agent Service, which the sandboxed gateway refuses). A red counts only when the ledger issue's stamp falls inside the run's window; a report with no issue URL is a fail on the product's record (#5076): count it among the runs the body cites, each by run id and outcome word, and re-run to add runs, never to replace one. A plant that crash-loops spends the install's event-watcher alert quota (five Warnings per UTC day): read the `alert_quota` row at lease start, say the counts in the body, and route the reset at release as an ask when your session cannot write the gateway's database.
7. **The record.** The body names the case as new, the run id, the failing check by name (its reason stays in the run directory, `.agents/rules/public_surfaces.md`), the install's release and mode without its name, the plant as captured (a `kubectl get pod` line), the destroy, the admission dry-run's output, and the marker's issue; when review changes the objective, the maintainers may ask three repetitions on the new head before the push.
8. **A plant outside the host cluster.** A class-B plant (a per-run cluster, a cluster setting, or project-level network objects) has no kubectl guard, so Terraform's own destroy replaces the module's guards. Where the run's kubeconfig points decides the safeguards: a plant that is itself a cluster puts that cluster in the stack's `cluster_name` and `cluster_location` outputs, the run's kubeconfig moves to it for the run's length, and `resource_property` then reads the plant; project-level network objects leave the outputs on the host cluster through `TF_VAR_host_cluster_name` and `_location` (`prebuilt/subnet-range-exhaustion`), nothing in the cluster is the plant, and the worker-commands read-only safeguard on the write that would undo the plant is the catastrophic one. A plant of a setting the API reads back proves itself with a data source whose `postcondition` fails the plan when the planted value is absent; a baseline's objective proves a network plant, and only a marked case needs the proof elsewhere. The objective's phrase is the planted object's name prefix, since a per-run name carries a hash of `cluster_name`. A leftover is swept by label or description, never by the host teardown: a labelled cluster by `reap_orphans` in `bench/tf/modules/cluster/gke/main.tf`, a Compute network, subnet or address by `hack/ci_sweep_compute_plants.py` through its description prefix; a kind neither lists (a forwarding rule, a service attachment, a backend service, a health check) waits for the sweep to gain it before the stack's first apply. Its "Live run needs" line names the runner's roles and that sweep (#2755): the pool runners hold no Compute network or load-balancer role today. Before the card, read the condition live on every cluster the eval projects hold, since a GKE default can move under the scenario (NodeLocal DNSCache is on by default from 1.34.1); then no standing cluster carries it and the fixture creates or shares one.

## Cost to expect

A check defect: one to two hours and four runs. A collector or procedure gap: half a day to a day, and up to forty runs when a family of cases shares the cause. An agent-behaviour fix needs an install serving the model the rule failed on.
